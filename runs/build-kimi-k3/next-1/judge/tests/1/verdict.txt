I've reviewed the app against the spec and the framework's current stable release (Next.js 16.4.3, per `app/package.json:9`). For this dimension the picture is unambiguous: the app ships **zero tests of its own** — no test script, no runner in devDependencies, no test/spec files anywhere under `app/`.

## What exists

The only guard is the acceptance suite in `tests/`, which the agent didn't write. `app/package.json` has only `dev`/`build`/`start` scripts and only runtime dependencies (`app/package.json:6-14`). Static analysis confirms 0 test files, 0 assertions.

## What that leaves unguarded

Reading the riskiest code, these are the places a refactor of the data layer would break silently once the acceptance suite isn't the only check:

- **Pure formatting helpers — `app/lib/format.js:8-42`.** `humanize`, `latestEnFlavor` (whitespace collapse + "last English entry"), `enEffect`, `dexNumber` padding. These are textbook unit-test targets; a subtle change to the `\s+` collapse or "last entry" semantics would go unnoticed. `enEffect` uses the *last* English entry where the spec says "the English `short_effect`" — with multiple entries this is a latent choice nobody would catch.
- **Derived data layer — `app/lib/api.js:101-121`.** `getPokemonTypesMap` reconstructs every Pokémon's slot-ordered types from the *type* records (an unusual inversion), and `mapToSpecies` dedupes, drops IDs ≥ `MAX_FORM_ID`, drops species not in the index, and merges `ref.extra`. The `!(id < MAX_FORM_ID)` idiom also silently swallows `NaN` from `idFromUrl` (`app/lib/api.js:52-54`) — deliberate-looking but fragile.
- **Filter/pagination composition — `app/app/page.js:13-58`.** Page clamping (`page > totalPages`), `PAGE_SIZE` slicing, the `pageHref` builder that must omit default/empty params, case-insensitive match against the *humanized* name, and three independently-toggleable filters. This is where "off-by-one on the last page" and "filters combined wrong" bugs live.
- **Sort comparator — `app/app/pokemon/[name]/MovesTable.js:14-24`.** Missing-values-sort-last-in-*both*-directions, numeric-vs-`localeCompare` branch, and the toggle state machine. The `if (aMissing) return 1` path ignores `dir` entirely — correct today, easy to "fix" into a bug.
- **Moves grouping — `app/app/pokemon/[name]/page.js:26-96`.** `METHOD_ORDER` with alphabetical fallback for unknown methods, default game = highest `order`, default sort (level then move name), and `gameParam` validation (an unlearned game silently falls back to the default without a URL update).
- **URL state — `app/app/Controls.js:17-33`** (debounce + `router.replace`, sync effects for back/forward) and `app/app/pokemon/[name]/GameSelect.js:21-25` (`router.replace('?game=...#moves')`). Back/forward navigation races with the 300 ms debounce are exactly the kind of thing tests would catch.
- **Error handling — `app/lib/api.js:28-30, 38-48`.** `limitedFetch` throws on any non-404 status, the promise cache evicts failed loads so a retry can succeed — but a thrown error propagates out of every `await Promise.all([...])` in `page.js:25` and 500s the whole route. Nothing exercises the 404→`notFound()` paths (`app/app/types/[name]/page.js:29` etc.) or a 500-API scenario.

Given Next.js's current docs point at Vitest + Testing Library for components and Playwright for routes — and this app already had Playwright in the environment — the absence of even one unit test for `lib/format.js` is a real miss, not just a stylistic one.
