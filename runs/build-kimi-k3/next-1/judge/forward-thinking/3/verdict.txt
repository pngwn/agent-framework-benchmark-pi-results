I've reviewed the app's source (data layer `lib/api.js`, `lib/format.js`, all routes under `app/app/`, the three shared components, CSS, and config), and checked the framework's current guidance. Facts verified against external sources:

- **Next.js current stable line**: GitHub releases show canaries at `v16.5.0-canary.34` (2026-10-30), so the app's pinned `next@16.4.3` (`app/package.json:8`) is the current stable generation. React `19.3.1` is likewise current.
- **Route segment configs**: the Next.js 16 docs (`nextjs.org/docs/app/guides/migrating-to-cache-components`) state that with Cache Components "route segment configs like `dynamic`, `revalidate`, and `fetchCache` are replaced by `use cache` and `cacheLife`". `export const dynamic = 'force-dynamic'` is still supported (not deprecated) when `cacheComponents` is off — and the build output confirms it's off here — but it is the pattern the framework has publicly earmarked for replacement, and the app repeats it in all six routes.
- **Async params/searchParams**: awaiting `params`/`searchParams` (e.g. `app/app/page.js:18`, `app/app/pokemon/[name]/page.js:86`) is the current, required-in-16 API. `useRouter` from `next/navigation` (`app/app/Controls.js:4`) is the current hook, not the legacy `next/router` one.

What holds up well: all data access is behind one module (`app/lib/api.js`) with a runtime cache on `globalThis` and failure eviction; the home page recomputes everything from the live API, which is why the app survives the live-data-overlay test with no changes. Dependencies are exactly `next`/`react`/`react-dom` — nothing to age. URL building uses `URLSearchParams` on both server and client, CSS is plain custom properties over the design tokens, and there are no polyfills or framework internals in sight.

What will cause churn: (1) `force-dynamic` in six files is the exact surface the Cache Components migration deletes, and there are no Suspense/`loading.js` boundaries to stream behind — every navigation blocks on the full fetch; (2) the API JSON is consumed completely untyped (plain JS, no JSDoc, no TS) via deep optional chains across all five pages; (3) the query-string contract is duplicated between `app/app/page.js:73` and `app/app/Controls.js:20`; (4) `limitedFetch` has no `AbortSignal.timeout`, so one slow API response stalls SSR indefinitely.
