## Review: editability of the Pokédex app

A small, well-factored Next.js 16 App Router app: six route pages, three shared components, and a single data layer (`app/lib/api.js`) with a memory-cache seam (`cached`, `fetchJson`). Route files are thin and per-feature; the real reuse lives in `lib/api.js` (`resource` factory, `mapToSpecies`) and `lib/format.js`. The main weaknesses are a card-list pattern repeated verbatim in four pages, a filter-URL contract split between server and client code, and small duplicated constants/helpers.

Scenario walkthroughs:

1. **Remove Abilities** — delete `app/app/abilities/`, then remove the Abilities `<Section>` in `app/app/pokemon/[name]/page.js:216-227`, the `hidden` prop/note in `app/components/PokemonCard.js:11,27`, `.hidden-note` in `app/app/globals.css:239`, and the one-line `getAbility` export at `app/lib/api.js:69`. All findable by grepping `/abilities`, but it's a handful of scattered edits, and the ability-specific `hidden` prop inside the generic card is a real entanglement.
2. **Sprite fix** — the sprite URL is built in exactly one place (`app/components/PokemonCard.js:18`, from the species id) and all four lists render through `PokemonCard`, so one fix covers every list. Caveat: if the fix needs the default variety's actual `sprites.front_default`, that data currently exists only behind `loadPokemonPage` (`app/app/pokemon/[name]/page.js:23`) and would have to be plumbed through `mapToSpecies` and the home page.
3. **Sort card lists by name** — four call sites render `CardGrid` with their own `.map()`: `app/app/page.js:96`, `app/app/moves/[name]/page.js:70`, `app/app/abilities/[name]/page.js:40`, `app/app/types/[name]/page.js:68`. Either four mechanical edits or a small refactor to a data-driven list component; `CardGrid` takes children, so it can't absorb the change as-is.
4. **Items section** — `resource('item')` is a one-liner in `lib/api.js:68`-style factory; `CardGrid`/`PokemonCard`, `Section`, and `lib/format` all reuse directly. The page shell (h1 + facts `<dl>` + sections) gets copied/adapted from `app/app/moves/[name]/page.js` (~80 lines) since there's no generic detail-page abstraction.
5. **API base URL / caching** — one file: `app/lib/api.js:7-8` (base + media URLs) and `app/lib/api.js:39-52` (`cached`), with every fetch funneled through `fetchJson` (`app/lib/api.js:57`). Perfectly centralized.

Framework check: Next 16.4.3 is current stable; async `params`/`searchParams` are handled correctly everywhere (`app/app/page.js:19`, `app/app/pokemon/[name]/page.js:131`). `export const dynamic = 'force-dynamic'` is repeated in all six pages but is redundant in Next 16 (uncached fetch + `searchParams` already opt out of static rendering) and is the config the cache-components migration removes first — harmless now, bulk-delete later.
