I've reviewed the app against the framework's current docs (gracile.js.org, `@gracile/gracile` 0.11.0 — the current stable, matching `app/package.json:13`) and the official starter projects. Here's my assessment.

## What I checked

**Framework idiom.** The app mirrors Gracile's own annotated examples almost exactly: `defineRoute` with `handler`/`document`/`template` and returned-props (`app/src/routes/index.js:69-86`), the server-only `html` from `@gracile/gracile/server-html` in the base document with `<route-template-outlet>` (`app/src/document.js:1-11`), `context.responseInit.status` for the 404 status (`app/src/routes/pokemon/[name].js:32`), route-sibling `.client.js` scripts (a documented convention, ignored by the router — `app/src/routes/index.client.js`, `app/src/routes/pokemon/[name].client.js`), `routes/404.js` (present verbatim in the official `minimal` starter), and the Express deployment shape `getClientBuildPath` + `nodeAdapter` (`app/server.js:8-13`). Using the server-only `html` in route templates instead of `lit`'s is an explicitly documented alternative when no hydration is needed — and it's the right call here since the app is no-JS by default with vanilla progressive enhancement (docs "progressive interactivity" layer 2/3, which the docs literally name "search bars" as a use case).

**Correctness.** Race guards (`requestId`) in both client scripts, 404s on every dynamic route, escaped interpolations via the SSR `html` tag, promise-caching with eviction-on-failure (`app/src/lib/api.js:27-36`), bounded concurrency (`mapPool`). Real but minor issues: the `routes/404.js` only matches `/404/`, so genuinely unmatched URLs (e.g. `/foo`) fall through to Gracile's default instead of the spec's "Not found" page — a `[...path]` catch-all (the documented catch-all pattern) would close that; a stale Game select after `popstate` to a URL without `?game` (`app/src/routes/pokemon/[name].client.js:36-38`); `pushState` on every debounced keystroke floods the back history (`app/src/routes/index.client.js:44-48`); and the network-error fallback navigates after already pushing state, creating a duplicate history entry (`app/src/routes/index.client.js:39-41`).

**Abstractions.** `lib/api.js` (transport+cache), `lib/data.js` (resource shaping), `lib/util.js` (formatting), `lib/views.js` (shared markup) — small, single-purpose, no god module. The one repeated wart is the `typeNames` Map→`Object.fromEntries`→`new Map(Object.entries(...))` dance in five routes, plus a duplicated `option` helper.
