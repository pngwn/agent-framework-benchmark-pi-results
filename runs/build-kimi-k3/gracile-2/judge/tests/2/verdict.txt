## Review: test quality

**Verification of the facts.** I confirmed the measured counts independently: `app/package.json:8-10` defines only `dev`/`build`/`start` scripts, there are no `devDependencies` at all (no runner of any kind), and a recursive search of `app/src` for `test`/`spec`/`assert` finds only identifiers like `flavor_text_entries` and the compiled `dist/` mirror. The agent wrote **zero tests**. The framework ecosystem explicitly supports testing (Gracile's starter projects include a "minimal setup with various kinds of test suites" template), so the absence is a choice, not a framework limitation.

**What that means for this dimension.** Per the anchors, `coverage_of_risk` and `regression_power` score 1 (no tests, trivial-only coverage), `behaviour_not_implementation` scores 1 ("or no tests"), and `signal_to_noise` scores 3 (no tests ⇒ no noise). So the value of this review is the `untested` inventory, and I read the risky code carefully:

- **Data pipeline** — `app/src/lib/data.js:57-73` (`pokemonRefsToSpecies`) excludes alternate forms via `idFromUrl(r.url) < 10000`, dedupes by species ID keeping the *first* occurrence's `extra` payload, and sorts by dex number. This is used by the move, ability and type pages; a refactor that flips "first occurrence" to "last" or drops the ID cutoff would silently duplicate cards, link a form, or lose the `Hidden ability` marker (`app/src/routes/abilities/[name].js:32`).
- **Filtering/pagination** — `app/src/routes/index.js:55-72` does the search/type/generation matching plus the 48-per-page slice with a `Math.min(pageParam, totalPages)` clamp. The acceptance suite checks page 1, the next/prev links and the last page; a middle-page off-by-one (`slice((page-1)*48, page*48)`) on page 3 would slip through.
- **Client sorting** — `app/src/routes/pokemon/[name].client.js:60-88` re-implements sorting against DOM `textContent`, with special handling for `—` (missing sorts last *in both directions*), numeric parsing and `aria-sort` reset. The descending direction with missing values is exactly the kind of edge that breaks in a refactor and is only lightly covered by one acceptance test.
- **Caching** — `app/src/lib/api.js:20-25` caches promises and deletes the entry on rejection so a retry can succeed. If someone "simplifies" this to cache without eviction, a single transient API error poisons every render until restart — nothing would catch it.
- **Concurrency** — `app/src/lib/api.js:49-62` (`mapPool`) shares a mutable `index` across workers; a dropped entry would only show up as a subtly shorter learned-by list.
- **URL state** — `app/src/routes/index.client.js:25-33,66-75` (query building, default-param omission, `requestId` race guard, popstate restore) and `app/src/routes/index.js:130-137` (`pageUrl`). The race guard only matters on slow networks, which the local acceptance run never simulates.
- **Pure helpers** — `app/src/lib/util.js:6-40` (`humanize`, `latestEnglishFlavorText` whitespace collapse, `dexNumber`, `formatMeasure`) are free, fast unit-test targets that nobody wrote.
- **Move method ordering** — `app/src/routes/pokemon/[name].js:158-170`: the rank function and the "others alphabetically" fallback branch are untested; the fallback may not even be exercised by the fixture data.

The only mitigation is that the provided acceptance suite is unusually thorough at the DOM/URL level, so *happy-path* behaviour is guarded today. But it tests against a fixed local API and fast responses — none of the silent-failure modes above.
