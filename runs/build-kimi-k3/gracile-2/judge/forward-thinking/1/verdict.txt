## Review: Pokédex on Gracile (with Lit) — forward-thinking

**Framework currency check (verified against sources, since my training data is stale):**

- npm registry: `@gracile/gracile` `dist-tags.latest` is **0.11.0** (published ~May 2026, built on Node 24), `next: 0.11.1-next.2`. The app pins `^0.11.0` — the current stable, not a training-data-era version. Its internal `@gracile/engine@^0.12.0` peer-accepts `vite ^7.0.0 || ^8.0.0` and `lit ^3.3.2`.
- The official docs site (gracile.js.org) and the official starter (`gracile-web/starter-projects/templates/minimal-server-express`) demonstrate exactly the API surface this app uses: `defineRoute` from `@gracile/gracile/route`, `html` from `@gracile/gracile/server-html`, `handler.GET` returning props, `context.responseInit.status`, `<route-template-outlet>`, `*.client.ts` route-entry convention, `@gracile/gracile/node` (`nodeAdapter`, `getClientBuildPath`, `printUrls`). `app/server.js:1-16` is near-identical to the official Express starter's `server.js`.
- Two picks are behind the current line: **Express 4** (`app/package.json:12`) while the framework's own starter ships `express ^5.0.1` and Express 5.3.0 is `latest` (4.x is in maintenance, EOL targeted from Oct 2026 per endoflife.date/TuxCare — i.e. right about now); **Vite 7** where 8.3.5 is current, though 7 is explicitly in Gracile's supported peer range.
- `lit` is declared but never imported anywhere in `app/src` (the framework supplies all templating); it is, however, a required peer of `@gracile/engine`, so it isn't strictly removable.

**What ages well:** all data access sits behind one client module (`app/src/lib/api.js:20-53` — cached promise map, 404→null, rejected fetches evicted for retry) plus one domain module (`app/src/lib/data.js`), so a change in PokeAPI shape or a move to a different transport touches two files. Route handlers do the filtering and pass plain props to templates, no framework internals are poked, and the filter form still works without JS via `method="get"` (`app/src/routes/index.js:114`) with vanilla progressive enhancement on top. Platform use is good: native `fetch`, `URLSearchParams`, `DOMParser`, `history.pushState`, design-token custom properties, no polyfills.

**What will cause churn:** zero types anywhere (no TS, no JSDoc — `typeLines: 0`), so handler→template prop objects are untyped strings that break silently on rename; the `Map → Object.fromEntries → new Map(Object.entries(...))` round-trip is copy-pasted into all five routes instead of one helper (`app/src/routes/index.js:86,99`, `app/src/routes/pokemon/[name].js:209,220`, etc.); and the two client scripts re-implement the same fetch/replace/popstate plumbing (`app/src/routes/index.client.js:23-52` vs `app/src/routes/pokemon/[name].client.js:11-30`) instead of sharing it — a third interactive page would paste it a third time. Neither uses `AbortController`; they guard with a `requestId` counter, leaving stale requests in flight.
