The app is a conservative, stable-only Astro 7 codebase. Summary of what I verified:

- **Dependencies** (`app/package.json:12-13`): `astro ^7.4.4` and `@astrojs/node ^11.1.9` — both are the *current stable* versions (Astro 7.4.4 and the Node adapter 11.1.9 are the latest published releases as of 2026-10-28, per astro.build's release feed and npm).
- **Config** (`app/astro.config.mjs:4-5`): `output: 'server'` with the Node adapter in standalone mode. Astro 7's upgrade guide doesn't deprecate this; the Node adapter docs still document exactly this configuration. No `experimental:` block, no `unstable_` names anywhere (confirmed by grep).
- **Framework surface used**: dynamic routes (`[name].astro` in `pokemon/`, `moves/`, `abilities/`, `types/`), `Astro.params`, `Astro.request.url`, `set:html` (`app/src/pages/pokemon/[name].astro:228`), `is:inline` scripts (`app/src/pages/index.astro:143`), `defineConfig`, `interface Props`. All of these have been stable since Astro 1–5; none of Astro 7's headline features (advanced routing/`src/fetch.ts`, route caching/`routeRules`, `notFound()` handler, CDN cache providers) appear — grep for `cache|routeRules|notFound|ClientRouter` in source found nothing.
- **Notable conservatism**: instead of Astro 7's newly-stable route-caching (`cache: { provider: memoryCache() }`), the app hand-rolls an in-memory `Map` cache (`app/src/lib/pokeapi.js:10`) — appropriate given the spec's "live data can change" requirement, and avoids newly-stable machinery entirely.
- **Astro 7.0 itself** was released 2026-06-22 (astro.build blog), so the major is ~4 months old, but no API the app touches is new in it.

So: zero experimental/preview/RC/canary APIs, and even zero "recently-stable" APIs in central places — the app simply runs on the latest stable release while using only long-stable primitives.
