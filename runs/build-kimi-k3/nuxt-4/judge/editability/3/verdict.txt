I've read all of `app/` (5 pages, 4 components, one lib, one composable, one global stylesheet, config) and checked Nuxt 4.x docs for the error-handling pattern it uses. Verdict below.

## Review

**Structure.** Clean Nuxt 4 layout: pages under `app/app/pages` with dynamic `[name].vue` routes, a shared data layer in `app/app/lib/pokeapi.ts` (fetching, caching, indexes, pure helpers), and one composable for the API base. Navigation is centralized in `app/app/layouts/default.vue:9-11`, so nav changes never touch pages.

**What works well for editability**

- **Cards are a single component.** Every Pokémon-card list (`pages/index.vue:119`, `pages/moves/[name].vue:64-66`, `pages/abilities/[name].vue:48-56`, `pages/types/[name].vue:56-58`) renders `PokemonCard`, and the shared ref→species mapping (`speciesCardsForRefs`, `lib/pokeapi.ts:217`) handles dedupe/alternate-form exclusion for moves and types. A sprite or card-layout fix lands in one component.
- **The data source is a real seam.** `base` is threaded explicitly into every lib function; caches (`lib/pokeapi.ts:66-88,103,147`) are all module-local and keyed by base. Changing the base URL is `composables/useApiBase.ts` + `nuxt.config.ts` only.
- **MoveTable is properly abstracted** — column config + internal sort state (`components/MoveTable.vue:12-84`), no flag creep beyond one justified `showLevel`.

**What costs you**

1. **No scoped styles anywhere.** All ~435 lines of CSS live in `app/app/assets/css/main.css` (grep for `<style` in `.vue` files: zero hits). Feature-owning selectors like `.hidden-ability` (main.css:199), `.artwork`, `.flavor`, `.game-field` sit in the shared file — deleting the Abilities feature leaves orphaned CSS, and you must hunt to find which styles belong to what.
2. **Detail-page boilerplate is copy-pasted 4–5×.** The `useAsyncData(key, loader, {watch: params})` + `useRequestEvent` + `setResponseStatus(404)` + `useHead(title)` block appears nearly verbatim in `pages/moves/[name].vue:26-36`, `pages/abilities/[name].vue:31-41`, `pages/types/[name].vue:40-50`, `pages/pokemon/[name].vue:116-125`, and `pages/[...slug].vue:5-9`. Nuxt's documented alternative (`throw createError({ statusCode: 404 })`) or an extracted `useDetailPage` composable would collapse this.
3. **Small duplications.** `spriteUrl` (`lib/pokeapi.ts:82`) is dead — `PokemonCard.vue:22` builds the sprite URL inline, so the pattern is known in two places, one of which is a trap. The `show` em-dash helper exists twice (`pages/moves/[name].vue:36`, `components/MoveTable.vue:78`). `pages/abilities/[name].vue:17-28` reimplements `speciesCardsForRefs`'s dedupe/sort to add `hidden` instead of reusing it.
4. **Loose typing in the data layer.** `api(): Promise<any>` and `(e: any)` casts throughout mean the compiler won't catch a rename or shape change during edits — the only typed contracts are `NamedRef`/`SpeciesEntry`/`PokeIndex`.

**Scenario answers:** Removing Abilities = delete one file + strip one `<section>` from the Pokémon page (+ CSS cleanup). Sprite fix = one component, though it needs new data plumbed through the index. Sorting by name = 3 places (index computed, `speciesCardsForRefs`, abilities' local sort). An Items section reuses card/NotFound/lib helpers but copies the page skeleton. Base URL/caching changes = 2–3 files, all obvious.
