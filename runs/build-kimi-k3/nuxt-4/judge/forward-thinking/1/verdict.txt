## Review: `app/` (Nuxt Pokédex) — forward-thinking

**Framework baseline:** the app pins Nuxt `4.6.3` (`app/package.json:9`), which as of 2026-10-30 is the current stable (released 2026-10-27; Nuxt 3 EOL'd 2026-07-31). Per the Nuxt 4.6 announcement (nuxt.com/blog/v4-6), Nuxt 4.6 introduced `nuxt/server` — a portable import surface typed against a `RequestEvent` — precisely so server code survives the move to Nuxt 5 / Nitro v3 / h3 v2; the post explicitly says code importing from `h3` directly will not.

### What holds up well

- **Current-generation Nuxt throughout**: Nuxt 4 `app/` srcDir layout (`app/app/pages/…`), `<script setup lang="ts">`, `useAsyncData` with the documented `watch: [() => route.query.game]` re-fetch option (`app/app/pages/pokemon/[name].vue:104-107`), `useHead` with computed titles, `useState`/`useRuntimeConfig`, `NuxtLayout`/`NuxtPage`. No Options API, no Vue 2-era patterns.
- **Data access behind exactly one module** (`app/app/lib/pokeapi.ts`) with in-flight promise dedupe, a concurrency limiter and per-`base` caches (`pokeapi.ts:48-79`, `getIndex` at `pokeapi.ts:130`). All five pages consume only that module — an API change or endpoint swap touches one file.
- **Platform-first where it counts**: native `fetch` (`pokeapi.ts:72`) instead of axios/ofetch wrappers, zero utility libraries (debounce is a 6-line `setTimeout` at `app/app/pages/index.vue:66-71` rather than pulling in `@vueuse/core`), CSS custom properties + grid + `:focus-visible` (`app/app/assets/css/main.css`), ES modules everywhere.
- **Dependencies**: 3 packages, no CSS framework, no lodash/vueuse/axios — very lean, and `nuxt` is the newest stable.

### What will age badly

- **`import { setResponseStatus } from 'h3'` in five page components** (`app/app/pages/pokemon/[name].vue:2`, `app/app/pages/moves/[name].vue:2`, `app/app/pages/abilities/[name].vue:2`, `app/app/pages/types/[name].vue:2`, `app/app/pages/[...slug].vue:2`). Nuxt already auto-imports its own `setResponseStatus` composable (visible in the project's own generated `.nuxt/types/imports.d.ts:89`, from `#app/composables/ssr`), and Nuxt 4.6 ships `nuxt/server` explicitly so apps don't import from h3. This is the single systematic pattern that ripples at the Nuxt 5 upgrade.
- **`compatibilityDate: '2025-07-15'`** (`app/nuxt.config.ts:2`) is ~15 months stale; Nuxt's own guidance is to set it to the current date when creating a project, and it silently pins an old behavior window.
- **`any` at the boundary**: the one well-defined module is internally untyped — `Promise<any>` cache and `api()` return (`pokeapi.ts:48`, `pokeapi.ts:67`), and page loaders cast records to `any` throughout (e.g. `pokemon/[name].vue:32-118`). The domain interfaces (`SpeciesEntry`, `PokeIndex`) are good, but the raw API shape is unguarded, so a schema change surfaces as runtime `undefined`s rather than type errors.
- **Rejected promises are cached forever** (`pokeapi.ts:77` sets the cache before the fetch settles): one transient API error during SSR poisons the server's in-memory cache for the process lifetime. Delete the entry on rejection.
- **Duplicated title suffix**: `– Pokédex` is hand-concatenated in six files (`pokemon/[name].vue:126`, `abilities/[name].vue:41`, `types/[name].vue:50`, `moves/[name].vue:36`, `types/index.vue:4`, `[...slug].vue:4`); a single `titleTemplate` in `nuxt.config.ts` or `app.vue` would remove the copy-paste.
- **URL handling by string surgery**: `${base.replace(/\/$/, '')}/api/v2${path}` and `url.match(/\/(\d+)\/?$/)` (`pokeapi.ts:20`, `pokeapi.ts:70`) instead of `new URL(path, base)` / `URL.pathname` — the platform API exists and is the better choice here.
- **Redundant direct deps**: `vue` and `vue-router` are declared in `package.json` but never imported directly (grep confirms only auto-imported `ref`/`computed`/`useRouter` usage); they're transitive deps of Nuxt anyway. Harmless, but not needed.

None of this is speculative churn — the h3 coupling and the stale compatibility date are the only items that will actually cost work at the next Nuxt major.
