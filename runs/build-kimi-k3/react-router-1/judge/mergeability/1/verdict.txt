## Review

I read `SPEC.md`, all of `app/` (routes, components, `lib/`, config), and checked guidance against the official React Router skill (`references/framework-mode.md`) and the current release train (v8.5.1 is the latest stable as of today; the app pins `^8.5.1`, so it is on the current release).

**Framework usage.** This is a clean framework-mode app: `app/routes.ts` config, route modules with server `loader`s, `data(..., { status: 404 })` responses, `Layout` export in `root.tsx`, `useSearchParams` for filter state, and a properly server-only data layer (`lib/api.server.ts` — the `.server.ts` boundary is exactly right, and `home.tsx` only calls `mediaBase()` inside the loader). Three things diverge from the current documented conventions:

1. **Generated route types are unused.** The skill and docs are explicit: "Use generated `Route.*` types from `./+types/<route>` for route module args and props." The app hand-declares loader args (`app/app/routes/pokemon.tsx:34`) and every component takes `loaderData: any` (`pokemon.tsx:182`, `move.tsx:39`, `ability.tsx:40`, `type.tsx:50`, `types.tsx:12`). Ironically `package.json` even ships `react-router typegen && tsc --noEmit` — the typegen output is generated and then ignored.
2. **404s via ad-hoc flags instead of the documented pattern.** Docs: "Missing record in a loader: throw `data("Not Found", { status: 404 })` and render the route `ErrorBoundary`." Instead each of the four resource loaders returns `data({ notFound: true }, { status: 404 })` and each component branches on it — a duplicated handshake in eight places — while the root `ErrorBoundary` (`root.tsx:48-58`) separately renders the *same* "Not found" UI for *any* thrown error, including a 500. Both work, but 404 handling is split across two mechanisms and the error boundary lies about what happened.
3. **Filtering ignores the loader.** Docs recommend parsing URL/search params in the loader; `home.tsx:9` takes no `request` and the full 1,025-species list (plus per-generation id lists) is serialized into every home response and filtered client-side. Defensible as an instant-filter UX choice, but it's the notable home-grown divergence.

**Correctness.** The parts teams usually get wrong are done right: debounce timer is cleaned up on unmount (`home.tsx:74-77`), the concurrency limiter's release/waiter pairing is correct (`api.server.ts:18-33`), alternate forms are consistently excluded via the species-id check (`api.server.ts:137-140`), 404 vs other errors are distinguished in `getRecordOrNull` (`api.server.ts:173-176`), and the search box resyncs on back/forward (`home.tsx:50-56`). The one real fragility: **rejected promises are cached permanently** — `cache.set(url, promise)` stores even rejections and `promise.catch(() => {})` swallows them (`api.server.ts:46-49`), and the same is true of every index promise (`api.server.ts:95`). One transient API hiccup and that resource is broken until process restart. There's also no timeout/abort on `fetch`, so a hung connection stalls a request forever.

**Abstractions & readability.** This is where the app is strong. `api.server.ts` is a single data module but earns it: tiny surface (`getJSON` + a few index helpers), clear why-comments, hard server/client boundary. `format.ts` is pure and shared. The components (`Section`, `PokemonCard`, `TypeBadge`, `MoveTable`) are small, focused, and the accessible-name requirements (`aria-labelledby`, `aria-sort`, `caption`) live in one place each. Nits: `hiddenBySpecies` serializes a Map to an object only for the component to rebuild a Map (`ability.tsx:35`, `ability.tsx:43`) — redundant with the `hidden` flag already on the entries; `searchParamsRef.current = searchParams` mutates a ref during render (`home.tsx:47`); the pokemon loader is ~100 lines doing five jobs.

**Verdict.** I'd want one round of changes before approving — adopt `+types`, unify 404 handling, evict failed promises from the cache — but nothing requires architectural rework.
