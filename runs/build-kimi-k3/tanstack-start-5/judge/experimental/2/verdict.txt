## Review: experimentalness

**What's in the code.** No `unstable_`/`experimental_` markers anywhere in `app/src` (grep confirmed; the only regex hits were `src={...}` attribute false positives). The route code (`app/src/routes/__root.tsx:5-13`, `app/src/routes/pokemon/$name.tsx:1-18`) uses long-stable TanStack Router APIs (`createFileRoute`, `createRootRoute`, `notFound`, `validateSearch`, `loaderDeps`, `head`, `notFoundComponent`). Server functions at `app/src/lib/server.ts:13-27` use `createServerFn().validator()` — the *current stable* API, not the deprecated `.inputValidator()` that TanStack removed in 1.169.

**The one prerelease.** The production build/serve path rests on **Nitro v3.0.261029-rc**, pinned at `app/package.json:21` and wired at `app/vite.config.ts:10` (`nitro()` from `nitro/vite`). Nitro published that RC on **2026-10-29 — two days before today**; v3 has no stable release yet (only betas before this RC, per the GitHub releases page and nitro.build/blog/v3-rc). Crucially, this is *mandated by stable TanStack Start*: the official "Migrate from the Release Candidate" doc says `@tanstack/nitro-v2-vite-plugin` was **removed** and you must use `nitro()` from `nitro/vite`, and TanStack's own `examples/react/start-basic/package.json` ships `"nitro": "^3.0.260903-beta"`. So the app is on the framework-blessed path with no stable alternative — but it is still an RC in the critical path, and `npm start` (`node .output/server/index.mjs`, `app/package.json:8`) executes its output.

**Recently-stable context.** `@tanstack/react-start@^1.169.4` (`app/package.json:12`) is the **first stable release line of TanStack Start** (per the migration-from-RC doc), and `.validator()` has only existed since ~1.168.25 (June 2026). Vite 8 (`app/package.json:23`) went stable 2026-03-12 and is required by Start — outside the "very new" window but part of a young stack. These are stable, correctly-used APIs; they carry upgrade-churn risk, not experimental risk.

**Verdict.** One RC dependency, forced by the framework, confined to two files (vite config + package.json), with everything app-facing on stable APIs. Low experimental exposure, well managed.
