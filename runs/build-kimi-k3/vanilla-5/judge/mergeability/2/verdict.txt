## Review

**Structure.** Small, well-factored vanilla TS + Vite app: `src/api.ts` (fetch + promise cache), `src/data.ts` (memoized domain loaders), `src/components.ts` (HTML string components), `src/pages/*` (one file per route), `src/main.ts` (router + link interception), `server.mjs` (static SPA server). This is the right shape for a no-framework Vite app; nothing fights the toolchain (Vite 8 is current stable — `^8.3.5` in `app/package.json:11` — and `defineConfig`/`configureServer` usage in `app/vite.config.ts:5-9` is unchanged in v8).

**The good.** Runtime API config via `/config.js` + `window.__API_BASE_URL__` (`app/src/api.ts:1-7`, `app/server.mjs:33-37`) is the correct pattern for a runtime env var that must not be baked at build time; HTML interpolation is consistently escaped through `esc` (`app/src/util.ts:2-5`); 404s are mapped to the Not-found page (`app/src/pages/pokemon.ts:51-53`); memoized loaders in `data.ts` are clean and promise-cached with retry-on-failure (`app/src/data.ts:17-20`).

**The problems** are two races and one data-model smell:

1. **Debounce leaks across navigation** (`app/src/pages/home.ts:139-144`): the search input's 200 ms timer is never cancelled when the route changes. Type a query, click a card within the window, and the timer still fires, calling `history.replaceState('/', queryFor(...))` (`home.ts:135`) — silently rewriting the URL of the newly-loaded Pokémon page. `renderHome` returns nothing to dispose; `main.ts` has no teardown hook.
2. **Stale-render guard is ineffective for content** (`app/src/main.ts:19-41`): `renderToken` is checked only *after* the page function resolves, but the page functions themselves write `root.innerHTML` and `document.title` at their end (`app/src/pages/pokemon.ts:139`, `move.ts:28`, …). If two navigations overlap and the older fetch resolves last, the older page overwrites the newer one; the `token !== renderToken` check at `main.ts:36` only protects the scroll call.
3. **DOM round-trip for sort data** (`app/src/pages/pokemon.ts:279-300`): `wireMovesSection` reconstructs `MoveRow` objects by parsing `textContent` and `href` attributes out of the freshly rendered table, duplicating the data model that `movesSectionHtml` already built (`pokemon.ts:233-243`). Fragile and a reviewer would ask for the rows array to be passed to the wiring.

Smaller: pervasive `any` for API payloads (`data.ts:63-90`, `api.ts:32`) undercuts `strict: true`; a module-level `sectionCounter` in `app/src/components.ts:39` makes heading ids non-deterministic and ever-growing across SPA navigations; `/pokemon/` (empty name) falls into a list request instead of Not found (`main.ts:23`); the moves section fires an unthrottled fan-out of one `/move/` request per row (`pokemon.ts:181-184`) — cached, but a burst of ~150 requests per game switch.
