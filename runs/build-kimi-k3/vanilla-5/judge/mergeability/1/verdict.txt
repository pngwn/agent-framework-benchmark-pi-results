The spec is a no-framework Pokédex SPA; the app is a hand-rolled client-side router over string-template rendering with a small static-file server — a reasonable shape for vanilla TS + Vite (Vite 8 / TS 5.9 per `app/package.json:9-12`).

Notable positives: runtime API base is injected via `/config.js` (vite.config.ts:6-17, server.mjs:41-45) instead of baked at build time, which the spec explicitly forbids — a correct and idiomatic choice; the fetch cache in `api.ts:30-40` uses promise caching with rejection eviction (no unhandled rejections); `data.ts` memoizes derived views with a tiny `memo` helper; escaping via `esc` is applied consistently in every interpolated user/API string I checked (e.g. `home.ts:61`, `components.ts:15-17`, `pokemon.ts:88`).

Real issues I found: a stale-render race (the token guard in `main.ts` only gates scrolling/title, but each page function writes `root.innerHTML` itself, so a slow earlier render can clobber a completed later one), a leaked debounce timer on the home page that rewrites the URL after navigating away, and a duplicated Pokémon→species mapping in `ability.ts` that already mirrors `speciesFromPokemonRefs` in `data.ts`. Also pervasive `any` typing and a DOM-scraping sort snapshot that a reviewer would flag.
