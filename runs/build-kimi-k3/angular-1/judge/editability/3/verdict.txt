## Review: `app/` (Angular 22.2 — current stable, confirmed v22.2.4 released Oct 2026)

### Architecture overview

The app is a modern, idiomatic Angular 22 SSR app: signal `input()`s fed from route resolvers via `withComponentInputBinding()` (app.config.ts:16, matching current docs), control-flow templates, `OnPush` everywhere, `ResolveFn` resolvers, request-time SSR (`app.routes.server.ts`), and a single data service (`PokeApi`) behind an `API_BASE` injection token with TransferState hand-off. Data flows: `PokeApi` → `CatalogService`/resolvers in `page-data.ts` → typed page components → shared leaf components (`PokemonCardsComponent`, `MoveTableComponent`).

### Scenario walkthroughs

1. **Remove Abilities** — touches `app.routes.ts:2,7,27` (route + imports), delete `ability.page.ts`, `page-data.ts:101-106,209-241` (resolver + interfaces) *plus* `page-data.ts:130,269-271` and `pokemon.page.html:59-70`, `pokemon.page.css:105` for the Abilities section on the Pokémon page, and the ability-only `hidden` flag in `cards.component.ts:26-28` / `catalog.service.ts:145-150`. Six files, several regions — a handful of scattered edits, not a delete-and-done.
2. **Sprite bug (Deoxys)** — sprite rendering is centralized in `cards.component.ts:35-37` (`sprite(id)`), and *every* card list (home, move, ability, type) renders through `PokemonCardsComponent`, so one fix covers all lists. But card data is constructed in two paths inside `catalog.service.ts` (`load()` species mapping ~line 87 and `pokemonRefsToCards` line 158), so if the fix needs the default Pokémon's name/URL (not just id), you touch both. ~2 files, obvious.
3. **Sort by name** — one computed in `cards.component.ts` covers every list; nothing else knows how cards are ordered beyond `pokemonRefsToCards`' dex sort. Trivial.
4. **Items section** — copy-adapt `moveResolver` (`page-data.ts:209-241`) + `move.page.ts`. Reusable as-is: `PokeApi`, `util.ts` helpers, `NotFoundComponent`, global `.panel`/`.type-badge` styles (`styles.css:33,47`). Not reusable (copied): the fetch-or-null resolver skeleton, the title effect, the facts `<dl>`. New page grows the `page-data.ts` monolith again.
5. **API base/caching** — `pokeapi.service.ts` is the only file that knows the origin (factory lines 17-30, `media()` line 62) and the only cache (`responseCache` lines 43-58). Default literal duplicated twice within it. One file.

### Criteria verdicts

- **removability 3** — pages are per-resource components with clean seams, but abilities removal scatters across ~6 files because page data types live centrally and the Pokémon page links into the feature.
- **changeability 4** — sprite URL, caching, base URL, humanize/english-name are each single-place, and every card list funnels through one component; deductions for title-effect duplication in 4 page components and `.count` CSS triplicated.
- **coupling 4** — narrow typed inputs, one HTTP service, clean server/client split (`provideApiBase`, `server.ts`); minor leak: presentational `PokemonCardsComponent` injects `PokeApi` for sprite URLs.
- **abstraction_design 4** — `PokemonCardsComponent` + `pokemonRefsToCards` (with the `extra` callback seam) and the config-driven `MoveTableComponent` are designed around real variation; the 352-line `page-data.ts` grab-bag is the main stretch-limiting factor.

No outdated APIs found — the resolver pattern, signal inputs, hydration with event replay, and SSR setup all match current v22 guidance.
