## Review

The app is a server-rendered Astro 7 project (current stable — 7.4.4, released Oct 2026) with the official Node adapter in standalone mode, plain `.astro` components, and two small vanilla-JS client scripts. Structure is clean: three small lib modules (`api.js` fetch/cache, `data.js` PokeAPI-shaped aggregations, `format.js` pure helpers), five focused components, pages mirroring routes exactly (`[name].astro` dynamic params, `404.astro`).

**Idiom.** Config (`app/astro.config.mjs:1-6`) is exactly what current docs prescribe: `output: 'server'`, `@astrojs/node` standalone. Data fetching in frontmatter with `await` + `Promise.all` (`app/src/pages/index.astro:23-32`) is the documented SSR pattern; `Astro.response.status = 404` (`app/src/pages/pokemon/[name].astro:130-135`) and `Astro.self` recursion for the evolution tree (`app/src/components/EvolutionNode.astro:17`) are both current APIs. Two small misses: client behavior lives as unbundled `/public` JS loaded with `is:inline` (`app/src/pages/index.astro:96`, `app/src/pages/pokemon/[name].astro:311`) instead of Astro's processed/TypeScript-checked `<script>` handling; and Astro 7's new route caching (`routeRules`/`memoryCache`) is ignored even though pages like `/pokemon/:name` do heavy, cacheable work — optional, but it's the framework's new headline feature for exactly this shape of app. The hand-rolled per-URL fetch cache (`app/src/lib/api.js:8-36`) is fine: Astro 7's cache API caches *responses*, not arbitrary data fetches, so this isn't a reinvented framework primitive.

**Correctness.** Genuinely careful: in-flight promise caching prevents fetch stampedes and failed promises are evicted so transient errors can be retried (`app/src/lib/api.js:22-35`); bounded-concurrency fan-out preserves order (`app/src/lib/api.js:39-50`); the home-page AJAX has a sequence guard against out-of-order responses (`app/public/js/home.js:28-36`); pagination clamps out-of-range `page` (`app/src/pages/index.astro:41`); 404s are handled uniformly, including pre-checking excluded types to avoid pointless fetches (`app/src/pages/types/[name].astro:17-20`). Unbounded memory cache is explicitly allowed by the spec. Remaining risks are minor: no timeout/abort on upstream fetches; `home.js:36-38` silently swallows a failed refresh and leaves stale results with no user feedback; a Pokémon holding the same ability both normally and hidden would take the first entry's flag (`app/src/pages/abilities/[name].astro:33-36`); `defaultVariety` is dereferenced without a guard (`app/src/pages/pokemon/[name].astro:37`). No XSS surface: all API data flows through Astro's escaping.

**Abstractions & readability.** Boundaries are good — server-only lib never leaks into client code, components are small and typed (`PokemonCard.astro:4-10`), `format.js` is pure and reusable. Two duplications will need untangling: the abilities page re-implements `pokemonRefsToSpecies` inline because it needs `is_hidden` (`app/src/pages/abilities/[name].astro:24-38` vs `app/src/lib/data.js:61-77`), and the identical 404 try/catch block is copy-pasted in four pages. The pervasive `let data: any` + `as any` style (`app/src/pages/pokemon/[name].astro:29` and throughout) throws away Astro's TS support on data the whole template depends on. The Pokémon page carries ~150 lines of data shaping inline in frontmatter; extracting it would help most.

**Review cost.** I'd approve after nits: mostly typing, one extracted helper, and possibly moving scripts into Astro's bundler. Nothing structural would block merge.
