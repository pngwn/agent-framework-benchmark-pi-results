## Review: `app/` (Pokédex, Next.js 16.4 App Router)

**Architecture in one paragraph.** Clean layering: pages (`app/app/**/page.jsx`) → presentational components (`components/`) → an aggregation layer (`lib/data.js`) → a single fetch/cache module (`lib/api.js`) → pure formatters (`lib/format.js`). Only two client components (`HomeControls.jsx`, `MovesSection.jsx`), both fed fully-precomputed serializable props — an excellent server/client seam. No TypeScript anywhere (a choice, and a mild drag on editability given zero type lines), but the code is small, consistently styled, and commented where it matters (e.g. `lib/api.js:1-2`, `lib/data.js:92-98`).

**Framework currency.** The app targets `next@^16.4.3` (app/package.json:9), the current stable line (16.4.0 released 2026-10-06; 16.5 still canary). `params`/`searchParams` are correctly awaited as promises (e.g. `app/app/page.jsx:23-24`, `app/app/pokemon/[name]/page.jsx:81-82`), matching Next 15/16 semantics. The one framework-level nit: Next 16.4's release post now recommends **Cache Components** as the default caching model (becoming the default in 17), while this app uses the legacy `export const dynamic = 'force-dynamic'` in all five pages (`app/app/page.jsx:8`, `app/app/pokemon/[name]/page.jsx:16`, `app/app/moves/[name]/page.jsx:16`, `app/app/abilities/[name]/page.jsx:9`, `app/app/types/[name]/page.jsx:11`). For this app (every fetch `no-store`, spec mandates request-time data) it's defensible and safe, but it's a known migration debt item.

### Scenario walkthroughs

1. **Remove Abilities.** Delete `app/app/abilities/[name]/` and delete the one inbound link block — the Abilities `<Section>` at `app/app/pokemon/[name]/page.jsx:228-236` (plus its `abilities` const at line 158). The nav (`app/app/layout.jsx:26-29`) links only Pokémon and Types; nothing else references `/abilities`. Leftovers are harmless generic seams: `PokemonCard`'s `note` prop and `pokemonRefsToSpecies`' wrapped-entry handling (`app/lib/data.js:99`) stay valid for future callers. Two files, both trivial.
2. **Sprite fix.** Every Pokémon card in the app — home (`app/app/page.jsx:66-72`), moves (`app/app/moves/[name]/page.jsx:80-84`), abilities (`app/app/abilities/[name]/page.jsx:41-47`), types (`app/app/types/[name]/page.jsx:75-80`) — renders through the single `PokemonCard`, and the sprite URL is built in exactly one expression: `app/components/PokemonCard.jsx:17` (`apiUrl(\`/media/sprites/pokemon/${id}.png\`)`), using the numeric id rather than any Pokémon *name*. The species↔Pokémon id mapping is likewise centralized in `pokemonRefsToSpecies` (`app/lib/data.js:92-106`), which is what makes "Deoxys-normal ref → Deoxys species card" correct on every list. One fix covers everything.
3. **Sort cards by name.** Two sort sites: `app/lib/data.js:106` (covers moves/abilities/types lists) and the home page's `matches`/`visible` ordering at `app/app/page.jsx:58-72`. Small, but note the lists carry only API names, so "by name" means either humanized-name sort duplicated at both sites or pushing a display-name into `pokemonRefsToSpecies`' results — a tiny seam mismatch, not a blocker.
4. **Items section.** Reusable as-is: `Section`, `apiJson`/`apiPath`, all of `lib/format.js`, and `pokemonRefsToSpecies` (items' `held_by_pokemon` maps straight in). Not reusable: the detail-page scaffolding. Each of the four existing pages hand-rolls the same fetch-or-404 + `generateMetadata` shape (`app/app/moves/[name]/page.jsx:18-24`, `app/app/abilities/[name]/page.jsx:15-21`, `app/app/types/[name]/page.jsx:17-25`, `app/app/pokemon/[name]/page.jsx:26-33`), and the "`<count> Pokémon` + `<ul className="cards">`" block is copy-pasted three times (`app/app/moves/[name]/page.jsx:79-84`, `app/app/abilities/[name]/page.jsx:40-47`, `app/app/types/[name]/page.jsx:74-80`). You'd clone ~90 lines of the moves page and edit, plus add a nav link in `app/app/layout.jsx:26-29`.
5. **Data source / caching.** Base URL: one constant (`app/lib/api.js:4`). HTTP caching: one module (`app/lib/api.js:12-28`, promise-level in-memory cache on `globalThis`, with 404→null semantics). Media URL prefix: `apiUrl` (`app/lib/api.js:34-35`). Route-level rendering policy, however, is declared per-page (`force-dynamic` in 5 files), so a change to "caching rules" that includes render strategy means touching six files. Good, not perfect, centralization.

### Scores

**removability — 5.** Deleting Abilities is a directory plus one self-contained section block; the nav never linked to it (`app/app/layout.jsx:26-29` vs. `app/app/pokemon/[name]/page.jsx:228-236`), and residual seams (`app/components/PokemonCard.jsx:12` `note` prop, `app/lib/data.js:99`) are generic rather than ability-specific.

**changeability — 4.** The headline bug class lands in one obvious place (`app/components/PokemonCard.jsx:17`, fed by `app/lib/data.js:92-106`), but several small behaviours are duplicated: the `typeLabels.get(x) ?? humanize(x)` fallback appears four times (`app/app/pokemon/[name]/page.jsx:117,176`, `app/app/moves/[name]/page.jsx:50`, `app/app/types/[name]/page.jsx:62`), and the missing-value em dash is a `MISSING` const in `app/components/MovesSection.jsx:10` but bare `'—'` literals in `app/app/moves/[name]/page.jsx:49-52`.

**coupling — 4.** Dependencies point strictly downward and props are narrow (`app/components/MovesSection.jsx:99-104` receives precomputed tables; `app/components/HomeControls.jsx:52-60` encapsulates all router/URL logic). Two tangles keep it from a 5: `PokemonCard` imports server-env-dependent `apiUrl` (`app/components/PokemonCard.jsx:3,17`) with nothing marking it server-only — drop it into a client tree and sprites silently break to `undefined/media/...`; and `PokemonCard` emits its own `<li>` (`app/components/PokemonCard.jsx:14`), coupling it to parents that must supply `<ul className="cards">`.

**abstraction_design — 3.** The real variation points got real abstractions — optional-`href` `TypeBadge` (`app/components/TypeBadge.jsx:5-13`), optional-`types`/`note` card, data-driven table columns (`app/components/MovesSection.jsx:37-45`), the `extra(entry)` hook on `pokemonRefsToSpecies` (`app/lib/data.js:92`). But detail pages share zero scaffolding despite sharing a shape: 4× fetch+metadata+notFound boilerplate and 3× card-list blocks are copy-paste, so the next resource type (Items) is written by duplication, and the two card-sort sites (scenario 3) can drift.
