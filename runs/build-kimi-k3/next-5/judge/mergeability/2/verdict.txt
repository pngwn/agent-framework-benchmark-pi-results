I've read the whole app (16 source files, ~670 significant LOC), checked it against Next 16 conventions, and verified the two framework-behavior claims I was least sure about (stale query params around `router.replace` — a real, documented fragility class in Next 16; and Cache Components as the current recommended caching model). Here's my review.

## What's good

- **Server-first architecture**: every page is an async Server Component; `'use client'` appears exactly twice, on the two components that genuinely need interactivity (`app/components/HomeControls.jsx:1`, `app/components/MovesSection.jsx:1`). That's the shape the App Router docs push you toward.
- **Current API usage**: `params`/`searchParams` are awaited promises (`app/app/page.jsx:22-24`, `app/app/pokemon/[name]/page.jsx:56-58` — correct for Next 15+), `generateMetadata` with a title template (`app/app/layout.jsx:5-10`), `notFound()` for all bad resources, `next/link` everywhere, no `useRouter` for what a `Link` does.
- **Data layer**: the in-memory promise cache (`app/lib/api.js:7-29`) is deliberate and clean — rejections are evicted from the cache (`app/lib/api.js:22-25`), 404s resolve to `null`, and `getSpecies` dedupes across the `generateMetadata` + page double call. The spec explicitly allows runtime caching, and it keeps every request live against the API.
- **No leaks found**: effect cleanup in the debounce (`app/components/HomeControls.jsx:51-53`), no SSR/CSR mismatch risk (search term is prop-synced, not read from `window` during render), fetch fan-out on the Pokémon page is bounded and memoized per process.

## What I'd ask about

1. **`HomeControls.navigate` reads `window.location.search`** (`app/components/HomeControls.jsx:66`) while a debounced 300 ms timer and `router.replace` transitions are in flight. The q value is safely captured via `termRef`, but type/generation can be dropped or resurrected depending on when history actually updates — a known-fragile pattern in the App Router (see vercel/next.js#92187 for the class of bug). Deriving params from the props would be race-free.
2. **Descending sort flips the tie-break** (`app/components/MovesSection.jsx:31-35`): reversing the ascending array inverts the move-name tie-break order too. Cosmetic, but wrong.
3. **`buildMoves` can throw on a 404 move record** — `apiJson` returns `null` but `record.name` is dereferenced unconditionally (`app/app/pokemon/[name]/page.jsx:145-151`).
4. **`PokemonCard` imports from the server-only `lib/api.js`** (`app/components/PokemonCard.jsx:3`) just for `apiUrl`. Works today (card is only used in server pages), but it's a boundary a future client reuse would trip over. Extracting the URL builder to a shared module would make the server/client split explicit.
5. Nits: `force-dynamic` + `cache: 'no-store'` are redundant together; no `error.jsx` boundary so an API outage renders the stock 500; the app directory has no `.gitignore`, so `.next/` build output sits untracked in the repo.

None of these block merge. Naming, comments-that-say-why, file layout and consistency are all well above the bar I'd expect for a codebase others will own.
