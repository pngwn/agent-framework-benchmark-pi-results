## Review: forward-thinking

**Verified against current framework state.** As of 2026-10-30, Next.js `16.4.x` is the Active LTS line (the Oct 14, 2026 security post instructs `npm install next@16.4.x` for Active LTS; 16.5 is still canary), so `next@^16.4.3` in `app/package.json` is exactly current. I checked the two APIs most at risk of being "of an older era" against the official docs: the top-level `turbopack` config key (docs: "previously named `experimental.turbo` … new configuration should use the top-level `turbopack` option") is the current name, and `export const dynamic = 'force-dynamic'` is still supported on stable — but the route-segment-config docs say these options are "disabled if the `cacheComponents` flag is on, and will eventually be deprecated," and the Cache Components migration guide's answer for `force-dynamic` is "just remove it." So the app's idiom is correct *today* and carries a known, documented migration cost *tomorrow*.

**What ages well.** Data access is genuinely well-factored: every route goes through `app/lib/api.js` (one fetch/cache module) and `app/lib/data.js` (derived aggregates), with spec text rules in `app/lib/format.js`. Swapping the caching strategy — including to Next 16's `use cache` — is a two-file change. All filtering/pagination state lives in the URL and is handled server-side, so there's no client state library to churn. Platform use is good: `URL`/`URLSearchParams` (`app/lib/api.js:27`, `app/app/page.jsx:14`, `app/components/HomeControls.jsx:35`), native form controls with real labels, CSS custom properties, `:focus-visible`, grid — and zero hand-rolled polyfills. Dependencies are exactly `next`, `react`, `react-dom`, nothing else.

**What will bite later.** The single biggest forward-looking weakness is that there are **no types at the API boundary** (0 type lines; JS with `jsconfig.json` only). A large external API's documents (`record.damage_class?.name` at `app/app/pokemon/[name]/page.jsx:118`, `t.damage_relations[key]` at `app/app/types/[name]/page.jsx:41`) are consumed untyped across six route files, so an upstream field rename is a runtime surprise, not a compile error. Second, the app has *no devDependencies at all* — no `eslint-config-next`, no formatter — where the current Next scaffold ships linting; future contributors get no automated guardrails. Smaller items: `window.location.search` instead of `next/navigation`'s `useSearchParams` (`HomeControls.jsx:35`), no timeout/`AbortSignal` on upstream fetches (`lib/api.js:13`), a process-lifetime unbounded cache that also caches 404-`null`s forever (`lib/api.js:9-25`), no `loading="lazy"` on the 48 home-page sprites (`PokemonCard.jsx:15`), and 36 hand-duplicated per-type CSS rules that a new type would require editing twice (`globals.css:224-296`).
