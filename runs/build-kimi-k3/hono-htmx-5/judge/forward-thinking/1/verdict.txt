## Review: Pokédex (Hono + htmx)

### Version currency (verified against releases/docs, today 2026-10-30)

- **Hono**: current stable is **v4.13.14** (2026-10-25, honojs/hono releases). v5.0.0 is only at **rc.1** (2026-10-10). The app pins `^4.13.14` — the current stable line, not a legacy one. Source: github.com/honojs/hono/releases, releasealert.dev.
- **@hono/node-server**: latest is **2.1.5** (2026-10-13); app pins `^2.1.5`. `@hono/node-server/serve-static` is the current import path (dist ships `serve-static.mjs`). Per the hono skill, `serveStatic` only moves out of this package at v5 — not yet stable.
- **htmx.org**: latest stable is **2.0.11** (2026-09-22); htmx 4.0 exists only as alpha/beta. App pins `^2.0.11` and uses htmx-2 attributes (`hx-push-url`, not the removed `hx-push`).

### What ages well

- All data access sits behind one module (`app/src/api.js`), with a single in-process promise cache (`api.js:11-27`) and one `API_BASE` config point (`api.js:5`) — swapping the data source or adding a cache layer touches one file.
- Views consume plain data objects shaped in the route layer (`app.js:150-172`), so templates never touch fetch/caching — a clean seam.
- `hono/html` tagged templates (`views/layout.js:1`, used everywhere) are the current-generation no-build templating primitive; escaping is on by default, so interpolated names like `mr-mime` are safe without hand-sanitizing.
- htmx is **vendored at build from node_modules** (`scripts/build.mjs:9-12`) rather than CDN-linked — reproducible, versioned upgrades, no external dependency at runtime.
- Progressive enhancement is real: both forms are plain `method="get"` forms (`views/home.js:63-66`, `views/pokemon.js:49-56`), so the app works with JS off; the small client script (`public/app.js:7-12`) only cleans URL params and adds table sorting via delegated events (`public/app.js:15-44`) so htmx-swapped tables stay sortable — forward-thinking against DOM churn.
- Platform-first habits: native `fetch` (no axios), `URLSearchParams` for query building (`views/home.js:8-14`), native `search` event for the clear button (`views/home.js:70`), explicit `role="list"`/`list-item` to preserve list semantics under `list-style: none` (`views/components.js:25`, `styles.css:198`), `defer` scripts (`views/layout.js:11-12`), `loading="lazy"` + fixed sprite dimensions (`views/components.js:16`), no polyfills, no build tooling at all.

### What will cause churn

- Upstream fetches have **no timeout or `AbortSignal`** (`api.js:13`): one hung PokeAPI connection hangs a page render, and the in-process promise cache pins that hang for the process lifetime.
- `serveStatic({ root: './public' })` (`app.js:33-34`) resolves against the **cwd**, not the module — works per spec (`npm start` from `app/`) but breaks silently if the process is launched from elsewhere; the asset list is also hardcoded, so every new file needs a route edit.
- Zero type information at the API boundary: the whole PokeAPI surface (`species.varieties`, `type.pokemon`, `damage_relations`, `version_group_details`…) is consumed untyped across `api.js`/`app.js` with no JSDoc typedefs — a shape drift surfaces as `undefined` deep in a template, far from its cause.
- Full-page vs fragment negotiation via the `HX-Request` header inside the page routes (`app.js:37,75,177`) couples two render modes to one handler; a dedicated fragment route would keep them independent — a common htmx idiom, but the more decoupled shape survives redesigns better.
