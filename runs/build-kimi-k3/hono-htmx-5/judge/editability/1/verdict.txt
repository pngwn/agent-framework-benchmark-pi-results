## Review: Pokédex app (Hono + htmx)

**Structure** (verified): clean three-layer split — `app/src/api.js` (data + caching), `app/src/app.js` (all routes in one 309-line file, plus data shaping), `app/src/views/*` (pure `hono/html` templates), `app/public/app.js` (htmx progressive enhancement). Dependencies are current stable (`hono@^4.13.14` is the latest v4 stable; Hono v5 is still at RC as of 2026-10-30, and `@hono/node-server@^2.1.5` is the current release — nothing outdated here).

**Scenario walkthroughs** (all files that would need touching):

1. **Remove Abilities**: `app.js:253-266` (route), `app.js:194-196` (data passed to `pokemonPage`), `app.js:18` (import), `details.js:19-23` (`abilityPage`), `pokemon.js:60-69` + `:123` (`abilitiesHtml` and its section), `components.js:14,24` (`hidden` flag + note on the shared card), `styles.css:250` (`.hidden-note`). No nav link to remove — moderate scatter, but no dead-code trap.
2. **Sprite fix**: every card list funnels through `pokemonCard` at `components.js:17`, which builds the sprite URL from an ID pattern. One render site covers home, moves, abilities and types. However the URL is *derived*, not taken from the Pokémon record, so a real fix needs plumbing (`speciesCardsFor` at `app.js:208-222` / `speciesIndex` in `api.js` currently never fetch sprite URLs).
3. **Sort by name**: two ordering sites, both in `app.js` — the home slice at `app.js:70-72` and `out.sort` at `app.js:221`. Views untouched.
4. **Items section like Moves**: mostly additive — new routes in `app.js`, new builders in `details.js` reusing `renderPage`/`section`/`cardList`/`speciesCardsFor`/`format.js`. But there's no shared "detail page"/"index page" abstraction; you'd copy `movePage`'s shape (`details.js:5-17`) and grow the monolithic router.
5. **API base URL / caching**: `api.js:4` (single env read), `api.js:6-20` (response cache), `api.js:53-56` (memo layer) — well centralized; the one leak is `components.js:2,17`, where a *template* imports `API_BASE` and hardcodes the `/media/sprites/pokemon/<id>.png` scheme.

**Notable latent defect**: `app.js:72` passes the `typeEnglishByName()` **Map** into `pokemonCard`, which indexes it with brackets (`components.js:21`) as if it were a plain object — `Map['fire']` is `undefined`, so every home-page card badge silently falls back to `humanize()`. It only renders correctly because the 18 English type names happen to equal the humanized API names. Compare `app.js:297`, which correctly does `Object.fromEntries(labels)` for the type page — two different conventions for the same data at the same seam.
