## Review

The app is a compact, well-layered Hono 4 + htmx 2 application (`app/package.json` pins `hono@^4.13.14` and `@hono/node-server@^2.1.5`, both current stable today), so the version choices and imports (`@hono/node-server/serve-static`) are correct for the present release. Rendering uses the officially documented `hono/html` tagged-template helper (hono.dev/docs/helpers/html) with `c.html()`, and the server-side half of the htmx integration — `HX-Request` detection returning fragments (`app/src/app.js:37`, `:75`, `:177`) — is the canonical pattern, wrapped in real `GET` forms so the app degrades gracefully without JS (`app/src/views/home.js:36-45`). Escaping is delegated to `hono/html` (only `raw()` would bypass it; the app never uses `raw()`), and 404s are handled both at the API-call layer (`apiJson` maps 404 → `null`) and at the router (`app.notFound`, `app/src/app.js:303`). I verified the two subtlest htmx claims against current sources: `from:` with a plain CSS selector attaches to **all** matching elements (htmx `querySelectorAllExt`; the "first match only" caveat applies only to `find`/`closest`/`next`/`previous` extended selectors — github.com/bigskysoftware/htmx#1597), so `change from:select` correctly covers both filter selects; and mutating `event.detail.parameters` in `htmx:configRequest` (`app/public/app.js:6-10`) does shape the pushed URL, so the "clean URL" trick works.

The main issue I'd flag is a latent type-shape bug: `pokemonCard` reads the `typeLabels` prop as a plain object (`app/src/views/components.js:21`), but the home route passes the `Map` from `typeEnglishByName()` (`app/src/app.js:72`); the lookup always misses and silently falls back to `humanize()` — correct today only because the 18 type English names equal their humanized names. One call site papers over the same inconsistency with `Object.fromEntries` (`app/src/app.js:297`), while `typePage`'s relations expect an object (`app/src/views/details.js:68`). Beyond that: rapid filter changes have no out-of-order response guard (no `hx-sync`/abort handling), `search from:#q` fires an extra request on top of the debounced `input` on clear, `fetch` has no timeout so a hung request stays cached forever (`app/src/api.js:13-19`), and htmx 2's default `responseHandling` refuses to swap 4xx/5xx — so an API hiccup during a filter change silently does nothing while `onError` returns plain text (`app/src/app.js:305-308`). Structure, naming and comments are genuinely good: a clean `api.js` data layer with promise-caching, tiny pure helpers in `format.js`, per-page view modules, and why-comments at each non-obvious choice; nits are the dead `speciesList` import (`app/src/app.js:7`), the 50-line move-assembly function living in the router file (`app/src/app.js:95`), and the per-path `serveStatic` loop (`app/src/app.js:33-34`).
