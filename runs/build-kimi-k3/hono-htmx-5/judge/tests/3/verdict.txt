I've reviewed the app, the spec, the acceptance suite, and verified the current Hono `html` helper's auto-escaping behavior (relevant to one untested risk). Summary of what I found for the tests dimension:

**The app contains zero tests of its own.** `app/package.json` defines only `build` and `start` (no `test` script), there's no test runner or dev dependency, and no `*.test.*`/`*.spec.*` files anywhere under `app/` — matching the measured facts. Everything the app does is guarded solely by the acceptance suite in `tests/`, which is page-level Playwright and not the app's work.

That's a real loss here because the app is full of pure, easily-testable logic: `app/src/format.js` is a textbook unit-test target (humanize, dex-number padding, "latest English flavor" = last-en-entry, em-dash fallbacks), and the riskiest code is all data transformation with no coverage at the unit level:

- Home filtering + pagination + URL state (`app/src/app.js:67-96`): combined q/type/generation AND-filtering, `PAGE_SIZE` slicing, page clamping past `totalPages`. A refactor that drops the clamp or gets the slice bounds wrong would render empty or duplicated pages.
- `pokemonMovesData` (`app/src/app.js:73-121`): the most complex function in the app — version-group ordering via a fetched `order` map with a `?? 0` fallback, defaulting to the highest-order game, method grouping with a custom sort (`Level Up, Machine, Egg, Tutor`, then alphabetical), level-up rows sorted by level-then-name. Dozens of plausible regressions, none caught without the Playwright suite.
- `speciesIndex` (`app/src/api.js:90-119`): type slots assembled from type records and sorted by slot, alternate forms dropped via `id > 10000`, species→generation mapping by name. Swapping slot order or misapplying the alternate-form filter would silently corrupt every home-page card and the type filter.
- `speciesCardsFor` (`app/src/app.js:126-146`): pokemon-id→species mapping, dedup, alternate-form exclusion.
- Client-side table sorting (`app/public/app.js:16-43`): missing-values-always-sort-last in both directions, numeric vs. lexicographic, aria-sort toggling — pure logic with subtle semantics, covered only indirectly by one acceptance test.
- Error/caching paths (`app/src/api.js:18-25` promise cache with failure eviction, `app/src/app.js:261-266` `onError`): a refactor that stops evicting failed fetches would make a transient API hiccup sticky for the process lifetime, and nothing would fail.
- An escaping assumption: `app/src/views/home.js:47` interpolates user-controlled `q` into an attribute relying on `hono/html`'s auto-escaping (current stable behavior, verified in docs). The acceptance tests never inject hostile input, so a refactor to `raw()`/string concatenation would introduce XSS with every test green.
