## Review: forward-looking

Framework: React Router **8.5.1** — the current stable, released 2026-10-27 (three days ago), verified via reactrouter.com/changelog and npm. Every framework API in use is v8-era; nothing here is carrying v7-era debt.

### `latest_apis` — 5
The app is on the newest framework version and uses only current-generation APIs:
- `app/package.json:9-24` — `react-router`/`@react-router/dev`/`@react-router/serve` at exactly `8.5.1`, matching npm's `latest` tag; React `19.3.1` is the current React release (npm/react.dev).
- `app/app/routes.ts:1-13` — current `RouteConfig`/`index`/`route` config; `app/app/root.tsx:11` exports the root `Layout` (the v7.16+ recommended root structure, so `ErrorBoundary` can wrap the whole document).
- `app/app/routes/pokemon.tsx:49`, `move.tsx:14`, `type.tsx:18`, `not-found.tsx:7` — `data(payload, { status: 404 })`, the current idiom for non-thrown 404s with a real status code.
- `app/app/routes/*/tsx` — `meta({ loaderData })` everywhere; the deprecated `meta` `data`/`match.data` arg was removed in v8 and is absent here.
- `./+types/*` typegen used consistently (`root.tsx:2`, `pokemon.tsx:3`, etc.) — the current type-safety model.
- No view-transition APIs are used, which is exactly right: v8.5.0 deprecated them in favour of React's `<ViewTransition>` (changelog, 2026-10-19). No experimental/unstable flags, which is the correct posture.

I looked for a current-generation API the app ignored and found none that would apply — middleware, RSC, view transitions and API-only mode are all opt-in features this app doesn't need.

### `platform` — 5
Reaches for the platform first, with no polyfills or hand-rolled substitutes:
- `app/app/lib/pokeapi.server.ts:18-32` — native `fetch` with a promise-based cache (dedupes concurrent identical requests and clears transient failures, no extra dep).
- `app/app/routes/home.tsx:50,68` and `pokemon.tsx:382` — `URLSearchParams`/`URL` for all query handling.
- `app/app/app.css` — modern CSS throughout: custom properties, logical properties (`:55` `margin-inline`, `:92` `padding-block`), `:focus-visible` (`:31-34`), `auto-fill/minmax` grid (`:171`), `image-rendering: pixelated` (`:193`). Plain CSS per the spec, no framework.
- `app/app/components/ui.tsx:52`, `pokemon.tsx:298` — intrinsic `width`/`height` on every `<img>` to prevent layout shift; native labelled `<input type=search>`/`<select>` controls (`home.tsx:91-127`).
- `mapLimit` (`pokeapi.server.ts:55`) is hand-rolled concurrency control, but there's no platform equivalent in Node 24, and it's 12 lines — a fair call, not a reinvented wheel.

### `dependencies` — 4
Leanest reasonable set: five runtime deps, all justified. `isbot` (`app/package.json:16`) looks vestigial but is real — the framework's built-in server entry imports it (`app/build/server/index.js:5`) and the app ships no `entry.server.tsx`, so it must be installed. Two nits keep this off a 5:
- `vite ^7.0.0` (lock resolves `7.3.7`) while Vite 8 is the current major and `@react-router/dev@8.5.1`'s peer range explicitly allows `^7.0.0 || ^8.0.0` (`app/package-lock.json:824-829`). One major behind on the bundler.
- `typescript ^5.9.0` while the same peer range allows `^6.0.0 || ^7.0.0`; also, framework packages are pinned exactly (`"8.5.1"` with no caret) while React uses `19.3.1` exact and `isbot` uses `^5` — three pinning styles in one manifest.

### `churn_resistance` — 3
Data access is genuinely well-contained — every API call lives in `app/app/lib/pokeapi.server.ts`, and loaders reshape into typed interfaces before returning — but several seams will make future changes harder than they should be:
- The external API contract is untyped. `apiGet<T = any>` (`pokeapi.server.ts:18`) and the `as any[]` casts throughout the loaders (`pokemon.tsx:60,61,132,141,150,151,159`; `move.tsx:9`; `type.tsx:19`; `ability.tsx:9`) mean a change in the PokeAPI response shape fails silently at runtime. If the upstream API changes (which the spec explicitly says it may — the tests run against a modified overlay), TypeScript won't help.
- `API_BASE_URL` is read in three places: `root.tsx:7`, `pokeapi.server.ts:5`, and `useRouteLoaderData<{ apiBase: string }>("root")` at `urls.ts:6` — the last of which hand-writes the root loader's return type instead of deriving it from `./+types/root`. Changing how the API base is resolved touches all three.
- Duplicate helpers: `spriteUrl` exists in both `pokeapi.server.ts:46` and `urls.ts:9`; the server one is dead code (only `urls.ts`'s is used, via `components/ui.tsx:3,52`).
- `root.tsx:65-74` renders "Not found" for *every* error, including thrown 500s — errors and not-found are conflated in one boundary instead of using `isRouteErrorResponse`/`useRouteError` to distinguish, so an API outage shows a 404 page.
- Home page filter state is split-brained: `q` lives in component state seeded once from the URL (`home.tsx:35,37`), so navigating Back/Forward changes `searchParams` but the input and the actual filter keep their stale local value. The URL is not the source of truth for the search filter — exactly the state-management churn the framework's URL-state guidance exists to avoid.

Findings I won't count heavily but worth noting: the home loader ships the entire 1025-species index to the client in every SSR payload (defensible for instant client-side filtering, but it's a large embed to carry forever), and `app/build/` artifacts are committed with no ignore rule.

### Verdict
This is a well-built, deliberately minimal framework-mode app that is fully current on React Router v8 and modern platform APIs — I'd expect a v9 upgrade to touch almost nothing. The forward-looking debt is concentrated in the untyped external-API boundary, duplicated origin/config plumbing, and the conflated error boundary, all of which are cheap to fix now and expensive to fix later.
