I've reviewed the app against Gracile's current release and verified each API status against upstream sources. Here's what I found.

## What the app uses

**Gracile core, current stable (0.11.0 = latest on npm, published ~Apr 2026):**
- `gracile({ output: 'server' })` Vite plugin — `app/vite.config.ts:1-9` — this is the *verbatim* example from the framework docs and engine's own `plugin.ts` docblock.
- `defineRoute` with `handler`/`document`/`template` — `app/src/routes/index.ts:33`, `app/src/routes/types/[name].ts:31` — the documented route shape ("Defining routes" page).
- `@gracile/gracile/server-html#html` + `<route-template-outlet>` — `app/src/document.ts:1,20` — matches the docs' annotated document example.
- `@gracile/gracile/node` (`nodeAdapter`, `getClientBuildPath`) — `app/server.js:2,7,9` — byte-for-byte the official `minimal-server-express` starter's `server.js` (I fetched the starter from `gracile-web/starter-projects` to compare).

Notably, the app *avoids* every actually-experimental corner of the ecosystem: no `@gracile-labs/islands` (explicitly "Experimental" on npm), no metadata add-on, no CSR router — client interactivity is plain vanilla DOM (`app/src/routes/index.client.ts:1-44`, `app/src/routes/pokemon/[name].client.ts:1-49`). The framework is pinned exactly (`app/package.json:12`), which is the right call for a pre-1.0 project that self-describes as alpha.

**The one reach past the documented surface:** every handler route guards on `url.hostname === 'gracile-static'` (`app/src/routes/index.ts:35`, `pokemon/[name].ts:104`, `moves/[name].ts:28`, `abilities/[name].ts:19`, `types/[name].ts:24`). I traced this: it's an *undocumented internal* sentinel in `@gracile/engine`'s build render pass (`packages/engine/src/routes/render.ts` in gracile-web/gracile creates `new URL(path, 'http://gracile-static')` and calls every route's GET handler during `vite build`, even in server output mode, to render documents and collect assets). It appears nowhere in the user docs, starter projects, or web-indexed sources. The guard is *justified* — without it, the build's stub pass would fetch live API data at build time, which `SPEC.md` explicitly forbids — but the magic string is copy-pasted across six files with no shared helper, so an engine change breaks all six simultaneously.

**Recently-stable, supported stack:** Vite 8 (stable since 2026-03-12 per vite.dev) is explicitly in `@gracile/engine@0.11.0`'s peer range (`vite ^7 || ^8`, confirmed via the engine package on jsDelivr). Express 5 and Lit 3 are long-stable. `context.props.GET` wrapping matches both the runtime pipeline (`request-pipeline.ts`: `{ [method]: handlerOutput }`) and the docs' examples, though the app leans on it via `as any` casts (`app/src/routes/index.ts:164`).

- **containment: 3** — Framework touchpoints are well contained (server.js mirrors the official starter, one shared `document.ts`, 9-line config), but the internal sentinel magic string is spread across six route files instead of one helper.
- **justification: 4** — The sentinel guard is the only way to honor the SPEC's "no API fetches at build time" given Gracile's undocumented build-time handler invocation; no stable API covers it. No gratuitous experimental usage anywhere else.
