## Review — Editability

This is a compact, well-factored Angular 22 app: one component + one resolver file per route, a shared `CardEntry`/`PokemonCards` abstraction for every card list, and a `PokedexData` service that owns the shared datasets and the Pokémon→species mapping. The main editability cost is repeated resolver boilerplate (title + 404 handling) and a second card-construction site in the home page.

### Scenario walkthroughs

**1. Remove Abilities pages.** Delete `app/src/app/ability-detail.ts` and `app/src/app/ability-resolver.ts`, drop the route block and import at `app/src/app/app.routes.ts:5,27-31`, then strip the Abilities section at `app/src/app/pokemon-detail.ts:93-104` and the `abilities` field it consumes (`app/src/app/pokemon.resolver.ts:44,181-189`, `app/src/app/models.ts:76-80`). No nav links to prune — `app/src/app/app.html` only links Pokémon/Types. Self-contained, ~5 files, mostly deletion.

**2. Sprite bug (Deoxys).** The ref→species resolution is centralized in `cardsFor` (`app/src/app/pokedex-data.ts:131-138` — falls back to fetching the Pokémon to find its species when the ref name isn't a species, exactly the Deoxys case), and the sprite URL is built in exactly one method (`app/src/app/api.ts:45-47`) used by one render point (`app/src/app/pokemon-cards.ts:46`). The home page starts from species ids directly (`app/src/app/home.ts:132-141`), so a fix in `cardsFor`/`spriteUrl` covers every list. One fix, all lists covered — well designed.

**3. Sorting by name on every card list.** All four lists render through `PokemonCards` (`app/src/app/pokemon-cards.ts:14-50`), so sorting in that component covers move/ability/type pages in one edit. But the home list is paginated before rendering (`app/src/app/home.ts:132-141` slices the page), so whole-catalog sorting also needs a touch to `filtered()`. Two files.

**4. Items section shaped like Moves.** Reusable: `util.ts` helpers, `PokedexData`/`Api`, `NotFoundView`, `PokemonCards`/`TypePill`, the route pattern. But the Moves page is two bespoke files (`app/src/app/move-detail.ts`, `app/src/app/move.resolver.ts`) with no shared detail-page/section abstraction, and `/items` (a list) has to copy `type-list.ts`/`types.resolver.ts` instead. You'd also duplicate the try/catch + `Title` + `RESPONSE_INIT` scaffold a fifth time. Roughly half copied.

**5. API base URL & caching.** Base URL: `app/src/app/api.ts:7,17-25` (token + default), `app/src/app/server.ts:16` (config.js), `app/src/index.html:9` (script tag) — the default literal `http://localhost:9000` appears in two of them. Caching is split three ways: per-URL promise cache (`app/src/app/api.ts:29-38`), dataset memoization (`app/src/app/pokedex-data.ts:36-38`), and HTTP transfer cache (`app/src/app/app.config.ts:11`). Five files know about data-source concerns.

### Criteria

- **removability — 4.** Features are per-route file pairs with lazy `loadComponent` (`app/src/app/app.routes.ts:6,18,23,28`) and no shared feature module; there are no dead nav surfaces. Only the Pokémon page's Abilities section (`app/src/app/pokemon-detail.ts:93-104`) and its resolver field (`app/src/app/pokemon.resolver.ts:181-189`) sit outside the feature directory — a legitimate dependency, but it means removal touches 5+ files.
- **changeability — 3.** Domain bugs mostly land in one place (`cardsFor` at `app/src/app/pokedex-data.ts:131-138`, `spriteUrl` at `app/src/app/api.ts:45-47`, `util.ts` helpers). But document-title handling is repeated in 11 `setTitle` calls across 8 files (`app/src/app/not-found-view.ts:16`, `app/src/app/home.ts:89`, `app/src/app/type-list.ts:26`, plus success/failure pairs in all four resolvers, e.g. `app/src/app/move.resolver.ts:33,54`), and the not-found recipe (Title + `RESPONSE_INIT` 404) is copy-pasted in `app/src/app/pokemon.resolver.ts:194-198`, `move.resolver.ts:53-57`, `ability.resolver.ts:42-46`, `type.resolver.ts:56-60`, `not-found-view.ts:15-18`. Changing either convention means editing five files.
- **coupling — 4.** Components receive narrow, per-page view models via `input.required` (`app/src/app/move-detail.ts:34`, `app/src/app/type-detail.ts:44`) and don't fetch; data concerns live behind `Api`/`PokedexData`; the SSR/client split for the API base is an explicit, documented seam (`app/src/app/api.ts:17-25` + `app/src/app/server.ts:20-28`). Minor tangles: `PokemonCards` injects `Api` directly for the sprite URL (`app/src/app/pokemon-cards.ts:42-47`), the raw `EvolutionNode` API model reaches the template (`app/src/app/pokemon-detail.ts:110-133`), and styling is a single global stylesheet rather than scoped component styles.
- **abstraction_design — 4.** The `CardEntry` abstraction genuinely captures the app's real variation — cards from species vs. cards from Pokémon refs, optional types, optional notes for hidden abilities (`app/src/app/pokedex-data.ts:19-24,125-149`) — which is why one component serves four lists and the Deoxys problem has one home. The shared type-label mapping is instead re-inlined four times (`app/src/app/type.resolver.ts:42`, `move.resolver.ts:44`, `pokemon.resolver.ts:101,171`) where a `typeLabel` helper on `PokedexData` would do, and detail-page scaffolding has no shared shape, so a similar new section is mostly a copy.
