## Review summary

**What's current and good:** The app pins `nuxt` to **4.6.3**, which is literally the latest stable release (released 2026-10-27, verified against GitHub/npm releases — three days before today). It uses the Nuxt 4 `app/` srcDir structure, auto-imports, `useAsyncData` (with keys, `await` in setup, and the current `watch: [source]` option), `useHead` with computed titles, `runtimeConfig`, `defineNuxtPlugin`, and `$fetch` — all current-generation APIs. Dependencies are minimal (3 total, no axios/lodash/CSS framework), and filter state lives in the URL rather than a state library.

**What will age badly:**
1. **The 404 pattern touches h3 v1 internals.** Five files do `event.node.res.statusCode = 404` (`app/app/pages/*/[name].vue`, `app/app/components/NotFound.vue:5`). Nuxt 4.6 already supports both Nitro majors, and Nuxt 5/Nitro 3 hands handlers a web-standard `RequestEvent` instead of the h3 v1 event (per Nuxt 4.6 release notes and the `nuxt/server` docs). The documented, portable utilities are `setResponseStatus(event, 404)` and `createError({ statusCode: 404 })` (verified in the Nuxt 4.x docs for both).
2. **The API origin is baked at build time.** `nuxt.config.ts:9` reads `process.env.API_BASE_URL` (evaluated only during `nuxt build` — the classic runtime-config anti-pattern, confirmed by the SO answer and Nuxt runtime-config docs: only `NUXT_*` names override after build). I verified in the build output that `.output/server/chunks/nitro/nitro.mjs:4131` bakes `http://localhost:9100`, while `entry.mjs:1262` still reads `process.env` at server start — and then the plugin (`app/app/plugins/api-base.ts:4`) overrides the runtime env read with the baked `$config` value. It works today only because the harness uses the same URL for build and start.
3. **The data layer is `any`-typed at the HTTP boundary** (`utils/poke.ts:66` `Promise<any>`), pushing 15+ inline `as {...}` casts into pages, so API shape changes surface at runtime rather than compile time. Counterweight: all fetching is genuinely funneled through one module and each page normalizes into an explicit view model — that part is excellent churn protection.
