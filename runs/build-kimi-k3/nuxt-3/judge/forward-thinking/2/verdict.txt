## Review: forward-thinking — Nuxt Pokédex app

**Verification of currency (sourced, not from memory):**
- `nuxt`'s latest stable is **4.6.3, released 2026-10-27** (github.com/nuxt/nuxt/releases) — the app pins exactly this (`app/package.json:10`). Nuxt 3 hit EOL 2026-07-31; this app is on the right major.
- Nuxt 4.6's headline is server-agnosticness: the new `nuxt/server` surface and a portable `RequestEvent` whose documented shape is `event.req/url/res` (nuxt.com/docs/4.x/api/composables/use-request-event: "Code that should work whichever server builder is configured should only read these properties"; nuxt.com/blog/v4-6: "Server code written against `nuxt/server` on 4.6 runs unchanged [on Nuxt 5, which moves to Nitro v3 and h3 v2]").
- `nuxt@4.6.3` itself depends on `vue ^3.5.44` and **`vue-router ^5.4.0`** (registry.npmjs.org/nuxt/latest). The app pins `vue-router ^4.5.0`, and the lockfile confirms **two copies** of vue-router installed: `vue-router@4.6.4` at the root and `vue-router@5.4.0` nested under `nuxt` (`app/package-lock.json:8423`, `app/package-lock.json:6227`). The app never imports vue-router directly (only auto-imported `useRouter`/`useRoute` via `#app`), so the pin is both unnecessary and one major behind the framework.
- The docs' minimal `package.json` does list `nuxt`/`vue`/`vue-router`, so listing three deps is per-docs; the fault is the stale vue-router range.

**What ages well here:** the whole data layer sits behind one module (`app/app/utils/poke.ts`) with a shared in-memory promise cache; zero experimental features (`nuxt.config.ts` has no `experimental` block); the Nuxt 4 `app/` directory layout is followed correctly; current data-loading (`await useAsyncData` with keys and a `watch` option at `app/app/pages/pokemon/[name].vue:17,112`), `useHead`, `defineNuxtPlugin`, `runtimeConfig.public`, typed `defineProps`, auto-imports everywhere. Platform use is good: Map/Set, `padStart`, `localeCompare`, token-driven CSS custom properties and grid/flex, a hand-rolled `mapLimit` concurrency helper (`app/app/utils/poke.ts:92`) instead of a `p-limit` dependency, and a hand-rolled debounce (`app/app/pages/index.vue:67-69`) instead of VueUse.

**What will cause churn:** the 404 status is set by mutating h3 v1's `event.node.res.statusCode`, copy-pasted into **five files** (`app/app/components/NotFound.vue:5`, `pages/pokemon/[name].vue:173`, `pages/moves/[name].vue:37`, `pages/abilities/[name].vue:32`, `pages/types/[name].vue:46`) — this is exactly the shape the portable `RequestEvent` (`event.res.status`) and `nuxt/server`'s `setResponseStatus`/`createError({ status: 404 })` exist to replace, and the docs explicitly flag `.node` as builder-specific. Rendering the 404 in-page (rather than `error.vue`) is defensible since it keeps the shell landmarks, but the status logic belongs in one shared composable at minimum. The API boundary is typed `any` (`app/app/utils/poke.ts:66,80`) with inline casts repeated at every call site (`pages/pokemon/[name].vue:22,35,49,66,72,87,92`). The API base default is duplicated in config and the data layer (`app/nuxt.config.ts:8` vs `app/app/utils/poke.ts:54`) and threaded through a plugin-mutated module global (`app/app/plugins/api-base.ts`) instead of `useRuntimeConfig()` at point of use. There's no root `tsconfig.json` (the Nuxt starter ships one) and no type-check script, so the TS codebase has no verification net.
