## Test-quality review: `app/` (Pokédex, SvelteKit)

**The agent wrote no tests at all.** There are no `*.test.*`/`*.spec.*` files under `app/`, no test runner or `test` script in `app/package.json:6-10`, and no test-related devDependencies — only the framework toolchain. Every line of logic — 4 `load()` functions, a hand-rolled fetch semaphore with an in-memory cache, pure text/number helpers, and a dense client-side sort comparator — is guarded solely by the harness's acceptance suite, which the app doesn't own and won't be the guard once someone refactors the data layer.

The riskiest unguarded spots I found while reading:

- **URL-state parsing** (`app/src/routes/+page.server.js:12,44-45`): `page` clamping via `Math.max/Math.min`, non-numeric `page`, invalid `type`/`generation` params (silently → zero results), and param-default omission. No test would catch a clamping or NaN regression.
- **Client-side table sorting** (`app/src/lib/components/MoveTable.svelte:56-84`): the "missing values sort last in both directions" null-handling, number-vs-string compare, the three-term tiebreak, and `aria-sort` bookkeeping are exactly the kind of comparator code that breaks in refactor, and it's the only place the spec's default ordering is enforced.
- **`speciesFromPokemonRefs` + augment coupling** (`app/src/lib/server/data.js:42-61` with `app/src/routes/abilities/[name]/+page.server.js:15-18`): the augment callback receives a ref index and the abilities route re-indexes into a *different* array (`entries`), relying on positional alignment. Any future filtering/reordering of the refs array silently mislabels which Pokémon have the hidden ability. This is the single most refactor-fragile seam in the app, and nothing pins it.
- **API client** (`app/src/lib/server/api.js:14-29`): a hand-rolled concurrency limiter (`inflight`/`waiters`) and an unbounded never-invalidating cache — deadlock or a fetch-storm would only show under load, and no test exercises it.
- **Learn-method ordering comparator** (`app/src/routes/pokemon/[name]/+page.server.js:115-118`): sentinel-based `indexOf` logic for the fixed-then-alphabetical method order.
- **Search debounce/`typed`-override interaction** (`app/src/routes/+page.svelte:9-38`): the `typed ?? data.q` dance with `afterNavigate` reset and the pending 250 ms timer is race-prone and untested.
- **Hard-wired data dependencies** (`app/src/lib/server/data.js:1`, `api.js:6,24`): `api()` binds `process.env` and global `fetch` at module level, so the data layer can't be unit-tested without module mocking — the structural reason no tests exist. The pure helpers in `app/src/lib/utils.js` were trivially testable and weren't tested either.
- **Non-404 API failures**: only 404 is handled (`api.js:41-42`); what a 500/timeout from the API renders is untested and likely the raw `+error.svelte` page.

Worth noting: the code is reasonably well factored (pure helpers, thin routes), so a small unit suite for `utils.js`, the two comparators, and `speciesFromPokemonRefs` (with an injected fetch) would be cheap and high-value. Its absence is the miss here.
