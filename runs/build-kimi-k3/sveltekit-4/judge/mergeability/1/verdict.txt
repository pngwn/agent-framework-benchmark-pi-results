## Review summary

**Structure.** The app is a clean SvelteKit layout: all data fetching lives in `+page.server.js` loads backed by two server-only modules (`app/src/lib/server/api.js` — HTTP client with in-memory cache and a concurrency limiter; `app/src/lib/server/data.js` — shared data assembly), a tiny pure `lib/utils.js`, and five small components. Server/client boundary is explicit (`lib/server/` is imported only from load functions), so nothing leaks across SSR/CSR.

**Idiom.** This is fully modern Svelte 5 / SvelteKit: runes throughout (`$props`, `$state`, `$derived`, `$derived.by`), `$app/state`'s `page` in `+error.svelte`, `{@render children()}` in the layout, keyed `{#each}` blocks everywhere, `onclick=`/`oninput=` attribute events, `style:--custom-prop` for theming (the pattern the official skill recommends), `import Self` recursion in `EvolutionNode.svelte`, `error(404)` from `@sveltejs/kit` for missing resources, and adapter-node with `npm start` → `node build`. Zero legacy `on:`, `$:`, `export let`, `{@html}`, or stores. URL-as-state (filters, `page`, `game`) is done the Kit way — server load reads `url.searchParams`, client does `goto()` with `reset: false`.

**Risks found (all minor):** an un-cleared debounce timer that can fire `goto` after navigating away; an unbounded response cache (spec-sanctioned, but worth a size note for a long-lived process); an undocumented `{#key}` block used to reset sort state; and a small duplication between English-name lookup (`getTypes`) and `humanize()` for type labels.
