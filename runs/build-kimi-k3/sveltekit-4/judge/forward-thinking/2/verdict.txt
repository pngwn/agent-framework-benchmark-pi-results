## Review: forward-thinking

**Framework currency.** This app was clearly written against SvelteKit 3 (the current stable, released 2026-10-01), not an older training-data version. The three tell-tale Kit 3 breaking changes are all handled correctly:

- Configuration lives in the Vite plugin options with the adapter passed inline — exactly the pattern the migration guide mandates now that `svelte.config.js` "is no longer supported" (`app/vite.config.js:1-9`). No `svelte.config.js` exists, which is correct.
- `page` is imported from `$app/state`, whose predecessor `$app/stores` was **removed** in 3.0 (`app/src/routes/+error.svelte:2`).
- `goto` uses the *Kit 3 option names* — `reset: false` (replacing `keepFocus`/`noScroll`) and `replace` (replacing `replaceState`) at `app/src/routes/+page.svelte:33`, `:38`, `:42` and `app/src/routes/pokemon/[name]/+page.svelte:14`. Using these post-training-data names rather than the old ones is strong evidence of current-generation API use.

Svelte 5 usage is likewise fully current: runes everywhere (`$props`, `$state`, `$derived`, `$derived.by` in `app/src/lib/components/MoveTable.svelte:66`), snippets + `{@render children()}` instead of slots (`app/src/routes/+layout.svelte:5,21`), event attributes (`onclick`/`oninput`/`onchange`), the self-import recursion pattern instead of `<svelte:self>` (`app/src/lib/components/EvolutionNode.svelte:2,10`), and `style:`-directive custom properties (`app/src/lib/components/PokemonCard.svelte:18`), which the official best-practices skill explicitly endorses. No `on:`, `export let`, `$:` stores, `<slot>` or `class:` legacy constructs anywhere.

Two misses keep it from perfect: `process.env.API_BASE_URL` (`app/src/lib/server/api.js:6`) bypasses Kit's documented env mechanism (`defineEnvVars` in `src/env.js` + `$app/env/private`, the recommended path since the `$env/*` modules were deprecated in 3.0), and the project uses no `#lib` subpath-import alias (Kit 3's replacement for `$lib`) — relative `../../../` imports instead. The latter is framework-churn-neutral but file-move-fragile.

**Platform.** Good instincts: native `fetch` with a small hand-rolled concurrency limiter (`app/src/lib/server/api.js:18-29`), `new URL` for re-pointing API URLs to the configured origin (`:35`), `URLSearchParams` for building query strings (`app/src/routes/+page.svelte:31`), logical CSS properties (`app/src/app.css:56,57`), `:focus-visible`, `aspect-ratio`, custom properties throughout, native form controls with no polyfills. Minor: `idFromUrl` regex-parses URLs that the platform can parse (`app/src/lib/utils.js:24`), and the search debounce has no abort of in-flight navigations (harmless here since `goto` coalesces, but `AbortController` would be the belt-and-braces choice).

**Dependencies.** Exemplary: zero runtime dependencies and exactly the five devDependencies Kit 3 requires, all at the current majors — kit ^3.1.1, svelte ^5.57.3, vite-plugin-svelte ^7.3.1, vite ^8.3.5 (Vite 8 / rolldown, Kit 3's minimum), adapter-node ^6.0.1 (latest, per npm). Nothing to add, nothing to cut.

**Churn resistance.** All upstream data access is behind one module (`app/src/lib/server/api.js`), all view-model assembly behind one (`app/src/lib/server/data.js`), config in one place, server-only code confined to `lib/server/` and only imported from `+page.server.js` files, and no framework internals or undocumented behaviour. The avoidance of `$lib` means the Kit 3 alias rename already can't bite it. The main gap is the absence of types at the load→page boundary: every `load` returns an untyped object consumed verbatim by templates (e.g. `app/src/routes/pokemon/[name]/+page.server.js:96-111` → `+page.svelte`), with row shapes documented only in comments (`app/src/lib/components/MoveTable.svelte:2-4`), so a rename or Kit-driven data-model change would surface as silent render bugs rather than check errors. The unbounded in-memory cache (`app/src/lib/server/api.js:10,53`) is spec-sanctioned but has no eviction story.
