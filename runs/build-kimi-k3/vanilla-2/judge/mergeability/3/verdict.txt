## Review: Pokédex app (`app/`)

**Architecture.** Server-rendered vanilla JS: a small Node `http` server (`app/server/server.mjs`) renders every page from live API data, and Vite 8 (verified current stable, 8.3.5) is used only to bundle the client behavior + CSS, wired in via Vite's build manifest. Logic is split `src/shared` (router, format, components, home view — used by both sides), `src/server` (api, pages, layout), `src/client` (interactivity, styles). The shared/client/server boundary is explicit and clean, which is the strongest thing about this codebase.

**Idiom.** This is a sensible, framework-appropriate use of Vite for a no-framework app: manifest-based asset injection (`app/vite.config.js:4`, `app/server/server.mjs:16-27`) matches the docs' SSR pattern; routing/data-loading by hand is expected in vanilla. The one non-idiomatic corner is `npm run dev` (`app/package.json:6`) — it bypasses Vite entirely and serves raw ESM, which can't load `import './styles.css'` (`app/src/client/main.js:4`), so the client bundle is dead in dev mode.

**Correctness.** Careful work overall: consistent `escapeHtml` on all interpolated API values (`app/src/shared/format.js:28`, used throughout `pages.js`), promise-caching that dedupes concurrent requests and evicts on failure (`app/src/server/api.js:21-27`), 404s mapped to a proper not-found page and status (`app/src/server/pages.js:455`, `server.mjs` writes `page.status`). But I found several minor risks: the `/src/` static branch's containment guard only checks ROOT, so `/src/../server/server.mjs` is served (guard at `server.mjs:45`, dispatch at `:68`); no fetch timeout in `getJson` (`api.js:21`); `variety.pokemon.url` throws (→500) if a species has no varieties (`pages.js:225`); `loadAssets` silently degrades production to broken dev mode when the manifest is missing (`server.mjs:24-27`); a mid-stream read error after a 200 leaves the response hanging (`server.mjs:59`). None of these hit the tested flow, so 3 rather than lower.

**Abstractions.** `format.js`/`components.js`/`home-view.js` are small, pure, and earn their sharing between SSR and client (identical markup on both sides — good design). `api.js` is the one god-ish data module (cache + summaries + species mapping + `mapLimit`), but it's cohesive and the only place that talks to the API. `pages.js` at ~460 lines is the file that will need splitting first.
