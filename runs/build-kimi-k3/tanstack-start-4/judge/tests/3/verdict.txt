# Review: test quality

## What I found

**The app contains zero tests.** Confirmed from three angles: the measured facts (`testLoc: 0`, `tests.runner: []`), `app/package.json` (no test script, no test runner or assertion library anywhere in deps — only runtime deps plus build tooling), and a direct look — `app/src/` is pure application code (`app/package.json:6-9`, `app/src/lib/*`, `app/src/routes/*`). There's no `npm test` hook in the app at all; the only safety net is the repo-root acceptance suite, which the app doesn't own.

That's a real gap, because `app/` contains exactly the kind of logic that breaks silently:

- **Pure, cheaply testable helpers**: `humanize`, `dexNumber`, `latestEnglishFlavorText` (whitespace-run collapse), `idFromUrl` — `app/src/lib/format.ts:8-48`. All pure functions, zero mocking needed.
- **The riskiest transformation in the app**: `cardsForPokemonRefs` maps Pokémon refs → species cards, excludes alternate forms via the `id > 10000` threshold, dedupes, and dex-sorts — `app/src/lib/data.ts:101-129`. The threshold lives at `app/src/lib/data.ts:23`; the id parsing it depends on is a regex at `app/src/lib/format.ts:46`. A regression here puts Mega Evolutions in every list, and only the acceptance suite would notice.
- **Client-side filtering + pagination**: substring/case rules, either-slot type match, page clamping and slicing — `app/src/routes/index.tsx:69-78`. The clamp at `index.tsx:77` also leaves the URL disagreeing with the view (view `?page=99` shows the last page but the URL keeps 99). URL search validation (`index.tsx:26-40`) handles `NaN`/`0`/fractions — all unpinned.
- **Sortable move tables**: the "missing values sort last in both directions" invariant — `app/src/lib/MovesTable.tsx:34-37` — is a classic two-line test. The mixed-type fallback at `MovesTable.tsx:40-43` silently degrades to string comparison ("9" > "10") if a column ever yields mixed types.
- **Default-game selection** (highest `order`, with a `?? 0` fallback that could misorder unknown groups) — `app/src/lib/data.ts:246-252`.
- **Error paths**: `withNotFound` maps only `ApiError 404` to `notFound()` — `app/src/lib/server.ts:14-23`; there is no `errorComponent` anywhere in the router (grep confirms), so a 500/network failure renders the framework's default error page. Worse, `buildPokemonPageData` does `Promise.all` over per-move fetches — `app/src/lib/data.ts:285` — so one missing nested move record 404s the *entire* Pokémon page. Neither path is exercised by anything the app owns.
- **Caching/live-data invariants**: process-wide promise caches (`app/src/lib/api.ts:16-33`, `app/src/lib/data.ts:24-74`) plus `staleTime: Infinity` (`app/src/routes/index.tsx:45`). The spec's "data can change at any moment" requirement (the overlay fixtures) is guarded *only* by the acceptance suite; an internal refactor could silently break it.

On framework practice: TanStack Start doesn't prescribe a test runner, so the *absence* isn't non-idiomatic — but for a codebase owned for years, unit tests of `format.ts` and the `data.ts` builders (with `apiGet` stubbed) plus a handful of Playwright smoke tests would be inexpensive and catch most of the above. The acceptance tests cover a lot of surface today, but they're not the app's, and they won't be in the PR's future.

## Scoring

- **coverage_of_risk: 1** — nothing in the app covers the data-layer transformations, URL state, pagination, or error paths that carry most of the bug risk.
- **behaviour_not_implementation: 1** — no tests exist, so there are no behavioural assertions at all.
- **regression_power: 1** — breaking `cardsForPokemonRefs`, the sort comparator, or any filter predicate fails nothing the app owns.
- **signal_to_noise: 3** — no tests means no noise; the scale explicitly scores this case 3.

**Overall: 1.** The acceptance suite is doing all the guarding; the moment someone refactors `app/src/lib/data.ts`, nothing catches it.
