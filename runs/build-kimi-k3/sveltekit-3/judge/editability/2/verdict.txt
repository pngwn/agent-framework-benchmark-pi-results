## Review: Pokédex app (`app/`), dimension — editability

The app is small (20 source files, ~660 significant LOC), but it's structured with real discipline. First, a framework-currency check, since the style is unusual enough to warrant it: the app targets **SvelteKit 3** (`@sveltejs/kit ^3.1.1`, config in `vite.config.js` with the `sveltekit()` plugin — app/vite.config.js:8), and every unusual choice is the *current* recommendation, not a legacy habit:

- `#lib` alias via package.json `imports` — the SvelteKit 3 replacement for `$lib` (app/package.json:8, confirmed against the SvelteKit 3 migration notes).
- `defineEnvVars` in `src/env.js` + `$app/env/private` (app/src/env.js:3, app/src/lib/server/api.js:3) — the stable explicit-env-vars feature; `$env/*` is deprecated. The env var is declared `static: false`, correctly read at runtime, not inlined at build.
- Shallow routing via `goto(..., { shallow: true, replace: true })` and `page.shallow?.url ?? page.url` (app/src/routes/+page.svelte:12,45) — the SvelteKit 3 pattern that replaced `pushState`/`replaceState`, with an accurate comment explaining the `page.shallow` subtlety. This is exactly how the docs say to do URL-state-without-reload.
- Svelte 5 runes throughout (`$props`, `$derived`, `$derived.by`, `{#snippet}`/`{@render}`, `onclick`), keyed `{#each}` blocks, no `$:` or `on:` anywhere.

### Scenario walkthroughs

1. **Remove Abilities** — delete `app/src/routes/abilities/` (its load is self-contained, greps show no other importer), then remove the one section that links to it (app/src/routes/pokemon/[name]/+page.svelte:82-89) and the `abilities` field in its load (app/src/routes/pokemon/[name]/+page.server.js:137-140). No nav links, no shared helpers used only by abilities, no dead CSS. Trivial.

2. **Sprite bug (Deoxys)** — sprite URLs are derived in one helper, `spriteUrl` (app/src/lib/server/api.js:35), fed from the Pokémon id, and every list renders through one component (app/src/lib/components/PokemonCardList.svelte:10). So a URL-derivation fix lands once and covers all lists. The caveat: the *card-construction* logic (id → species mapping, `human`, sprite) exists twice — `getSpeciesMeta` (api.js:144) and `speciesCardsFromRefs` (api.js:173) — so a fix at the mapping level (e.g. resolving the default variety like the detail page does at app/src/routes/pokemon/[name]/+page.server.js:22-24) must be made twice or requires first extracting a shared builder. Notable: the app as written is actually correct here (default Pokémon id == species id), but the duplication is the editability risk.

3. **Name sorting on every card list** — all four lists (home, move, ability, type) render through `PokemonCardList`; adding a sort there (or a `sortBy` prop) is one file. Alternatively the three ref-based lists are built in one function (`speciesCardsFromRefs`, api.js:159-175) and home sorts in `+page.svelte:48-54` — two places. Either way easy.

4. **Items section like Moves** — copy the `moves/[name]` pattern: new `items/[name]/+page.server.js` reuses `api`, `error(404)`, `englishName`, `latestEnglishFlavor` (app/src/routes/moves/[name]/+page.server.js:1-10); the `surface`/`dl.facts` CSS classes are global and reusable (app/src/app.css). There's no moves *index* to clone, so `/items` is a small new build; no generic "detail page" abstraction exists, but the repetition is thin and consistent. Moderate.

5. **Data source / caching change** — base URL is declared in `app/src/env.js` and consumed in exactly one module (`lib/server/api.js:3-6`), which also owns the cache (api.js:8-27) and the media-URL prefix (api.js:35). All fetches funnel through `api()`/`listAll` (api.js:28-31). Changing TTLs, headers, or origins touches one file. Excellent.

### Criteria assessment

**removability — 5.** Routes are self-contained directories; the only cross-route coupling for abilities is the (spec-mandated) section on the Pokémon page. CSS is global but organized by concern, so nothing abilities-specific dangles.

**changeability — 4.** Most fixes are one obvious place (`spriteUrl`, `PokemonCardList`, the cache, the load functions), and the home page's URL-driven filter state is genuinely the clean way to change filter behavior. Held back from 5 by the duplicated card builder and by `MovesTable`, which describes each column three times (columns array MovesTable:20-27, `value()` :29-42, hardcoded `<td>` cells :83-95) — adding a column means three synchronized edits in one file.

**coupling — 5.** Server and client are cleanly separated: all PokeAPI knowledge lives in a server-only module (`lib/server/api.js`, and importing it client-side would fail because of `$app/env/private`), loads return plain serializable data, and the three components take narrow props. Shared pure helpers live in `app/src/lib/utils.js` and are imported from both sides without server leakage. The home page's only "global" dependency is SvelteKit's own `page` state, used idiomatically.

**abstraction_design — 4.** `speciesCardsFromRefs` (api.js:159) is a genuinely well-shaped seam — one function turned three spec pages into near-copies of each other (compare moves/[name]/+page.svelte and abilities/[name]/+page.svelte). `PokemonCardList`'s `showTypes` and `MovesTable`'s `showLevel` flags are small and match real variation. Two dings: the card shape is constructed independently in two builders instead of one `toCard` helper, and `TypeBadge` is only half-adopted — the linked-badge variant is inlined as `class="type-badge type-{x}"` anchors in four templates (pokemon hero +page.svelte:33, MovesTable:96, moves/[name]/+page.svelte:24, types/[name]/+page.svelte:31). A markup-level badge change (not a CSS one — that's centralized in app.css) touches five files.

Minor extras: the search debounce timer is never cleared on unmount (app/src/routes/+page.svelte:48-53), and `MovesTable` keys rows by object identity (`{#each sorted as row (row)}`, MovesTable:81), which churns DOM nodes on re-sort.
