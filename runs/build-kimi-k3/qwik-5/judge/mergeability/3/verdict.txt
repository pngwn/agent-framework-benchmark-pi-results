## Review: Pokédex app (Qwik 1.20.3 / Qwik City)

I read the full source tree (`app/src` routes, components, libs, entries, configs), spot-checked the built output, and verified the app's framework usage against the current stable release. Notably, `app/package.json` pins `@builder.io/qwik`/`@builder.io/qwik-city` at **1.20.3** — the release published 2026-10-25, i.e. the actual current stable, not a stale one. The server entry (`src/entry.node-server.tsx`) uses `createQwikCity({router, notFound, staticFile})` from `@builder.io/qwik-city/middleware/node`, which matches the framework's own node-server starter pattern and the current API reference.

**What's good**

- All data loading goes through `routeLoader$` with query/params read from the request event; page state (filters, page, game) lives in the URL exactly as the spec demands, and the only client state is two `useSignal`s (sort state in `moves-table.tsx:59-60`, debounce timer in `index.tsx:68`). No `useStore`, no hand-rolled reactivity.
- Server/client boundary is clean: `lib/api.ts` (with `process.env`, module-level promise caches) is only referenced from inside `routeLoader$` closures, so the optimizer keeps it server-side; `lib/format.ts` is shared pure helpers with doc comments.
- `entry.ssr.tsx:8-13`, `root.tsx`, `adapters/node-server/vite.config.ts` read like the official starter; `head` exports use `resolveValue(useXData)` per current docs (`pokemon/[name]/index.tsx:296-301`).
- 404 handling is thorough: `status(404)` + `null` per resource route, plus a `[...all]` catch-all.
- `lib/api.ts:16-30` caches promises, dedupes in-flight requests, and deliberately evicts 404s/failures from cache ("Don't cache misses or failures forever") — exactly the "caching at runtime is fine" allowance.

**Concerns**

1. **Build artifacts sit in `app/`** — `app/dist/` and `app/server/` (minified `q-*.js`, `entry.node-server.js`) are in the tree, and neither the root nor app `.gitignore` excludes them, while `npm start` (`app/package.json:9`) executes `server/entry.node-server.js`. A stale bundle can silently diverge from source; a `git add .` would commit ~190KB of minified output. This is my main merge objection.
2. **Fetch fan-out with fail-fast** — the Pokémon page loads every move record in one unbounded `Promise.all` (`pokemon/[name]/index.tsx:89`); a single transient API error rejects the whole loader → generic 500 page. No timeout/AbortSignal anywhere in `apiGet` (`lib/api.ts:14-21`). Mitigated by the promise cache, but the first request for a given game is fragile.
3. **Debounce lifecycle** — the 250 ms timer is never cleared on unmount (`index.tsx:92-95`); a pending callback can navigate after the user leaves the home route, and the controlled `value={d.filters.q}` can clobber mid-flight typing when the debounced navigation lands.
4. **Small duplications** — `EXCLUDED_TYPES` exists twice (`api.ts:86`, `types/[name]/index.tsx:22`); the "collect ids → filter alternate forms → sort → map to CardData" block is triplicated (`moves/[name]:30-49`, `abilities/[name]:20-36`, `types/[name]:52-67`); the `typeIndex.byName.get(x)?.label ?? humanize(x)` fallback pattern recurs in four files.
5. **Nothing enforces the types** — `tsconfig.json` sets `strict: true`, but there is no `typecheck`/`tsc --noEmit` script and no unit tests inside `app/`; build goes through vite/esbuild which doesn't type-check. Loaders lean on `any` (~20 sites, e.g. `pokemon/[name]/index.tsx:138-168`).
6. **Consistency nits** — raw `<a>` everywhere except `not-found.tsx:6` which uses `<Link>`; selects are driven by `<option selected>` (`index.tsx:77`) rather than a `value` on `<select>`; `[...all]/index.tsx:4-6` spins up a `routeLoader$` solely to call `status(404)` where an `onRequest` middleware is the idiomatic tool; all styling lives in one 594-line `global.css` rather than Qwik's scoped per-component styles (plain CSS is allowed by the spec, so this is a taste call).

None of these are structural: the layering (routes → components → lib, server data isolated in loaders) is the shape I'd want a teammate to produce, and every route file follows the same small, readable template.
