## Scenario walkthrough

**1. Remove Abilities.** Route block `app/src/app.js:170-186` (one contiguous handler), `abilityPage` in `app/src/views.js:373-396`, the Abilities section inside `pokemonPage` (`app/src/views.js:257-266`), the `hidden` flag in the shared `pokemonCard` (`views.js:62,74-75`) and `.hidden-ability` CSS (`styles.css:305`). The nav (`views.js:31-34`) has no Abilities link, so nothing there. Three files, five small edits, all findable by grepping `abilit` — but the `hidden` flag in the *shared* card component and the CSS rule are easy to leave as dead code.

**2. Sprite fix.** The good news: every list (home, move, ability, type) renders through the single `pokemonCard` component, and the URL rule lives in one helper `spriteUrl` (`app/src/api.js:71`, used at `views.js:65`), so one fix *does* cover every list. The friction: cards are fed by the global index, whose species objects only carry `{name, id, types, generation}` (`api.js:91`) — they know nothing about the default Pokémon. A fix that must consult the Pokémon record (name/sprite) requires extending `buildIndex` (`api.js:82-126`) with ~1000 more fetches or per-card data plumbing. The knowledge is centralized, but the data model doesn't currently support the fix.

**3. Sort card lists by name.** `cardGrid` (`views.js:78-80`) is the choke point for home/move/type lists — one sort there covers three of four. But `abilityPage` bypasses `cardGrid` and hand-rolls `<ul class="cards">` around `pokemonCard` directly (`views.js:387-392`), so the fourth list would silently stay unsorted. Two render paths for the same concept.

**4. Items section shaped like Moves.** Reusable as-is: `layout`, `section`, `apiFetch`, `englishName`/`humanize`, `typeBadgeLink`, and the "detail page" skeleton. Not reusable: `movePage` (`views.js:344-371`) is a hand-rolled page body with no generic resource-page abstraction to hang `/items/:name` on; the list page has no template either (`typesPage` is the closest, still bespoke); and `getIndex` doesn't know about items, so `api.js` needs an extension. Roughly the layout/helpers are reused, the page body is copied.

**5. Change data source.** Everything lives in `app/src/api.js`: `API_BASE`/`API_ROOT` (`api.js:3-4`), the cache (`api.js:7-29`), the media URL patterns (`api.js:71-73`), and the index build strategy (`api.js:78-126`). One file — but four distinct spots inside it, and the promise-cache (`indexPromise ??=`) plus "cache the promise, not the response" pattern would need rework for a TTL/invalidating cache. Views touch media URLs only through `spriteUrl`/`artworkUrl` imports (one inline fallback at `views.js:241`).

## Cross-cutting observations

- The **"latest English flavor text" rule is implemented twice**: `latestEnglishFlavor` in `api.js:46-50` (used for moves at `app.js:207`) and an inline reimplementation in `pokemonPage` (`views.js:227-231`). A rule change is a two-place fix.
- `englishGenus` (`api.js:42-43`) is **dead code** while `pokemonPage` inlines its own identical genus lookup (`views.js:226`).
- The `typeEn` lambda `(n) => index.typeEn.get(n) ?? humanize(n)` is **duplicated five times** (`app.js:112`, `views.js:186`, `views.js:349`, `views.js:379`, `views.js:426`) and thread-ed through components as an option, including the awkward `index.typeEn.get.bind(index.typeEn)` (`views.js:151`).
- "Omit empty/default query params" is known in two places: the server-side `pageUrl` builder (`views.js:138-146`) and the client-side `htmx:configRequest` tweak (`app/public/app.js:2-9`).
- Views reach into the `index` object's internals (`index.types`, `index.generations`, `index.typeEn`) rather than a narrow interface — acceptable at this size, but the shape is an implicit contract shared by three modules.
- `serveStatic` uses cwd-relative paths (`app.js:27-29`); starting the server from another directory breaks assets silently.

Positives worth crediting: clean module roles (data / routes / views), one card component for all four card lists, one API module for all URL/caching knowledge, `homeResults` doubling as full page and htmx fragment (`views.js:133` vs. `app.js:63`), and `movesTable` reused for both initial render and sort interactions (`app.js:159`, `views.js:315`).
