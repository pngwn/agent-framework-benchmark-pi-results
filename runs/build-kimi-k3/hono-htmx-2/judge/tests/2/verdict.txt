## Review: test quality

**The app contains zero tests of its own.** `app/package.json` has no `test` script and an empty `devDependencies` block; `app/src/` contains only `api.js`, `app.js`, `server.js`, `views.js` plus static assets. There is no test runner, no fixture, nothing. Everything that follows is about what the acceptance suite in `tests/` will *not* catch once someone starts refactoring this code.

### What's most at risk

The codebase is actually well-factored for testing — almost all of its risky logic is pure or nearly-pure — which makes the total absence of tests more painful:

- **Sorting** (`app/src/app.js:151-162`): `sortedRows` implements "missing values sort last in both directions" via early returns that bypass the `sign` multiplier. A refactor that "simplifies" this to `sign * cmp` uniformly would silently put null Power/Accuracy at the *top* of descending tables. Nothing would fail.
- **Moves-table assembly** (`app/src/app.js:65-143`): the default-game selection (highest `order`, `app.js:76-78`), the per-move dedup key `${method}:${level}` (`app.js:100`), and the method-ordering comparator with its `99` sentinel (`app.js:114-118`) are all subtle invariants. `Level Up`-by-level-then-name ordering lives at `app.js:135-138`.
- **Index building** (`app/src/api.js:72-126`): the entire data layer — species list, type/generation association, alternate-form exclusion (which works only implicitly, via `byId.get(pid)` missing IDs >1025) — is built once per process. If the API ever ignored `?limit=100000` and the `next` cursor were dropped, the dex would silently truncate to the first page.
- **URL construction** (`app/src/api.js:16`): the template appends a trailing `/` *after* the query string — `?limit=100000/` — which only works because the local API server uses lenient `parseInt` on the limit. This is a latent bug a one-line unit test on `apiFetch` would have caught.
- **Duplicated flavor-text logic**: `app/src/api.js:46-51` exports `latestEnglishFlavor`, but `app/src/views.js:182-183` re-implements it inline on the Pokémon page. Two implementations can diverge; no test pins either.
- **Ability dedup** (`app/src/app.js:228`): the "non-hidden entry wins" rule is encoded as the boolean pun `existing.hidden && entry.is_hidden`. Clever, correct, and completely untested.
- **URL state and pagination** (`app/src/views.js:145-152`, `app/src/app.js:73-76`): page clamping and "omit parameters at default" are spec'd behaviours with no guard.
- **htmx behaviour**: the fragment endpoints (`app/src/app.js:84-85`) and the `htmx:configRequest` empty-param stripping (`app/public/app.js:1-8`) — which is the only reason pushed URLs omit default filters — are only exercised end-to-end by the acceptance suite.

### Scores

- **coverage_of_risk: 1** — no tests exist; the riskiest logic (sorting, index building, moves assembly, URL state) is entirely unguarded.
- **behaviour_not_implementation: 1** — no tests at all.
- **regression_power: 1** — nothing would fail; only the borrowed acceptance suite catches anything.
- **signal_to_noise: 3** — vacuously lean; nothing to maintain, nothing padding.

The one mitigation I'll note: the code is unusually easy to retrofit tests onto — pure helpers in `api.js` and a plain `app.request()`-able Hono instance in `app.js` mean a `node:test` suite could cover `sortedRows`, `humanize`, `latestEnglishFlavor`, `toSpeciesList`, `buildIndex` and the `?limit=` URL building in an afternoon. `hono ^4.13.14` is the current stable release (v5 is still RC), so no framework-version excuse applies.
