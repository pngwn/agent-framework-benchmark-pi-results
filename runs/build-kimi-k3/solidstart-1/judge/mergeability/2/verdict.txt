I've reviewed the app against the current stable SolidStart (v2.1.0, released 2026‑10‑22, per npm/GitHub releases) and Solid Router v1.0 docs, which I fetched to verify idioms rather than relying on training data. Verified idiomatic patterns: `query` + `"use server"` + `createAsync` (docs.solidjs.com/solid-start/v2 data-fetching), `route.preload` exports with `satisfies RouteDefinition`, `FileRoutes`, `props.params` on route components (shown verbatim in the router README), `MetaProvider`/`Title`, `useSearchParams`, `createHandler(..., { mode: "async" })`, and `vite.config.ts` with `solidStart()` + `nitro()` — the documented SolidStart v2 + Nitro v3 setup. The stack (`@solidjs/start` 2.1, router 1.0, vite 8, nitro v3‑rc) is current, not outdated.

Where the app is strong: a clean three-layer split (`routes/` → `lib/queries.ts` server boundary → `lib/api.ts` server-only data assembly with a failure-invalidating cache → `lib/util.ts` pure helpers), careful 404-to-`null` handling, correct missing-values-sort-last table sorting, and defensive `value` + `selected` on selects for SSR.

Where it needs work: there is no `ErrorBoundary` anywhere (only one `try/catch` in the whole `src/`), so any non-404 API failure leaves a blank page/500; the entire data layer is `any` with `strict` tsconfig that nothing actually runs (no `tsc` in any script, `typeLines: 1`); and the moves table's header columns and body cells are maintained independently, a classic drift bug waiting for the next column.
