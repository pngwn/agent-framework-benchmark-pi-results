## Review: test quality

I read the spec, then the whole of `app/`'s source: `src/lib/util.ts`, `src/lib/api.ts` (the entire server data layer), `src/lib/queries.ts`, all six routes, and both components. Confirmed against the measured facts: `app/` contains **zero tests** — no test files (`tests.files: 0`), no test runner in `package.json` scripts (`app/package.json:5-8` only defines `dev`/`build`/`start`), and no devDependencies at all. The app was built solely to satisfy the acceptance suite in `tests/`.

That's a meaningful gap, because this app has an unusually large amount of **pure, testable logic** — filtering, pagination, sorting, name normalization, alternate-form exclusion, URL-state management — exactly the code that breaks silently during refactors:

- `app/src/lib/util.ts:10-29` — `humanize`, `enName`, `latestEnFlavor` (last-English-entry + whitespace-collapse rules are easy to get subtly wrong and easy to test).
- `app/src/lib/api.ts:69-90` — `toSpeciesCards`: alternate-form exclusion (`id >= 10000`), dedupe, and species-name remapping (`speciesNameById.get(id) ?? p.name`). The live-overlay requirement (an extra Pokémon at runtime) means the remapping must stay live; nothing pins it.
- `app/src/routes/index.tsx:47-62` — search/type/generation filtering, `totalPages`/`currentPage` clamping, and the `slice((page-1)*48, page*48)` pagination.
- `app/src/routes/index.tsx:31-38, 63-72` — URL-state contract: filter changes must reset `page` to 1 and omit default params.
- `app/src/routes/pokemon/[name].tsx:169-215, 232-246` — move-table grouping (method order: level-up/machine/egg/tutor then alphabetical), per-version-group dedupe key, level-up sort, and nulls-last bidirectional column sorting with `aria-sort`.
- `app/src/lib/api.ts:19-28` — the 404-vs-other-error split: `NotFoundError` becomes a rendered Not Found, but any non-404 API failure throws with **no ErrorBoundary anywhere**, which would blank the page. That's an untested error path likely to bite in production.

None of this is covered; the only guard is the acceptance suite, which the team will not keep running against refactor-scale changes. The good news is that most of this logic is already factored into pure functions (`util.ts`, `toSpeciesCards`) or trivially extractable memos (`filtered`, `pageItems`, `tables`), so a vitest setup would pay for itself quickly.
