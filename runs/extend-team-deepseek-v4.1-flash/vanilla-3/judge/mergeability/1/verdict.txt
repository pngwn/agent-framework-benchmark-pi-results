## Review summary

This is a clean, well-bounded vanilla TS + Vite app: `api.ts` (data + cache), `dom.ts` (tiny hyperscript helper that avoids `innerHTML` entirely — no injection risk anywhere), `format.ts` (pure helpers), `components.ts` (shared cards/sections), per-route page modules, `team.ts` (localStorage state), and a small Node server that injects `API_BASE_URL` into `index.html` at request time (justifying a custom server over `vite preview`). Routing via `history` + regex routes is the right answer when there's no framework. Navigation is race-guarded with a monotonic `navigation` id and pages render into a detached target (`main.ts:57-90`), and the game-picker uses a token guard (`pokemon.ts:190-199`).

The main problems are cancellation discipline gaps and silent error paths, not structure:

- **Stale debounce corrupts the URL** — `app/src/pages/home.ts:132` schedules `applyFilters(true)` → `history.replaceState` (`home.ts:123`) with no `isCurrent()` check and no teardown; typing then clicking a card within 150 ms rewrites the *new* page's history entry to `/?q=…`.
- **Team page is all-or-nothing** — `app/src/pages/team.ts:70` `Promise.all(names.map(loadMember))` has no per-member catch, so one stale species name in localStorage (spec: "treat the API as a live service whose data can change at any moment") turns the whole page into "Something went wrong".
- **`ready` rejections swallowed** — `app/src/main.ts:87` `await result.ready?.catch(() => {})` leaves the Moves section permanently blank and `aria-busy` with no user feedback.

Minor: `ctx.url` ignored in favour of `new URL(location.href)` (`pokemon.ts:197`), `isOnTeam` dead export (`team.ts:33`), duplicated variety→default-Pokémon resolution (`team.ts:14` vs `pokemon.ts:23-26`), and the `labels.get(x) ?? humanize(x)` idiom repeated in four page modules.
