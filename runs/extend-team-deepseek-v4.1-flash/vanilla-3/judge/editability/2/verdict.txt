## Review

A vanilla-TS + Vite SPA with a hand-rolled router (`app/src/main.ts:22-30`), a small `h()` DOM helper (`app/src/dom.ts:13`), a typed API layer with in-memory promise caching (`app/src/api.ts:114-141`), and shared card/section components (`app/src/components.ts`). Pages are independent modules wired through a narrow `PageContext`/`PageResult` contract, imported type-only so there's no runtime cycle. The later team-builder feature follows the existing seams: a storage module (`app/src/team.ts`), a page (`app/src/pages/team.ts`), one inline block on the Pokémon page (`app/src/pages/pokemon.ts:33-58`), and a delimited CSS section (`app/src/style.css:579-666`).

**Scenario walk-through**

1. **Remove Abilities**: delete `app/src/pages/ability.ts`, the import + route row (`app/src/main.ts:8,29`), the `Abilities` section on the Pokémon page (`app/src/pages/pokemon.ts:95,132-143`), and the route regex in `app/server.mjs:31`. Four files, each one contiguous grep-findable edit; no dead CSS (`.plain-list` at `style.css:134` is shared with the evolution list). A handful of scattered edits — the classic "3".
2. **Sprite fix**: every list of cards (home, move, ability, type, team) renders through `pokemonCardLink` (`app/src/components.ts:21`), and the sprite URL comes solely from `spriteUrl(card.id)` (`app/src/api.ts:11` → `components.ts:26`); species-name normalization happens once in `cardsFromPokemon` (`components.ts:51-60`). One fix covers every list. Caveat: if the fix needed per-variety `front_default` URLs from the API, `CardData` would need a new field supplied by three producers (`components.ts:51`, `pages/home.ts:63-73`, `pages/team.ts:21-27`) — the rendering site still stays single.
3. **Sorting by name**: `cardsFromPokemon`'s sort (`components.ts:60`) covers the move/ability/type lists in one edit; home keeps its own order (`pages/home.ts:63`), and team must *not* be sorted (insertion order, `pages/team.ts:82`). Two or three sites, can't be pushed into `cardList` without breaking the team page — correctly varied, but not one place.
4. **Items section**: new `pages/item.ts` (the move page is only ~27 lines, `pages/move.ts`), plus `main.ts:23`, `server.mjs:31`, an `Item` interface in `api.ts`. Helpers (`getByName`, `section`, `countLine`, `orDash`, `englishName`) carry most of the weight; there is no reusable "resource page" abstraction, but at this page size copying the shape is cheap.
5. **API base/caching**: base URL resolves in one client place (`api.ts:3-11`) with the cache in one Map (`api.ts:114-141`); the server injects it via a meta placeholder (`server.mjs:15`, `index.html:5`). Two files, but the `__API_BASE_URL__` placeholder is an implicit contract spanning three files (`index.html:5` → `server.mjs:16-24` → `api.ts:5`).

**Cross-cutting observations**

- The route table exists twice: client (`main.ts:22-30`) and server (`server.mjs:31`). They can drift; today drift only affects the HTTP status code, but every add/remove-a-page scenario touches both.
- Types-per-Pokémon plus type-label resolution is computed three ways: inverted from `type.pokemon` lists (`pages/home.ts:47-63`), from the Pokémon payload (`pages/pokemon.ts:24-26`), and again in `pages/team.ts:21-33`; `api.typeNames` (`api.ts:175`) is used by some callers while `types.ts:53` and `team.ts:71` rebuild their own label maps.
- URL/history updates bypass `navigate()`: home does its own push/replace (`pages/home.ts:122-125`) and the game picker does its own replaceState (`pages/pokemon.ts:222`). Justified locally (partial re-render, focus preservation), but a change to navigation semantics (scroll, announcements) touches three files.
