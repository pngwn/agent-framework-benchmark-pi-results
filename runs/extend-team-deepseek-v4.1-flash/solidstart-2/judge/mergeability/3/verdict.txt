I've reviewed the full app against SolidStart v2's current docs (data fetching via `query` + `"use server"` + `createAsync` + `preload`, `vite.config.ts` with `solidStart()` + `nitro()` from `nitro/vite`, Vite 8, `createHandler` options). Here's my assessment.

## Idiom

The stack and patterns track the current stable release exactly:

- `app/vite.config.ts:1-7` — `solidStart()` followed by `nitro()` from `nitro/vite`, matching the documented SolidStart v2 setup (Vite 8 + Nitro v3 + Node ≥24 engines in `app/package.json:18-20`).
- `app/src/lib/queries.ts:1-46` — every data loader is a `query` with `"use server"` inside the body; pages read them with `createAsync`. This is verbatim the documented pattern.
- `app/src/routes/index.tsx:10-16`, `app/src/routes/pokemon/[name].tsx:20-22`, `app/src/routes/types/[name].tsx:9-11` — route-level `preload` export, as the docs recommend for preloading.
- `app/src/app.tsx:39-53` — `Router` root + `FileRoutes` + `MetaProvider`/`Suspense`; `app/src/entry-server.tsx:8` — `createHandler(..., { mode: "async" })` with a comment explaining why (fragment links resolve on first load).
- 404 handling is idiomatic: catch-all route `app/src/routes/[...404].tsx:3` rendering `app/src/components/NotFound.tsx:7` with `HttpStatusCode`, plus null-guards per page (`Switch`/`Match` on `pokemon() === null`).

Home-grown bits (`mapLimit` at `app/src/lib/server/pokeapi.ts:51-59`, the TTL cache at lines 27-40, manual `document.cookie` reads in `app/src/lib/team.tsx:13-19`) are all cases where no framework primitive exists, and each is small and commented.

## Correctness

Careful things done right: in-flight de-duplication and rejection cleanup in the cache (`pokeapi.ts:52`), page clamping (`pokeapi.ts:180`), duplicate-key deduping for move rows (`pokeapi.ts:290-292`), case-insensitive name normalization on team add/remove (`team.tsx:36-46`), `onCleanup` for the debounce timer (`routes/index.tsx:39`), and `createUniqueId` for SSR-stable section ids (`components/Section.tsx:4`). The team-button "no flash" requirement is solved properly: the cookie is read server-side in the shell query (`queries.ts:38-41`, `pokeapi.ts:383-386`) and passed as the initial context value (`app.tsx:17-19`).

Risks I found: no `ErrorBoundary` anywhere (grep found none), so a non-404 PokeAPI error (`pokeapi.ts:47-48` throws) leaves you with only the framework's default error page and no app-level recovery; no fetch timeout/abort; and `createAsync` re-suspension on team edits means a blank flash since Suspense fallbacks are `null` (`app.tsx:31`, `app.tsx:46`).

## Abstractions & readability

`app/src/lib/server/pokeapi.ts` is a 437-line module covering every resource, but it's cohesive, sectioned, and hidden behind `lib/queries.ts` — a single, clean client/server seam that routes never cross directly. Team state is split sensibly (`team-store.ts` for the shared cookie codec used by both server parse and client write, `team.tsx` for the reactive client context). The one structural wart is feature-specific code in the global shell: `app.tsx:17-20` gates the *entire* layout (header, main, footer) behind the team-names query, so the global layout both depends on and disappears with a feature query.

Naming, file layout, component size and consistency are excellent; comments explain intent (e.g. `routes/index.tsx:22`, `team.tsx:12-13`, `entry-server.tsx:3-4`).
