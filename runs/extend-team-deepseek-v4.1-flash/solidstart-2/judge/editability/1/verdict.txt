## Review

**Layout.** `app/src` splits cleanly into `routes/` (file-based pages), `components/` (presentational), and `lib/` with a hard server/client seam: `lib/queries.ts` is the only file with `"use server"` and just re-exports typed wrappers over `lib/server/pokeapi.ts`; `lib/types.ts` holds the shared DTOs. Routes consume plain typed objects (`Card`, `MoveRow`, `Named`), never raw API JSON.

**Scenario walkthroughs** (details in the JSON):

1. *Remove Abilities* — delete `routes/abilities/`, then three mechanical lib removals (`queries.ts:40`, `pokeapi.ts:342`, `types.ts:64`) plus the Abilities section on the Pokémon page (`pokemon/[name].tsx:150-160`). No nav link, no ability-specific CSS to orphan, TS catches leftovers.
2. *Sprite fix* — card sprite URLs are derived in `card()` (`pokeapi.ts:116`) for moves/abilities/types/team, but `homeList` re-inlines the same expression at `pokeapi.ts:187`. One module, two expressions; `grep media/sprites` finds both.
3. *Name sorting* — ordering lives in the data layer (`cardsFor` at `pokeapi.ts:131`, `homeList` at `:179`), with team ordering deliberately preserved at `:408-413`; two one-line sorts, but a naive sort inside `PokemonCards` would silently break the team page.
4. *Items section* — you'd copy the ~60-line route skeleton from `moves/[name].tsx`, but `Section`, `PokemonCards`/`CountText`, `NotFound`, `cardsFor`, and the format helpers all reuse untouched; the team feature already proved `PokemonCards` stretches via an optional `onRemove` prop, not a flag.
5. *Data source / caching* — `apiBase()`, `TTL_MS`, and the whole cache live in `pokeapi.ts:21-53`; nothing else in the app knows the API exists. Trivial.

**Weakest spots**: the home-list card construction duplicating `card()`; team/type label+slot mapping duplicated from `pokemonDetail`/`typeLabels`; the `Switch/Match → NotFound` block repeated across four route files; and zero app-owned tests, so refactors lean on the external acceptance suite.
