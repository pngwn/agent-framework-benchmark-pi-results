## Review

I read `SPEC.md` and `FEATURE.md`, all of `app/`'s pages, components, composables, and server routes, and confirmed the app targets the current stable Nuxt (4.6.x, latest 4.6.3; the app pins `^4.6.2` — `app/package.json:8`).

**What's good.** This is a recognisably well-run Nuxt 4 app: the new `app/` + root `server/` layout, server API routes with `defineEventHandler`/`getRouterParam`, `useFetch` with explicit keys, `useHead`-backed titles, a catch-all page that `throw createError({statusCode: 404})` (`app/app/pages/[...slug].vue:2`), and a proper `error.vue`. The team feature is the textbook SSR-correct way to do browser-owned state: cookie-backed `useState` so the add/remove button renders with the right label on the server (`app/app/composables/team.ts:23-46`), and `/api/team` revalidates against the API at request time (`app/server/api/team.get.ts`). The pokeapi client's 404-to-`NotFound` mapping feeding `withNotFound` gives every route consistent 404 behavior. Components are small, composition-based (`PageSection`, `TypeBadge`, `PokemonCard`, `EvolutionNode` recursion) and naming is consistent throughout.

**What I'd push back on.** Three things, all fixable in comments:

1. **Helper duplication across the client/server boundary.** `humanize` exists twice, nearly character-for-character: `app/app/composables/format.ts:1` and `app/server/utils/pokeapi.ts:39`. Nuxt 4 added the `shared/` folder (auto-imported on both sides) exactly for this; today the two copies can drift, and `dexNumber`/`orDash`/`spriteUrl` have the same half-server/half-client split. This is the only structural change I'd ask for.
2. **Hand-rolled TTL cache where Nitro's caching exists.** `app/server/utils/pokeapi.ts:4-5` implements a promise-dedup/TTL cache by hand; Nitro's `cachedFunction` (auto-imported in server routes) covers in-flight dedup and TTL expiry, and would also evict expired entries — the current Map only deletes an entry on a failed fetch, so keys that expire and are never revisited linger (`pokeapi.ts:14-30`). Practically bounded by the API's size, but it's a wheel the framework already ships.
3. **Loose typing in the server layer.** The client pages all declare careful `interface`s for their payloads, but the server routes lean on `any` throughout (`app/server/api/pokemon/[name].get.ts:39,76,82,88`, `app/server/api/species.get.ts`) — the shape contracts live only on the consuming side, so a payload change fails silently at the boundary rather than in the producer. Minor, but a team would want response types next to the handlers.

Minor nits I'd mention without blocking: `usePageData`'s `key` is evaluated once at setup so it goes stale when the route param changes on an in-place navigation (`app/app/composables/format.ts:18`, used at `app/app/pages/pokemon/[name].vue:24`); the synthetic pre-hydration `onSearch({target: ...} as unknown as Event)` hack (`app/app/pages/index.vue:83`); the `<n> of 6` count comes from the cookie while the cards come from server-filtered members, so a stale team entry shows a mismatch (`app/app/pages/team.vue:22` vs `app/server/api/team.get.ts:26`); selects set both `:value` and per-option `:selected` (redundant); and per-request `Promise.all` fan-out of up to ~180 move fetches has no concurrency limit (`app/server/api/pokemon/[name].get.ts:39`) — fine here, but worth a comment.

No correctness problems of consequence: listeners are cleaned up, debouncing is correct and cancelled on unmount, filters paginate/reset correctly, 404s are handled everywhere, all output is Vue-escaped, and SSR/CSR agree on the team state via the cookie.
