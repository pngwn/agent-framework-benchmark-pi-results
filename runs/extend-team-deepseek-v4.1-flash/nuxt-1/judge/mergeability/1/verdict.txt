# Review: Nuxt Pokédex (SPEC.md + team-builder feature)

**What this is:** a Nuxt 4.6 full-stack app — pages in `app/app/pages`, Nitro server routes under `app/server/api` acting as a data layer over the local PokeAPI, a shared `server/utils/pokeapi.ts` client with a 60s in-memory cache, and browser team state in a cookie. The feature (team builder) was added via a new composable, a new server route and one new page, and it follows the existing conventions exactly.

**Framework fit (verified against current Nuxt 4.6.x):** `nuxt.config.ts:1` sets `compatibilityDate: '2026-10-01'` on Nuxt `^4.6.2` (current stable line). The structure (srcDir `app/`, auto-imported components/composables/server utils), reactive-getter `useFetch` (`app/app/composables/format.ts:22`), `useAsyncData` with `watch` (`app/app/pages/team.vue:16-19`), `useCookie` for SSR-consistent client state (`app/app/composables/team.ts:8`), `useHead` via `usePageTitle`, and the `NUXT_PUBLIC_API_BASE` runtime-config override in the `start` script (`app/package.json:8`) are all exactly what the docs recommend. Using a cookie rather than `localStorage` for the team is the right call — it makes the "no flash of the wrong button label" requirement fall out of SSR for free.

**What I'd push back on before approving:** the biggest one is `usePageData` throwing only at setup (`app/app/composables/format.ts:23-26`), so a client-side navigation that reuses the same route record (e.g. `/pokemon/a` → `/pokemon/b`) refetches but a 404 in that refetch never surfaces as the error page — the initial setup-time throw has already happened. In practice every in-app link carries a valid name, so it's latent, but it's a trap for anyone who later adds cross-links between arbitrary names. Second, the API cache (`app/server/utils/pokeapi.ts:5`) never evicts expired entries, so long-lived processes retain every distinct URL's parsed JSON (species records are large); a delete-on-expiry or bounded LRU would be safer. Third, the Pokémon endpoint fans out one fetch per move of the Pokémon (`app/server/api/pokemon/[name].get.ts:39`) — ~100–200 parallel requests per uncached view, more than the one selected game actually needs.

Smaller nits: `humanize` is duplicated verbatim between client (`app/app/composables/format.ts:1`) and server (`app/server/utils/pokeapi.ts:39`) where Nuxt 4's `shared/` directory is designed for this; sprite-URL construction is likewise duplicated (`app/server/utils/pokeapi.ts:54` vs `app/app/pages/index.vue:48`); `composables/format.ts` mixes formatting helpers with data-fetching and head-title composables; the server layer is effectively untyped (`any` throughout) while each page hand-writes an interface describing the server's payload; and `index.vue`'s onMounted DOM-read hydration workaround (`app/app/pages/index.vue:82-86`) is clever but surprising.

None of these block merge. Naming is consistent, components are small and single-purpose, comments explain *why* (cache TTL, cookie rationale, the hydration hack), and the feature diff reuses `PokemonCard`, `PageSection` and the existing data module rather than growing a parallel one.
