I've read the full app (all pages, components, composables, server handlers, utils, config) and cross-checked Nuxt 4 conventions. Findings and scores below.

**How the code is organized.** It's a clean Nuxt 4 BFF layout: pages never talk to PokeAPI directly; every page fetches its own `/api/*` endpoint (`app/composables/format.ts:23` `usePageData`), and all PokeAPI access funnels through `server/utils/pokeapi.ts` (`api`, `cardsFor`, `englishName`, `spriteUrl`, cache). Components are small and prop-driven (`CardList`, `PokemonCard`, `MovesTable`, `PageSection`, `TypeBadge`, `EvolutionNode`), which gives the app real seams.

**Scenario walkthroughs (locations):**

1. **Remove Abilities**: delete `app/pages/abilities/[name].vue` + `server/api/abilities/[name].get.ts`; then strip the required-by-spec Abilities section from `app/pages/pokemon/[name].vue:144-154`, the `abilities` field in its `PokemonData` interface (`[name].vue:28`), and the `abilities` mapping in `server/api/pokemon/[name].get.ts:85-89`. No nav links, no dead code left. Five edit sites, all greppable via "abilit".
2. **Sprite bug (Deoxys)**: the sprite URL for every server-built card comes from one place, `cardsFor` → `spriteUrl` (`server/utils/pokeapi.ts:54`, used by moves/abilities/types/team endpoints) — one fix covers those. But the home page builds its own sprite URLs client-side, bypassing that seam: `app/pages/index.vue:48` inlines `${mediaBase}/media/sprites/pokemon/${s.id}.png`. Two fixes, one of which re-implements the URL scheme.
3. **Sort card lists by name**: `CardList.vue` is the single seam used by home, move, ability and type pages (`index.vue:111`, `moves/[name].vue:33`, `abilities/[name].vue:19`, `types/[name].vue:26`). Adding a sort there covers four lists at once; `team.vue:24-33` deliberately renders its own grid (add-order + remove button), which is correctly excluded.
4. **Items section**: copy the shape of `app/pages/moves/[name].vue` + `server/api/moves/[name].get.ts` (~80 lines total), reuse `withNotFound`, `api`, `englishName`, `latestFlavorText`, `cardsFor`, `usePageData`, `usePageTitle`, `PageSection`, `orDash`, `TypeBadge`. The plumbing is all shared; only the thin per-resource page/endpoint is duplicated — that's the intended variation point.
5. **Data source change**: base URL lives in `nuxt.config.ts:17` runtimeConfig and is consumed in exactly two places — `server/utils/pokeapi.ts:8` and `app/pages/index.vue:18` (the leak from finding above). Cache rules (TTL, promise dedupe) are entirely in `pokeapi.ts:4-28`.

**Duplication worth noting:** `humanize` is implemented twice, identically — `server/utils/pokeapi.ts:39` and `app/composables/format.ts:1`. Nuxt 4's `shared/` directory exists exactly for this; if one copy drifts (e.g. a hyphenation rule change), search/filter behavior on the home page diverges from all labels. Also the effect-extraction expression is copy-pasted between `moves/[name].get.ts:10-12` and `abilities/[name].get.ts:5-7`, and the `labels[t] ?? humanize(t)` fallback appears in three handlers plus two pages. The `Card` shape is redeclared four times (`pokeapi.ts:72-77`, `CardList.vue:2-4`, `PokemonCard.vue:2-7`, page interfaces) with no shared type.

These are real but modest: each is a grep away, and the architecture itself (server/client split, `withNotFound` wrapper, `usePageData`, component seams) is the kind you want to inherit.
