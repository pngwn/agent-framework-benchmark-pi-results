# Review: Pokédex app (Astro 7, team-builder feature)

## What I checked

- The app runs **Astro 7.4.2** (`app/package-lock.json:1637`), which is the current stable major (7.0 released June 2026, 7.3.x current as of late Sept 2026). Config (`output: 'server'` + `@astrojs/node` standalone, `app/astro.config.mjs:1-8`) and the `.astro/types.d.ts` tsconfig convention (`app/tsconfig.json`) match Astro 7's recommended SSR setup; `Astro.response.status`, `Astro.cookies`, and `<Astro.self>` recursion are all current, documented APIs.
- `CHANGES.diff` shows the feature diff: the team builder is a clean addition (new `lib/team.ts`, `TeamButton.astro`, `team.astro`, a `removable` prop on `CardList`, a nav link in `Base`) that doesn't disturb the existing structure.
- I read every source file in `app/src` and checked Astro 7 docs/release notes on view transitions and config.

## Assessment

The strongest part of this code is the data layer: `lib/api.ts` is a small, well-commented stale-while-revalidate cache with a concurrency limiter, 404-as-`null` semantics, and clean helper extraction (`apiPath`, `idFromUrl`); pages consume it uniformly and render `NotFound` with a real 404 status for missing resources. The client-side interaction scripts are unusually careful — abort controllers against out-of-order responses, focus restoration after a partial DOM swap, page clamping, `aria-sort` management with stable secondary sorting.

The main weaknesses are cross-file rather than local. The team cookie's wire format and parse logic are implemented three times — once on the server (`lib/team.ts:parseTeam`, which lowercases/trims/dedupes) and twice inline in component `<script>` blocks (`TeamButton.astro`, `team.astro`) whose copies already drift from the server version (no lowercase/trim, a hardcoded `'team='` in one and `TEAM_COOKIE` in the other). Changing the format later means finding three inline scripts. Second, each interactive page hand-rolls the same fetch→DOMParser→replaceWith micro-router; Astro's `ClientRouter` exists for exactly this, though the spec's "no animations or transitions" rule and the need for precise partial swaps (keeping focus in the search input) make the hand-rolled choice defensible rather than wrong. Third, API failure handling is entirely absent — a non-OK upstream response rejects through `Promise.all` in every page frontmatter and becomes a 500 — and the cache `Map` has no eviction policy (practically bounded by the ~3k-resource dataset). Finally, despite a strict tsconfig, API payloads are typed as `any` throughout, so the "domain types" live only in the reader's head.

None of this is structural: naming is consistent, files are small and single-purpose, comments explain *why* (SWR rationale, dedupe keys, concurrency limits), and a new teammate would find their way in minutes. I'd approve after one round of small changes.
