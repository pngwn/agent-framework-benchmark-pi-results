# Editability review — Pokédex app (Next.js 16)

## Scenario walkthroughs

**1. Remove the Abilities pages.** Delete `app/src/app/abilities/` and remove the Abilities section from `app/src/app/pokemon/[name]/page.tsx:120-128`. No nav link exists for abilities (nav is Pokémon/Types/Team, `app/src/app/layout.tsx:20-27`), so no other mandatory edits. Optional dead code left behind: `getAbility`/`ApiAbility` (`app/src/lib/api.ts:163`), `CardData.hiddenAbility` (`app/src/lib/api.ts:219`), and `.plain-list`/`.card-note` CSS (`app/src/app/globals.css:124,227`). Essentially delete-a-route plus one section.

**2. Sprite bug (species vs default-Pokémon).** Every card list renders through `PokemonCard` (`app/src/components/pokemon-cards.tsx`), which computes the sprite in exactly one place (`pokemon-cards.tsx:10`, `spriteUrl(card.id)`), so a markup-level fix covers home, moves, abilities, types and team at once. But the data-side semantics of `CardData.id` are constructed three ways: `pokemonCards` uses the *Pokémon* id from the ref URL (`app/src/lib/api.ts:240-250`), `getSpeciesIndex` and `loadTeam` use the *species* id (`api.ts:232-236`, `app/src/app/team/page.tsx:45-48`). A real fix (show the species' default Pokémon) would go in `pokemonCards` and require re-verifying the other two constructors, plus the default-variety resolution duplicated in `loadSpecies` (`app/src/app/pokemon/[name]/page.tsx:43-45`) and `loadTeam` (`app/src/app/team/page.tsx:40-42`).

**3. Sort every card list by name.** All four secondary lists go through `PokemonCardList` (`app/src/app/moves/[name]/page.tsx:39`, `app/src/app/abilities/[name]/page.tsx:31`, `app/src/app/types/[name]/page.tsx:51`, `app/src/app/page.tsx:73`); the team page renders `PokemonCard` directly (`app/src/app/team/page.tsx:96-101`). A default sort or a `sortBy` prop in `pokemon-cards.tsx` plus one sort in the team page covers everything; `CardData.name` is always present.

**4. Add an Items section shaped like Moves.** There's no shared "resource detail page" skeleton: the `cache`-load + `generateMetadata` + `notFound` boilerplate is repeated per route (`app/src/app/moves/[name]/page.tsx:14-25`, same in pokemon/abilities/types pages). You'd copy ~20 lines of boilerplate plus resource-specific markup into `items/[name]/page.tsx`, but genuinely reuse `Section`, `PokemonCardList`, `format.ts` helpers, and the `fetchApi`/typed-resource pattern in `api.ts` (just add `ApiItem`/`getItem`).

**5. Change API base URL / caching rules.** All knowledge is in `app/src/lib/api.ts`: `apiBaseUrl` (line 7), URL building (line 37-42), fetch + cache TTL/size/concurrency (`api.ts:15-17,44-95`), and media URLs (`api.ts:274,280`). One file. The `connection()` calls in six pages are about render strategy, not the data source, and are idiomatic for Next 16 request-time rendering.

## Assessment

This is a well-factored small app. Data access, formatting, and API shape knowledge are each concentrated in one module; every card list funnels through one component; server/client boundaries are explicit (`server-only` in `api.ts`/`team-server.ts`, cookie utilities in `team.ts` shared by both sides). The main editability risks are three duplicated micro-logics: URL query serialization (page + filters), default-variety resolution (two pages), and the "follow server value" controlled-state pattern (filters, game-select, team-toggle). Nothing is entangled; nothing requires flag-parameter gymnastics.
