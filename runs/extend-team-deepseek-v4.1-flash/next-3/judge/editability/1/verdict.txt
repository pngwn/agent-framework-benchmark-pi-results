I've read the full app (all 5 routes, 5 components, 4 lib modules, config). It's a compact App Router codebase on Next 16.4.3 / React 19.3: one `lib/api.ts` seam for all data, small typed components per concern, per-resource route directories. Here's my editability assessment, worked through the five scenarios.

**Scenario walk-through**

1. **Remove Abilities**: delete `app/src/app/abilities/` and the one inbound link block (`app/src/app/pokemon/[name]/page.tsx:121`), plus ~4 dead lines in `lib/api.ts` (`getAbility:172`, `ApiAbility` type). No nav link exists, no CSS block, no state. Near the ideal "delete a directory" shape.
2. **Sprite fix**: every card on every list (home, type, move, ability, team) renders through `PokemonCard`, which derives the sprite from `spriteUrl(card.id)` (`app/src/components/pokemon-cards.tsx:11`, `app/src/lib/api.ts:274`). A species↔default-Pokémon mapping fix lands once. Caveat: `CardData.id` is assembled in three places (`lib/api.ts:225`, `lib/api.ts:258`, `app/src/app/team/page.tsx:66`) and triple-duties as sprite path, dex number and React key, so a fix that changes *which* id means what must respect all three — but today they agree, and the render choke point is single.
3. **Sort by name**: one-line sort in `PokemonCardList` (`pokemon-cards.tsx:24`) covers home/type/move/ability lists; the team list deliberately bypasses it (insertion order per FEATURE.md) with hand-rolled markup, so a reviewer must notice that second list.
4. **Items section**: copy `app/src/app/moves/[name]/page.tsx` (~76 lines) as the template; reuse the fetch/cache machinery, `Section`, `pokemonCards`, format helpers. The per-page boilerplate (`cache(loadX)` + `generateMetadata` + `connection()` + `notFound`, ~10 lines × 4 pages) is copy-paste, but that's idiomatic App Router; the shared parts are genuinely shared.
5. **Data source change**: one file. `apiBaseUrl()` (`api.ts:5`), URL building (`api.ts:37`), fetch options (`api.ts:46`), cache constants (`api.ts:16-18`), and media/sprite URL rewriting (`api.ts:274`, `api.ts:279`) all live in `lib/api.ts`. No page fetches directly.

**Notable frictions (mostly introduced by the team feature):** the team page re-implements the card-list markup instead of extending `PokemonCardList`; the URL-query builder for filters exists twice (`page.tsx:22` `pageHref` vs `filters.tsx:10` `href`); the cookie read-modify-write + `router.refresh()` pattern is duplicated in `team-toggle.tsx:33` and `team-remove-button.tsx:11`. Also worth a forward-looking note: the app uses the classic dynamic model (`connection()` per page + `no-store` + a hand-rolled in-memory cache), which is fully supported, but Next 16.4 now recommends Cache Components (`use cache` + `cacheLife`) for every app — a future migration would touch `lib/api.ts` and delete `await connection()` lines, all mechanical.
