## Review

The app is a small, hand-rolled SPA: a regex route table in `main.ts`, one `h()` DOM helper, one API/cache module (`api.ts`), shared presentational helpers (`components.ts`, `format.ts`), one file per page, and a Node static server that injects the API base URL. It's an unusually disciplined vanilla setup — most logic that could have been duplicated (cards, species mapping, name formatting, caching, base-URL resolution) lives in exactly one module.

**What I verified for each scenario:**

1. **Remove Abilities** — delete `app/src/pages/ability.ts`; drop the import and route at `app/src/main.ts:8` and `:29`; remove `abilitiesSection` and its call at `app/src/pages/pokemon.ts:67,104-115`; drop the regex in `app/server.mjs:31`; optionally the `Ability` interface at `app/src/api.ts:57-63`. The `hidden` flag on `CardData` (`app/src/components.ts:31,58`) and the "Hidden ability" note would become dead code, and `.plain-list` CSS is shared with Evolution so it stays. Four files, all mechanical and grep-able — a handful of scattered edits, but zero entanglement.

2. **Sprite bug (Deoxys)** — the sprite is derived in exactly one place: `app/src/components.ts:28` calling `spriteUrl` (`app/src/api.ts:11`). Every card list (home, move, ability, type, team) renders through `pokemonCard`, so one fix covers all of them. The caveat: `spriteUrl` constructs the URL from an ID rather than reading `pokemon.sprites.front_default`, so it leans on the spec's "front sprites follow `<pokemon id>.png`" invariant; a data-driven fix would need `CardData` to carry a sprite, and the "species → default Pokémon" resolution is duplicated between `app/src/pages/pokemon.ts:26-29` and `app/src/pages/team.ts:22-27` (home sidesteps it entirely by deriving types from the type endpoints at `app/src/pages/home.ts:57-67`).

3. **Sort all card lists by name** — `CardData` already carries `name` (`app/src/components.ts:9`), so it's a comparator change in `cardsFromPokemon` (`app/src/components.ts:68`) plus the entry ordering in `api.ts:104`/`home.ts`. Two places, no structural change; team keeps insertion order (a product decision, not a code obstacle).

4. **Items section like Moves** — most of what matters is already shared: `section`, `cardList`, `cardsFromPokemon`, `countLine`, `typeBadge`, `getByName`, the `facts` dl pattern, `format.ts` helpers. You'd write a thin `pages/item.ts` (move.ts is only 25 lines), add an interface to `api.ts`, a route in `main.ts`, and — annoyingly — a regex in `server.mjs:31`.

5. **API base URL / caching** — fully centralized: `resolveApiBase`/`API_BASE`/`spriteUrl` and the in-memory cache all live in `app/src/api.ts:3-11,88-105`, with the server injecting the value in one place (`app/server.mjs:19-21`). One module knows anything about it.

**Main deductions:** route patterns are duplicated between the client router (`app/src/main.ts:20-28`) and the server's 404 list (`app/server.mjs:31`), which is optional per SPEC (404 status "isn't tested") yet doubles the cost of every route change; the species→default-Pokémon resolution exists in two files; and URL/history mutation is spread across three files (`main.ts:99`, `home.ts:127-131`, `pokemon.ts:172`) instead of going through one helper — pragmatic for partial re-renders, but a third navigation idiom to learn.
