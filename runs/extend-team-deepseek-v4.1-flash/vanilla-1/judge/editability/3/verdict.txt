## Review

This is a small, tidy vanilla-TS/Vite SPA: a single router (`app/src/main.ts`), one file per page under `app/src/pages/`, and three genuinely shared modules — `api.ts` (fetch + cache), `format.ts` (pure name/number helpers), `components.ts` (card/section primitives). `server.mjs` is a clean, framework-free static server. The team feature (FEATURE.md) landed in its own module (`app/src/team.ts`) and one page file, which is exactly how a later addition should fit.

**Scenario walkthroughs** (what I actually traced):

1. **Remove Abilities**: delete `app/src/pages/ability.ts`, drop the import + route row in `app/src/main.ts:8,29`, remove the Abilities section's links in `app/src/pages/pokemon.ts:104-113`, and remove one regex from `server.mjs:31`. Four files, but each edit is a single obvious line; there's no ability-specific CSS or state. The wrinkle is that route knowledge lives in *both* `main.ts` and `server.mjs` — though forgetting the server edit only changes the HTTP status, not behavior (client falls back to Not found, `main.ts:49`).

2. **Sprite bug**: this code largely *avoids* the bug class. `spriteUrl` is a single function (`api.ts:11`) keyed on the numeric ID, and `pokemonCard` (`components.ts:21-33`) is the only card renderer; every list — home (`home.ts:100`), move (`move.ts:20`), ability (`ability.ts:9`), type (`types.ts:18`), team (`team.ts:88`) — flows through it. The pokemon→species mapping for ref-based lists (Deoxys → `deoxys-normal`, ID 386) is centralized in `cardsFromPokemon` (`components.ts:51-60`), so one fix there covers the move/ability/type lists, and species-based lists (home, team) share the same `spriteUrl`. If the fix needed the default variety's data, note that `varieties.find(is_default)` is duplicated verbatim in `pokemon.ts:20` and `pages/team.ts:22` and absent from `cardsFromPokemon`.

3. **Sort cards by name**: `cardList` (`components.ts:37`) is the choke point, but each caller owns its own order today: `cardsFromPokemon` sorts by dex (`components.ts:60`), home's order comes from `allSpecies` (`api.ts:113`) via its `entries` array (`home.ts:71`), and team's order is the feature itself (`pages/team.ts:55`, deliberately add-order). A single sort inside `cardList` would silently break the team page's ordering contract. Realistically 2–3 files (`components.ts`, `home.ts`, plus a team opt-out) — findable but not one line.

4. **Add Items like Moves**: `pages/item.ts` would mirror `move.ts` (~35 lines), plus two route rows in `main.ts:20-29` and two regexes in `server.mjs:31`. High reuse: `getByName`, `section`, `orDash`, `englishName/shortEffect`, `countLine`, `cardsFromPokemon`, `cardList` all apply unchanged. Only the tiny `fact()` dl-row helper (`move.ts:12`) gets copied — a smell, not a blocker.

5. **Change API base/caching**: base URL flows env → `server.mjs:13,28` → `index.html:6` meta → `resolveApiBase` (`api.ts:3-9`) → `API_BASE` (`api.ts:9`); each file has exactly one role, and every client consumer goes through `API_BASE`. The cache is a single `Map` with one policy in one function (`api.ts:114-136`). Changing caching rules is a one-file edit; changing the base mechanism is three files but each is the obvious place.

**Checks against current practice**: Vite 8 + TS 7 (devDeps), `import.meta.env`, `type: "module"`, no deprecated Vite APIs; the click-interception router and `history.scrollRestoration = 'manual'` (`main.ts:93`) are current, idiomatic vanilla SPA practice. Nothing here contradicts the framework's current stable release.
