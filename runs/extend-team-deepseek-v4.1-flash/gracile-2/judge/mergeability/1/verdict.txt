## Review

I read `SPEC.md`, `FEATURE.md`, all 23 source files under `app/`, and verified the Gracile APIs in use against the current stable release (`@gracile/gracile` 0.11.0, npm, and the `main` docs at gracile.js.org). Notable verifications: `handler` as a bare function with `handler` declared before `document`/`template` is the documented pattern (docs + `packages/server/src/route.ts` type doc); the Express `server.js` mirrors the official `minimal-server-express` starter; vanilla custom-element islands without hydration are an explicitly supported "progressive interactivity" layer; and the `gracile-static` stub hostname the app detects is real — `packages/engine/src/routes/render.ts` renders every route at build time with `new URL(pattern, 'http://gracile-static')` and invokes the handler — though this is internal, undocumented behavior.

The app is a clean Gracile MPA: server-only Lit-SSR templates, one handler per route returning typed props, tiny vanilla custom elements for the three interactive bits, and a server-side fetch client with TTL cache, request de-duplication, and a concurrency limiter. The team feature is a well-contained additive change (4 new client files, a small `lib/team.ts` shared across the cookie boundary, a new route) that follows the existing conventions exactly.

Issues found are minor: the API cache never evicts expired entries; `fetchFragment` hides a module-global `AbortController` shared by all islands; the build-render detection leans on an internal hostname; island listeners have no teardown; and a few small consistency nits (triplicated name-validation regex, two different props shapes across routes). Nothing I'd block a merge over.
