# Review: `app/` (SvelteKit 3, Pokédex + Team builder feature)

## Verification of current-framework claims

I checked the app's patterns against the current stable release (SvelteKit 3, released 2026-10-01) and the official Svelte skills before judging:

- **Config in `vite.config.ts` plugin options, no `svelte.config.js`** — `app/vite.config.ts:6-16` matches the Kit 3 migration guide exactly (`adapter` and `compilerOptions` as top-level plugin options). ✅
- **`#lib` subpath imports** — declared in `app/package.json:13`, used with explicit `.ts` extensions everywhere. ✅
- **`$app/state` `page` instead of stores** — no `$app/stores`, no `$:`/`export let`/`on:` anywhere (grep clean). ✅
- **Kit 3 `goto` option names** — `goto(target, { replace, reset: false })` (`app/src/routes/+page.svelte:35`) uses the new `replace`/`reset` names, not `replaceState`/`noScroll`. ✅
- **`page.url` readonly** — copied via `new URL(page.url.href)` before mutation (`app/src/routes/pokemon/[name]/+page.svelte:35`), exactly as the migration doc prescribes. ✅
- **`tsconfig.json` extends `$app/tsconfig`** — `app/tsconfig.json:2`. ✅
- Two genuine deviations found: `process.env.API_BASE_URL` instead of Kit 3's `src/env.ts` + `$app/env/private` (`app/src/lib/server/api.ts:5`), and team state duplicated into page-local `$state` copies kept in step by `$effect` blocks that *write state* (`app/src/routes/team/+page.svelte:13`, `app/src/routes/pokemon/[name]/+page.svelte:24`) — the official Svelte skill explicitly says to avoid updating state inside effects and recommends a `$state` class module for shared cross-component state.

## Detailed assessment

**Data layer** (`app/src/lib/server/api.ts`, `pokedex.ts`) is the strongest part: a bounded in-memory cache (TTL 5 min, `MAX_ENTRIES` cap, promise de-dup, eviction of failed requests — `api.ts:50-64`), `mapLimit` for concurrency, 404→`null` semantics, `encodeURIComponent` on every user-supplied path segment, and server-side clamping of `?page=` (`pokedex.ts:182`). Server code is correctly confined to `lib/server/` and never imported client-side; shared view-model types live in `lib/types.ts`.

**The feature diff** (`CHANGES.diff`) fits the existing code well: `getTeamPage` follows the established per-page loader convention with its own section banner, the cookie helpers live in a small isomorphic module, and only the layout nav, one load, one component and two new files were touched. The main structural smell is that team *state* is now copy-pasted as "local `$state` + `$effect` resync" in two pages — a third team-aware page would copy it again.

**Minor fragility I found that tests wouldn't catch:** the 200 ms search debounce timer is never cleared on unmount (`+page.svelte:40`), so clicking a card within that window lets a late `goto` yank the user back to the filtered list; `getTeamPage` silently drops cookie entries the API no longer has (`pokedex.ts:370`), so "<n> of 6" can disagree with the stored team; and `selectGame` appends `#moves` to the URL with `reset: false`, so the hash never scrolls but a reload jumps. None are serious.
