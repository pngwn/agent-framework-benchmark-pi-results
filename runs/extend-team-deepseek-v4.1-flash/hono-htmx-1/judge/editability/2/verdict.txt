# Review: Pokédex app (Hono + htmx) — Editability

## What's here

Ten source files: a slim API client with SWR caching (`src/api.ts`), data-shaping helpers (`src/data.ts`), a shared component kit (`src/views/components.tsx`), one layout (`src/views/layout.tsx`), per-feature view modules (`home`, `pokemon`, `details`, `team`), and a flat route table (`src/index.tsx`). The team-builder feature (per `CHANGES.diff`) landed as one new file plus small, targeted diffs — a good sign the seams were already in the right places. The stack is current: hono 4.13.14 is the stable line (v5 is still RC), `jsxRenderer` + `ContextRenderer` declaration, `hono/cookie`, and `@hono/node-server/serve-static` are all the idiomatic v4 patterns shown in the framework's own skill docs.

## Scenario walk-through

1. **Remove Abilities** — routes+loader: `index.tsx:6,78-82`, `details.tsx:53-76`; the one non-obvious touch is the Abilities *section* on the Pokémon page (`pokemon.tsx:286-294`) which links to `/abilities/...`. Three files, no dead code left behind (CSS `.bullets` is shared with Evolution). Easy but not single-file.
2. **Sprite bug (Deoxys)** — `spriteUrl` is defined once (`data.ts:28`) and consumed only by the single `CardList` renderer (`components.tsx:25`). Every list of cards (home, move, ability, type, team) flows through that one component, so one fix covers all of them. The id-based URL is also already correct per the spec's "species id = default Pokémon id" rule, so there is no name→URL mapping to get wrong.
3. **Sort every card list by name** — `CardList` (`components.tsx:20`) is the single render point, but a blanket sort there would silently reorder the team page, whose order is semantic ("order added"). You'd sort at the assembly sites: `cardsForPokemon` (`data.ts:91`), `loadHome` (`home.tsx:38-41`), and consciously *not* `loadTeam` (`team.tsx:55-62`). A few files, with one trap.
4. **Items section shaped like Moves** — the reusable substrate is genuinely reusable: `Section`, `CardList`, `Count`, `orDash`, `TypeBadge`, `apiList`/`englishName`/`humanize` (`data.ts`), and the load-render-route pattern in `details.tsx`. Mostly a new `views/items.tsx` + ~4 route lines in `index.tsx`. Some copy of the `dl` summary block, which is fine-grained enough not to hurt.
5. **API base URL / caching change** — base URL read once (`api.ts:2`), re-exported for `spriteUrl` (`data.ts:28`); caching policy (`FRESH_MS`, `refresh`, `api`) lives entirely in `api.ts:4-53`. One file.

## Notable strengths

- **One card abstraction, proven by the feature diff**: `Card = Species & {types?, note?}` plus `CardList`'s optional `action` callback (`components.tsx:20`, `CHANGES.diff:157-178`) absorbed the team feature with zero flag creep — five different card lists render through it.
- **Colocated loaders with inferred types**: `loadHome`/`loadPokemon`/`loadMoves` etc. sit next to their views, and props use `Awaited<ReturnType<...>>` (`details.tsx:63`, `pokemon.tsx:220`) so there's no duplicated type surface to keep in sync.
- **Shared helpers each defined once**: `humanize`, `englishName`, `latestFlavorText`, `dexNumber`, `orDash`, `typeLabel` (`data.ts:9-40`, `components.tsx:37`) — no duplicated formatting logic anywhere.
- **Team state is explicit**: cookie read/writes are isolated in `team.tsx:16-49`, and the team is passed into `PokemonPage` as a plain `string[]` prop (`index.tsx:40`, `pokemon.tsx:222`) rather than reached for globally.

## Friction

- `pokemon.tsx:3` imports `TeamButton`/`TEAM_SIZE` from the *team* feature module — a page view now depends on another feature's file, so removing/shipping the team feature separately requires editing the Pokémon view too. Moving the button atom into `components.tsx` (where every other shared atom lives) would fix it.
- `any` at every API boundary (`pokemon.tsx:71,78,224-230`, `details.tsx:57,107`, `team.tsx:68`, `data.ts:49`) — the seams between "raw API JSON" and "shaped data" are convention-only; a renamed field in the API won't be caught by `tsc`.
- The three home filters each repeat the same htmx wiring (`home.tsx:94,99,110`), and `MoveTable`'s row cells hardcode columns parallel to the `COLUMNS` array (`pokemon.tsx:123-183`) — two spots where a change must be made twice.
- Fragment endpoints in `index.tsx` share implicit DOM-id contracts with the views (`#results` at `home.tsx:53`, `#move-tables` at `pokemon.tsx:197`) — inherent to htmx, but the ids could at least be exported constants.

This is an easy codebase to own: every change I traced landed in one obvious place or a small, findable set, and the one real entanglement (team button in the Pokémon view) is a one-move refactor.
