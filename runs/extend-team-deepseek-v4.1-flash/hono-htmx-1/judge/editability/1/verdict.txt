## Review: editability

I read the whole app (`app/src/` — `api.ts`, `data.ts`, `index.tsx`, and all six view files) plus the Hono skill guidance. The stack is current stable Hono (4.13.x) with the recommended `jsxRenderer` + `ContextRenderer` layout pattern (`app/src/views/layout.tsx:10`), JSX built via esbuild, interactivity purely declarative htmx — so no server/client state-split tangles to worry about.

**What's genuinely good:**

- **Data access is funneled**: every fetch goes through `api`/`apiUrl`/`apiList` (`app/src/api.ts:14-56`). Base URL, cache TTL, stale-while-revalidate all live in one file, and even the sprite URL builder re-imports `API_BASE_URL` from it (`app/src/data.ts:28`). The "change the API base/caching" scenario is a one-file edit.
- **All five Pokémon-card lists render through one component**. `CardList` (`app/src/views/components.tsx:23`) is the only consumer of `spriteUrl` (`app/src/components.tsx:25` → `app/src/data.ts:28`), so a sprite fix (the Deoxys scenario) lands in one place and covers home, moves, abilities, types and team. The `action?: (card) => Child` callback slot is exactly the variation the team feature needed, and it was reused rather than copied — good abstraction design.
- **Loaders and views are paired and colocated** with types inferred from the loader (`Awaited<ReturnType<typeof loadMove>>`), so there's no duplicated shape declaration to keep in sync.

**Where it strains:**

- Card *construction* (species + types + note) is duplicated in three producers: `cardsForPokemon` (`app/src/data.ts:91-105`), `loadHome` (`app/src/views/home.tsx:44`), and `loadTeam` (`app/src/views/team.tsx:61`). Adding a card field or changing type attachment is a three-site edit — this is also the residual cost if a sprite fix ever needs more than the species id.
- The sort-key vocabulary is declared twice: `SORT_KEYS` for validation in the router (`app/src/index.tsx:51`) and `COLUMNS` in the table component (`app/src/views/pokemon.tsx:32`). The router also reaches into `MovesData` internals to pick a table by method (`app/src/index.tsx:58`), so the moves feature is smeared across two files with no module seam.
- `details.tsx` is a grab-bag (moves + abilities + types in one file), so "remove a feature" means subtracting from a shared file rather than deleting one; abilities additionally has a link site inside the Pokémon page (`app/src/views/pokemon.tsx:286-293`).
- Cross-feature coupling: the Pokémon page imports `TEAM_SIZE`/`TeamButton` from the team module (`app/src/views/pokemon.tsx:4`) and relies on the implicit `.team-action` swap-target markup contract defined in `team.tsx`.
- Small copy-paste: the effect fallback expression appears verbatim for moves and abilities (`app/src/views/details.tsx:14`, `app/src/views/details.tsx:65`).

None of this would block the PR; all edits are greppable and no change I traced required touching unrelated files. But "one obvious place" holds for data access and sprite URLs and fails for card construction, card ordering, and the moves tables' route layer.
