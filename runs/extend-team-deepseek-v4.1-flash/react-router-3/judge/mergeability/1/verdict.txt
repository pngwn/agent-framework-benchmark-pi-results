## Review summary

This is a well-executed React Router v8 framework-mode app. Key strengths verified against the framework's current guidance (`reactrouter.com`, skill reference, v8 changelog):

- **Routing/data loading**: manual `route()` config in `app/app/routes.ts`, generated `+types` imports, loaders that parse URL search params (`app/app/routes/home.tsx:24`), `data()` thrown for 404s (`app/app/lib/api.server.ts:57`), root `Layout`/`ErrorBoundary` split (`app/app/root.tsx:9,43`).
- **`<title>` in components**: this is *not* a deviation — the current route-module doc says "Since React 19, using the built-in `<title>` element is recommended over the use of the route module's `meta` export." The app follows exactly that (`app/app/routes/home.tsx:96` etc.).
- **Team feature**: `fetcher.Form` to a cross-route action for stay-on-page mutations is the documented pattern, with automatic revalidation of loaders giving correct label updates with no SSR flash (cookie read server-side in the loader, `app/app/routes/pokemon.tsx:91`). HttpOnly cookie set server-side (`app/app/routes/team.tsx:56`, `app/app/lib/team.server.ts:33`) is the right call. The change reuses `PokemonCards`/`speciesCard`/the `Index` aggregate rather than adding a parallel path — minimal, clean diff.
- **Server**: Express 5 `/{*splat}` catch-all with `createRequestHandler`, immutable asset caching, proxy concerns correctly left out (`app/server.mjs`).
- **Server/client boundary**: `.server.ts` modules are stripped from the client build by convention; `API_BASE_URL` only read server-side.

Remaining concerns are minor: an in-memory cache that never evicts expired entries (bounded only by the fixed dataset), a cookie read-modify-write race on rapid toggles, a couple of small code smells (`find` where a `Map` exists, a `!` assertion), and per-move fetch fan-out in the Pokémon loader.
