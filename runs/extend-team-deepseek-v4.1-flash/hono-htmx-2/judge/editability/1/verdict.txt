I've reviewed the app thoroughly against the spec, the feature file, and Hono's current guidance. Here's my assessment.

## Review notes

**Structure** (11 source files, ~770 significant LOC): thin router (`app/src/index.tsx`) orchestrating view modules that each colocate their loader + page (`views/details.tsx`, `views/pokemon.tsx`, `views/home.tsx`), a single API seam (`api.ts`), a shared data/helpers module (`data.ts`), shared JSX components (`views/components.tsx`), and a self-contained team feature (`team.ts` + `views/team.tsx`). This is a genuinely workable shape: every data fetch funnels through `api()`/`apiUrl()` (api.ts:38-51), and every Pokémon-card list in the app renders through the one `CardList` component (components.tsx:21) fed by the shared `Card` type (data.ts:86) and `cardsForPokemon` mapper (data.ts:88-102) — that's the right abstraction for this app's real variation (optional types, note via callback, action slot).

**Scenario results:**

1. *Remove Abilities* — touches `index.tsx:8,80-83` (import + route), `details.tsx:53-73` (loader + page), and `pokemon.tsx:286-294` (the spec-mandated Abilities section links). Three files, four edits; no nav link exists, nothing else references `/abilities/`. Acceptable but scattered, because `details.tsx` bundles Move/Ability/Type in one file and routes are all flat in `index.tsx`.
2. *Sprite fix* — one render choke point: `spriteUrl` (data.ts:28) is consumed only by `CardList` (components.tsx:25), and all five card lists (home, move, ability, type, team) go through it. One fix covers everything. (Caveat: if the fix needed Pokémon-record data, the three card producers — `loadHome`, `cardsForPokemon`, `loadTeam` — would each populate a new `Card` field; still one render site.)
3. *Sort by name* — `CardList` can't just sort internally, because the team page must keep insertion order (FEATURE.md), so you'd sort in `loadHome` (home.tsx:70) and `cardsForPokemon` (data.ts:96), or add a prop to `CardList`. Two or three findable edits, but not one obvious place.
4. *Items section* — `loadMove`/`MovePage` (details.tsx:14-47) is a clean template; `api`, `apiList`, `englishEffect`, `latestFlavorText`, `Section`, `Count`, `TypeBadge`, `CardList`, `orDash` are all directly reusable. Mostly new code composed from existing helpers, plus a nav link in `layout.tsx:26-33`.
5. *Data source / caching* — everything lives in `api.ts:3-5` (`API_BASE_URL`, `FRESH_MS`, `load`/`refresh`); `spriteUrl` imports `API_BASE_URL` from there so media URLs follow automatically. One module, period.

**Weak spots:** `details.tsx` is a three-feature grab bag; API payload typing is pervasive `any` (pokemon.tsx:99, data.ts:46, details.tsx:54-59), so the compiler won't catch shape changes; htmx fragment contracts (`#results` home.tsx:80, `#move-tables` pokemon.tsx:319, `SORT_KEYS` index.tsx:68) are implicit cross-file agreements between router and view; `hx-get="/"` is repeated three times in home.tsx; `TypeBadge`'s `link` boolean is mild flag creep.
