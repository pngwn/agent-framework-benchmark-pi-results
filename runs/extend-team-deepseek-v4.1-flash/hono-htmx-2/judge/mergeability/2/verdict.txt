# Review: Pokédex (Hono + htmx)

## Framework currency check

Versions are the current stable releases as of today: `hono@4.13.14` (v5 is only at RC), `@hono/node-server@2.1.5`, `htmx.org@2.0.11` (`app/package.json:7-13`). None of the APIs in use — `jsxRenderer`, `ContextRenderer` module augmentation, `c.render`, `c.html`, `getCookie`/`setCookie`, `serveStatic`, `parseBody` — are deprecated in 4.x.

## What's good

This is a disciplined, docs-faithful implementation. The `ContextRenderer` augmentation (`app/src/views/layout.tsx:4-8`) is exactly the pattern the official hono-jsx skill documents for passing a title to the layout. The team builder uses plain form POSTs + 303 redirects (`app/src/views/team.tsx:13-33`, `app/src/index.tsx:91-117`) — the skill's stated default of "no client JavaScript required" — with the htmx budget spent only where interactivity is genuinely needed (search, sort, game select). `hx-sync="…:replace"` on the search input and the per-route `Vary: HX-Request, HX-History-Restore-Request` + `HX-Push-Url` handling (`app/src/index.tsx:19-33`) show real understanding of htmx's history/partial model, not cargo-culting. The `load*` + `Page` co-location pattern is applied uniformly across all four view modules. 404s return real 404 status via a shared `notFound` helper, `onError` exists, and there's no `dangerouslySetInnerHTML`/`raw()` anywhere — JSX escaping covers all the user-controlled interpolation.

## What I'd ask about

- The module-level SWR cache (`app/src/api.ts:9`) never evicts, and its keys are partly user-controlled (`/pokemon/:name`, `/moves/:name` feed arbitrary strings straight in at `app/src/index.tsx:39`, `app/src/index.tsx:78`). Behind the reverse proxy the spec assumes, that's an unbounded-memory vector from a crawler hitting random 404 names. A cap or a negative-result TTL is a ten-line fix, but I'd want it before merge.
- The API boundary is `any` end-to-end (`api<T = any>`, `versionGroups(pokemon: any)`, `(a: any)` sorts in `app/src/views/pokemon.tsx:71-75,224-230`, `app/src/views/details.tsx:57,107`, `app/src/data.ts:49`). The types in `data.ts` are good, but nothing verifies the app's assumptions about API records; the first upstream data change fails silently rather than at a type check.
- `serveStatic({ root: './dist' })` is cwd-dependent (`app/src/index.tsx:16`); fine under `npm start` from `app/`, brittle the first time someone runs the built file from elsewhere.
- `POST /team/remove` writes `Set-Cookie` regardless of whether the request carried the cookie (`app/src/index.tsx:103-115`): `sameSite=Lax` protects the *request*, not the response, so a cross-site form can blank a visitor's team. Harmless data, but a `fetch`-gated mutation or hono's `csrf` middleware would close it.
- No `Cache-Control` on dynamic responses; the fragment-only endpoints (`/pokemon/:name/moves`, `/moves-table`) are reachable by direct navigation and return a bare fragment a shared proxy could hand to a normal request.

Nothing here is structural — every fix is local, and the loader/view seams make them easy to place. I'd merge after the cache bound and the `any` typing pass, and happily own this code.
