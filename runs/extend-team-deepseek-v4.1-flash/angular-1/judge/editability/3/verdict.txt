# Editability review — Angular 22 Pokédex

## Architecture in brief

The app uses a clean three-layer seam: `src/server/api-client.ts` (fetch + TTL cache) → `src/server/loaders.ts` (per-page view-model builders, dispatched by `loadPageData`) → dumb page components that take a resolved VM through `input.required` + `withComponentInputBinding` (`app/src/app/app.config.ts:17`, `app/src/app/app.routes.ts:11-13`). The browser never touches PokeAPI: it gets server-built VMs via TransferState or the custom `/_data` endpoint (`app/src/app/data/page-data.ts`, `app/src/server.ts:21-29`). This is well documented in `app/README.md`. The patterns (`@Service()`, `provideAppInitializer`, `linkedSignal`, `linkedSignal`-reset sort state, `RenderMode.Server`, default-export route components with intent-based names) match current Angular guidance — I checked the skill references; resolvers + input binding and `@Service` are the documented modern forms.

## Scenario walkthroughs

1. **Remove Abilities** — delete `app/src/app/pages/ability/`, the route (`app/src/app/app.routes.ts:49-54`), `loadAbility` + `case 'abilities'` (`app/src/server/loaders.ts:341-353, 461`), `AbilityVM`/`AbilityRef` (`app/src/app/shared/models.ts:60-71`), and the Abilities section of the Pokémon page (`app/src/app/pages/pokemon/pokemon-page.html:72-84`). But it also leaves dead machinery behind: the `Card.hidden` flag exists *only* for ability pages and threads through `app/src/app/shared/models.ts:17`, `app/src/app/shared/card-list.ts:14` and the "Hidden ability" note in `app/src/app/shared/pokemon-card.ts:29`. Plus the `<meta>` description (`app/src/index.html:8`). Grep-clean but genuinely scattered: **3/5**.

2. **Sprite bug (Deoxys-type species)** — the sprite URL is derived in exactly one render place (`app/src/app/shared/pokemon-card.ts:37`), which is good. But the *data* the fix needs (the default Pokémon's sprite/id) is constructed in three separate places: `toCards` (`app/src/server/loaders.ts:121-133`), the inline card build in `loadHome` (`app/src/server/loaders.ts:152-172`, built from the *species* list, which doesn't even know the default Pokémon's id — a correct fix would require new fetching there), and team members (`app/src/server/loaders.ts:386-404`). One render fix, three data fixes — all in one file, so findable, but the duplication means the fix doesn't land in one obvious place. **3/5**.

3. **Sorting by name on all card lists** — `CardList` covers move/ability/type lists in one place (`app/src/app/shared/card-list.ts:12-17`), but the home page deliberately renders its own grid inline (extra types, pagination, priority) so it needs its own sort *before* the pagination slice (`app/src/app/pages/home/home.ts:46-58`), and the team list renders cards a third way (`app/src/app/pages/team/team-page.html:7-9`) and must stay in user order. Two code sites plus an exclusion judgment. **4/5**.

4. **Add an Items section like Moves** — this is where the architecture pays off. New page dir + route entry + `loadItem`/`case` in the loader switch + `ItemVM`. Everything else — the `pageData()` resolver factory (`app/src/app/app.routes.ts:10-13`), `CardList`, `PokemonCard`, `TypeBadge`, `orDash`, the `/_data` endpoint, TransferState, title strategy — is reused untouched. Roughly 60 lines of new component plus ~15 lines of wiring. **4/5**.

5. **Change API base URL / caching rules** — base URL is computed in one place (`app/src/server/loaders.ts`'s `api-client.ts:12-13`) and published to the browser via TransferState (`app/src/app/app.config.server.ts:13`), but the default `http://localhost:9000` is duplicated (`app/src/app/server/api-client.ts:13` and `app/src/app/data/page-data.ts:41`), and there are two parallel cache implementations with different eviction policies (`app/src/server/api-client.ts:18-70`, `app/src/app/data/page-data.ts:13-32`) plus the `/_data` `Cache-Control` header (`app/src/server.ts:31`). The sprite media path pattern lives in a fourth place, a render component (`app/src/app/shared/pokemon-card.ts:37`). **3/5**.

## Scoring

**removability — 3.** Removal is grep-clean but spreads over ~7 files, and the `hidden` card flag shared across three shared components exists solely for the ability pages — deleting Abilities without also cleaning `Card.hidden` leaves dead code.

**changeability — 4.** Most behaviours land in one obvious place: filters (`app/src/app/pages/home/home.ts:46-58`), move sorting (`app/src/app/pages/pokemon/move-table.ts:60-77`), titles (`app/src/app/page-title-strategy.ts:13-21`). The card/sprite family is the exception, with three construction sites in the loader.

**coupling — 4.** Pages depend only on narrow VM interfaces; server and client are separated behind the `PAGE_DATA_LOADER` token override (`app/src/app/app.config.server.ts:10`); shared state (team) is explicit via `TeamStore` + cookie. Minor tangles: the data-path convention couples route config to the loader switch with an asymmetric key (`types/:name` → `/type/`, `app/src/app/app.routes.ts:53-58` vs `app/src/server/loaders.ts:461-465`), and the title strategy inspects the literal resolver key `data['vm']` (`app/src/app/page-title-strategy.ts:19`).

**abstraction_design — 4.** The loader/VM/page triad stretches to new resources with near-total reuse (scenario 4); `MoveTable` handles column variation through label/value maps rather than flags (`app/src/app/pages/pokemon/move-table.ts:12-32`). Held back by card-construction copy-paste (`toCards` vs `loadHome` vs `loadTeam`), twin cache implementations, and the repeated `@else { <app-not-found /> }` block in four page components.
