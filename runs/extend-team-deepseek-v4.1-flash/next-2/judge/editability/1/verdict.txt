## Review: `app/` (Next.js 16.4.3, App Router)

I read every source file in `app/src/`, the spec/feature docs, the tests' expectations, and verified the framework idioms against current Next.js 16 docs (`connection()` is the stable way to opt into request-time rendering — the app uses it correctly in every server page before touching `process.env.API_BASE_URL`; async `params`/`searchParams`, `cookies()`, `useTransition` + `router.replace` are all current).

The codebase is genuinely well-layered: one `server-only` data layer (`lib/api.ts`) owns the origin, cache and every API shape; `lib/format.ts` owns every display rule; `components/` holds small presentational units (`Section`, `PokemonCard(List)`, `TypeBadge`, `MovesTable`); team state is an explicit, isomorphic cookie module (`lib/team.ts` + `lib/team-server.ts`). Client/server boundaries are clean (`'use client'` on exactly the four files that need it, `server-only` guards on both server libs).

The recurring weakness is **small logic duplicated at use sites instead of lifted into the lib**: the species→default-Pokémon resolution exists twice, query-string serialization three times, the type-labels map twice, and the `cache(load)/generateMetadata/notFound` boilerplate four times. One feature-specific field (`hiddenAbility`) is baked into the shared card type, which is the only real dead-code trap on removal.

### Scenario walk-throughs

1. **Remove Abilities**: delete `app/src/app/abilities/`, drop the Abilities `<Section>` from `pokemon/[name]/page.tsx:121`, then prune `getAbility`/`ApiAbility` (`lib/api.ts:172`) and `CardData.hiddenAbility` (`lib/api.ts:219`, rendered at `components/pokemon-cards.tsx:14`). Nav/layout know nothing about abilities. Clean, but not a pure directory delete.
2. **Sprite bug**: rendering is single-site (`components/pokemon-cards.tsx:15` → `lib/api.ts:274`), so a URL-pattern fix covers every list. A fix that needs the *Pokémon record's* sprite, though, runs into the fact that card data is assembled in three independent paths (`lib/api.ts:258` `pokemonCards`, `lib/api.ts:225` `getSpeciesIndex`, `app/team/page.tsx:26` `loadMembers`), and the default-variety lookup is duplicated in two of them.
3. **Sort cards by name**: one change in `PokemonCardList` covers home, move, ability and type pages; the team page bypasses it with its own `<ul className="card-grid">` (`app/team/page.tsx:78`) and must be touched separately.
4. **Items section**: `Section`, `PokemonCardList`, `TypeBadge`, `format.ts` and the whole fetch/cache layer are reusable; the page itself is a copy-adapt of `moves/[name]/page.tsx` (~60 lines) plus `getItem`/`ApiItem` in `lib/api.ts` and a nav link — no shared "resource detail page" abstraction exists to inherit from.
5. **Change data source / caching**: everything lives in `lib/api.ts` (`apiBaseUrl` :5, `mediaUrl` :279, `spriteUrl` :274, `CACHE_TTL_MS`/`CACHE_MAX_ENTRIES` :16, `cache: 'no-store'` in `request`). One file.
