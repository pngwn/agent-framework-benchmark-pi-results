I've reviewed the app thoroughly — SPEC, FEATURE, routes, loaders, shared components, pages, and server entry. Here's my assessment.

## How the code is shaped

The architecture is a consistent "page → view model" pipeline: a route resolver (`app/src/app/app.routes.ts:8`) asks `PageData` for a path like `/pokemon/pikachu?game=...`; on the server `loadPageData` (`app/src/server/loaders.ts:434`) builds a typed VM from the PokeAPI, on the client the same VM is fetched from the app's own `/_data` endpoint (`app/src/server.ts:22`, `app/src/app/data/page-data.ts:18`), with TransferState bridging the two so hydration doesn't refetch. Pages are thin templates bound to `input.required<VM>()`, and `PokemonCard`/`TypeBadge`/`CardList`/`orDash` are single-sourced. This makes most bug fixes land in one obvious place, but a few real seams leak: the card-grid markup is hand-rolled in three templates because `CardList` never grew `types`/per-item-content support, and the team's query-string contract is built in two places.

3. **Sort by name** — three places: inside `CardList` (covers move/ability/type), the `results` computed in `home.ts:77-82`, and team (either `team-page.ts` or `loadTeam` in `loaders.ts:233`). Or all three sorts in `loaders.ts`. Difficulty 3.
4. **Items section** — the Moves pattern (route via the `pageData` factory, `loadItem` + switch case in `loaders.ts`, `ItemVM` in `models.ts`, new page reusing `TypeBadge`/`CardList`/`orDash`/`NotFound`/panel CSS) is uniform and thin; mostly reuse, ~50 lines of new template. Difficulty 4.
5. **Data source change** — API base URL is built in one spot (`server/api-client.ts:12-14`, published via `app.config.server.ts:13` → token in `page-data.ts:39-42`); caching rules live in two caches (server `api-client.ts:16-19`, client `page-data.ts:13-28`) plus per-page TransferState. Difficulty 3.

## Scores

**removability: 3** — Each feature (abilities, team) has a predictable footprint — page dir, route, loader+switch case, VM model — but "delete and the links to it" means editing shared registries (`loaders.ts`, `models.ts`) and the pokemon page (`pokemon-page.html:67-79`, team button in `pokemon-page.html:17-25`), which is exactly "a handful of scattered edits".

**changeability: 4** — The highest-leverage fix (card sprite URL, `pokemon-card.ts:47`) is genuinely single-sourced and covers every list; `humanize`/`dexNumber`/`orDash` (`shared/format.ts`) and `toCards`/`typeRef` (`loaders.ts:133-148`) are shared helpers. Docks: team query built twice (`app.routes.ts:18`, `team-page.ts:97`), and home re-derives type labels client-side (`home.ts:93-99`) that loaders already compute.

**coupling: 4** — Components depend only on typed VM inputs and narrow tokens (`API_BASE_URL` in `pokemon-card.ts:36`); server and client code are cleanly split (`src/server/` vs `src/app/`) with a single seam (`PAGE_DATA_LOADER` swap in `app.config.server.ts:8`). Docks: the `page:<path>` string contract is defined implicitly by both the route resolvers (`app.routes.ts:28-35`) and the loaders switch (`loaders.ts:434-459`), and the root `App` embeds scroll policy via manual URL parsing (`app.ts:22-44`).

**abstraction_design: 3** — `CardList` (`card-list.ts`) exists for the move/ability/type card lists, but it never grew the variations the app actually has — `types` on cards (home, team) and per-item extra content (team remove buttons) — so home (`home.html:36-40`) and team (`team-page.ts:25-35`) duplicate the card-grid markup instead. `TypeBadge` handles its one flag (`link`) well, and `toCards`/`typeRef`/`MoveTable` stretch fine; the gap is contained but it's the one place copy-paste crept in.

**overall: 4** — Consistent VM-loader seams, single-sourced card component, and a clean server/client boundary make most changes easy; the duplicated card-grid/team-query and the implicit path contract are real but small drags.
