## Review

**Framework currency.** `app/package.json` pins `nuxt@4.6.3`, which is the current stable (released 2026-10-27, verified via the nuxt/nuxt releases page). The resolved tree (`app/package-lock.json:4645` h3 1.15.11, `:5805` nitropack 2.13.5, `:8325` vue 3.5.44) confirms the app targets Nuxt 4.6's actual runtime, so `defineEventHandler`/`getRouterParam` are the *current* Nitro-2/h3-1 APIs here — h3 v2's `defineHandler` rename applies only to the h3 v2/Nitro v3 beta (per h3.dev/migration and nitro.build/docs/migration), not to what this app runs on.

**What ages well.** All upstream PokeAPI access sits behind one module (`app/server/utils/pokeapi.ts`) with a single in-process cache; the client only ever calls the app's own five Nitro routes; `API_BASE_URL` is read in exactly one place (`app/server/utils/pokeapi.ts:4`); `compatibilityDate` and the `node-server` preset are pinned (`app/nuxt.config.ts`). A framework upgrade would touch the five thin route files and the util, not the pages.

**What will churn.** Every page throws away the response typing Nuxt infers for server routes (`useFetch<any>` at `app/pages/index.vue:63`, `app/pages/pokemon/[name].vue:116`, `app/pages/moves/[name].vue:53`, `app/pages/abilities/[name].vue:31`, `app/pages/types/[name].vue:53`), and the server module itself is `any`-heavy (`mapEvolutionNode(node: any): any` at `pokeapi.ts:319`), so payload-shape changes ripple silently. The `/api/pokemon/:name` route returns move rows for *every* version group when the page renders one (`pokeapi.ts:347-365`), and "not found" is in-band data rather than `createError`/404.

**Platform.** Native `fetch`, `Map`/`Set`, CSS custom properties and grid, `loading="lazy"` — good. But `app/pages/index.vue:112-116` hand-rolls query-string encoding instead of `URLSearchParams`/`router.resolve`, and `pokeapi.ts:40-43` regex-parses IDs instead of `new URL`; upstream fetches (`pokeapi.ts:63`) have no `AbortSignal.timeout`.
