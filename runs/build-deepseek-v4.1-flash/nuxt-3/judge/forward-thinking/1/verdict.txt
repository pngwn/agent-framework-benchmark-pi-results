## Review

I read the spec, all 19 source files in `app/`, and verified the framework facts against the Nuxt docs and release notes: **Nuxt 4.6.3 is the current stable release (2026‑10‑27)**, and the app pins exactly it. Nuxt 4.6.0 (2026‑10‑05) introduced two things this review hinges on: the `nuxt/server` import surface for Nuxt 5 portability, and the rebuilt typed `$fetch`/`useFetch` — I confirmed the app generates route types at `app/.nuxt/server-routes.d.ts` but discards them. I also confirmed against the h3 v1 source (`src/utils/request.ts` on the v1 branch) that `getRouterParam` does **not** decode by default in h3 v1, but h3 v2 (Nuxt 5) decodes by default and its docs explicitly say "Do not decode the result again."

**What holds up well:** upstream API access is behind exactly one module (`app/server/utils/pokeapi.ts`), server routes are thin 5-line wrappers, config is a single 10-line `nuxt.config.ts`, and the dependency list is just `nuxt` — no CSS framework, no axios, no state library. The current-generation APIs (`useFetch` with reactive URL + `await`, `useHead` as a function, type-only `defineProps`, `app/` directory layout, `[name].get.ts` routes) are used consistently, and nothing deprecated appears anywhere.

**What will churn:** `useFetch<any>` in all six page fetches throws away the route-typed fetch Nuxt 4.6 just rebuilt; the 404 flow is a hand-rolled `notFound` flag copy-pasted into four page templates (including the title ternary) instead of the documented `throw createError({ status: 404 })` + `error.vue` pattern, and the HTTP status stays 200; server handlers rely on h3 auto-imports rather than `nuxt/server`, so the already-announced Nuxt 5 (Nitro 3 / h3 2) transition touches every server file and turns the manual `decodeURIComponent` into a documented double-decode bug; `compatibilityDate` is pinned to `2025-07-15` — the framework's own year-old default, not the current date the docs recommend. Platform use is solid but not first-choice: query strings and hrefs are hand-encoded where `URLSearchParams`/`router.resolve` apply.
