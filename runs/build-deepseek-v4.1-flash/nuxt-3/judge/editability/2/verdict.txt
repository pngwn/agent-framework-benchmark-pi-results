# Review: Editability of the Nuxt Pokédex app

The app is a single-dependency Nuxt 4.6.3 project (current stable, verified against nuxt/nuxt releases: 4.6.3 shipped 2026‑10‑27). Structurally it's textbook Nuxt: `pages/` + thin Nitro routes under `server/api/` + all data assembly in one `server/utils/pokeapi.ts` + five small components. The server/client seam is the strongest part of this codebase.

**Where changes land well.** The entire upstream API is behind one module: `app/server/utils/pokeapi.ts:4` (base URL), `:30` (response cache), `:105-106` (sprite URL pattern), `:109` (index cache). Pages never see `API_BASE_URL`; they only know internal `/api/*` routes, so scenario 5 is genuinely a one-file change. Card construction flows through exactly two functions (`buildIndex`'s entry mapper and `cardFromRef` at `:219-231`, both delegating to `spriteForId`), so the sprite/species-mapping fix in scenario 2 is confined to one file and automatically covers every card list, since all four lists are fed by either the index or `cardsFromRefs` (`:236-247`).

**Where change is harder than it should be.**

1. **Untyped contracts across the server/app boundary.** Every page does `useFetch<any>` (`app/pages/pokemon/[name].vue:116`, `app/pages/moves/[name].vue:53`, `app/pages/abilities/[name].vue:31`, `app/pages/types/[name].vue:53`), and `MoveMethodTable` takes `rows: Array<Record<string, any>>` whose keys (`moveLabel`, `typeLabel`, `categoryLabel`…) are invented in `getPokemonPageData` (`server/utils/pokeapi.ts` around the `rows.push` block). Rename a field server-side and nothing fails until runtime. Nuxt 4's `shared/types/` directory (auto-imported in both bundles, verified in current docs) exists precisely for this and is unused.

2. **Duplicated page skeleton.** The `route param → reactive useFetch → useHead title/notFound → <NotFoundContent v-if="data?.notFound || !data">` pattern is copy-pasted verbatim into four detail pages (`pokemon:116-128`, `moves:53-64`, `abilities:31-42`, `types:53-61`). A title rule or not-found behavior change is a four-file edit. A `useResourcePage(getXPageData)` composable would collapse this.

3. **Monolithic global stylesheet.** All 700+ lines live in `app/assets/css/main.css` with page-scoped selectors (`.moves-section:521`, `.hidden-ability:238`, `.ability-page`, `.evolution-list:507`). Deleting a feature leaves its styles behind, and Nuxt's favored per-component `<style scoped>` would make styles travel with the components that own them.

4. **No card-list abstraction.** The "`<count> Pokémon` + `<ul class="card-grid">` + `<PokemonCard v-for>`" block is repeated in `moves:38-44`, `abilities:11-21`, `types:28-36`, and inline in `pages/index.vue:37-44`. Adding name sorting to *every* list (scenario 3) therefore touches four templates; the three server-fed lists share one sort point (`cardsFromRefs`), but the home page's list is separate client-side logic.

Minor residues: `formatValue`/`isMissing` em-dash logic is defined twice (`app/pages/moves/[name].vue:65`, `app/components/MoveMethodTable.vue:104,109`) instead of `app/utils/`; empty `definePageMeta({})` at `app/pages/index.vue:57` is dead noise; `cardFromRef`'s fallback sets `speciesName: ref.name` from a *Pokémon* ref, which would link `/pokemon/deoxys-normal` (a 404) — the exact seam the spec warns about, latent today only because index lookups usually succeed; removing Abilities would orphan `PokemonCard`'s `hidden` prop (`components/PokemonCard.vue:28`) and its CSS.

**Verdict.** Data-source, bug-fix, and remove-a-feature work is easy and central; extend-the-app work (new sections, new card-list behaviors) is copy-paste-prone and untyped. Overall: good, not exemplary.
