## Review

I read the spec, all 19 source files in `app/`, and verified framework behavior against current docs (Nuxt 4.6.3 is the current stable — the app pins exactly it; h3's `getRouterParam` decodes by default; computed `useFetch` URLs are auto-watched; Nuxt 4 has a `shared/types` directory for cross-boundary types).

**What's good.** The architecture is exactly what I'd want: a Nitro server-route BFF (`app/server/api/**/[name].get.ts`) that owns the upstream PokeAPI contract and caches it, with pages consuming it via `useFetch` (`app/pages/index.vue:63`, `app/pages/pokemon/[name].vue:116`). Nuxt 4 srcDir layout (`app/app.vue`, `app/pages`, `app/server`), `useHead` for titles, a catch-all `app/pages/[...slug].vue` for 404, auto-imports used consistently. File organisation mirrors the spec's resource model, naming is consistent, and the two comments that exist (`app/server/utils/pokeapi.ts:1`, `:151`) are the "explain why" kind. CSS is a single organised, token-driven stylesheet.

**What blocks a clean merge.**

1. **Error/404 conflation.** Every detail page renders `NotFoundContent` when `data` is falsy (`app/pages/pokemon/[name].vue:2`, `app/pages/moves/[name].vue:2`, etc.), but `error` from `useFetch` is never read. An upstream API outage or a 500 from the proxy shows "Not found" with HTTP 200 instead of an error state.
2. **404 as payload, not status.** Server handlers return `{ notFound: true }` with status 200 (`app/server/utils/pokeapi.ts:264`, `:396`, `:421`, `:441`). Nuxt's documented pattern is `throw createError({ statusCode: 404 })` + handling `error`/`showError` on the page. Works against these tests, but it's semantically wrong HTTP and misleads any proxy/cache layer.
3. **`any` everywhere on the client.** `useFetch<any>` in all six data pages (`app/pages/index.vue:63`, …) while the server defines perfectly good types in `app/server/utils/pokeapi.ts:10-31` — Nuxt 4's `shared/types/` is exactly the documented place to put them so both bundles see them.
4. **Double URI-decode.** `decodeURIComponent(getRouterParam(event, 'name'))` in all four handlers (`app/server/api/pokemon/[name].get.ts:4` etc.) — h3 already decodes; a param containing a literal `%` throws `URIError` → 500.
5. **One 489-line data god-module.** `app/server/utils/pokeapi.ts` holds humanize, cache, index builder and page-data builders for all four resources. Coherent today, but it's the single file every future feature touches; splitting per resource is cheap now.

Minor: hand-rolled query-string builder (`app/pages/index.vue:97-103`) instead of `router.resolve`/`withQuery`; the pokemon page fetches *all* move details for *all* version groups up front (~100-fetch fan-out, `app/server/utils/pokeapi.ts:285-295`) when only one game's tables are rendered; duplicated `formatValue`/dex-number/title logic; `PokemonCard`'s root is an `<li>` that only works inside a parent `<ul>` (`app/components/PokemonCard.vue:1`); redundant `watch: [name]` and empty `definePageMeta({})`.
