## Review: test quality

The app contains **zero tests of its own**. `tests.files: 0` in the measured facts matches what I found on disk: no test/spec files anywhere under `app/` (the only `describe|it|expect` hit is a regex literal in `app/src/lib/api.server.ts:75`), no test script in `app/package.json:11-13` (only `dev`, `build`, `start`), and no test runner or testing library among the 11 dependencies. The app was verified only against the acceptance suite in `tests/`, which is not its work and won't survive as a regression guard for someone refactoring the substantial data layer it wrote.

That's a real gap, because `app/` contains ~1000 lines of genuinely risky logic that currently has no unit-level protection:

- **Data transformation**: `app/src/lib/api.server.ts:258` (`loadHome`) composes type, generation and search filters; `:329` (`loadPokemonPage`) builds move tables with method ordering (`:430-445`), dedup keys (`:402-407`), latest-game selection (`:394-395`), and missing-value coercion (`:409-416`). `app/src/lib/api.server.ts:224` (`cardsFromPokemonRefs`) maps Pokémon refs to species and excludes alternate forms via the `id > 10000` heuristic. A one-line refactor here (e.g. flipping `id > 10000` to `>=`, changing the dedup key, or reordering `reverse().find` in `englishEntry` at `app/src/lib/format.ts:21`) would break the app with no failing test until someone re-runs the full Playwright suite against a live API.
- **Pagination math**: `app/src/lib/api.server.ts:307-313` — `perPage = 48`, `Math.ceil`, page clamping and the `slice(start, start + perPage)`. Classic off-by-one territory, untested.
- **Sorting**: `app/src/components/MovesSection.tsx:29-46` (`compareRows`) implements the subtle "missing values sort last in both directions" rule and the numeric-vs-string split; the aria-sort state machine is at `:62-71` and `:81`.
- **URL state**: `app/src/routes/index.tsx:13` (`validateSearch` — page parsing/flooring/default omission), `:48` (`updateSearch` — page reset on filter change, `replace` for search) and `:66` (`pageSearch`).
- **Caching**: `app/src/lib/api.server.ts:40-56` (`memo`) — TTL, in-flight dedup, rejected-promise handling.
- **Error paths**: `apiGet` (`app/src/lib/api.server.ts:62-73`) throws on non-404, but no route defines an `errorComponent` and the root (`app/src/routes/__root.tsx:7-15`) only sets `notFoundComponent` — an API 500 renders the framework's default error UI (no `Not found` h1, no footer), a path nothing exercises.

The code itself is reasonable quality — pure functions like `humanize`, `collapseWhitespace`, `latestEnglishFlavor` (`app/src/lib/format.ts`) are trivially testable, which makes the absence of even a handful of unit tests harder to excuse. If the team owns this for years, the first PR after the acceptance suite stops being the gate should add unit tests for the filter/pagination/sorting pure logic (it's already factored to be testable) and one integration test for the API-error path.
