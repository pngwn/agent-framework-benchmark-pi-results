## Review: `app/` (TanStack Start + React, forward-thinking dimension)

### What this code gets right

**Version currency is exceptional.** Every dependency sits at the framework's *current* stable release, checked against release notes: `@tanstack/react-router@1.170.46` / `@tanstack/react-start@1.169.4` are the exact versions published in TanStack's 2026-10-22 release; Start went 1.0-stable on 2026-10-13 and requires **Vite 8**, which the app pins (`vite@8.3.5`, `app/package.json:6-9`, `app/package.json:21`). `react@19.3.1` is the latest React stable (2026-10-14), and `typescript@7.0.2` is the first stable native-compiler release (2026-07-08). The `start` script `srvx serve --prod --entry dist/server/server.js --static ../client` (`app/package.json:7`) matches the srvx production pattern used in the official Start examples (router PR #5915).

**API usage matches the current docs, including post-training-data APIs.** `shellComponent` on the root route (`app/src/routes/__root.tsx:22`) is the newer root-shell API (added via router PR #4528, June 2025, used in `examples/react/start-basic`). `head: ({ loaderData }) => ({...})` per-route (`app/src/routes/pokemon.$name.tsx:23`) is the current head API. `getRouter()` in `app/src/router.tsx:7` with `Register { ssr: true }` in the generated tree (`app/src/routeTree.gen.ts:191-193`) matches what the current generator emits — no copy-pasted boilerplate a newer release would regenerate differently. Server functions use `createServerFn({ method: 'GET' }).validator(...).handler(...)` (`app/src/lib/data.functions.ts:7-9`), exactly as the shipped `start-core/server-functions` skill prescribes, and the split into `api.server.ts` (server-only helpers) + `data.functions.ts` (server-fn wrappers) mirrors the skill's documented file organization.

**Data access is behind one well-typed module.** All 1,025-species fan-out, caching, filtering and shaping lives in `app/src/lib/api.server.ts`, with typed view models (`app/src/lib/model.ts`) crossing the client/server boundary; routes only consume `Route.useLoaderData()`. An upgrade to the fetch layer or API shape touches essentially one file.

### What ages less well

1. **The framework's not-found primitive isn't used.** Loaders return `null` and every route component repeats `if (!data) return <NotFound />` (`app/src/routes/moves.$name.tsx:24`, `abilities.$name.tsx:16`, `types.$name.tsx:13`, `pokemon.$name.tsx:55`). The current idiom is `throw notFound()` in the server-fn handler or loader — that renders `notFoundComponent` *and* sets HTTP 404 (which the spec explicitly encouraged). As written, missing resources respond 200 and the null-check pattern must be remembered on every new route.
2. **No error boundary.** `__root.tsx` registers only `notFoundComponent`; an API failure (non-404) in `apiGet` (`api.server.ts:60-64`) throws out of the loader into the default framework crash UI. The official example registers a `DefaultCatchBoundary`/`defaultErrorComponent`.
3. **Small cruft:** the alternate-form threshold `10000` is hand-repeated four times (`api.server.ts:173,233,282,532`); the `found: true` discriminator in every `*PageData` type (`model.ts:63,81,90`) is dead weight since null is the actual signal; `#/*`/`@/*` aliases are declared (`app/package.json:4-5`, `tsconfig.json:7-9`) but every import is relative; `idFromUrl` hand-parses with a regex (`format.ts:23-26`) where `new URL(url).pathname` is the platform tool; the hash-scroll `useEffect`+`requestAnimationFrame` (`pokemon.$name.tsx:47-54`) works around the router rather than leaning on its scroll behavior; `app/dist/` and `app/.tanstack/` build output aren't gitignored.

Platform usage is otherwise good: native `fetch` with a thoughtful `response.body?.cancel()` on 404 (`api.server.ts:55-57`), native form controls throughout, CSS custom properties + grid (`styles.css:169,242`), `localeCompare`, `padStart`, `.at(-1)`. No dependency could be removed without replacing it with something worse — four runtime deps total, no state/fetch library, which is correct for this architecture.
