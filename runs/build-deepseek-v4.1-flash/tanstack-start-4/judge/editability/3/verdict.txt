## Review: Pokédex app (editability)

Framework check first: the app's shape matches the **current stable TanStack Start** conventions, not stale ones. `createServerFn({ method: 'GET' }).validator(...)` (`app/src/lib/data.functions.ts:8-14`) uses `validator()`, which became the canonical method when `inputValidator()` was deprecated (router #7566, June 2026) and is the only option in Start 1.169 stable. `createRootRoute({ head, shellComponent, ... })` (`app/src/routes/__root.tsx:8-16`) is the current root-document API, and the `lib/api.server.ts` / `lib/data.functions.ts` / shared `lib/model.ts` split exactly mirrors the framework's recommended file-separation pattern (`*.server.*` files are denied in client bundles by Start's import protection). So the foundation an editor inherits is idiomatic; the deductions below are about duplication the agent introduced itself.

### Scenario walkthroughs

1. **Remove the Abilities pages.** No nav link exists (nav is only Pokémon/Types, `__root.tsx:26-35`), so no header edit. But the removal is more than "delete a route": you must also delete `app/src/routes/abilities.$name.tsx`, strip the Abilities *section* from `app/src/routes/pokemon.$name.tsx:110-122`, and then chase down the data chain or leave dead code: `loadAbilityPage`/`getAbility` (`api.server.ts:522, 173`), `getAbilityData` (`data.functions.ts:24`), `AbilityPageData` (`model.ts:53`). The Pokémon-page section is spec-mandated so some of this entanglement is inherent, but the loader/server-fn/model trail has to be found by grep. **Difficulty 3.**

2. **Sprite fix (Deoxys-style).** Excellent seam: the sprite URL is derived in exactly one function, `spriteForId` (`api.server.ts:80`), called only from `cardFromSpecies` (`api.server.ts:219`), which every card list funnels through — home (`api.server.ts:314`), moves/types via `cardsFromPokemonRefs` (`api.server.ts:237`), abilities (`api.server.ts:541`). One fix in one file covers every list. **Difficulty 5.**

3. **Sort cards by name.** All four card lists render through the shared `PokemonCardList` (`components/PokemonCard.tsx:26`), so the sort itself is a one-line change there and lands on home, move, ability and type pages simultaneously. If a visible sort *control* per list is wanted, each page component needs a few lines. **Difficulty 4.**

4. **Items section shaped like Moves.** The pattern is legible and repeatable: new `items.index.tsx` (clone of `types.index.tsx`, 26 lines), new `items.$name.tsx` (clone of `moves.$name.tsx`), a nav link in `__root.tsx`, plus one block each in `model.ts`, `api.server.ts` (a `getItem` memo + `loadItemPage` + `loadItemList`) and `data.functions.ts`. Reusable as-is: `NotFound`, `PokemonCardList`, `displayOrDash`/`humanize`, the `memo` cache and the `.server.ts`/`.functions.ts` seam. Not reusable: the page body itself — there is no generic "detail page" abstraction, so the panel/`<dl>`/section markup is copied and adapted. **Difficulty 3.**

5. **Change API base URL / caching.** `API_BASE_URL` is read once (`api.server.ts:23`) and every URL builder (`apiGet:59`, `mediaUrl:76-77`, `spriteForId:81`) goes through it; caching is one `memo` function with a single default TTL (`api.server.ts:37-56`) and no per-call-site TTL overrides. The `/api/v2/` path prefix is also only in `apiGet`. One file. **Difficulty 5.**

### Findings driving the scores

The recurring weakness is that when a variant appeared (hidden ability cards, type badges in links), the agent **copied the loop instead of extending the helper** — the same trait appears three times:

- `loadAbilityPage` re-implements the pokemon-ref→card loop (ID ≤ 10000 filter, `speciesById` lookup, `byId` dedup) inline (`api.server.ts:528-542`) rather than extending `cardsFromPokemonRefs` (`api.server.ts:228`) to carry the hidden flag. Any future change to card membership rules must be made twice.
- `type-badge type-${name}` markup is hand-inlined in five spots across four files (`MovesSection.tsx:109`, `pokemon.$name.tsx:76`, `moves.$name.tsx:31`, `types.$name.tsx:36`, plus the one shared `TypePill` at `PokemonCard.tsx:6` which is only a `<span>` and used by nothing but cards). Renaming or restyling type badges touches all of them.
- `loadTypePage` rebuilds `typeMap` by hand (`api.server.ts:563`) when `getTypeMap()` (`api.server.ts:139`) already exists.

Smaller copy-paste: the power/accuracy/pp null→`Number` coercion is duplicated between `loadPokemonPage` and `loadMovePage` (`api.server.ts:386-390` and `:511-515`), and the home-search shape is known in three places (`index.tsx:13` `validateSearch`, `data.functions.ts:14` validator, and the defensive `typeof input.*` re-checks in `api.server.ts:272-274`). None of these will surprise an editor — everything is grep-able and honestly named — but they're the reason changeability isn't a 5.

On the plus side, the design choices around real variation are genuinely good: `PokemonCardData` makes `types` and `hidden` optional (`model.ts:8-15`) instead of spawning flag parameters; `MovesTable` computes its column list from `table.method` (`MovesSection.tsx:52`) rather than taking booleans; `MovesSection` takes an `onGameChange` callback (`MovesSection.tsx:127`) instead of importing `useNavigate`, so the component stays route-agnostic; and `model.ts` view-models mean the pages never see raw API JSON, so API-shape changes are quarantined in `api.server.ts`.
