## Review — test quality

The app contains **zero tests of its own**. A repo-wide search for `*.spec.ts` / `*.test.ts` matches only a tsconfig exclusion (`app/tsconfig.app.json:12`), the facts confirm `tests.cases: 0`, and every Angular schematic is configured with `skipTests: true` (`app/angular.json:12-32`). Worse than absent: the `test` script is *broken*. `app/package.json:10` declares `"test": "ng test"`, but `angular.json` defines only `build` and `serve` targets (no `test` builder, `app/angular.json:25-81`) and neither `vitest` nor `jsdom` is in devDependencies — the current Angular 22 default test setup requires both (angular.dev/guide/testing). Running `npm test` inside `app/` fails outright, a trap for the next engineer.

So per the dimension rules, `coverage_of_risk` and `regression_power` score 1, and the value of this review is in *what the missing tests would have guarded*. Reading the risky code, there is a lot of it, and it's the kind of hand-rolled logic that regresses silently:

- **Pure helpers, the easiest and highest-value unit-test targets, are untouched** — `humanize` capitalization, `latestEnglishFlavor` reverse-scan + whitespace collapse, `idFromUrl` regex, `dexNumber` zero-padding, `formatDecimal`'s `/10` conversion and `—` fallback (`app/src/app/core/helpers.ts:12-56`). A refactor here breaks every page's display strings with no signal.
- **The move-table sort engine** (`app/src/app/shared/move-table.ts:122-140`): the "missing values sort last in both directions" rule, the null-vs-null tie-break, the two-key default ordering, and the `aria-sort` flip logic (`sortBy`/`ariaSort`, lines 96-118) are exactly the behavior a spec change or refactor would quietly break.
- **Home-page filtering, pagination and URL state** (`app/src/app/pages/home-page.ts:151-162`): page clamping (`Math.min(Math.max(1, params.page), totalPages)`), the 48-per-page slice, `requestedPage`'s `Number`-then-`floor` parsing (`home-page.ts:128-131` — `page=2.7` silently becomes page 2), and `buildQuery`'s default-omission rules (`home-page.ts:243-250`) are all untested round-trip logic.
- **Promise-caching in the API layer** (`app/src/app/core/poke-api.ts:14-21`) caches *rejections* permanently: one transient 500 and that species page is broken until a full reload, and nothing would ever catch it.
- **Game/URL sync on the Pokémon page** (`app/src/app/pages/pokemon-page.ts:263-268`): an invalid `?game=foo` falls back to the highest-order version group in the `<select>` while the URL keeps the bogus value — a state/URL divergence no test would surface.
- **Ability-page aggregation** (`app/src/app/pages/ability-page.ts:70-77`): the `id > 10_000` alternate-form exclusion and the OR-folding of `is_hidden` across slots are one-character regressions.
- **Error handling**: every page renders the not-found component for *any* loader error (`home-page.ts:107`, `pokemon-page.ts:196`, etc.), conflating network failure with a genuine 404 — untested and misleading.
- Minor: the `#moves` hash scroll via `effect` + `setTimeout` (`pokemon-page.ts:346-353`) and the recursive evolution-chain template (`pokemon-page.ts:189-202`) are brittle by nature and unguarded.

All of this logic is pure or near-pure (helpers, sort comparators, the loader's transformation step) and would be cheap to test with Angular 22's built-in Vitest setup; the current setup (broken script, no runner, `skipTests: true`) suggests tests were actively skipped rather than deferred.
