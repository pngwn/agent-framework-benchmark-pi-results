## Review notes

**Structure.** Clean layering: `routes/` → `lib/data.ts` (fetch+transform) → `lib/api.ts` (single HTTP/cache seam) → `routes/api-proxy` + `routes/media` (server proxies). All client data goes through `/api-proxy/*`, so the API base URL never leaks into client code. Components (`PokemonCard`, `MoveTable`, `TypeBadge`) are narrow, prop-driven, with typed `CardData`/`MoveRow` interfaces.

**Main editability drag.** The per-resource page-function pattern in `lib/data.ts` is copy-pasted three times with drift (the `seen` dedup exists in `getAbilityPage` and `getTypePage` but not `getMovePage`; `speciesById` is rebuilt from the same index at data.ts:298, 322, 353). The data layer is `any`-typed end to end, and routes reach into raw payloads (`data().pokemon.height`, `data().move.damage_class?.name`) alongside transformed fields, so no compiler catches shape changes. `data.ts` is a 430-line god module holding all five pages' logic.

**Scenarios.**
1. **Remove Abilities**: contained — delete `routes/abilities/`, `getAbilityPage` (data.ts:310–341), the Pokémon-page section (`routes/pokemon/[name].tsx:155–166`), and 3 CSS rules in `app.css`. No nav link exists to remove. Easy.
2. **Sprite fix**: rendering is in exactly one place (`PokemonCard.tsx:17`), so one fix covers every list — but the card pipeline only carries the species `id`/`name` (index built at `data.ts:56–66`), so a real default-variety fix needs plumbing through two separate card builders (`cardForSpeciesId` and `getHomeData`'s `items`).
3. **Name sorting**: the `.sort((a,b)=>a.id-b.id)` appears three times in `data.ts` (304, 335, 364) plus the home memo — four small edits, no shared helper.
4. **Items section**: `PokemonCard`, `format.ts`, and the route skeleton reuse, but the ~20-line "fetch → english name → effect → card list" transform would be cloned from `getMovePage`.
5. **Data source**: base URL duplicated in two proxy files (both read the same env var); caching rules split across `api.ts`'s TTL cache and `data.ts`'s permanent module-level promise memos — two layers with different invalidation semantics.
