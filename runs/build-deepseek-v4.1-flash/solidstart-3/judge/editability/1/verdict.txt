## Review: editability of the Pokédex app (SolidStart 2.1.0)

### What I checked

Spec: Pokédex with Pokémon/Moves/Abilities/Types pages over a proxied PokeAPI. Stack: SolidStart 2.1.0 (current stable, per npm and the 2.1.0 changelog), Vite 8, `ssr: false` CSR with two Nitro proxy routes (`api-proxy`, `media`). Framework docs for the current release recommend `query`/`createAsync` + route `preload` for data fetching; this app instead uses `createResource` per route plus a hand-rolled TTL/in-flight cache in `app/src/lib/api.ts:20-31`.

### Scenario walk-throughs

1. **Remove Abilities**: delete `app/src/routes/abilities/[name].tsx`, remove `getAbilityPage` (`app/src/lib/data.ts:313-341`), the Abilities section (`app/src/routes/pokemon/[name].tsx:155-165`), the `hidden` flag on `PokemonCard` (`app/src/components/PokemonCard.tsx:36`, `CardData.hidden` at `:10`), and orphaned CSS (`app.css:248,473,477`). Five files, but every edit is mechanical and findable by grep on `abilit`. No nav link, no shared state.
2. **Sprite bug (Deoxys-type)**: the sprite URL is built in exactly one shared component, `app/src/components/PokemonCard.tsx:18`, from `card.id` rather than the API-provided `front_default`, and all four card lists render through `PokemonCard` (`routes/index.tsx:133`, `moves/[name].tsx:66`, `abilities/[name].tsx:36`, `types/[name].tsx:68`). One fix covers every list — but a correct fix needs the sprite/pokémon identity to travel in `CardData`, which is populated in `cardForSpeciesId` (`data.ts:174-186`) and separately in `getHomeData`'s `HomeItem` (`data.ts:154-160`), so it's a 2-file, 3-edit fix.
3. **Sort by name on every card list**: there is no card-list abstraction — four routes each own their `<ul class="pokemon-grid">` + `For`/`map` block. The change is either 4× duplicated sort+control code or an extract-a-`PokemonCardList` refactor first. Also inconsistent: `routes/index.tsx:132` uses `.map` while the others use `<For>`.
4. **Items section shaped like Moves**: mostly additive. Reusable as-is: `apiGet`/`apiGetList`/caching (`lib/api.ts`), all of `lib/format.ts`, `PokemonCard`, `NotFound`, the `panel`/`section` CSS conventions. Copy the Move page shape (`routes/moves/[name].tsx`) plus a `getItemPage` in `data.ts` (or a new module — the repo convention funnels everything into the 430-line `data.ts`, which is itself a growing grab-bag).
5. **API base URL / caching change**: the client only knows the `/api-proxy/` prefix (`lib/api.ts:31`) — good seam. But the server base is declared twice (`routes/api-proxy/[...path].ts:3`, `routes/media/[...path].ts:3`), TTL lives in `lib/api.ts:24`, and media cache headers in the media proxy. Three files, one duplicated constant.

### Criteria scoring notes

- **changeability**: the shared `PokemonCard` is exactly the right seam for the sprite bug, but the "alternate forms excluded" rule (`data.ts:131,301,329,358`) and the `speciesById` map (`data.ts:124,298,322,353`) are each built in four places, so domain-level fixes land N times.
- **coupling**: server/client split is genuinely clean (two server-only route files vs. client-only `lib/`), and components take narrow prop interfaces (`CardData`, `MoveRow`). But view models are half-normalized: routes read raw API fields (`routes/moves/[name].tsx:33` `data().move.damage_class?.name`, `routes/pokemon/[name].tsx:96` `data().species.id`) alongside normalized ones, and the `type-badge type-${name}` CSS convention is hand-rolled in five places, bypassing the existing `TypeBadge` (`routes/types/[name].tsx:51`, `routes/types/index.tsx:25`, `components/MoveTable.tsx:152`, `components/PokemonCard.tsx:31` vs `components/TypeBadge.tsx`).
- **abstraction_design**: `PokemonCard`, `MoveTable`, `format.ts` and `api.ts` are real, well-shaped seams — but there's no card-list or page-scaffold abstraction, the per-route `createResource` + double-`Show` loading skeleton is repeated five times, and `HomeData` exposes three fields no route consumes (`data.ts:47-49,165-167`).
- **removability**: Abilities is one route file plus ~5 scattered edits including CSS; acceptable, not self-contained.
