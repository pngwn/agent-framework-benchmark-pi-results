## Review: SolidStart Pokédex (`app/`)

I read `SPEC.md`, all of `app/src` (routes, components, `lib/`, entrypoints, config), and checked the current SolidStart v2 docs (`docs.solidjs.com/solid-start/v2` — data-fetching via `query`/`createAsync`, API routes via `APIEvent`, `vite.config.ts` with `solidStart()` + `nitro()` from `nitro/vite`, and the documented `ssr: false` SPA option).

**Architecture in brief.** The app is SolidStart v2 with `ssr: false` (`app/vite.config.ts:5`), so it's a SPA: all data loads client-side via `createResource` through a same-origin proxy route (`app/src/routes/api-proxy/[...path].ts`), with a hand-rolled TTL cache + inflight dedupe (`app/src/lib/api.ts:23-33`) and module-level promise memoization (`app/src/lib/data.ts:28-32`).

**What's good.** Vite config matches current v2 docs exactly; file routing, `useParams`/`useSearchParams`-driven resources, `For`/`Show`/`createMemo` usage, and `APIEvent`-typed proxy routes are all idiomatic. URL-as-state on the home page is done cleanly (debounced `q`, `page` reset on filter change, `queryHref` preserving filters for pagination links — `app/src/routes/index.tsx:14-21, 76-82`). The moves section (game select, per-method tables, sortable headers with `aria-sort`) is careful, and `MoveTable` resets sort state when rows change. 404 handling via resource-returns-null → shared `NotFound` component is a tidy pattern.

**What I'd push back on.**
1. **Data layer reimplements framework features.** v2's recommended data API is `query`/`createAsync` (request dedupe + keyed cache + optional `"use server"`); the app hand-rolls TTL/inflight caching and `??=`-promise memoization. That's acceptable, but the memoization **caches rejections forever** (`data.ts:67`, `118`): one transient proxy/API failure during a session permanently blanks the home page with no error UI and no retry (`index.tsx:42` fallback is a bare `<h1>`).
2. **Un-aggregated fan-out.** Because `ssr: false`, every browser session re-runs the ~28-fetch home-data bootstrap (`data.ts:112,118`) through the proxy; a server-side `query` would amortize this across users and shrink time-to-content.
3. **Unguarded move fetch.** `data.ts:405` fetches every move detail with no catch; one failure rejects the `moveData` resource, which is never read for errors, leaving the moves section stuck on "Loading moves…" (`pokemon/[name].tsx:195`).
4. **`data.ts` is a ~420-line god module**, imported by every route, typed almost entirely `any` at the API edge, with the same `getSpeciesIndex → speciesById → dedupe → card` block duplicated three times (`data.ts:297`, `321`, `352`).
5. Small smells: `document.documentElement.lang = "en"` side-effect in `App` (`app.tsx:12`), `typeLabel` double-imported under two names (`data.ts:2`), a misnamed `moveNames` helper that applies `typeLabel` to move names (`data.ts:365`), `.map` in JSX instead of `<For>` (`index.tsx:132`, `PokemonCard.tsx:29`), and an untouched template `README.md` that doesn't record the `ssr: false`/proxy decision.
