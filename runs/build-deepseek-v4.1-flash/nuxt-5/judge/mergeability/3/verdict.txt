## Review notes

**Idiom** — This is recognizably textbook Nuxt 4: correct v4 `app/` srcDir layout (`app/app.vue`, `layouts/`, `pages/`), Nitro server routes with `server/utils` auto-imports, `useFetch`/`useAsyncData` with reactive getters, `useHead`/config-level `htmlAttrs lang`, typed `defineProps`/`defineEmits`, URL-as-state via `router.push/replace`, `:value`+`@change` instead of `v-model` for URL-backed selects. The internal `/api/app/*` aggregation layer with in-memory caching is the documented server-routes pattern and is genuinely good design for taming a 1,000-request PokeAPI. Two mild home-grown spots: `NotFoundPage` rendered inline in four detail pages instead of the framework error path (`throw createError` + `error.vue`), and a hand-rolled hash-scroll routine in `pokemon/[name].vue`.

**Correctness** — Debounce timer never cancelled on unmount (`index.vue:107`): type in search, click a card within 250 ms, and the pending `router.replace('/')` fires after navigation away. Unbounded `Promise.all` fan-out for move details in `getPokemonPage` (`pokeapi.ts:354`) — no `mapLimit` as used elsewhere; a big learnset (Mew, ~200+ moves) fans out hundreds of concurrent upstream fetches. Non-404 upstream errors degrade to the "Not found" page (500 conflation). Cold start: `getDexIndex` gates the first request behind ~1,100 upstream fetches at concurrency 48. Caches are unbounded but bounded by the fixed dataset, so acceptable.

**Structure** — `server/utils/pokeapi.ts` is a 550-line god data module every page flows through: cohesive and server-only (good boundary), but with module-level hidden caches, page-shaped (presentation) responses, and the `typeLabel` Map built identically in four functions. `displayNumber` is duplicated in two files. Pervasive `any` in both server utils and components throws away the end-to-end type inference that typed `$fetch` against server routes would give — the one place Nuxt 4's typed-fetch story is left on the table.
