## Review

**What this app is:** a Nuxt 4 SSR Pokédex. Pages (`app/app/pages/`) fetch from thin internal Nitro routes (`app/server/api/app/*`), which delegate all upstream PokeAPI access to a single module, `app/server/utils/pokeapi.ts`, that keeps promise-level in-memory caches and does the mapping/labeling server-side. This is a genuinely well-shaped boundary: the browser never sees PokeAPI shapes, never talks to the upstream host, and a change to the upstream API touches exactly one file.

**Currency of the stack.** `nuxt` is pinned to 4.6.3, which is literally the latest stable release (GitHub `nuxt/nuxt` releases, v4.6.3, 2026-10-27). `vue` 3.5.44 and `vue-router` 5.4.0 match exactly what Nuxt 4.6.3 resolves (`app/package-lock.json:6198` shows Nuxt depending on `vue-router ^5.4.0`), and the three-dependency `package.json` mirrors the official starter's dependency set. Data fetching uses `useFetch`/`useAsyncData` + `$fetch`, still the documented primitives (nuxt.com/docs/4.x/...), with reactive URLs and `query`/`watch` options on `app/app/pages/pokemon/[name].vue:85-88`. The Nuxt 4 `app/` srcDir layout, `NuxtLayout`/`NuxtPage`, `defineEventHandler`/`getRouterParam`/`getQuery`/`setResponseStatus`, typed `defineProps`/`defineEmits`, and a `compatibilityDate` are all current. No options API, no Vuex, no axios.

**Platform use.** Native `fetch` for all upstream calls (`pokeapi.ts:78-82`), `new URL` for parsing (`pokeapi.ts:65-67`), `Map`/`Set` for caches, native `<select>`/`type="search"` controls, a real `<table>` with `<caption>`/`aria-sort` for sorting, `loading="lazy"` + fixed dimensions on images (`PokemonCard.vue:12-19`), and design tokens via custom properties. The only hand-rolled piece is the 250ms debounce and a small concurrency limiter (`mapLimit`, `pokeapi.ts:98`), both of which have no platform primitive; fine. CSS is flat (no native nesting) — a minor missed simplification for ~680 lines, not a defect.

**Where it will age badly.** The achilles heel is the outgoing type boundary. `getPokemonPage`, `getMovePage`, `getAbilityPage`, and `getTypePage` are all typed `Promise<any | null>` (`pokeapi.ts:267, 432, 473, 506`), so Nuxt's generated route→`useFetch` response inference (a headline feature of the 4.x data layer) is forfeited; downstream everything devolves to `any` (`index.vue:64-67`, `MoveTables.vue:61`). Second, `VALID_TYPE_NAMES` (`pokeapi.ts:33`) hardcodes the 18 type names as a whitelist, whereas the spec defines them *exclusionarily* ("every type except stellar, unknown, shadow") and explicitly says the API is live data that changes — a Gen X type would silently vanish from every filter and list. Third, small data-coupling fragilities: generation order is derived from a regex for trailing digits on the API name (every current generation matches `0`, so the sort is accidentally correct), and per-species lookups are `Array.find` inside loops (O(n²) on move/ability pages). And the home page ships the entire 1,025-species index to every client for client-side filtering — instant UX, but the payload grows linearly with upstream data.

Net: architecture that upgrades cheaply, undermined by `any` at the one boundary that matters.
