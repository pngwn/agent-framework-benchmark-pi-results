## Review: test quality

**Facts on the ground.** The app contains zero tests of its own. `app/package.json` has no `test` script and no test tooling among its five dev dependencies (`app/package.json:6-19`); a grep for `vitest|playwright|jest|\.test\.|\.spec\.` across `app/` matches nothing, and there is no test config anywhere under `app/`. The only tests in the repo are the acceptance Playwright specs in `tests/`, which the agent didn't write. So `wroteTests` is false, and per the rubric `coverage_of_risk` and `regression_power` score 1, `behaviour_not_implementation` 1 (no tests), `signal_to_noise` 3 (no tests ⇒ 3 by definition).

**What that means in practice.** Every guard on this codebase is a slow, end-to-end Playwright run against a live API. The acceptance suite is decently broad (roles, URLs, sorting, live-data overlay), but it only exercises the paths the spec called out, and it will not protect the many pure functions and comparators here during a refactor. Reading the riskiest code, these are the behaviours nothing would catch breaking:

- **URL-state dual bookkeeping on the home page** (`app/src/routes/+page.svelte:35-96`). `search`/`selectedType`/`pageNumber` are component state seeded once at mount, and `syncFromUrl` only runs on `popstate` (`app/src/routes/+page.svelte:90-92`). Since SvelteKit reuses the route component, clicking the header `Pokémon` link (an href to `/`, `app/src/routes/+layout.svelte:6`) while filtered would clear the URL but leave the old filters rendered — a real latent bug the acceptance suite never triggers. Likewise `?page=999` is clamped for display (`currentPage`, line 53) but the URL keeps `page=999`.
- **The move-table comparator** (`app/src/lib/components/MoveTable.svelte:43-78`) — the single most intricate logic in the app: missing-values-last, direction flip, two tie-breaks, numeric vs locale string compare. The both-missing tie-break at line 63 is *not* flipped by `direction`, so a descending sort of an all-missing column stays ascending — exactly the kind of subtlety nothing pins down. The `{#each}` key `moveName + ':' + level` (line 111) can collide when a move appears twice in one table.
- **Triplicated "latest English flavor text" logic.** `latestEnglishFlavorText` is exported from `app/src/lib/server/pokeapi.js:52-56` but never called; both the Pokémon page (`app/src/routes/pokemon/[name]/+page.server.js:51-53,156`) and the move page (`app/src/routes/moves/[name]/+page.server.js:24-29`) re-implement the filter/`at(-1)`/whitespace-collapse inline. A refactor that fixes one copy (say, the `\f` collapse) will silently miss the others.
- **Error paths.** `+error.svelte` renders `Not found` for *every* error (`app/src/routes/+error.svelte:4-5`), so an API 500 surfaces as "Not found". `getJson` throws a bare `Error` on non-404 failures (`app/src/lib/server/pokeapi.js:27-29`) and the `memo` promise cache (`:8-18`) is unbounded and permanent. No test simulates API failure, timeout, or slow responses.
- **Dex index construction** (`app/src/lib/server/pokeapi.js:160-186`): species→generation mapping with `?? ''` fallback, type-slot ordering, form exclusion (`>= 10000`), and `cardsFromPokemonRefs` dedup/sort (`:216-236`) are all untested data transformation — the exact layer the prompt worries about. A bug in slot ordering or the generation map would produce subtly wrong filter results that only the acceptance suite's two or three spot checks might notice.

**What good tests here would look like.** `humanize` (`app/src/lib/format.js:1-5`), `idFromUrl`, `latestEnglishFlavorText`, the MoveTable comparator, and the filter/pagination derivation are all pure or near-pure and would be trivial to cover with Vitest in milliseconds — the cost of adding them was very low, which makes the omission more notable. The one mitigation: the app's logic is mostly in plain `.js` load functions and pure modules, so *adding* tests later is easy; the structure doesn't fight testability.
