## Review summary

**Framework currency check** (verified against npm + gracile.js.org, 2026-10-30): the app pins `@gracile/gracile@^0.11.0` — the current stable release (dist-tag `latest`). Its structure matches the current docs closely: `(home).ts` → `/` is a documented index convention; `routes/[name].ts` params, the `404.ts` route (Gracile's request pipeline explicitly falls back to a `/404/` route for unmatched URLs), handler-returns-props → `template(context.props.GET)`, `@gracile/gracile/server-html`, and the Hono adapter (`serveStatic` before `honoAdapter`) all read like the official examples. Gracile ships no CSR, so the full-page-navigation + small progressive-enhancement script is in keeping with the framework's MPA philosophy.

The problems are concentrated in the API client layer and small hygiene debt:

1. **`app/src/lib/api.ts:22`** — the non-OK path does `throw new Error(\`HTTP ${res.status} ${res.statusText}\`)`, but the variable is `response`; this throws a `ReferenceError: res is not defined` instead. It's masked by `tryApi`/`.catch` so 404s still render, but every "API failed" path is broken and logs garbage. The `ApiError` class at `api.ts:4-8` is dead code that was clearly meant to be used here.
2. **`app/src/lib/api.ts:25`** — rejected promises are cached forever in the module-level `Map`. A transient API error (or a 404 for a resource that later appears) is sticky until process restart, and `getMoveDetailsForGame` (`data.ts:283`) silently drops moves whose fetch failed — data disappears from tables with no signal.
3. **`app/src/routes/abilities/[name].ts:16`** — `.catch(() => null)` turns any upstream failure into a 404 "Not found" page; error vs. not-found is conflated across all detail routes via `tryApi`.
4. **`app/src/document.ts:12-13`** — asset URLs built with `new URL('./document.css', import.meta.url)` instead of the docs' explicit instruction to use "the full real path (relative to the project root)" (e.g. `/src/document.client.ts`). Vite's build rewrites it correctly (verified in `dist/server/entrypoint.js`), but it deviates from the documented pattern every starter uses.
5. Duplication/dead code: the Not-found markup is repeated in five places (`pokemon/[name].ts:55`, `moves/[name].ts:31`, `abilities/[name].ts:33`, `types/[name].ts:29`, `404.ts:11`) while the shared `notFound()` helper sits unused at `components.ts:43`; `sectionHeading` (`components.ts:50`) is also unused; `(home).ts:60-62` re-implements `idFromUrl`/`isSpeciesId` inline.
6. Pervasive `any` for the PokeAPI shapes (`data.ts` throughout, ~11 type lines total) leaves the external API contract untyped, and `data.ts:261` has a NaN edge (`??` doesn't catch `idFromUrl`'s `NaN`).

On the positive side: the server/client boundary is clean (client JS isolated in `client/interactions.ts`), concurrency is throttled everywhere via `mapLimit`, URL/filter state handling is correct and test-proofed (NaN page, invalid game, empty params), and the CSS is token-driven and consistent.
