I've reviewed the app end to end (routes, data layer, client script, build config, server) and cross-checked it against Gracile's current stable release (0.11.0, published April 2026 — the version pinned in `app/package.json:7`) and the official starter templates and annotated examples on gracile.js.org.

**What holds up well.** `app/server.mjs:7-12` is a near-verbatim match for the official "Minimal server (Hono)" starter (`gracile.getClientBuildPath` + `gracile.honoAdapter`); the `defineRoute` handler/document/template split with `responseInit.status = 404` and `context.props.GET` matches the docs' annotated examples exactly (`app/src/routes/pokemon/[name].ts:14-19`); file-based routes (`[name].ts`, `index.ts`, `(home).ts`) and the ambient `route-template-outlet` document are all textbook Gracile. The vanilla-MPA-with-global-client-script approach (`app/src/document.client.ts:1`, `app/src/client/interactions.ts`) is supported by the framework ("document.client.ts" is in the official starter) even though per-route `.client.ts` islands would be the more idiomatic cut. Lit is declared but never imported anywhere — dead weight on a "Gracile with Lit" project.

**Real bugs the tests wouldn't catch.**
- `app/src/lib/api.ts:24` throws with `` `HTTP ${res.status} ${res.statusText}` `` — `res` doesn't exist, so every non-OK response raises a `ReferenceError` instead of the intended error; the `ApiError` class at `app/src/lib/api.ts:8-12` is dead code.
- `app/src/lib/api.ts:19-27` caches the *promise*, so a rejected fetch (transient API hiccup) is cached forever — that URL fails for the life of the process, with no eviction.
- No timeout/abort on `fetch` (`app/src/lib/api.ts:23`): a hung API hangs the SSR response indefinitely.
- The home handler uses the throwing `api()` for its three base lists (`app/src/lib/data.ts:19,41,49`; `app/src/routes/(home).ts:45-47`), so an API outage produces an unhandled rejection → raw 500, with no error page anywhere (only `404.ts` exists).
- `app/src/routes/(home).ts:63-65` re-implements the URL-ID regex inline instead of the existing `idFromUrl`/`isSpeciesId` helpers (`app/src/lib/api.ts:38-47`) — same file, two sources of truth.
- The "Not found" template is copy-pasted into five route files while the `notFound()` helper at `app/src/lib/components.ts:44-49` sits unused; `getAbility` at `app/src/lib/data.ts:139` is also dead.
- `app/src/lib/data.ts:261`: `Number(detail?.order ?? idFromUrl(ref.url) ?? 0)` yields `NaN` when both are missing (a rejected version-group fetch), silently corrupting the game order.

All of these are one small round of review changes, not structural rework — the layering (`api` → `format` → `data` → `components` → routes) is coherent and each file is easy to navigate, though `lib/data.ts` is a 355-line god module every route depends on, `any` is used pervasively, and there are zero comments explaining magic numbers (255, 1530, 10000, concurrency limits 8/20/40).
