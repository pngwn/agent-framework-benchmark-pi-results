## Review

The app contains **zero tests of its own** — no test script in `app/package.json`, no test files anywhere under `app/` (confirmed by grep for `*.test.*`/`*.spec.*` and by the measured counts). All quality gating was done by leaning on the acceptance suite in `tests/`, which is broad but lives outside the app and won't guard future refactors of `app/`'s own logic.

That's a real loss here, because a large share of this codebase is *pure, trivially unit-testable transformation logic*:

- `humanize`, `latestEnglishFlavor`, `dexNumber`, `statLabel`, `displayValue` — `app/src/lib/format.ts:1-39`
- method ordering / row sorting for the moves tables — `app/src/lib/data.ts:225-283`
- evolution-chain recursion — `app/src/lib/data.ts:220-221`
- ID parsing and the `<10000` species rule — `app/src/lib/api.ts:37-43`
- pagination clamping (NaN, out-of-range, zero matches) — `app/src/routes/(home).ts:73-77`
- client-side table sorting and aria-sort toggling — `app/src/client/interactions.ts:66-92`

And the absence of tests has already let a genuine bug through: `app/src/lib/api.ts:22` throws `HTTP ${res.status} ${res.statusText}` inside a callback whose parameter is `response` — any non-OK API response raises a `ReferenceError` instead of the intended `Error`. It's masked today only because every caller wraps `api()` in `tryApi`/`.catch(() => null)`, so the blanket catch converts the `ReferenceError` into a "not found". The `ApiError` class at `app/src/lib/api.ts:8-12` is defined but never thrown — evidence the error path was written and then never actually exercised. One unit test (`api('nonexistent/')` rejects with status info) would have caught both.

Other latent risks with no local safety net: the promise-level cache in `app/src/lib/api.ts:27-33` caches *rejected* promises forever, so a single transient API failure poisons that resource for the process lifetime; the home route re-implements ID parsing with a subtly different regex instead of reusing `idFromUrl`/`isSpeciesId` (`app/src/routes/(home).ts:53-57` vs `app/src/lib/api.ts:37-43`); and `getMoveSectionData`'s fallback `Number(detail?.order ?? idFromUrl(ref.url) ?? 0)` produces `NaN` when a version-group detail fetch fails (`app/src/lib/data.ts:251`), making game ordering unstable — precisely the kind of edge the acceptance suite (happy-path Pikachu/Scarlet-Violet) won't revisit.

Since there are no tests, `coverage_of_risk` and `regression_power` score 1, `behaviour_not_implementation` scores 1 (no tests), and `signal_to_noise` is 3 per the rubric.
