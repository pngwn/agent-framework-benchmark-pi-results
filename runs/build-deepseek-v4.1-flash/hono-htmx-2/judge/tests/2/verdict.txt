## Review — Dimension: test quality

**Did the app write its own tests?** No. `app/` contains 8 files, all source/config — no test files, no test script in `app/package.json:6-11` (`build`, `start` only), no devDependencies, no runner (confirmed by the measured facts: `tests: {files: 0, cases: 0}`). The acceptance suite in `tests/` is the only guard, and it is heavily a happy-path, full-stack Playwright suite.

So `coverage_of_risk`, `regression_power` and `behaviour_not_implementation` score on what would be caught — which is almost nothing.

**What the acceptance suite does *not* cover, and the bugs that could hide there** — I read the riskiest code to check:

1. **Move-table column sorting is silently broken for two of seven columns, and nothing catches it.** `sortRows` looks up `a[sortKey]` (`app/src/views.mjs:236-238`), but the column definitions use keys `move` and `type` (`app/src/views.mjs:290-297`) while the row objects only have `moveName`/`moveDisplay` and `typeName`/`typeDisplay` (`app/src/views.mjs:425-434`). For those keys every value is `undefined`, so all rows are "missing" and the comparator falls back to `defaultCompare` — clicking the **Move** header on the Level Up table sorts by *level*, and clicking **descending** produces the *same ascending* order while `aria-sort="descending"` is announced. The acceptance test only asserts the `aria-sort` attribute, never the row order, for the Move column (`tests/specs/pokemon.spec.mjs:160-164`), so this ships. This is exactly the class of bug a 10-line unit test on `sortRows` would have caught.

2. **Filter/pagination composition** (`app/src/views.mjs:38-86`): type ∩ generation ∩ search ordering, `PAGE_SIZE` slicing, and the `page > totalPages → clamp` behavior (`views.mjs:66-67`) are only exercised via full page loads with valid inputs. A refactor that flips filter order or off-by-ones the slice (`start + PAGE_SIZE`) would only be caught on the specific fixtures the acceptance tests visit.

3. **URL-state serialization** (`homeUrl`, `app/src/render.mjs:89-97`): "omit empty/default params" is tested indirectly through htmx interactions, but not for direct loads like `/?q=&type=fire&page=0` or `page=abc`. `server.mjs:51-53` silently coerces junk `page` values to 1 — reasonable, but untested and undocumented.

4. **The in-memory API cache** (`app/src/api.mjs:45-77`): 404 cached as `null`, error paths delete the cache entry, in-flight dedupe via `pending`. This is load-bearing for the "live data" requirement (the overlay fixture test depends on it not over-caching), but it has zero direct tests. A refactor that, say, cached rejected promises or cached non-404 errors would break the app subtly and the acceptance suite would only catch it if the fixture happens to overlap.

5. **Alternate-form exclusion and mapping Pokémon→species** (`dedupeSortedPokemonEntries`, `app/src/views.mjs:159-171`; ability `hiddenById`, `views.mjs:236-247` in the ability renderer): the `id <= 10000` cut, dedupe, and the hidden-ability OR-logic across duplicate entries. Acceptance tests cover three or four representative species; a refactor changing the threshold or dropping the dedupe would pass for most inputs.

6. **Error paths**: `app.onError` renders the *Not found* page with status 500 (`app/server.mjs:137-140`) — a misleading UX choice, and untested. API failure, malformed query params, and the `renderNotFound()` branches at `server.mjs:77, 84, 92` are untested at unit level (only the 404 fixture URLs are covered end-to-end).

7. **Trivial-but-tweetable pure helpers with zero tests**: `humanize` (`app/src/api.mjs:11-16`), `formatDex`, `latestEnglishFlavorText` whitespace collapsing (`api.mjs:32-36`), `statLabel` (`api.mjs:198-205`). These are the *cheapest* things to test in the whole codebase and the most refactor-vulnerable (string munging), yet they're only covered transitively through full-page assertions.

Also worth flagging (maintainability, not testing): `renderMovePageByName`/`renderAbilityPageByName`/`renderTypePageByName` (`app/src/views.mjs:543-559`) are dead code — `server.mjs` inlines the same logic — and `section()`'s `sectionId` parameter (`app/src/render.mjs:88`) is never passed by any caller.
