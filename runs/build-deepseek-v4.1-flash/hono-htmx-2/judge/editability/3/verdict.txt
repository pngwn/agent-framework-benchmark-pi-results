I've read the whole app (`server.mjs`, `src/api.mjs`, `src/render.mjs`, `src/views.mjs`, `scripts/build.mjs`, `package.json`), the spec, and the Hono skill reference. The app is a small, layered, plain-JS Hono + htmx service: `api.mjs` (fetch + cache + formatters), `render.mjs` (layout + shared fragments), `views.mjs` (page data assembly + views), `server.mjs` (routes + htmx partial negotiation). Here's my assessment.

## Scenario walkthroughs

1. **Remove Abilities** — delete route `server.mjs:88-93`, its imports (`server.mjs:7`, `server.mjs:9-19`), `renderAbilityPage` (`src/views.mjs:250-279`), and the Abilities section's links inside `renderPokemonPage` (`src/views.mjs:~560`); optionally `getAbility` (`src/api.mjs:160`). No nav links point at it. Two files, ~5 edits — self-contained, but not "delete a route and a link", and the unused `renderAbilityPageByName` (`src/views.mjs:602`) lingers as a decoy.
2. **Sprite fix** — every card list renders through `cardGrid` → `pokemonCard` (`src/render.mjs:79`, `66-77`), which computes the sprite in exactly one place via `spriteUrl(id)` (`src/api.mjs:46`). One fix covers home, type, move and ability lists. (The card descriptors only carry `{id, name}`, so a fix needing the default Pokémon's actual sprite URL rather than the ID-pattern would require threading data through four list builders — the main latent risk.)
3. **Sort every card list by name** — four separate builders each own their own ordering: `getHomeData` (`src/views.mjs:69-73`), type page (`152-166`), move page (`223-235`), ability page (`258-265`, which hand-rolls its own id map instead of `dedupeSortedPokemonEntries`). One file, four spots, three different idioms.
4. **Items section** — reusable: `apiGet`/`fetchJson`/`memoize` (`src/api.mjs:49-102`), `section`/`cardGrid`/`layout`/`wrapPage` (`src/render.mjs`), `humanize`/`englishName`/`formatValue`. Copied: the catalog loader pattern (`loadTypeCatalog`, `src/api.mjs:104-135`), the list page (`renderTypesPage`, `src/views.mjs:131`), and the detail page shape (`renderMovePage`, `217-247`). Roughly half reused, half copy-adapted.
5. **Data source/caching change** — `API_BASE_URL`/`API_ROOT` (`src/api.mjs:1-2`), the cache/pending dedupe (`src/api.mjs:49-77`), `memoize` (`84-102`), `versionGroupCache` (`167-174`) and `spriteUrl`'s use of the base URL (`46`) all live in one module. One file owns it; minor wart: three separate caching mechanisms inside it.

## Criteria

- **removability: 4** — features are route + view pairs with no cross-links beyond their own page; Abilities removal is 2 files / ~5 edits (`server.mjs:88`, `views.mjs:250`, `views.mjs:602`). Dead `*ByName` wrappers are the only leftover-trap.
- **changeability: 4** — sprite, formatting (`formatDex`/`formatValue`/`statLabel`, `src/api.mjs:33-45`, `186-195`), and table sorting (`sortRows`, `src/views.mjs:283-305`) each live in one obvious place; deducted because card-list derivation is triplicated.
- **coupling: 3** — layering is real (api → render/views → server) and htmx negotiation is cleanly isolated in `server.mjs:55`, `117-124` with views taking a `partial` flag (`views.mjs:87`). But data assembly lives inconsistently in two layers (`server.mjs:73-93` fetches inline while `getHomeData`/`getPokemonPageData` sit in `views.mjs:37`/`534`), and the presentation layer imports API-config-tied `spriteUrl` (`render.mjs:1`).
- **abstraction_design: 3** — the primitives (`pokemonCard`, `section`, `typeBadge`, memoized catalogs) stretch well, but there is no abstraction for the app's most-repeated shape — "Pokémon cards from API references" — which is copy-pasted with per-view variations (`views.mjs:152-166`, `223-235`, `255-276`), and the half-built `*ByName` seam (`views.mjs:596-613`) was abandoned mid-design.
