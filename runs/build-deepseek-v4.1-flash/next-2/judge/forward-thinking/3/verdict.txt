## Review: forward-looking, Pokédex app (Next.js 16.4.3)

**Version currency.** `app/package.json:11` pins Next 16.4.3 — the current Active LTS stable (released 2026-10-16/23, includes the October 2026 security patches) with React 19.3.1. So the app is on the current release. The question is which *programming model* it uses, and here it lags: since Next 16.4 (2026-10-06), Vercel recommends Cache Components "as the best choice for every Next.js app", `create-next-app` scaffolds it on by default, and it "will become the default in Next.js 17" (nextjs.org/blog/next-16-4). The docs now file `dynamic`/`revalidate` segment configs under "Caching and Revalidating (Previous Model)" (nextjs.org/docs/app/guides/caching-without-cache-components) and they're rejected outright when `cacheComponents` is on. This greenfield app builds entirely on the previous model: `export const dynamic = 'force-dynamic'` in all 7 routes (`app/app/page.jsx:13`, `app/app/[...slug]/page.jsx:3`, etc.) plus `cache: 'no-store'` in `app/lib/api.js:36`. That guarantees a real migration — per-route Suspense boundaries plus `'use cache'` annotations — the moment the team wants the 17 model or its instant navigations.

**What ages well.** API-level usage is genuinely current: `params`/`searchParams` awaited as promises (`app/app/pokemon/[name]/page.jsx:133`), `useRouter`/`usePathname`/`useSearchParams` from `next/navigation` (`app/components/Filters.jsx:5-6`, `app/components/MovesSection.jsx:3-4`), `generateMetadata`, `Link` with explicit `prefetch={false}` on pagination (`app/app/page.jsx:130`). Platform use is strong: `URL`/`URLSearchParams` for parsing and query building (`app/lib/api.js:18`, `app/components/Filters.jsx:9`), native `type="search"`/`<select>` controls, `loading="lazy"` + width/height on sprites, a hand-made data-URI SVG placeholder instead of a library (`app/lib/format.js:5`), CSS custom properties, zero polyfills. Dependencies are irreducible: exactly `next`, `react`, `react-dom`, nothing else.

**Churn surface.** Data access is properly centralized in one module (`app/lib/api.js`, with `app/lib/cards.js` on top), env config in one place, no framework internals touched — upgrades to the data layer would be contained. But every route file carries its own rendering-mode config (7 copies of `force-dynamic`), `single()` is copy-pasted twice (`app/app/page.jsx:19`, `app/app/pokemon/[name]/page.jsx:30`), and there are no types at all (plain JS, `typeLines: 0`), so API-shape changes surface as runtime failures rather than build errors. The 404 is a catch-all route rendering a `<NotFound/>` component (`app/app/[...slug]/page.jsx:10`) instead of the framework's `notFound()` / `not-found.js` convention, which also duplicates "Not found" titles in every `generateMetadata`.
