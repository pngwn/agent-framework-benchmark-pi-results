## Review: experimentalness

**What's in the code.** The complete framework surface of this app is: `next/link` (with `prefetch={false}`), the three `next/navigation` client hooks (`useRouter`, `usePathname`, `useSearchParams`), App Router file conventions (`page.jsx` / `layout.jsx`), `use client`, `export const metadata` / `generateMetadata` with awaited `params`/`searchParams`, and the route segment config `export const dynamic = 'force-dynamic'`. Every one of these is a long-stable, fully documented API. There are zero `unstable_`/`experimental_` identifiers, zero experimental config flags (`app/next.config.mjs:3` sets only `reactStrictMode`), no canary or RC dependencies, and no newly-recommended model APIs.

**What the app deliberately did *not* do.** Next.js 16.4 (2026-10-06) promoted Cache Components (`cacheComponents: true`, `use cache`, `cacheLife`, `ensureStatic`, `navigation()`, `prefetch()`) to the recommended model for every app, with new `create-next-app` projects opting in and Next.js 17 slated to make it the default. This app keeps the classic model — which is still fully supported, and honestly the lower-risk choice for a spec that mandates request-time data fetching (`app/lib/api.js:33` uses `cache: 'no-store'`). The trade-off is a known migration debt: the docs state that route segment configs like `dynamic` are disabled under `cacheComponents` and "will eventually be deprecated", so the seven `force-dynamic` exports are the one thing that will have to change when the framework moves.
