## Review

**Context confirmed:** The app runs `next@16.4.3` (`app/package.json:7-13`), which is the latest stable release as of 2026-10-30 (16.4.3 shipped 2026-10-23; Next.js 16 is Active LTS, per endoflife.date/nextjs and nextjs.org release pages). Next.js 17 does not exist yet, so 16.4.x is the correct "current stable" baseline.

**What the code actually uses:**

- App Router conventions only: `layout.tsx`, `page.tsx`, `not-found.tsx`, `[...slug]/page.tsx` catch-all, `[name]` dynamic routes (`app/app/layout.tsx:24`, `app/app/not-found.tsx:3`, `app/app/[...slug]/page.tsx:1`). All stable since the 13/14 era.
- Async `params`/`searchParams` as Promises (`app/app/page.tsx:12-16`, `app/app/pokemon/[name]/page.tsx:27-28`, `app/app/types/[name]/page.tsx:11`). This is the *required* API in Next 16 — sync access was fully removed (nextjs.org/docs/app/guides/upgrading/version-16), so it's stable-and-mandatory, not experimental. Note it does *not* use the newer `PageProps<'/route'>` typegen helpers, i.e. it picked the older-stable typing style.
- Route segment config `dynamic = 'force-dynamic'`, `revalidate = 0`, `fetchCache = 'force-no-store'` (`app/app/layout.tsx:4-6`, repeated per-route, e.g. `app/app/page.tsx:4-5`). All long-stable segment configs. `fetchCache` is redundant belt-and-braces on top of `force-dynamic`, and these configs are exactly the ones that need rework if/when the app migrates to Cache Components (`cacheComponents`, PPR) — but that migration is opt-in in 16, so no risk today.
- `next/link` everywhere, `next/navigation#useRouter` in one client component (`app/components/MovesSection.tsx:3-4`), `Metadata`/`generateMetadata` (`app/app/layout.tsx:8`, `app/app/pokemon/[name]/page.tsx:24`). All long-stable.
- Zero `unstable_`/`experimental_` identifiers, zero config flags — `app/next.config.mjs:1-4` is an empty config; grep for `unstable_|experimental_|cacheComponents|use cache|cacheLife|updateTag|proxy|experimental_ppr|useOptimistic|useActionState` returned nothing.
- Deliberately avoids the "new" stack of Next 16 entirely: no Cache Components/`use cache`, no `next/image` (plain `<img>` via `PokemonCard`), no Turbopack-specific config, no React Compiler (`reactCompiler` is stable-but-off-by-default), no Server Actions, no `proxy.ts`. React usage is `useState`/`useMemo`/`useEffect` only (`app/components/HomeBrowser.tsx:4`).
- Client-side URL sync uses raw `window.history.replaceState` (`app/components/HomeBrowser.tsx:82-86`) rather than any newer router API — plain DOM API, no framework surface.

This is about as conservative a Next 16 app as you can write: the spec's "fetch everything at request time, treat the API as live" requirement is satisfied with the boring, long-stable no-store/dynamic configuration rather than reaching for the new Cache Components model. The trade-off is that if the team later adopts Cache Components (where `force-dynamic`/`fetchCache` are no longer valid idioms), the per-route config block is repeated in 6+ files and would need mechanical rework — a small containment nit, not an experimentalness problem.
