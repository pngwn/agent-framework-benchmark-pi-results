I've read the full app. The verdict for this dimension is straightforward on the facts: `app/` contains **zero tests of its own** — no test script (`app/package.json:6-12` has only `build`/`dev`/`start`/`typecheck`), no test runner or testing library in devDependencies, and no test files anywhere under `app/` (confirmed by `find`/`ls` and the measured `tests: 0`). The only safety net is the acceptance suite in `tests/`, which the agent was handed and which doesn't live in `app/`.

That's a real loss here, because this app is unusually testable and unusually risky to refactor:

- **The pure helpers in `app/app/lib/format.ts`** (`humanize` at :4, `latestEnglishFlavorText` at :21, `dexNumber` :34, `inMetres`/`inKilograms` :37-44, `orDash` :47, `statLabel` :49) are exactly the spec-pinned edge cases ("Mr. Mime" vs `mr-mime`, `\f` collapse, em dash) and are one-line vitest targets.
- **The home loader** (`app/app/routes/home.tsx:31-99`) does the riskiest logic in the app: three filters, alternate-form exclusion via `id <= 10000` (:54), pagination math with a `Math.min(requestedPage, totalPages)` clamp (:93) and slice (:94). An off-by-one in the slice or the clamp would silently shift every page and nothing in `app/` would fail.
- **URL state + debouncing** (`home.tsx:66-86`): a 250 ms debounce that `replace`s the URL and deletes `page` (:75). Stale `searchParams` in the closure, race with the `qFromUrl` sync effect (:61-64), or dropping the `page` reset would all pass today and only be caught by hand-testing.
- **Move table aggregation** (`app/app/routes/pokemon.tsx:169-262`) — the densest code in the repo: default game = highest `order` via `games[games.length-1]` (:202-204), method ordering `level-up/machine/egg/tutor` then alphabetical (:49-56, :244-252), level-up default sort (:254-263), and the `compareRows` missing-sorts-last-in-both-directions comparator (:60-77). That comparator plus the `aria-sort` toggle (:93-121) is precisely the kind of subtle spec behavior that breaks under refactor with no signal.
- **Duplicated alternate-form logic** (`app/app/lib/data.server.ts:113` `id > 10000` skip in `cardsFromRefs` vs an inline reimplementation in `app/app/routes/ability.tsx:26-34` with its own dedupe/hidden-merge). No test pins either copy, so a "cleanup" of one can diverge from the other — e.g. breaking the hidden-ability merge `existing?.hidden || entry.is_hidden` (ability.tsx:32).
- **The in-memory promise cache** (`data.server.ts:9-18`) deletes rejected promises — correct, but a refactor to cache the resolved value directly would make API outages sticky, and nothing would catch it.

Also worth noting: the framework made testing cheap. React Router v8 (the app's `react-router@^8.5.1`, current stable) ships `createRoutesStub` for rendering routes/components in isolation (reactrouter.com/start/framework/testing), and every loader here is a plain async function that can be called directly against a stubbed `fetch` — no server needed. Not writing even a handful of pure-function tests around `format.ts` and the home loader was an easy, cheap opportunity missed.

One incidental observation: `latestEnglishFlavorText` (format.ts:21-31) returns the last *non-empty* English entry, while the spec says the *last* English entry — a benign divergence, but exactly the sort of thing a pinned unit test would have forced a decision on. Similarly `type.tsx:52-54` sorts moves by humanized display name where the spec says "sorted alphabetically by name" (usually identical, occasionally not).
