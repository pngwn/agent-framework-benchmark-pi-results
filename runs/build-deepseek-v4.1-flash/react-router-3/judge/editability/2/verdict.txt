# Review: Editability of the Pokédex app (`app/`)

The app is Framework Mode React Router on the current stable line (`react-router@^8.5.1`, `@react-router/dev`, `app/routes.ts` — verified against the 8.5.1 release notes). Data access is centralized in one server-only module, formatting in one pure module, and UI in two shared components. The main editability liabilities are: pervasive `any` typing that discards the framework's generated `Route.*` types, a duplicated card-building loop in the ability route, two independent sprite-resolution paths, and a `notFound` sentinel pattern repeated in every route.

## Scenario walkthroughs

**1. Remove the Abilities pages** — Delete `app/app/routes/ability.tsx` and one line in `app/app/routes.ts:5`. But the feature also owns: the Abilities section and its loader block in `app/app/routes/pokemon.tsx:258`–`265` and `381`–`388`, the `hidden` flag rendered by `app/app/components/ui.tsx:69`–`71`, and the `hidden?: boolean` field on the shared `SpeciesCard` type (`app/app/lib/data.server.ts:86`). Five files, all small and greppable via `/abilities`/`is_hidden`. **Difficulty 3.**

**2. Fix the wrong-sprite bug** — Card sprites come from two independent paths: the species-ID URL pattern in `app/app/lib/data.server.ts:99` (feeds the ability, move and type lists via `getSpeciesCardMap`/`cardsFromRefs`), and the `front_default` override fetched per-Pokémon in `app/app/routes/home.tsx:90`. A fix in `data.server.ts` covers three lists, but a fixer must discover that home has its own path — one fix does *not* automatically cover every list, and the two paths can drift (they already disagree in behavior: only home consults the Pokémon record). **Difficulty 3.**

**3. Sort every card list by name** — Ordering by dex number is decided in three places: `app/app/lib/data.server.ts:117` (`cardsFromRefs`, serves move/type), `app/app/routes/ability.tsx:39`, and the implicit species-index order that home paginates over (`app/app/routes/home.tsx:86`–`89`). Sorting inside `PokemonCardList` (`app/app/components/ui.tsx:74`) would be one edit but would only re-sort the current 48-item page on home. **Difficulty 3.**

**4. Add an Items section shaped like Moves** — High reuse of the seams: `getResource`/`getList`/`cardsFromRefs` (`data.server.ts:54`, `:47`, `:106`), `displayName`/`orDash`/`titleFor` (`format.ts`), `PokemonCardList`/`TypeBadge` (`ui.tsx`), and the `NotFound` component. What gets copied is the per-route glue: the identical `meta` function, the `notFound` guard, and section markup (compare `move.tsx:17`–`55`). New `routes/item.tsx` + two lines in `routes.ts`. **Difficulty 4.**

**5. Change the API base URL / caching rules** — `API_BASE_URL`, the `absoluteUrl` resolver, the `/api/v2` path prefix, the media-sprite pattern, and the promise cache all live in `app/app/lib/data.server.ts:7`–`99`. Nothing else in `app/` knows the origin (grep confirms). The `.server.ts` naming also guarantees the data layer can't leak into client code. **Difficulty 5.**

## Criteria

**removability — 3.** The ability *route* is self-contained, but removing the feature ripples into four more files (`pokemon.tsx:258,381`, `ui.tsx:69`, `data.server.ts:86`) because one card variant flag lives in shared code. A pure "delete route + nav link" removal isn't available for any feature that touches the shared card abstraction.

**changeability — 3.** Formatting and naming fixes are exemplary — one place each (`format.ts:5,24,37`). But card-related rules are duplicated: card construction (`ability.tsx:22`–`31` vs `cardsFromRefs` at `data.server.ts:106`–`118`, differing only in the `hidden` flag), sprite resolution (`data.server.ts:99` vs `home.tsx:90`), and sort order (`data.server.ts:117`, `ability.tsx:39`). The N-times-fix risk is real but localized to two files each.

**coupling — 4.** Server/client separation is enforced by the `.server.ts` convention (`data.server.ts`) and the framework's loader boundary; UI components (`ui.tsx:32,60,74`) consume plain card objects, not API payloads; shared state is explicit loader data. The deduction: `any` erases every interface boundary — `PokemonCardList` takes `cards: any[]` (`ui.tsx:63`) even though `SpeciesCard` exists, and all loaders/meta are `({ loaderData }: any)` (`home.tsx:21,110`, `pokemon.tsx:142,292`), so payload-shape changes fail silently rather than at compile time.

**abstraction_design — 4.** The helpers are designed around the app's real variation: data-driven tables (`COLUMNS` `pokemon.tsx:70`, `FIXED_METHODS` `:31`, `RELATIONS` `type.tsx:16`), a cached generic fetch layer, and one card component stretching across four lists with a single `showTypes` flag. The miss: the ability route's hidden-ability variation was copy-pasted into its loader instead of extending `cardsFromRefs`, and `SpeciesCard.hidden` (`data.server.ts:86`) is a one-consumer flag tacked onto a shared type — mild boolean-flag creep.

**overall — 4.** Most changes land in one or two obvious, greppable files; the duplicated card/sprite/sort logic and the discarded type generation are the traps a maintainer will actually hit.
