I've read all of `app/`, the framework skill reference, and verified against the current stable React Router (v8.x, which is what's pinned). The app is a clean framework-mode layout with a single server data module, but it leaves the framework's route-type generation entirely unused.

## Scenarios

**1. Remove Abilities pages** — Delete `app/app/routes/ability.tsx`, drop one line from `app/app/routes.ts:7`, and remove the Abilities section + loader block from `app/app/routes/pokemon.tsx:258-266,381-391`. Nav (`root.tsx`) never links to abilities, so no unrelated files. Only dead code left behind is the `pokemon-card-hidden` CSS class only abilities cards set. Difficulty **4**.

**2. Deoxys sprite fix** — The shared card sprite is built from the species-ID URL pattern in one place (`data.server.ts:99`), so fixing it there covers the move/type/ability lists at once; but `home.tsx:90` separately overrides the sprite from a fetched Pokémon, so sprite knowledge lives in two places and the "real" fix has to reconcile both. Difficulty **3**.

**3. Sort by name on every card list** — All four lists render through `PokemonCardList` (`components/ui.tsx:56-68`), so a sort there (or a prop) is one edit — except the home list is paginated by dex in its loader, so whole-dataset sorting there also needs `home.tsx:74-75`. Difficulty **4**.

**4. Items section shaped like Moves** — New `routes/items.tsx` (copy `types.tsx` skeleton) and `routes/item.tsx` (copy `move.tsx`'s meta/notFound/loader-panel skeleton), plus two `routes.ts` entries. The reusable layers are genuinely shared: `getResource`/`cardsFromRefs` (`data.server.ts`), format helpers, `PokemonCardList`/`TypeBadge`, CSS panels. What gets copied is the per-route boilerplate (meta guard, notFound guard, panel sections). Difficulty **3**.

**5. API base URL / caching rules change** — Everything lives in `lib/data.server.ts`: base URL (`:7-9`), the promise cache (`:16-24`), and the media sprite pattern (`:99`). One file, three spots. Difficulty **5**.

## Criteria judgment

**removability — 4.** Features are one-route-per-concern with a central route table (`routes.ts:5-12`); ability removal touches only related files. No nav/footer entanglement. Not a 5 because `pokemon.tsx` embeds the Abilities section and loader block, and the shared `PokemonCardList` carries an `hidden`/`pokemon-card-hidden` concern (`ui.tsx:49-51`) only abilities use, which would linger as dead capability.

**changeability — 3.** Format helpers and the data layer centralize a lot (`format.ts:1-45`, `data.server.ts`), and card lists share one builder (`cardsFromRefs`). But the sprite rule is split between `data.server.ts:99` and `home.tsx:90`; the alternate-form `10000` cutoff is hardcoded in three files (`data.server.ts:111`, `home.tsx:45`, `ability.tsx:25`); and `dexNumber()` (`format.ts:28`) is dead while its logic is inlined at `ui.tsx:43` and `pokemon.tsx:307`.

**coupling — 4.** Routes consume narrow functions from `data.server.ts` and `format.ts`; components take prop objects; server/client split is clean (`.server.ts` module, all fetching in loaders). Marked down because `PokemonCard` re-declares the `SpeciesCard` shape inline instead of importing the interface (`ui.tsx:34-44` vs `data.server.ts:78-86`), and props/loaderData are `any` everywhere, so the seams are untyped and can't be verified by the compiler.

**abstraction_design — 3.** Where variation is real (cached fetch with 404→null, `MoveTable` with column-driven sorting, `PokemonCardList`, `TypeBadge`) the abstractions are well-parameterized with no boolean-flag creep. But the "resource detail page" pattern (meta guard, notFound guard, panel sections, `<count> Pokémon` section) is hand-copied across five route files (`move.tsx:18,27,55,80-91` etc.), and `ability.tsx:21-29` re-implements `cardsFromRefs` inline just to add the hidden flag — the helper could have absorbed that variation.

**overall — 3.** Easy to navigate and to remove things from, with genuinely shared data and UI seams, but pervasive `any` and several small duplicated rules mean every non-trivial fix needs a sweep of the route files rather than one verified spot.
