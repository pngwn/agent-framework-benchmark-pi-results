I've now read every source file, verified the framework guidance (React Router 8.5.1 is the current stable line; the app is on it), and checked the documented patterns for 404s, root `Layout`, `ScrollRestoration`, and route-module types against what this app actually does.

## Assessment

**What's good.** This is recognisably a framework-mode app, not a fight against the framework: `routes.ts` uses the current `RouteConfig`/`index`/`route` API with a splat catch-all (`app/app/routes.ts:1-9`); filtering/pagination/game selection is URL-driven and parsed in the loader (`app/app/routes/home.tsx:21-107`); `meta` uses the v8-correct `loaderData` arg (`app/app/routes/pokemon.tsx:22`); API access is centralized in a server-only module via the `.server.ts` convention with a rejection-invalidated promise cache (`app/app/lib/data.server.ts:11-30`), which is a clean client/server boundary, not a leak. Client state is seeded from loader data, so there are no hydration mismatches (`app/app/routes/home.tsx:111-112`), the search debounce cleans up its timer (`app/app/routes/home.tsx:127-141`), and there are no unescaped-HTML or XSS vectors anywhere.

**What I'd ask to change.**
1. The app-wide 404 convention is home-grown: loaders return `{ notFound: true }` and each component/meta re-checks it (`app/app/routes/pokemon.tsx:144`, `:27`, `:20`, `:31`), instead of the documented `throw data("Not Found", { status: 404 })` → `ErrorBoundary` pattern (reactrouter.com/8.5.1/how-to/status). It works deterministically, but it also means missing resources are served with HTTP 200 and the protocol is duplicated five ways.
2. The root `Layout` export is used only for the document shell; the site chrome lives in `App`, so when any loader throws, the root `ErrorBoundary` renders a page with no banner, navigation or footer (`app/app/root.tsx:86-108`) — precisely the duplication the `Layout` export exists to prevent, and a landmark loss the spec requires on every page.
3. ~70 `any` annotations sit exactly at the seams the framework's typegen is designed to type: `loader({ request }: any)` and `Home({ loaderData }: any)` (`app/app/routes/home.tsx:21`, `:110`), when `Route.LoaderArgs`/`Route.ComponentProps`/`Route.MetaArgs` from `./+types/*` are one import away. Strict mode on (`app/tsconfig.json:22`) is undermined by this.
4. Smaller nits: `HashScroller` reimplements hash scrolling that `<ScrollRestoration />` already performs, with magic double timers (`app/app/root.tsx:33-50`); `isbot` is a dead dependency since there's no custom `entry.server` (`app/package.json:14`); dex padding is duplicated instead of reusing `dexNumber` (`app/app/components/ui.tsx:52` vs `app/app/lib/format.ts:28`); `species.genera.find(... entry.language.name ...)` is unguarded against odd data (`app/app/routes/pokemon.tsx:273`); and an unknown `?type=` leaves the select showing "All types" while the list is empty (`app/app/routes/home.tsx:196-203`).

**Abstractions** are, on balance, a strength: one data module with a clear server-only boundary, pure format helpers, and small composable card/badge components. The only globally-problematic pattern is the `notFound` protocol above. **Readability** is good (files map 1:1 to routes, spec vocabulary in naming) but zero comments across 879 LOC leaves the clever bits (cache invalidation, scroll timers, method sort order) unexplained, and `pokemon.tsx` at 430 lines mixes a ~150-line loader with three view components.

Overall: solid, current-generation framework code I'd be comfortable owning, but with one round of changes requested before approving.
