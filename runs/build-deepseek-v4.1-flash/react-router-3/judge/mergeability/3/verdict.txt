## Review

**Structure and idiom.** This is a recognizable, well-organized React Router framework-mode app: `app/routes.ts` config (`app/routes.ts:1-11`), route modules with `loader`/`meta`, a root route that correctly exports `Layout` separately so `ErrorBoundary` renders inside the document shell (`app/app/root.tsx:10-30`), a server-only data layer correctly named with the `.server` convention (`app/app/lib/data.server.ts:1`), SSR on with `@react-router/serve` for production. Data loading lives in loaders, filters live in the URL as the docs recommend. That part reads like the framework's own examples.

Three things pull it away from a 5 on idiom:

1. **404 handling is a home-grown pattern, not the documented one.** The official guidance (skill `references/framework-mode.md:136`) says: "Missing record in a loader: throw `data("Not Found", { status: 404 })` and render the route `ErrorBoundary`." Instead, all four resource loaders return `{ notFound: true }` (`app/app/routes/pokemon.tsx:144`, `move.tsx:27`, `type.tsx:31`, `ability.tsx:20`) and components branch on it, with a duplicated `meta` guard in each file (`pokemon.tsx:26`, `move.tsx:20`, `ability.tsx:12`, `type.tsx:12`). Consequence: missing resources serve HTTP 200 (the spec calls 404 "encouraged", so not a spec failure, but it's the exact case the framework feature exists for), and the "not found" concept now exists in three shapes: the flag, the shared `NotFound` component, and a second hand-rolled page in the root `ErrorBoundary` (`root.tsx:70-90`).

2. **Type safety is configured but unused.** `tsconfig.json:13` sets `"strict": true` and `rootDirs` for generated `.react-router/types`, yet there is not a single `+types` import in the app; every loader arg and component prop is `any` (`home.tsx:21`, `pokemon.tsx:142`, `Home({ loaderData }: any)` at `home.tsx:109`). For a v8 TypeScript app this throws away the framework's flagship DX (generated `Route.LoaderArgs`/`ComponentProps` catch param typos and missing-404 regressions).

3. **`HashScroller` re-implements router behavior** (`root.tsx:30-49`): `ScrollRestoration` already scrolls to `location.hash` on navigation, and the double-schedule (`setTimeout(scroll, 0)` plus a 100 ms retry, `root.tsx:37-40`) is a timing hack to paper over hydration/layout shift rather than a documented technique. It works, but it's the kind of local workaround that lingers for years.

**Correctness.** One real race in the search flow: the input is synced from the URL with `setQ(qFromUrl)` whenever the loader result arrives (`home.tsx:125-128`). If the user keeps typing while a debounced navigation is in flight, the effect fires with the *older* committed `q` and clobbers the in-flight keystrokes; the debounce effect then sees `q === qFromUrl` and never commits them. Fast local API masks it; a slow connection makes search visibly revert. Minor items: the root `ErrorBoundary` renders raw `error.message` (`root.tsx:78-82`), which can leak internal details; an unknown `?type=` value yields an empty result set but leaves the `<select>` with a value matching no option (`home.tsx:193-204`). Caching is bounded by API cardinality and correctly self-evicts on rejection (`data.server.ts:11-19`); the per-page fan-out (48 `getResource("pokemon", …)` per home render, `home.tsx:80-96`) is cached and acceptable. `EvolutionList` keys, sort-state handling in `MoveTable`, and page clamping (`home.tsx:41`, `home.tsx:68-69`) are all sound.

**Abstractions and readability.** The layering is genuinely good: `data.server.ts` is the single API boundary (cache, id parsing, typed card/entry interfaces), `format.ts` is pure helpers, `components/ui.tsx` holds the three shared visual primitives. Nothing is a god module at this size. Small duplication: `ability.tsx:19-26` re-implements the dedup/exclusion loop of `cardsFromRefs` (`data.server.ts:96-106`) to add the `hidden` flag, instead of extending the shared helper. Zero comments and the `any` typing mean a reviewer must read loader bodies to learn data shapes; `pokemon.tsx`'s loader runs ~110 lines across six distinct concerns (`pokemon.tsx:142-290`).

**Verdict.** I'd approve the architecture, but I'd want a round of changes before merge: the documented `data(..., { status: 404 })` 404 pattern, generated `Route` types instead of `any`, the search race fixed, and `HashScroller` either removed or justified. All are contained changes — the foundation is worth building on.
