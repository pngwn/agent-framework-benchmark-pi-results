## Test quality review

The app contains **no tests of its own**. `app/package.json` defines only `dev`/`build`/`start` scripts and a single devDependency (`vite`) — no runner, no `test` script, no spec files anywhere under `app/` (confirmed by `find`/`grep`; the measured facts agree: 0 test files, 0 cases). Everything passes today only because the harness's acceptance suite in `tests/` exercises the rendered pages; the moment someone refactors the data layer, nothing in `app/` will catch a regression.

That's a notable miss because the codebase is unusually testable: `app/src/api.js` and `app/src/data.js` are pure, dependency-light modules with exported functions (`humanize`, `extractId`, `latestEnglishFlavor`, `buildSpeciesTypeMap`, `speciesIdsFromPokemonRefs`), and even the riskier UI logic in `main.js` is factored into named functions (`sortRows`, `defaultRows`, `readHomeFilters`, `homeUrl`, `prepareMoves`, `loadRowsForGame`) that could be unit-tested with plain fixtures. Adding vitest (a 10-line config against the existing Vite setup) would have covered the spec's trickiest rules — alternate-form exclusion, 48-per-page slicing, missing-values-last sorting, default-game-by-highest-order — at near-zero cost.

While reading for the `untested` list I also found two latent bugs that tests would have caught:

- **Game-select race** — `app/src/main.js:424-441`: the `change` handler mutates shared `state.selected` and then awaits `loadRowsForGame`. Two rapid selections run concurrently; the slower (older) fetch can resolve last, clobber `state.rowsByMethod`, and render rows for the wrong game. The `renderToken` guard only protects against route changes, not against this handler.
- **Error path conflates failure with not-found** — `app/src/main.js:816-824`: every non-ApiError-404 failure (network error, API 500, malformed JSON) renders the `Not found` page, so a transient API outage looks like a missing Pokémon with no retry or message.
