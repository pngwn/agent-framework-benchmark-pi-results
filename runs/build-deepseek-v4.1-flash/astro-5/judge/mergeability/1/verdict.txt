## Review

**Framework version check:** `app/package.json` pins `astro@7.4.4` + `@astrojs/node@11.1.9` — these are the current stable releases as of 2026-10-30 (Astro 7.4.4 shipped 28 Oct 2026; the node adapter's latest stable is 11.1.9). The config uses `output: 'server'` + standalone adapter, `src/pages/` file routing, `Astro.params` / `Astro.url.searchParams` / `Astro.response.status = 404`, and `Astro.self` recursion for the evolution tree — all still the documented, recommended primitives in v7. Nothing deprecated or removed in the v7 guide is used.

**What's good:** clean layout (`layouts/`, `components/`, `lib/`, `pages/`, `styles/`), small focused components, sensible error model (`ApiError` with `isNotFound()`), and a genuine attempt at progressive enhancement — the home page works without JS, and the filter/sort behavior is handled with modest vanilla scripts rather than pulling in a UI framework, which suits Astro's zero-JS-by-default philosophy.

**What I'd push back on before approving:** the home page is the weak point. It renders the card grid on the server, then ships the *entire* 1,025-species dataset inline as JSON (`app/src/pages/index.astro:53-58`, `:124` — roughly 140 KB per request) and re-implements `humanize`, the filter predicate, the pagination-URL builder and the card markup a second time in the client script (`:146`, `:188-224`, `:228-244` vs. `:31-47`, `:43`). Two sources of truth for the same UI will drift; a JSON endpoint + one shared module, or a small framework island, would fix both at once. Secondarily, the try/catch not-found block is copy-pasted verbatim across four dynamic pages, `set:html` on `JSON.stringify` is unescaped for `</script>`, and `[...path].astro` is a byte-for-byte duplicate of `404.astro` (one of them is dead code). Types are pervasive `any` with `strict: false`, so the TypeScript the project does define buys little.

None of this is reject-worthy — it's a competent, framework-faithful implementation with one real structural untangling to do.
