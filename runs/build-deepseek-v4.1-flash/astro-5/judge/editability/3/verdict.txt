I've reviewed the app against the spec, the Astro 7 docs (current stable is 7.4.4 — the app is on it), and walked each editability scenario through the actual files. Key observations:

**Architecture shape.** The app is idiomatic Astro 7: `output: 'server'` with the Node adapter (`app/astro.config.mjs:4`), thin pages over a single data layer (`app/src/lib/pokeapi.ts`), small props-driven components (`Section`, `PokemonCard`, `EvolutionNode`), and a well-sectioned global stylesheet. The data layer is the strongest part — `mapPokemonToSpecies()` (pokeapi.ts:246) is the one seam three different card lists flow through, and `getPokemonPageData`/`getPokemonMovesData` pre-shape page data into typed view models.

**The main drag.** The home page (`index.astro`) implements the whole pipeline twice: once in the frontmatter and once in a hand-written client `<script>` — `createCard()` at line 188 re-implements `PokemonCard.astro`'s markup and class names, `humanize` at line 146 duplicates `pokeapi.ts:56`, and filtering at line 228 duplicates line 31. Sprite derivation exists in three places (`PokemonCard.astro:16`, `index.astro:27`, `pokemon/[name].astro:54`). So the Deoxys-style bug fix would cover moves/abilities/types lists but not the home page, which carries its own sprite in a JSON payload (line 53/124).

**Smaller warts:** five memoized promise caches bypass the `api()` cache (pokeapi.ts:117–121); the 404 try/catch boilerplate is copy-pasted in four pages; `[...path].astro` and `404.astro` are byte-identical duplicates; `export const prerender = false` is repeated in all 8 pages although the docs say it's "not needed in 'server' mode"; `strict: false` plus pervasive `any` weakens refactor safety.
