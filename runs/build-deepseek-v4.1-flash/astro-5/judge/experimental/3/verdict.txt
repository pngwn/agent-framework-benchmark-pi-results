## Review: experimentalness

This app is about as far from the experimental edge as an Astro app can be, and in a good way for a codebase a team will own for years.

**What's there.** The entire framework surface is `output: 'server'` with the official `@astrojs/node` adapter in standalone mode (`app/astro.config.mjs:3-4`) — no `experimental` block, no flags. In the components and pages, the only framework APIs used are `Astro.props` (`app/src/layouts/Layout.astro:9`, `app/src/components/PokemonCard.astro:13`), `Astro.params` (`app/src/pages/pokemon/[name].astro:18`), `Astro.url.searchParams` (`app/src/pages/index.astro:15`), `Astro.response.status` (`app/src/pages/pokemon/[name].astro:30`, `app/src/pages/[...path].astro:7`), `Astro.self` recursion (`app/src/components/EvolutionNode.astro:17`), processed `<script>` tags (`app/src/pages/index.astro:127`), and `set:html` for the JSON payload (`app/src/pages/index.astro:124`). Every one of these has been stable since Astro 1–2.x; none of the v7-era APIs (advanced routing/`src/fetch.ts`, route caching/`routeRules`, CDN cache providers, CSP config) appear anywhere. Data fetching is plain `fetch` with a hand-rolled promise cache in `app/src/lib/pokeapi.ts:36-48` rather than any newer caching API.

**Version currency.** I verified against current sources: the app pins `astro@7.4.4` and `@astrojs/node@11.1.9` (`app/package.json:13-14`), which are both the exact latest stable releases as of 2026-10-29 (astro 7.4.4 released 2026-10-28 per astrobuild.eu release calendar and npm; @astrojs/node 11.1.9 published 2026-10-19 per npm). So the app is on the current stable major with zero canary/beta tags. I checked the official v7 upgrade guide (docs.astro.build/en/guides/upgrade-to/v7/): nothing the app uses is deprecated or removed in v7 — no `astro:transitions` internals, no Container API imports, no unified-markdown dependencies.

**One nit.** `export const prerender = false` is repeated in all 8 page files (`app/src/pages/index.astro:6`, `app/src/pages/404.astro:5`, the four `[name].astro` pages, etc.). Under `output: 'server'` (the config's setting) on-demand rendering is already the default, so these exports are vestigial noise — harmless and long-stable (stable since Astro 2.0), but they'd be deletable.

Verdict on this dimension: zero experimental/preview/RC/canary APIs; the app meets the spec (runtime HTTP fetching, SSR) entirely with long-stable APIs on a current stable release. Risk of framework churn breaking this code is minimal.
