I've now read the spec, all source files, and verified the Astro APIs used against the current docs and release notes. The app is on Astro 7.4.4 (current major, released 2026-06-22), but every framework API it touches predates Astro 5. Here's my assessment.

**What I verified:**

- **Config** (`app/astro.config.mjs:1-6`): only `output: 'server'` + `@astrojs/node` standalone. `output: 'server'` has been stable since Astro 5.0 (Dec 2024) and is the documented on-demand mode; the Node adapter's `mode: 'standalone'` is long-stable.
- **Render-context APIs**: `Astro.props`, `Astro.params`, `Astro.url.searchParams` (e.g. `app/src/pages/index.astro:15`, `app/src/pages/pokemon/[name].astro:18,37`) — stable since Astro 1.x. `Astro.response.status = 404` (`app/src/pages/[...path].astro:6`, each detail route) is the exact pattern shown in the current API reference (docs.astro.build/en/reference/api-reference), stabilized in Astro 4.9.
- **Template features**: `Astro.self` recursion (`app/src/components/EvolutionNode.astro:17`) and `set:html` (`app/src/pages/index.astro:124`) — both stable since Astro 1.0.
- **`export const prerender = false`** on every page (`app/src/pages/index.astro:6` and 7 more) — stable since Astro 4.0, but redundant under `output: 'server'`; the current docs literally annotate it "Not needed in 'server' mode".
- **New-in-7 features not used**: Astro 7's Advanced Routing (`src/fetch.ts`), stabilized route caching, and experimental CDN cache providers (astro.build/blog/astro-7, June 22, 2026) are all absent — the app is a plain SSR setup with a runtime `fetch` cache in `app/src/lib/pokeapi.ts:31-47`. No client framework, no view transitions, no `astro:actions`, no `astro:env`.
- No `experimental`/`unstable_` markers anywhere in config or source (confirmed by grep and by the measured facts).

**Verdict:** zero experimental, preview, RC or canary APIs; zero even "recently-stable" APIs (everything used has been stable for ~2+ years, with the possible exception of running on the brand-new Astro 7 major itself, which is a version choice, not an API choice). Risk of breaking-change churn from framework evolution is essentially nil for this codebase.
