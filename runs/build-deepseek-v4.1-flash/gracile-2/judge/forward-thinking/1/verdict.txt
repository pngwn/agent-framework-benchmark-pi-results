**Framework version/APIs.** `@gracile/gracile` 0.11.0 is the current stable release (npm `latest`; 0.11.1 exists only as `-next` prereleases), and the app pins it exactly. Every Gracile API in use matches the current docs and engine source I verified:
- `defineRoute` with `handler: { GET: async ({ url, params, responseInit }) => … }` — matches `app/src/routes/(home).js:26-36` against the documented handler-context shape (`packages/engine/src/server/request-pipeline.ts`: `request`, `url`, `responseInit`, `params`, `locals`).
- `html` from `@gracile/gracile/server-html` for the document vs. `lit`'s `html` for templates — the documented split (`app/src/document.js:1`, `app/src/lib/components.js:1`).
- `route-template-outlet` (`app/src/document.js:28`), `.client.js` sibling scripts, `(home).js`/`index.js`/`[name].js` file conventions — all per docs.
- `src/routes/404.js` — this is a real framework convention: `packages/engine/src/server/request.ts` falls back to `/404/` for unmatched routes (confirmed in engine source), so `/no/such/page` works without a catch-all route.
- `app/server.js:3-18` is verbatim the documented Express integration (`@gracile/gracile/node`, `getClientBuildPath`, `nodeAdapter`, locals middleware), not a legacy pattern.

**Build-time guard.** I confirmed in `packages/engine/src/vite/plugin-client-build.ts` that Gracile renders all routes (invoking handlers) during `vite build` to collect assets even in `output: 'server'` mode — so the `if (BUILDING()) return {}` guard is genuinely necessary to satisfy the "no build-time API data" rule. But it's an invented `process.env.GRACILE_BUILD` flag, copy-pasted into six route files, and 404.js doesn't have it — a churn hotspot.

**Dependencies.** vite `^8.3.5` is the current line (8.3.5 published Oct 2026, within Gracile's `^7 || ^8` peer range), lit `^3.3.3` is latest, express 5.x is the current major and the adapter Gracile documents. Nothing redundant, no dev-dep bloat.
