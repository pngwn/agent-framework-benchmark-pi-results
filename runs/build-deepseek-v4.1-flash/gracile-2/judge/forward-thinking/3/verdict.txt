## Review: forward-thinking

### Framework version & APIs (verified)

- `@gracile/gracile` **0.11.0** is the current stable release (npm registry shows `0.11.0 (latest)`, published ~Apr 2026, with only `0.11.1-next.*` pre-releases after it). The app pins it exactly — `app/package.json:7`.
- Route modules use the exact API shape from the current docs' annotated example (`defineRoute` from `@gracile/gracile/route` with `handler` / `document` / `template`, plus `route-template-outlet`) — `app/src/routes/(home).js:1,26,133,135`, `app/src/document.js:28`.
- The document uses `html` from `@gracile/gracile/server-html` (`app/src/document.js:1`), which the docs explicitly recommend for SSR-only rendering (avoids hydration markers).
- The server matches the official `minimal-server-express` starter almost verbatim: `gracile.getClientBuildPath()` + `gracile.nodeAdapter(handler)` (`app/server.js:7,14`) — confirmed against `gracile-web/starter-projects` on GitHub.
- Interactivity uses the documented "semi-static" layer (sibling `.client.js` scripts + DOM APIs, `app/src/routes/(home).client.js:1`) and deliberately avoids the client-side router / page-premises, which the docs mark "Experimental — not well tested, not customizable enough" and advise keeping disabled unless needed. That's the stability-correct current choice, not a legacy one.

### Notes worth the team's attention

1. **`app/src/document.js:14`** — the stylesheet href is `new URL('./document.css', import.meta.url).pathname`. This only works because Gracile's build extracts `<link>`s at build time into `routeAssets` (`app/dist/server/entrypoint.js:61` emits `/assets/document-CKJfxvWA.css`). The runtime expression itself never resolves to a servable URL (nothing under `dist/server/chunk/`). The docs' pattern is a plain source-relative href that Vite serves in dev and rewrites at build. This couples the app to undocumented build-time behavior.
2. **`BUILDING()` guard duplicated in 6 route files** (`app/src/routes/(home).js:15`, `pokemon/[name].js:23`, `moves/[name].js:18`, `abilities/[name].js:15`, `types/[name].js:13`, `types/index.js:7`) and wired to an app-invented `GRACILE_BUILD=1` env contract with `package.json`'s build script. The guard itself is justified (the document/template are evaluated during build to collect route assets, and the spec forbids fetching API data at build time), but it should be one shared helper in `lib/`, not a private convention copy-pasted six times.
3. **Untyped handler→template boundary.** All props flow as anonymous JS objects destructured with defaults (`app/src/routes/pokemon/[name].js:219-259` → `template` at `:262`). The framework is TS-first in docs; with `typeLines: 0`, a renamed prop breaks silently.

Everything else ages well: all HTTP/API access is behind one module (`app/src/lib/api.js` — promise-cache with error eviction, locale/i18n extraction, ID parsing), shared markup in `lib/components.js`, config only in `vite.config.js`, and the client code is platform-first (native `fetch`, `URL`/`URLSearchParams`, `history`, `DOMParser`, `crypto.randomUUID()`, `color-mix()` in `app/src/document.css:337`, logical properties, `localeCompare` with collation options).
