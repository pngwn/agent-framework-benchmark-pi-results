## Review

The app is a Gracile 0.11 (current stable, npm) MPA: `handler` → props → `template` per file-based route, a shared `document.js`, and two `.client.js` progressive-enhancement scripts. That shape matches the official starter idiom (`defineRoute({ handler: { GET: (ctx) => props } }, document, template)` and `context.props.GET`), and the pin `@gracile/gracile 0.11.0` is the latest release, so nothing here is fighting the framework.

**What makes it easy to change**
- All Pokémon cards funnel through one component: `app/src/lib/components.js:15` (`pokemonCard`) / `:41` (`pokemonCardList`). Every list on every page (home, moves, abilities, types) renders through it, so the sprite bug fix is one function and one URL builder (`app/src/lib/api.js:245`) — it covers all card lists at once. The detail page's artwork fallback at `app/src/routes/pokemon/[name].js:235` is the only other place sprite/media URLs are known.
- API base URL and caching live in exactly one file: `app/src/lib/lib/api.js:1` (`API_BASE`), `:3` and `:31-43` (request-dedup cache), `:246` (media base). Neither `server.js`, `vite.config.js` nor the client scripts know anything about them.
- Handlers normalize API payloads into flat view props and templates are pure functions of those props (`app/src/routes/moves/[name].js:31-44` → `:55-80`), so server data shape and markup changes are well separated.

**What makes it hard**
- The "don't fetch during build" policy is copy-pasted into every route: `const BUILDING = () => process.env.GRACILE_BUILD === '1'` appears six times (`app/src/routes/(home).js:15`, `pokemon/[name].js:23`, `moves/[name].js:18`, `abilities/[name].js:15`, `types/[name].js:13`, `types/index.js:7`), plus the `GRACILE_BUILD=1` incantation in `app/package.json`'s build script. A cross-cutting change to that policy is six edits.
- The not-found experience is duplicated five times: the `catch → responseInit.status = 404 → {notFound: true}` block (`app/src/routes/moves/[name].js:46-49`) and the `h1 Not found` template (`moves/[name].js:58-62`) are repeated near-identically in `abilities/[name].js:46,56`, `types/[name].js:72,82`, `pokemon/[name].js:275,285`, and `404.js:8,14` — and the home page invents a different 500 shape (`(home).js:101-112`).
- The `<h1 text> – Pokédex` title rule is re-implemented as a string in five handlers (`moves/[name].js:35`, `abilities/[name].js:38`, `types/[name].js:57`, `types/index.js:17`, `pokemon/[name].js:245`) rather than being composed once in `document.js`.
- Client scripts are coupled to server markup by stringly-typed DOM contracts with no shared constants: `(home).client.js:34,49` must know `id="home-results"` (emitted at `(home).js:165`), and `[name].client.js:11,36` must know `.move-table` + `data-sort-value` cells (`pokemon/[name].js:97-112`). Also `q/type/generation/page` query-param knowledge is duplicated between `(home).client.js:21-31` and `(home).js:22,37-41,76`.
- Cruft: unused exports `sortSpeciesById` (`api.js:222`) and `getApiBase` (`api.js:27`); an empty leftover `app/src/features/` directory; and one 588-line global `document.css` holding per-feature styles, so deleting a feature (e.g. `.hidden-ability`, `document.css:215`) needs a CSS sweep.

**Stretch test (Items section):** `getRecord` is generic (`api.js:49`), so `getRecord('item', name)` works with no new fetch code, and `englishName`/`englishEffect`/`displayValue`/`pokemonCardList`/`uniqueSpeciesFromPokemonReferences` are directly reusable. But the route scaffolding — BUILDING guard, error handler, not-found template, document wiring, title format — would be copied wholesale from `moves/[name].js`, i.e. ~40 lines of boilerplate per new section. `pokemonCard`'s options object (`showTypes`, `hidden` callback at `components.js:15-17,41-47`) is a good example of variation handled without flag creep, but there's no "resource page" abstraction above it.
