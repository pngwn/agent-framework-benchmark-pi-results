## Review: test quality

**No tests exist in `app/`.** `app/package.json:6-9` defines only `dev`, `build`, and `start` scripts — there is no test script, no test runner among the two devDependencies (`typescript`, `vite`), and static analysis confirms zero test files/cases. The acceptance suite in `tests/` is the only guard.

That's a real loss here because this codebase is unusually unit-testable for a no-framework app: `app/src/api.ts` is dominated by pure, dependency-free helpers (`humanize`, `englishName`, `latestEnglishFlavor`, `idFromUrl`, `formatDex`, `displayNumber`, `speciesFromPokemonList`, `speciesFromEntries`, `api.ts:131-247`) that encode exactly the spec's trickiest formatting/normalization rules, and the home page's filter/sort/paginate math (`home.ts:94-126`) plus the moves-table builder and sorter (`pokemon.ts:60-194`) are pure-in/pure-out given API fixtures. None of it is covered.

### What isn't tested, and the bugs it could hide

- **Home filtering + pagination math** (`app/src/pages/home.ts:94-126`): the search/type/generation predicates, `Math.ceil(filtered.length / PAGE_SIZE)`, `slice(start, start + PAGE_SIZE)`, and the page-clamp (`state.page > totalPages`). A refactor of the filter chain or an off-by-one in the clamp would ship silently. Related: `buildUrl` (`home.ts:16-25`) decides which query params get omitted at defaults — a regression here breaks deep links like `/?type=fire&generation=generation-i` without failing any unit-level check.
- **Moves-table assembly** (`app/src/pages/pokemon.ts:112-194`): filtering `version_group_details` by selected game, grouping by learn method, the `level-up/machine/egg/tutor/then-alphabetical` method ordering, and default row ordering. Note `loadMoveTables` swallows per-move fetch failures (`pokemon.ts:139-146`, `catch { return null }` → row silently dropped) — nothing would catch a change from "row skipped only on error" to "rows dropped routinely". Also `apiFetch<any>` (`pokemon.ts:141`) erases the type the rest of the file works hard to keep.
- **Column sorting** (`pokemon.ts:60-102, 328-345`): nulls-last in *both* directions, numeric vs `localeCompare` comparison, direction toggle on second click, and `aria-sort` placement. These are subtle rules with known failure modes (e.g., nulls jumping to the top in descending, string-comparing numbers) and are completely uncovered.
- **Species transforms** (`api.ts:220-247`): the `id > 10000` alternate-form exclusion is a bare boundary comparison with no test pinning it, and the hidden-ability merge (`existing.hidden || entry.is_hidden`, `api.ts:236`) is exactly the kind of boolean-accumulation logic that breaks in a refactor.
- **Text normalization rules**: `latestEnglishFlavor`'s whitespace collapse (`api.ts:146-151`), `englishName`'s humanize fallback (`api.ts:140`), `humanize` (`api.ts:135-139`) — the spec defines these precisely (e.g., "last en entry", `\n`/`\f` collapsed) and they're one-line regression targets.
- **Error paths**: a non-404 API failure and a 404 both render the same "Not found" page (`main.ts:66-72`), so a transient 500 would masquerade as a missing resource — no test distinguishes them, and the cache-delete-on-failure behavior (`api.ts:164-176`) is unverified.
- **URL/query round-trips and race guards**: `?game=` fallback (`pokemon.ts:231-234`), popstate re-render, the `gameRequest` stale-response guard (`pokemon.ts:351-358`), and `isActive()` token checks across `main.ts`/`home.ts`/`pokemon.ts` — regressions here (double-render, stale tables after rapid game switches) only show up in manual interaction.

### Verdict

For a PR into a codebase the team will own, I'd require at least a thin layer of unit tests over `api.ts`'s pure helpers and the sort/filter/paginate logic (Vitest would slot into the existing Vite toolchain trivially), plus one or two DOM-level tests for the moves tables. The acceptance suite passing proves the app works today; it proves nothing about the next refactor.
