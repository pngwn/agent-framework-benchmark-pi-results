The codebase is small and clean: a single data layer (`api.ts`), a single string-template component module (`components.ts`), one page module per area (`pages/home.ts`, `pages/pokemon.ts`, `pages/details.ts`), a ~90-line router (`main.ts`), and a separate static-file server (`server.mjs`) that injects `API_BASE_URL` at request time. Working through the five scenarios:

**1. Remove Abilities** — touches `app/src/main.ts:12` (import), `app/src/main.ts:64` (route branch), `app/src/pages/details.ts:77` (`renderAbilityPage`), `app/src/pages/pokemon.ts:295` (Abilities section on the Pokémon page), `app/src/components.ts:20` (`abilityHref`), `app/src/api.ts` (`AbilityRecord` + `speciesFromEntries`, used only by abilities), `app/src/style.css:242` (`.hidden-ability`). Six files, no dead code left behind, but scattered.

**2. Sprite bug** — every card renders through `pokemonCard` (`app/src/components.ts:48-52`), which builds its sprite via `spriteUrl` (`app/src/api.ts:210`). One fix covers home, moves, abilities and types lists. Caveat: cards carry only `{id, name}`, so a fix that needs the default Pokémon's actual `sprites.front_default` would require threading sprite data through `SpeciesRef` and the three list builders in `api.ts`.

**3. Sort cards by name** — default ordering is baked in at data-build time in three places (`api.ts:241`, `api.ts:266`, `api.ts:372`), and home paginates in `home.ts:update()` before rendering, so you can't just sort inside `pokemonCardList`. Two-to-three coordinated edits.

**4. Items like Moves** — Moves is `renderMovePage` (`details.ts:26-62`, ~35 lines) built entirely from reusable pieces: `apiFetch`, `englishName`, `englishShortEffect`, `detailRow`, `pokemonCardList`, `speciesFromPokemonList`, `escapeHtml`. An Items page is a new ~40-line function plus an `ItemRecord`, an `itemHref`, and one route branch — copy-then-adjust, but the copy is small.

**5. Data source change** — base URL lives in one client module (`api.ts:1-7`) plus the injector (`server.mjs:8`), and media URLs go through the same `API_ORIGIN` (`api.ts:210`). But caching rules are spread over five sites in `api.ts`: the `cache` Map in `apiFetch` plus four hand-rolled promise singletons (`speciesIndexPromise` 218, `generationsPromise` 285, `typeCatalogPromise` 323, `homeDataPromise` 355), each repeating the same `.catch(() => { x = null })` reset idiom.

Notable strengths: the `(main, url, name, isActive)` render signature is a consistent, narrow seam; the `renderToken`/`gameRequest` guards handle stale async renders correctly; server and client are cleanly separated. Notable weaknesses: `details.ts` is a grab-bag of unrelated pages; nearly zero comments despite non-obvious derivations (home-page per-species types are inferred from the *type catalog's* `pokemon` lists at `api.ts:355-372`); two `apiFetch<any>` calls (`pokemon.ts:144`); evolution links bypass `speciesHref` (`pokemon.ts:114`).
