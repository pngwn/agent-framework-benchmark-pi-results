I've read the full app: `api.ts` (types + fetch/cache + formatters + domain indexes), `components.ts` (shared HTML helpers + the single Pokémon-card renderer), `main.ts` (router), `pages/home.ts`, `pages/pokemon.ts`, `pages/details.ts` (moves, abilities, types, not-found), `server.mjs` (static server), and confirmed Vite 8 / TS 7 usage is idiomatic for a framework-less setup (no deprecated APIs in play; `history.pushState` + delegated-link routing and `<template>`-free string rendering are standard vanilla patterns today).

## Review

**Scenarios worked through**

1. **Remove Abilities**: touches `main.ts:37-43` (route + import), `pages/details.ts:61-86` (`renderAbilityPage`), `pages/pokemon.ts:293-338` (Abilities section on the Pokémon page), `api.ts:108-118` + `speciesFromEntries` (only abilities uses the entries shape), `components.ts:17` (`abilityHref`), and `style.css:242` (`.hidden-ability`). Five small, findable edits — but no directory to delete; the feature is spread across the "everything else" file, the data module, and the Pokémon page.
2. **Sprite fix**: every card in the app (home, move, ability, type lists) renders through `pokemonCard` at `components.ts:42-59`, which gets its sprite URL from `spriteUrl` (`api.ts:210-212`). One fix covers every list. The only caveat: cards receive only `{id, name}` (`SpeciesRef`), so if the fix needed real per-Pokémon sprite data rather than the ID pattern, `getSpeciesIndex`/`getHomeData` would need to plumb a sprite field through — still one seam, but two files.
3. **Name sorting everywhere**: lists all funnel through `speciesRefsFromPokemon` (`api.ts`, `speciesFromPokemonList`/`speciesFromEntries`) which sorts by id, but home has its own order via `getHomeData` + its own filter/slice pipeline in `pages/home.ts:96-124`. So it's 2 sort sites + possibly per-call-site choice, not N.
4. **Items section**: you'd reuse `apiFetch`/`englishName`/`humanize`/`escapeHtml`/`detailRow`/`pokemonCardList` wholesale, but the page itself means copying the ~40-line `renderMovePage` template (`details.ts:24-58`) into a new function plus a route in `main.ts` and an href helper — there's no generic detail-page abstraction to extend.
5. **Data source / caching**: base URL lives in `server.mjs:9-10,28-30` (env → injected global) and `api.ts:1-7` (global → env → hard-coded default) — exactly two places, cleanly separated. Caching, however, is five places in `api.ts`: the `apiFetch` promise cache (`api.ts:152-169`) plus four hand-rolled memoized loaders (`speciesIndexPromise`, `generationsPromise`, `typeCatalogPromise`, `homeDataPromise`), each repeating the same `catch(() => { x = null })` reset boilerplate.

**Strengths**: single card renderer, single fetch/cache, one router, consistent `escapeHtml` discipline, the pokemon↔species normalization (`speciesRefsFromPokemon`, `speciesFromEntries`) is exactly the right abstraction for the app's real variation, and the `isActive()` render-token pattern is applied uniformly for race safety.

**Weaknesses**: `api.ts` is a 300-line module doing five jobs (API types, fetch+cache, formatters, species/type/generation indexes, home-page data shaping); `pages/details.ts` is misleadingly named and holds four unrelated pages; `apiFetch<any>` + `record: any` in `loadMoveTables` (`pokemon.ts:140-152`) discards the typing the rest of the file pays for; hash-scrolling is duplicated in `main.ts:66-70` and `pokemon.ts:396-399`; and there are two identical `NamedResource`/`NamedAPIResource` interfaces (`api.ts:16-30`).
