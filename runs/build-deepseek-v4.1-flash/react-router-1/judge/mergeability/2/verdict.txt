I've reviewed the app, the spec, the framework-mode skill references, and verified React Router 8.5.1 is the current stable release (released 2026-10-27). Here's my review.

## Review

**Overall shape.** This is a competent, working Framework-mode app: `routes.ts` config (`app/app/routes.ts:1`), SSR enabled (`app/react-router.config.ts:4`), route modules with server `loader`s, `meta`/`links` exports in `root.tsx`, `useSearchParams` for URL state, and — nicely — a `.server.ts` module (`app/app/lib/api.server.ts:1`) that correctly keeps Node-only fetch code out of the client bundle. The framework's recommended practices are followed in most places.

**Where it departs from the docs:**

1. **404s are faked, not thrown.** Four loaders return `{ notFound: true }` and the component renders a shared `<NotFoundPage />` (`app/app/routes/pokemon.tsx:14-17`, `move.tsx:5-10`, `ability.tsx:5-10`, `type-detail.tsx:5-10`). The framework-mode reference is explicit: *"Missing record in a loader: `throw data("Not Found", { status: 404 })` and render the route `ErrorBoundary`."* Here unknown names return HTTP 200 with a hand-rolled branch duplicated four times, plus a duplicated `loaderData?.notFound` branch in four `meta` functions.

2. **Generated route types are configured but never used.** `app/tsconfig.json:3-4` includes `.react-router/types/**/*` and sets `rootDirs`, yet the route modules type their loader args and props as `any` (`app/app/routes/pokemon.tsx:13,23`) or hand-derive them (`app/app/routes/home.tsx:16`). The docs make `Route.LoaderArgs` / `Route.ComponentProps` from `./+types/<route>` the default; here `strict: true` is undermined by `any` throughout the largest module.

3. **Boot-time index promises never recover from failure.** `typeInfosPromise`, `generationInfosPromise`, `speciesIndexPromise` and `homeDataPromise` (`app/app/lib/api.server.ts:65,82,96,174`) are module-level IIFEs with no rejection handling. A transient API hiccup at boot rejects them permanently (they're memoized forever), and because they're started at import and not yet awaited, the rejection surfaces as `unhandledRejection` — which kills the Node server by default. Contrast with `fetchJson` (`api.server.ts:37-40`), which correctly evicts the failed cache entry so later requests retry. That resilience just wasn't extended to the top-level indexes.

4. **Every search keystroke is a server round trip.** `onSearch` calls `setSearchParams` per keystroke (`app/app/routes/home.tsx:49-63`), which navigates the home route and — since there's no `shouldRevalidate` — re-runs the home `loader` and re-serializes the entire 1025-species dataset (~hundreds of KB of HTML + hydration payload) for every character typed. A `shouldRevalidate: () => false` (the data is param-independent) or a `clientLoader` would fix it; neither appears anywhere in the app (grep confirms no `shouldRevalidate`, `clientLoader`, or `ErrorBoundary`).

**Other findings:** `lib/api.server.ts` is a 520-line god data module that eagerly builds every page's indexes at import, so a request to `/types` warms the entire home dataset too (`api.server.ts:174`); `Card` in `components.tsx:29` duplicates `PokemonCard` in `api.server.ts:117`; the `page` display is clamped to `totalPages` while the URL still says the out-of-range value (`home.tsx:82-86`); and compiled `build/` artifacts are committed to the repo. On the plus side, `format.ts` is a tidy, well-named pure module, the `Section`/`PokemonGrid` components are small and reusable, and the live-overlay concern (species beyond ID 1025) is explicitly handled (`api.server.ts:143-150`).
