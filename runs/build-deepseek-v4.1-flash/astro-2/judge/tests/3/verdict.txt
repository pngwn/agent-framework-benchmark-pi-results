## What the acceptance tests will stop guarding once the app is refactored

The app has substantial pure-logic and data-shaping code that is a single keystroke away from silent breakage:

**Pure helpers (ideal unit-test targets, all untested)** — `app/src/lib/pokeapi.ts:64-73` `humanize` (spec-critical: `mr-mime` → `Mr Mime`), `:76-82` `englishName`, `:90-98` `latestEnglishFlavorText` (whitespace-run collapse via `/\s+/g`), `:103-116` `formatHeight`/`formatWeight` (`(x/10).toFixed(1)` — an off-by-ten or rounding change renders wrong on every page), `:123-125` `dexNumber` zero-padding.

**Home filtering/pagination/URL state** — `app/src/pages/index.astro:20-41` combines search/type/generation filters, clamps `page` to `[1, totalPages]`, and slices 48-per-page; `:43-49` `pageHref` reconstructs the query string, omitting defaults. Refactoring the filter predicate or the clamp breaks only what the acceptance tests happened to assert.

**Home client-side behavior has an actual latent bug nothing would catch** — `app/src/pages/index.astro:96-160`: the script `pushState`s after each debounced fetch and swaps `#results.innerHTML`, but installs **no `popstate` handler**. Pressing Back reverts the URL but leaves the DOM showing the *newest* filter results (and the search input keeps its value) — stale view on history navigation. A single integration test exercising Back would have caught this.

**Pokémon moves pipeline** — `app/src/pages/pokemon/[name].astro:87-160`: default game = highest `order` (`gameGroups[gameGroups.length-1]`, relies on the sort at `:106`), `?game=` matching, method ordering via the `priorities` map (`:141-153`), level-then-name row sort. The default-game selection depends on the sort actually being stable in direction — one flipped comparator and the wrong game's moves render with no test failing.

**Client-side table sorting** — `app/src/pages/pokemon/[name].astro:355-393`: missing-values-last in both directions relies on `data-power` etc. being `''` when `?? ''` at `:326-331`; `aria-sort` toggling and numeric vs `localeCompare` branches are behavior no internal test pins down.

**Cross-resource index construction** — `app/src/lib/data.ts:129-171` `getHomeIndex` builds `generationBySpecies` and `typesByPokemon`, excludes alternate forms (`id > 10000`), and slot-sorts types. Also `app/src/pages/abilities/[name].astro:42-49` de-dupes per-species hidden flags with `||`. All of the "alternate forms excluded" spec rules live in scattered magic-number filters (`id > 10000` / `id <= 10000` at `data.ts:154`, `types/[name].astro:72`, `moves/[name].astro:59`, `abilities/[name].astro:47`) with nothing pinning the boundary.

**Error/not-found paths** — `app/src/lib/pokeapi.ts:39-47` maps 404 to `NotFoundError`, every page catches it (`pokemon/[name].astro:27-36` etc.); but a non-404 API failure (500, network) rethrows and yields a raw SSR 500 with no user-facing page — untested and a realistic production failure mode.

**Concurrency helper** — `app/src/lib/pokeapi.ts:117-131` `mapLimit` worker-pool; correct today, but a subtle refactor (e.g. removing the `index` capture) would deadlock or drop results silently.

Astro itself supports testing (Vitest + the Astro container API for component/page testing against Astro 7), and the app is an SSR Node adapter (`app/package.json:6-11`), so route-level tests are cheap to add. Their total absence in an app with ~750 lines of script/logic is the headline finding.
