I've now read every source file in `app/`, the spec, and checked the framework APIs against current releases (`hono` 4.13.x tagged templates via `hono/html`, `@hono/node-server` 2.x `serve`/`serve-static`, htmx 2.x — all the APIs used here are current and idiomatic, so nothing dings editability on framework grounds). My judgment is driven by how the code is factored, not by outdated usage.

## Review

**Structure.** The app is four modules with genuinely clean seams: `lib/api.mjs` is the only place that knows the API base URL, the cache, and URL construction; `lib/format.mjs` is pure string/label logic; `views/layout.mjs` holds the shared shell and the `pokemonCard`/`section`/`typeBadge` components; `server.mjs` is routes plus everything else. The data/format/layout split is the strongest thing here — changing the API base or caching rules (scenario 5) touches exactly one file (`app/lib/api.mjs:3,8-14,38-50`).

The weakness is that `server.mjs` is an 820-line monolith: every page's markup is inlined in its route handler (`renderPokemonPage` at `server.mjs:339`, the move page at `server.mjs:604-650`, abilities at `server.mjs:652-700`, types at `server.mjs:728-780`), alongside sorting, filtering, pagination and htmx endpoint wiring. `views/layout.mjs` proves the author knew how to extract view modules; the per-page templates just never got the same treatment.

**The concrete scenarios:**

1. **Remove Abilities** — route at `server.mjs:652`, the linking section at `server.mjs:398-412`, the `getAbility` import and getter (`server.mjs:9`, `lib/api.mjs:105`). Then dead code is left behind: `pokemonCard`'s `hidden` param (`views/layout.mjs:50,62`) and its CSS (`public/styles.css:254`), plus `.hidden-inline` (`public/styles.css:460`). Four files, small edits, residue — a solid "3".
2. **Sprite fix** — every card list renders through one component, `pokemonCard` (`views/layout.mjs:44-64`, sprite at line 47 via `spriteUrl(species.id)` from `lib/api.mjs:110-116`), so one fix covers home, moves, abilities and types. The only wrinkle: the species catalog carries only `{id, name}` (`lib/api.mjs:76-92`), so a fix that needs the default variety's identity would also touch the catalog loader.
3. **Sorting by name on all card lists** — the ref→dedupe→sort→cards logic is *triplicated*: shared helper `speciesCardsForRefs` (`server.mjs:87-106`, used only by moves at `server.mjs:615`), plus hand-rolled copies in abilities (`server.mjs:672-687`) and types (`server.mjs:742-757`), and the home route's own pipeline (`server.mjs:432-470`). Any cross-list change is an N-place edit.
4. **Items section like Moves** — `renderLayout`, `section`, `countText`, `pokemonCardGrid`, `speciesCardsForRefs` and the `getMove` getter pattern (`lib/api.mjs:101-103`) are all reusable; the page template itself is inlined in the route, so it's copy-adapt (~45 lines).
5. **Data source change** — one file, `lib/api.mjs`.

**Abstraction design.** The components are well-shaped around real variation: `pokemonCard`'s optional `types`/`hidden` params match the spec's actual per-page card differences rather than boolean-flag creep, and `renderMoveTable` is shared by both the full page and the htmx sort partial (`server.mjs:244`, used at `server.mjs:545-567` and via `renderMovesSection` at `server.mjs:322-328`), so the two can't drift. Against that: `speciesCardsForRefs` has a speculative, never-used `hiddenBySpecies` flag (`server.mjs:87,100-103`) that the abilities route bypasses by duplicating it inline; `capitalize` is dead (`lib/format.mjs:63`); and `methodLabel` is used to humanize damage *categories* (`server.mjs:198,288`), a misleading name to trip over when editing.
