## Review — `app/` (SolidStart Pokédex), dimension: editability

**Framework fit.** The setup matches SolidStart v2's current stable guidance: `vite.config.ts` uses `solidStart()` + `nitro()` from `nitro/vite` exactly as the docs prescribe, data goes through `query()` + `"use server"` functions consumed with `createAsync`, and state lives in URL search params rather than client stores. Nothing here is stale-idiom.

**What holds up well.** The server/client seam is unusually clean: every byte of API knowledge — base URL (`app/src/lib/queries.ts:132`), caching (`queries.ts:130`), sprite URL construction (`queries.ts:184`) — lives behind `"use server"` query functions, and components receive serializable DTOs. The sprite scenario is the best case: all four card lists are built through one `cardSpecies()` call (`queries.ts:188`), so a sprite fix lands in one function and covers everything.

**What drags.** The "turn API refs into Pokémon cards" pipeline (exclude `id > 10000`, resolve species, dedupe, sort) is copy-pasted three times (`queries.ts:364-371`, `413-420`, `450-463`), the English-effect fallback twice (`queries.ts:422-430`, `465-473`), and the `<ul class="pokemon-grid">` card-list markup four times across routes. Adding name-sorting to every list, adding an Items section, or changing card contents all mean touching 3–4 files. `queries.ts` is also a ~700-line module mixing cache infrastructure, DTO types, and six query functions — deleting a feature (Abilities) leaves dead exports there plus a now-unused `hidden` prop on `PokemonCard` and `.hidden-note` CSS.
