## Review

The app is on **current stable SolidStart v2.1.0** (released 2026-10-22) with Vite 8 and the `nitro()` Vite plugin in `vite.config.ts` — exactly the v2 layout. Data fetching uses the currently documented pattern (`query` + `"use server"` bodies in a shared module, `createAsync` in routes, `Suspense` in the root), so nothing I'd flag as outdated.

What makes this code easy to change:

- **One data seam.** All API knowledge lives in `app/src/lib/queries.ts`: base URL (`apiBase`, queries.ts:132), in-memory cache (`jsonCache`/`fetchJson`, queries.ts:130, 154-171), sprite URL construction (`spriteForId`/`cardSpecies`, queries.ts:184-193). Every Pokémon card in every list — home, move, ability, type — flows through `cardSpecies`, so the Deoxys-style sprite fix (scenario 2) is genuinely a one-function change covering all four lists.
- **Routes are thin views over typed query results** (`routes/moves/[name].tsx:38-64`, `routes/types/[name].tsx:13-56`), components take plain props (`components/PokemonCard.tsx:10-15`), and `format.ts` holds pure helpers. Server ("use server" query bodies) and client (signal/memo UI logic in `routes/index.tsx:83-105`) are cleanly separated.

What makes it harder than it needs to be:

- **The "resolve refs → exclude forms >10000 → directory lookup → dedupe → sort by id" block is copy-pasted three times** (queries.ts:364-371, 413-420, 450-463), and the `<count> Pokémon` + `<ul class="pokemon-grid">` card-list markup is duplicated in four route files (`routes/moves/[name].tsx:53-58`, `routes/abilities/[name].tsx:20-25`, `routes/types/[name].tsx:38-46`, `routes/index.tsx:194-201`). An Items section (scenario 4) would clone both a fifth time; sorting by name (scenario 3) means editing four independent sort sites.
- **The route skeleton (createAsync + `Show when={data() === null}` → NotFound) is repeated in all four detail routes** (`routes/moves/[name].tsx:69-82`, `routes/abilities/[name].tsx:38-51`, `routes/types/[name].tsx:62-75`, `routes/pokemon/[name].tsx:158-176`), so changing 404 handling is a 4-file change.
- **URL schemes are scattered**: `/pokemon/` is hard-coded inside `PokemonCard.tsx:16`, `/moves/` inside `MoveTable.tsx:66`, `/types/` inside `TypeBadge.tsx:11`, plus inline in the routes.
- **`MoveTable` renders columns via magic-string `if (column.key === ...)` matches against `MoveRowData` fields** (`MoveTable.tsx:57-78`) while the column list is built server-side (queries.ts:636-646) — adding a column needs coordinated edits in two files with no compiler help.
- Minor: `TypeBadge` derives its CSS variable name from the API type name (`--type-${props.name}`, `TypeBadge.tsx:8-10`), an implicit contract with `tokens.css`; and `PokemonCard`'s `hidden` prop bakes ability-domain text ("Hidden ability") into the generic card (`PokemonCard.tsx:11, 23-26`), which is also dead code once Abilities is removed.

Removability of Abilities (scenario 1) is the weakest spot: nav is clean (`app/src/app.tsx:23-26`), but removal means the route directory, one query + interface in the shared module (queries.ts:444-480), the Abilities section on the Pokémon page (`routes/pokemon/[name].tsx:104-117`), plus dead `hidden` prop/CSS left in `PokemonCard.tsx` and `app.css:226` — a handful of scattered edits.
