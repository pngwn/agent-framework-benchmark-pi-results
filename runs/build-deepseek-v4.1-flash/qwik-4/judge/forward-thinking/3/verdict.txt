I've now verified the key facts: the app pins `@builder.io/qwik`/`@builder.io/qwik-city` at `^1.20.3`, which is exactly the latest stable release (per learn-qwik.com/releases, Oct 25, 2026), and its devDependencies are a verbatim match for the current `create-qwik@1.20.3` base starter (confirmed via unpkg), so the toolchain is the framework's own current baseline with zero additions. All framework APIs used (`routeLoader$`, `useComputed$`, `useSignal`, `DocumentHead` with `resolveValue`, `useLocation`, `useDocumentHead`, `qwikCity`/`qwikVite` vite plugins, `eslint-plugin-qwik` recommended config) are current per qwik.dev's docs and deprecated-features page; notably the app picked `useComputed$` over the older `useTask$`/`useResource$`, and the Qwik v2 upgrade guide confirms `useComputed$` is the API v2 builds on (async-capable) while `useResource$` is deprecated. Qwik v2 (renamed `@qwik.dev/*`, AsyncSignal loaders) is only at RC status, so building on 1.20.3 is correct.

The forward-looking weak spots are all in how URL state and the data layer are handled, not in API choice: the home page mutates the URL with raw `window.history.replaceState` (app/src/routes/index.tsx:63-68, 86-92, 104-109), which leaves Qwik City's `useLocation()` signal stale and means browser back/forward won't re-sync the filter signals; the moves game selector does a full `window.location.assign` reload (app/src/routes/pokemon/[name]/index.tsx:397-403), throwing away SPA navigation where `useNavigate` is the supported primitive; and `fetchJson` (app/src/lib/data.ts:66-78) has no `AbortSignal`/timeout and swallows every error to `null`, and the whole API boundary is typed `any` with `no-explicit-any` turned off (app/eslint.config.js:74-78).
