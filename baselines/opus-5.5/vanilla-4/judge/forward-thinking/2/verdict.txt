## Review: forward-thinking — Pokédex vanilla TS + Vite app

**Toolchain currency.** `app/package.json` pins `vite ^8.3.5` and `typescript ^7.0.2` — exactly the current stable releases as of 2026-10 (Vite 8.0 GA'd 2026-03-12 with Rolldown as the unified bundler, current minor is 8.3.5; TypeScript 7.0, the native Go port, GA'd 2026-07-08, 7.0.2 is the stable tag with 7.1 still in beta). The lockfile (`app/package-lock.json:10`) resolves real Rolldown/oxc native bindings, so the build genuinely runs on the Rolldown pipeline. `build` is the idiomatic `tsc --noEmit && vite build`, which under TS7 means the native compiler does type-checking — no legacy flags in `app/tsconfig.json` (modern `moduleResolution: "bundler"`, strict). There's no `vite.config` at all (configLoc 0): zero-config is the right call for an app with no plugins or custom transforms, so there's no boilerplate for a newer Vite scaffold to regenerate differently.

**Latest APIs.** There are no framework-level APIs beyond Vite itself, so this criterion mostly reduces to Vite/TS currency plus not using anything superseded. Nothing here is legacy-era. One deliberate architecture choice deserves credit: instead of the conventional `import.meta.env` build-time injection, the app injects `window.__API_BASE_URL__` at request time from `app/server.mjs:26` into a `<!--app-config-->` placeholder in `app/index.html:6`. That's not just idiomatic — it's the only correct option given the spec's requirement that one build run against a different API, and it future-proofs the build artifact against environment changes.

**Platform.** The code reaches for the platform first: `fetch` with an in-memory promise cache (`app/src/api.ts:117`), `URL`/`searchParams` for all query handling (`app/src/pages/home.ts:26`), `history.pushState`/`replaceState` with `history.scrollRestoration = 'manual'` (`app/src/main.ts:97`), `replaceChildren` (`app/src/main.ts:44`, `app/src/pages/home.ts:106`), native `<input type="search">` with the `search` event, `String.localeCompare` with the proper locale-undefined collator semantics, `padStart` for dex numbers, `loading="lazy"` plus explicit `width`/`height` on sprites for CLS (`app/src/components.ts:12`), CSS Grid + custom properties throughout (`app/src/styles.css:193`), and a hand-rolled `node:http` static server with correct immutable asset caching instead of pulling in express/serve (`app/server.mjs:39`). It skips CSS nesting and `:has()` where plain selectors work — fine. The one genuine platform gap: **no `AbortController`**. Stale-request handling is done with render tokens (`app/src/main.ts:23` `renderToken`, `app/src/pages/pokemon.ts` `token` in `movesSection`) and cache eviction on failure (`app/src/api.ts:124`), which prevents visual races but never cancels in-flight fetches — a moves-table game switch or rapid navigation keeps hammering the API. `fetch(url, { signal })` is the current, supported primitive for this.

**Dependencies.** Two dev-only dependencies, zero runtime packages. That's as lean as the platform allows — routing, DOM construction (`app/src/dom.ts`), debouncing, and serving are all hand-rolled on stable web/Node APIs rather than imported. Nothing outdated, nothing redundant. A 5.

**Churn resistance.** All HTTP access goes through one module: `get<T>` + typed response interfaces in `app/src/api.ts:117`/`:18` — swapping the transport or the API's shape touches one file. Filter state, page size, stat labels, and method ordering each live in exactly one place (`app/src/pages/home.ts:8`, `pokemon.ts:15`). Types sit at the API boundary rather than scattered. Weak points: (1) the route list is duplicated — regexes in `app/src/main.ts:15` and a server-side allow-list `ROUTES` in `app/server.mjs:32`; adding a route means editing both, and a miss yields a correct-but-404-status HTML response. (2) `API_BASE_URL`'s default (`http://localhost:9000`) is stated twice, in `app/server.mjs:14` and `app/src/api.ts:13`. (3) `idFromUrl` regex-parses entity IDs out of URL strings (`app/src/api.ts:129`), a documented PokeAPI invariant but one the server owns, not this app — it is at least confined to one function. None of these ripple widely; they're two-file edits at worst.
