I've read the full app, verified the toolchain against current release notes, and checked the framework guidance. Here is my review.

**What the app is:** a zero-runtime-dependency vanilla TS SPA on Vite — a ~70-line typed `h()` DOM helper (`app/src/dom.ts`), a regex router (`app/src/main.ts`), all API access behind one module with payload interfaces (`app/src/api.ts`), plus a small Node static server with SPA fallback and runtime config injection (`app/server.mjs`).

**Toolchain currency (verified):** `vite ^8.3.5` is the latest stable (Vite 8 shipped 2026-03-12, Rolldown-based; 8.3.5 published two days ago — vite.dev/blog/announcing-vite8, npm) and `typescript ^7.0.2` is the current stable native compiler (devblogs.microsoft.com/typescript/announcing-typescript-7-0, July 2026; 7.1 still in beta). The app is on the current generation of both. No `vite.config` exists at all — the app runs on zero-config defaults, so there is no generated boilerplate to go stale.

**Platform use:** consistently modern — `fetch` with a promise-dedup cache (`api.ts:113-125`), `URL`/`searchParams` everywhere for filter state, History API with `history.scrollRestoration = 'manual'` (`main.ts:84`), `replaceChildren`, `loading="lazy"` on sprites (`components.ts:18`), `:focus-visible`, logical CSS properties, CSS custom properties from the design tokens. Gaps: no `AbortController` (navigation races are handled with hand-rolled render tokens at `main.ts:32` and `pokemon.ts:303` instead of aborting the actual requests), and the CSS is flat where nesting would now be safe in the spec's "latest Chromium" target — both minor.

**Churn resistance:** strong — typed API boundary in one module, config injected at runtime in one place (`server.mjs:26`, consumed at `api.ts:9`), no framework internals. The one real duplication: the route regexes exist twice, in `main.ts:20-27` and again in `server.mjs:25` for HTTP 404s; adding a route means editing both.
