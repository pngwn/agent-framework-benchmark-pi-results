## Review summary

The app is a clean Framework-Mode React Router (v8.5) project: manual route config in `app/app/routes.ts`, thin route modules with typed `+types` imports, a server-only data layer (`api.server.ts`), a pure formatting lib (`format.ts`), and shared presentational components (`components/ui.tsx`, `move-tables.tsx`). Server/client separation is explicit and the framework idioms (loader + meta array + `ErrorBoundary`, root `Layout`, `throw data(null, {status: 404})`) are all current.

### Scenarios worked through

1. **Remove Abilities**: delete `routes/ability.tsx`, drop one line from `routes.ts:8`, remove the Abilities `Section` and the loader's `abilities` field (`routes/pokemon.tsx:116,197-205`). `getAbility`/`ApiAbility` in `api.server.ts` become dead code (easy cleanup). The nav doesn't link abilities, so `root.tsx` is untouched. Mostly deletions — good.
2. **Sprite bug**: every card's sprite goes through one helper, `spriteUrl` (`api.server.ts:232`), called by both card builders (`api.server.ts:250`, `routes/home.tsx:63`) — a URL-level fix is one edit covering every list. But the *robust* fix (use the API's `front_default` instead of the constructed URL) changes the `Card` shape, which is constructed in two places, so a deeper fix lands twice.
3. **Sort cards by name**: all card lists funnel through `CardList` (`components/ui.tsx:60`), so a client-side sort is one edit. If it must respect home's server-side pagination, `routes/home.tsx:41` also changes.
4. **Add Items**: reuse is good — `getRecord` pattern (`api.server.ts:66`), `Section`/`Count`/`CardList`, `englishName`/`englishShortEffect`/`latestEnglishFlavorText`. But route modules are per-resource hand-rolls with no shared "detail page" abstraction, and `/items` (an index page) has no Moves analog to copy — nearest template is `routes/types.tsx`. Touch `routes.ts`, two new route files, and `api.server.ts` (which is already a grab-bag).
5. **Change data source**: `apiBase()` (`api.server.ts:11`) and `CACHE_TTL_MS` (`api.server.ts:9`) are the only places that know the base URL and cache TTL; sprite/artwork URLs either go through `spriteUrl` (same file) or come from API data. One file, but the mixed provenance (constructed sprite URLs vs API-provided artwork, `routes/pokemon.tsx:57`) means a media-layout change needs checking both paths.

### Cross-cutting deductions

- Card construction is duplicated between the home loader (`routes/home.tsx:61-67`) and `cardsFromPokemon` (`api.server.ts:237-251`), so card-shape changes land twice.
- The alternate-form cutoff `id > 10000` appears twice (`api.server.ts:249`, `routes/home.tsx:41`).
- The type-label fallback `typeNames[x] ?? humanize(x)` is repeated four times (`routes/pokemon.tsx:47`, `routes/move.tsx:23`, `routes/type.tsx:23`, `routes/home.tsx:66`).
- `Card` is exported from the server module and type-imported by client components (`components/ui.tsx:4`) — works, but a shared types module would be a cleaner seam.
