I've now read all of `app/` (8 source files, ~630 significant LOC) and verified the stack against current stable releases (hono 4.13.14, @hono/node-server 2.x, htmx.org 2.x — all current; async FC components are the documented Hono pattern). Here's my review focused on **editability**.

## Scenario walkthrough

**1. Remove the Abilities pages** touches four files: the route + two imports in `app/src/index.tsx:7,76-81`, the component in `app/src/pages/details.tsx:65-80`, the Pokémon page's Abilities section (`app/src/pages/pokemon.tsx:97-104` — a spec-mandated link, so unavoidable), and the now-dead `getAbility`/`Ability` type (`app/src/api.ts:125,181`). TS won't flag the unused exports, so dead code lingers unless removed by hand. Contained, but scattered: a solid **3**.

**2. Sprite bug (default Pokémon with a different name, e.g. Deoxys).** Every card list renders through `PokemonCard`/`CardList` (`app/src/components.tsx:62,73`) with `CardData = {id, name, label}` (`components.tsx:60`), and every list's data comes from exactly two producers: `speciesForPokemon` (`api.ts:225`) and `getDex` (`api.ts:242`). So one fix *does* cover every list — but the fix is not one line. `spriteUrl` synthesizes `/media/sprites/pokemon/<id>.png` from the species ID (`api.ts:172`, used at `components.tsx:65`) instead of using the API-provided `sprites.front_default` (which is only consumed for artwork, `pokemon.tsx:50`). A real fix means widening `CardData` with a sprite field and pluming it through both producers in `api.ts` plus `PokemonCard`. One conceptual fix, three files: **3**.

**3. Name-sort every card list.** Ordering lives in the data layer: `speciesForPokemon` sorts by dex id (`api.ts:236`), `getDex` sorts by id (`api.ts:259`), and `loadResults` preserves that (`pages/home.tsx:59-68`). `CardList` has no sort, so you touch two api.ts producers (covering move/ability/type lists) plus the home page's slice logic. The single rendering chokepoint (`components.tsx:73`) keeps the template side untouched, which helps: **3**.

**4. Add Items (`/items`, `/items/:name`) shaped like Moves.** The per-resource pattern is consistent and genuinely reusable: `page()`/`notFound` helpers and route shape (`index.tsx:23-34,83`), `Layout`/`Section`/`Count`/`CardList`/`dash`/`docTitle` (`components.tsx:4-96`), and the generic `get<T>` + cache + `listAll` + `speciesForPokemon<X>` with its `extra` channel (`api.ts:128-236`) — the "held by" list is a one-liner. The new work is a `pages/items.tsx`, two routes, and an `Item` type + `getItem` in `api.ts`. Nav needs no change (spec fixes it). Mostly reuse rather than copy: **2** difficulty.

**5. Change API base URL / caching rules.** `API_BASE_URL` (`api.ts:6`), `FRESH_MS`/`MAX_ENTRIES`/`MAX_CONCURRENT` (`api.ts:8-10`) and the media-URL pattern (`api.ts:172`) are all in one file; no other module knows how data is fetched. Note `API_BASE_URL` is captured at module load, so it's restart-to-change, which is normal for env config: **5** difficulty (trivial).

## Criteria

- **removability: 3.** Each feature is findable (route in `index.tsx`, component in `pages/`, helpers in `api.ts`), but no module *owns* a feature — Abilities removal is four files (`index.tsx:76-81`, `details.tsx:65-80`, `pokemon.tsx:97-104`, `api.ts:125,181`) with silently-dead exports left behind if you miss them.
- **changeability: 3.** Most rules are centralized helpers (`humanize`, `dexNumber`, `latestEnglishFlavor`, `englishName` in `api.ts:152-176`), but the sprite fix spans `components.tsx` + two `api.ts` producers because `CardData` carries only an ID (`components.tsx:60`); the English-name title lookup is inlined four times in the route layer (`index.tsx:55,73,79,88`) despite `englishName` existing (`api.ts:160-161`), and the `typeLabels.get(x) ?? humanize(x)` fallback is repeated in four templates (`pokemon.tsx:69,260`; `details.tsx:34,132`).
- **coupling: 4.** Clean server/client seam: `public/app.js` talks to templates only via `data-sort`/`data-sort-type` attributes emitted at `pokemon.tsx:186,197-205`; htmx partials reuse `MovesBody` for both full page and fragment (`index.tsx:66-68`, `pokemon.tsx:118`). Pages depend on narrow exported helpers, not API internals. Small tangles: `components.tsx:2` imports `spriteUrl`/`dexNumber` from the data module, and the route layer re-implements name extraction instead of calling the helper.
- **abstraction_design: 4.** Abstractions track the app's real variation: `speciesForPokemon<X>` with an `extra` channel covers three different Pokémon-list sources plus per-card notes (`api.ts:225-236`, used at `details.tsx:16-17,66,122`); `CardList.extra` covers types-on-home vs hidden-note (`components.tsx:73`, `home.tsx:69`); `Section` derives its heading id from one prop (`components.tsx:44`); `MoveTable.withLevel` is a justified flag for the one table that has levels. Weak spot: four unrelated detail pages share `details.tsx`, and the effect-fallback chain is duplicated between `MovePage`/`AbilityPage` (`details.tsx:29,59`) instead of being a helper next to `latestEnglishFlavor`.
