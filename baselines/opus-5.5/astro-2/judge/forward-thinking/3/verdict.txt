## Review: `app/` (Astro Pokédex) — dimension: forward-thinking

I verified every API against Astro's current docs and release notes. Astro 7 is the current major (7.4.4 released 2026-10-28 per the Astro release feed), and this app pins `astro ^7.4.2` / `@astrojs/node ^11.1.9` — i.e. it targets the *current* generation, not my training-data-era one. `output: 'server'`, `node({ mode: 'standalone' })`, `Astro.response.status = 404`, `Astro.self`, `class:list` are all documented and current in v7 (docs.astro.build routing reference + `astro@7.2.7` `context.d.ts` shows `Astro.response.status = 404` as the canonical example). The one place the docs have moved ahead of this code is `app/src/lib/api.ts:5`: Astro's environment-variables guide explicitly says "we recommend using `getSecret()` instead of `process.env`" (since astro@5.0), and the typed `astro:env` schema is the current primitive.

The platform story is the strongest part: zero client-side dependencies, and every enhancement is vanilla — `AbortController` request cancellation (`app/src/pages/index.astro:102,126`), `DOMParser` partial swaps instead of a router lib (`index.astro:129`, `MoveTables.astro:124`), `URLSearchParams`/`FormData`/`URL` for state (`index.astro:106-111`, `MoveTables.astro:137`), history API with a `popstate` handler (`index.astro:142-160`), CSS grid + logical properties + custom properties (`global.css:223,488,98`), and a `<noscript>` submit fallback that keeps the game picker functional without JS (`MoveTables.astro:16-25`). Data access is cleanly walled off behind `app/src/lib/api.ts` + `app/src/lib/moves.ts`; no page touches `fetch` server-side, so an upstream change is one-module churn.

The churn-resistance deductions: pervasive `any` at API boundaries despite `astro/tsconfigs/strict` (`app/src/lib/moves.ts:29` `pokemon: any`, `app/src/pages/moves/[name].astro:16-18`, `app/src/pages/pokemon/[name].astro:40-52` — five `(a: any)` casts), so PokeAPI schema drift fails silently; two near-identical client-side partial-navigation implementations that will drift from each other (`index.astro:124-136` vs `MoveTables.astro:119-133`); and an unbounded in-memory cache whose expired entries are never evicted (`api.ts:22-26`) — fine today, a slow leak in a long-lived Node process that browses many move pages. Astro 7's now-stable route caching (`cache: { provider: memoryCache() }` + `routeRules`, per the v7 upgrade guide) would also cheaply absorb the per-keystroke home-page renders without code, but the hand-rolled approach is defensible since it caches *upstream* data, not routes.
