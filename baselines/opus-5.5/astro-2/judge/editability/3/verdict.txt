## Review

The app is on the current stable stack (Astro `^7.4.2`, `@astrojs/node ^11` — 7.4.x is the current stable line as of 2026-10-30), with `output: 'server'` + Node adapter (`app/astro.config.mjs:5-6`) and everything data-related funneled through one module, `app/src/lib/api.ts`. Structure is idiomatic Astro: routes mirror URLs, components are dumb and prop-driven, and client scripts attach via `data-*` contracts.

**Removability** is the strongest axis. Abilities has exactly two touchpoints: the route directory `app/src/pages/abilities/[name].astro` and one `Section` block in `app/src/pages/pokemon/[name].astro:106-116` — no nav entry, no lib helpers that exist only for it (`pokemonRefsToSpecies` is shared with moves and types), nothing left dead. Type/Moves pages would be equally clean.

**Changeability** is good but not quite single-point. The sprite fix lands in `app/src/lib/api.ts` — `spriteUrl` (`api.ts:73`) plus the two id-resolution helpers (`pokemonRefsToSpecies`, `api.ts:92`; `getPokemonIndex`, `api.ts:141-158`); one fix there covers every card list since all four lists route through those helpers, but the id is derived in two places and the `MAX_SPECIES_ID` alternate-form filter is independently re-implied in both (`api.ts:97`, `api.ts:144`), so form-exclusion rules need two edits. The fetch-parse-swap partial-refresh script is also duplicated between `app/src/pages/index.astro:110-131` and `app/src/components/MoveTables.astro:119-131`.

**Coupling** is clean: API base URL, media URL, cache TTL and all formatting live only in `app/src/lib/api.ts:5-8,17,73`; components take narrow props (`PokemonCard.astro:5-10`); `pokemonRefsToSpecies` is generic over the ref type and hands the original ref back so the ability page can read `hidden` (`app/src/pages/abilities/[name].astro:14-18,38`). The one seam break is `app/src/pages/types/index.astro:13` inlining the badge styling/`--badge-bg` hook instead of reusing `TypeBadge`.

**Abstraction design** is solid — `Section`, `TypeBadge`, `PokemonCard`, and the generic `pokemonRefsToSpecies` are shaped around real variation, with no flag-parameter creep. The recurring miss is that the "count + `<ul class="card-grid">`" list markup is hand-rolled in four pages (`pages/index.astro:79-83`, `pages/moves/[name].astro:68-74`, `pages/abilities/[name].astro:32-38`, `pages/types/[name].astro:59-65`), so any list-level change (sorting, empty state, layout) is a 4-file edit. An Items section, by contrast, mostly *writes* one file (`pages/items/[name].astro`) and reuses Layout/Section/NotFound/`getJson`/`humanize`/`show` — exactly the reuse you want.
