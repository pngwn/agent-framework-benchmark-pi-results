I've reviewed the app against Astro 7 (current stable, 7.4.x as of late Oct 2026 — the app pins `^7.4.2`, and `output: 'server'` + `@astrojs/node` standalone is the current idiom). The codebase is small, flat, and well-factored: two lib modules, six small components, five routes, one layout. Here's my assessment per scenario, then scores.

**Scenario work-through:**

1. **Remove Abilities** — delete `app/src/pages/abilities/`, remove one contiguous `<Section id="abilities">` block (`app/src/pages/pokemon/[name].astro:106-114`) plus its one-line const (`:45`). No nav link exists (`app/src/layouts/Layout.astro:19-21` links only Pokémon/Types), no other references (grep confirms). Only residue: `PokemonCard`'s `note` prop (`app/src/components/PokemonCard.astro:12`) becomes unused.
2. **Sprite bug** — sprite derivation is a single function, `spriteUrl` (`app/src/lib/api.ts:73`), and *every* card on every list renders through `PokemonCard.astro:16`. One fix covers home, moves, abilities and types lists. Caveat: it's pattern-derived from ID, not read from each Pokémon's `sprites.front_default`, so if the fix must become data-driven you'd also touch `pokemonRefsToSpecies`/`getPokemonIndex` to plumb a URL through the card's props.
3. **Name sorting on every card list** — ordering lives in the *data* helpers (`pokemonRefsToSpecies` sorts by dex at `api.ts:104-110`; `getPokemonIndex` at `api.ts:169-176`), so a sort option there plus the home page's own sort covers it; no per-page rendering changes needed. ~2 files for a parameterized helper, or 5 files if applied at call sites.
4. **Items section like Moves** — `Layout`, `Section`, `TypeBadge`, `PokemonCard` and the whole `api.ts` helper surface (`getJson`, `englishName`, `latestEnglishFlavorText`, `englishShortEffect`, `show`, `pokemonRefsToSpecies`) are directly reusable; a new `pages/items/[name].astro` reuses maybe 60% and copies the "facts dl + Effect section + count + card grid" shape that is already copy-pasted between `moves/[name].astro:36-77` and `abilities/[name].astro:32-58`.
5. **Data source/caching change** — `API_BASE_URL` (`api.ts:4`), `CACHE_TTL_MS` (`api.ts:6`), URL resolution (`api.ts:12-14`) and the single fetch/cache gate `getJson` (`api.ts:20-33`) all live in one file; media URL building also uses the same base (`api.ts:73`). One file, trivial.

The main deductions: the client-side "fetch page → DOMParser → swap fragment" logic is duplicated verbatim in `pages/index.astro:124-133` and `components/MoveTables.astro:115-127`, and three pages share copy-pasted page furniture (facts `dl`, effect section, "N Pokémon" + card grid) that a fourth similar page would clone. Everything else — narrow prop interfaces, one data-access layer, explicit `data-*` seams between server render and client scripts — is clean.
