I've reviewed the whole app (routes, pages, shared components, data layer, server, styles) and verified the framework context: this is Angular 22 (current stable, released June 2026), where `@Service`, `resource`, and the signal-based control flow used here are all stable APIs. The code follows the modern "intent over role" naming conventions throughout.

## Review

This is a small, well-factored CSR Angular app. The data layer is a single `PokeApi` service behind an `API_BASE_URL` injection token, pages are self-contained lazy components fed by pure `loadX(api, name)` loader functions, and view models (`CardData`, `TypeLabel`, `MoveTable`) form narrow seams between data and templates. The custom Node server is cleanly separated from the client.

### Scenario walkthrough

1. **Remove Abilities**: delete `app.routes.ts:7` + `pages/ability-page.ts`, but also the Abilities section in `pages/pokemon/pokemon-page.html:67-79`, the `AbilityRow`/`abilities` mapping in `pages/pokemon/pokemon-data.ts:10,38,91-93`, the `ability()` method in `core/poke-api.ts:92-93`, the `Ability` model, and — the easy one to miss — `server/server.mjs:48`. A handful of scattered but findable edits.
2. **Sprite bug (Deoxys)**: every non-home card list resolves pokemon-name → species through `cardsFor` (`core/poke-api.ts:105-116`), and the sprite URL is derived solely from `card.id` via `spriteUrl` (`core/poke-api.ts:120-122`) rendered once in `shared/pokemon-card-list.ts:14`. One fix in `PokeApi` covers all four card lists; the home list is built from the species index so it can't exhibit the bug.
3. **Sort by name everywhere**: every list renders through `PokemonCardList`, so a single sort in that component (or one in `cardsFor` plus one in `home.ts`) covers everything.
4. **Add an Items section**: `PokeApi.byName` (`core/poke-api.ts:73-76`) makes the API method a one-liner; `LoadState`, `syncPageTitle`, `PokemonCardList`, `TypeBadge`, panel CSS and the whole `format.ts` kit are reusable. What gets copied is the ~60-line detail-page skeleton (`resource` + `syncPageTitle` + template), which is repeated identically in `move-page.ts`, `ability-page.ts`, `type-page.ts`. Plus edits to `app.routes.ts` and `server/server.mjs`.
5. **Change data source**: base URL is a single client seam (`api-config.ts` token), caching rules live in one method (`poke-api.ts:57-70`, TTL at `:48`). But the default origin is duplicated in `server/server.mjs:20` and `api-config.ts:3`, and the server re-encodes the API path (`server.mjs:67`) that `PokeApi.byName` also encodes.

### Dings

The main structural criticisms: (a) `server/server.mjs` duplicates the client's route and resource knowledge (`DETAIL_ROUTES` at `server.mjs:45-51` mirrors `app.routes.ts`; the 404-check path mirrors `byName`), so route/resource changes need synchronized edits in two runtimes; (b) all ~500 lines of CSS live in one global stylesheet that targets component selectors (`styles.css:153,157-159,192,530`), so renaming a component class silently breaks styling and new list pages don't automatically inherit the spacing rules given to `app-home`/`app-types-page`; (c) the per-page `resource`/`syncPageTitle`/`errorHeading` wiring is repeated 4× without a shared shell, and the "Something went wrong" string is duplicated in `page-title.ts:24` and `load-state.ts:17`. These are all modest on a codebase this size.
