## Analysis

**Structure** — The app has a clean three-layer split: `src/server/pokeapi.ts` (all API + cache knowledge), `src/server/functions.ts` (one `createServerFn` per page, using the current `.validator()` API), and thin route components consuming typed loader data (`src/lib/types.ts`). The API base URL, TTL and memo cache live in exactly one file (`pokeapi.ts:6,9,16,33`), so a data-source change is genuinely one-file. Every Pokémon card list (home, move, ability, type) flows through one seam: `toCards` (`pokeapi.ts:96`) → `PokemonCardList` (`PokemonCard.tsx:10`), so sorting or a sprite fix covers all lists at once.

**Wrinkles** — `CardData.id` is the *Pokémon* id (`idFromUrl(ref.pokemon.url)`, `pokeapi.ts:87`) but is used as both the dex number and the sprite id (`PokemonCard.tsx:16-18`); that conflation is fine today (spec: default Pokémon shares the species id) but means the Deoxys-style fix touches 3–4 files in one seam rather than one. The sprite path shape is hard-coded in a pure formatting helper (`format.ts:23-24`), and there are two mechanisms for type labels (server-resolved `TypeRef` vs the client-side `typeLabels` map passed to `PokemonCardList`). Resource detail pages share no scaffolding, so an Items section is copy-adapt of Moves rather than reuse. Title/head and the notFound pattern repeat per route.
