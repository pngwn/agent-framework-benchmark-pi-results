## Review

This is a small, disciplined Next.js 16 App Router app (18 source files, ~670 significant LOC), and it reads like one: three library modules (`api`, `data`, `format`), six presentational components, five route files. I verified the framework practices against the current release (Next 16.4.3, Turbopack default, async `params`/`searchParams`, top-level `turbopack` config key) and the app is fully idiomatic on all counts. The editability picture is good, with a handful of duplicated seams worth tightening before the next feature lands.

**Remove a feature (Abilities).** Clean. Delete `app/app/abilities/[name]/page.tsx`, delete the Abilities section in `app/app/pokemon/[name]/page.tsx:117-126`, and optionally drop a word from the description in `app/app/layout.tsx:11`. The nav never links to it. What keeps this from a 5: removal leaves inert code scattered across `app/lib/api.ts:120` (the `Ability` type), `app/lib/data.ts:18` (`CardData.note`), `app/components/PokemonCards.tsx:17`, and `.card__note` CSS — nothing marks these as belonging to the feature.

**Fix a bug (card sprite for Deoxys-like species).** The good news: the sprite URL is built in exactly one function, `spriteUrl` at `app/lib/data.ts:21-23`, and both the species-list path (`cardsForPokemon`, `app/lib/data.ts:66`) and the home page (`app/app/page.tsx:37`) go through it — a pure URL-pattern fix is one line and covers every list. The catch: card *assembly* exists in two places (`app/lib/data.ts:55-69` vs `app/app/page.tsx:33-39`), so a fix that needs per-Pokémon record data (e.g. using `front_default` instead of the ID pattern) touches both and they can drift.

**Add sorting by name.** Best-case. Every card list on the site renders through the single `PokemonCards` component (`app/components/PokemonCards.tsx:6`); sorting the `cards` prop before the map covers home, moves, abilities and types in one edit.

**Add Items.** The heavy machinery is reusable wholesale: `find`/`get`/`list` (`app/lib/api.ts:27,49,58`), `cardsForPokemon` for held-by Pokémon, `Section`, `PokemonCards`, and the `format.ts` helpers. What gets copied is the ~25-line detail-page frame (`getX` + `generateMetadata` + `notFound`), which already exists four times near-verbatim (`app/app/moves/[name]/page.tsx:12-19`, `abilities/…:11-18`, `types/…:22-29`, `pokemon/…:19-28`), plus the "facts" `<dl>` markup. One new route file plus an `Item` type in `api.ts`.

**Change data source / caching.** Excellent. `API_BASE_URL` is read in exactly one place (`app/lib/api.ts:16`) and the sprite base flows through `apiBase()` too, so even media URLs follow. Cache policy is three spots in two files: TTL/eviction + `fetch(…, { cache: "no-store" })` in `app/lib/api.ts:7-11,20`, and `export const dynamic = "force-dynamic"` in `app/app/layout.tsx:7`.

Notable framework note: as of 16.4, Vercel recommends Cache Components (`cacheComponents: true` + `cacheLife`/`cacheTag`) over the classic model this app uses (`force-dynamic` + a hand-rolled 60s in-memory cache at `app/lib/api.ts:7-11`). The hand-rolled cache is confined to one module, so a later migration is contained, but it duplicates functionality the framework now owns.
