## Review: test quality

The app contains **zero tests of its own** — no test script, no runner, no test dependencies anywhere in `app/` (`app/package.json:6-15`). Everything below is therefore about what the acceptance suite in `tests/` (which it didn't write) leaves unguarded, and where a refactor will silently break behaviour.

The codebase is unusually testable for a Next.js app: most of the risk lives in small pure functions (`app/lib/format.ts`), pure-ish aggregation (`app/lib/data.ts`), and URL-state math (`app/app/page.tsx`, `app/components/Filters.tsx`) — all of which could be covered with a minimal Vitest setup and no browser. That no such setup exists is the finding.

**Risky, untested logic, in rough order of danger:**

1. **Alternate-form exclusion and ordering** — `app/lib/data.ts:57` (`id <= MAX_SPECIES_ID`, relying on NaN-comparison-to-false), `app/lib/data.ts:48-54` (dedup by species id, sort by dex). Flip the comparison, drop the dedup, or sort by name instead of id and the dex pages reorder or Megas leak into every list. The acceptance fixtures only include *one extra Pokémon*, so a partial regression (e.g. dedup gone but IDs still sorted) can slip past them.
2. **URL-state sync in `Filters`** — `app/components/Filters.tsx:29-41`: the `sentQuery`-ref trick that stops a slow navigation from clobbering what the user typed, plus the 200ms debounce (`app/components/Filters.tsx:49-51`) and the pending-timer cancellation on select (`app/components/Filters.tsx:60`). This is exactly the kind of code that breaks invisibly on a refactor (back/forward, fast typing, select-while-typing) and can only regress silently because nothing exercises it.
3. **Pagination clamping and param parsing** — `app/app/page.tsx:15` (`first()` picking `value[0]` of an array param), `app/app/page.tsx:32-33` (`parseInt` NaN → 1, clamp to `[1, totalPages]`). A refactor to `Number()` or a searchParams library changes edge behaviour (`?page=0`, `?page=99`, `?page=abc`, `?q=a&q=b`) with nothing to catch it.
4. **Spec-critical formatters** — `app/lib/format.ts:10-16` (`humanize`: `filter(Boolean)` handles `--` names like `ho--oh`-style doubles, digit words like `nidoran-f`), `app/lib/format.ts:44-49` (`latestFlavorText` uses `findLast`, an ES2023 method — a single line a unit test would pin), `app/lib/format.ts:55-58` (`idFromUrl` returning `NaN` and everything downstream depending on that).
5. **The in-memory cache** — `app/lib/api.ts:34-52`: TTL, the somewhat convoluted eviction loop (`if (entry.expires <= now || cache.size > MAX_ENTRIES) cache.delete(key)`), and error-invalidation via `value.catch` identity check (`app/lib/api.ts:39-42`). A tweak here (e.g. caching rejections, off-by-one in expiry) wouldn't fail any test until production.
6. **Moves assembly on the Pokémon page** — `app/app/pokemon/[name]/page.tsx:145-203`: game-selection fallback to `games.at(-1)`, the dedup key `${l.method}:${l.move}:${level}` at line 176, and the two-level sort (level vs. label at line 193, method rank at line 199). Subtle, data-heavy, completely unguarded.
7. **Not-found / error paths** — the `isApiName` guard + `find` → `notFound()` pattern in all four `[name]` pages (e.g. `app/app/moves/[name]/page.tsx:9-12`) and `app/app/error.tsx`. Some of this is covered by the acceptance suite today, but nothing in `app/` pins it.

Nothing here is framework-version-sensitive enough to change the verdict: Next 16 with `params`/`searchParams` as Promises is handled correctly, and the right test tooling (Vitest + Testing Library, Playwright component tests for `Filters`) is all current — it just wasn't used.
