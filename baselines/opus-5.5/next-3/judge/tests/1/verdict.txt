## Test quality review

**The app contains no tests of its own.** `app/package.json` has no `test` script and no test runner (vitest/jest/playwright) among its devDependencies (`app/package.json:7-22`); the only Playwright reference in `app/package-lock.json` is Next's optional *peer* dependency (`app/package-lock.json:872-883`). `grep` for `test(`/`describe(`/`expect(` across `app/` finds only incidental matches (`lib/format.ts:35`, `lib/api.ts:28`, etc.), never a test case. That matches the measured facts (`tests.files: 0`). So the entire risk surface is guarded only by the acceptance suite, which the repo won't run in CI once the task is over.

What makes this painful is that a large share of the riskiest logic is **pure functions that cost nothing to test** — `lib/format.ts` (humanize, dexNumber, idFromUrl, latestFlavorText, collapseWhitespace, orMissing), `lib/data.ts` (alternate-form exclusion, card dedupe, index building), and the move-table comparator. Instead, that logic lives inline in pages and client components where only full-browser tests would reach it:

- Home filtering, pagination math and page clamping are inline in the server component (`app/app/page.tsx:41-56`) — the "48 per page", the combined predicate, and `Math.min(Math.max(requested, 1), totalPages)` clamp. A one-token refactor of `IndexEntry`'s shape (`lib/data.ts:72`) or the `slice((page-1)*PAGE_SIZE, page*PAGE_SIZE)` bounds shifts every page boundary, and nothing in `app/` fails.
- `idFromUrl`'s regex (`app/lib/format.ts:45-48`) is the linchpin mapping Pokémon→species and excluding alternate forms everywhere (`lib/data.ts:57-61`); a refactor to e.g. `parseInt(url)` would silently drop or admit forms in every card list on the site.
- `cardsForPokemon` dedupes by first occurrence (`lib/data.ts:62-68`): if a Pokémon appears twice in `ability.pokemon` (normal + hidden instance of the same ability), only the *first* entry's `note` wins (`app/abilities/[name]/page.tsx:34-36`) — an order-dependent mislabel that no test would catch.
- The "omit empty/default params" URL rule is duplicated in two hand-rolled builders (`app/app/page.tsx:61-69` and `app/components/Filters.tsx:12-18`); they already disagree subtly (one handles `page`, the other doesn't need to), and one being fixed without the other is a classic future regression.
- The API cache's TTL, in-flight dedupe, failed-request eviction and the size-cap sweep (`app/lib/api.ts:17-50`) implement the spec's "live data" requirement; a "cleanup" to Next's fetch cache or a broken eviction break would only be caught by the overlay fixture for the specific overlaid records.
- Client-side risk is equally bare: the `sentQuery`-ref reconciliation in `Filters` that avoids clobbering in-flight typing (`app/components/Filters.tsx:20-46`) and back/forward restoration of the search input are only touched incidentally by acceptance; `MoveTable`'s missing-last comparator and string-descending direction (`app/components/MoveTable.tsx:39-52`) are exercised for one column of one table; `getMoves`' default-game tie-break (`a.order - b.order || a.id - b.id`, `app/app/pokemon/[name]/page.tsx:173-177`) is validated only for Pikachu.
- `error.tsx` (`app/app/error.tsx:1-15`) — the API-down path — is never exercised by anything: acceptance never stops the API.

For the criteria: with zero tests, `coverage_of_risk`, `behaviour_not_implementation` and `regression_power` score 1 by the anchors (nothing covered, so "what would be caught" is nothing), and `signal_to_noise` gets the prescribed 3. The pure helpers in `lib/` are exactly the functions a five-minute vitest setup would have covered, which is what keeps this at the bottom of the scale rather than "merely thin".
