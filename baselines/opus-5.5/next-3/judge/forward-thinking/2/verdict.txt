## Review — forward-thinking

**What's current.** This is a Next.js 16.4.3 app (the exact current stable, released 23 Oct 2026 per endoflife.date / GitHub releases) and it gets the 15→16 breaking changes right: `params`/`searchParams` are awaited `Promise`s (`app/app/pokemon/[name]/page.tsx:20-21`), `generateMetadata` resolves titles through the layout's `%s – Pokédex` template (`app/app/layout.tsx:14`, `app/app/pokemon/[name]/page.tsx:30`), `notFound()`/`error.tsx`/`not-found.tsx` are the current conventions, and `next.config.ts` with `turbopack: { root: __dirname }` is the 16-era config shape (`app/next.config.ts:1-8`). The `AGENTS.md` managed block (`app/AGENTS.md:1`) is even present — the 16.2+ hygiene feature.

**The one real gap.** The caching layer is the *previous* model. Next 16.4's announcement (nextjs.org/blog/next-16-4, 6 Oct 2026) recommends **Cache Components for every Next.js app**, ships it on by default in `create-next-app`, and the docs state `dynamic`/`revalidate`/`fetchCache` segment configs are **removed** when Cache Components is enabled, with Cache Components becoming the default in Next 17. This app instead does `export const dynamic = "force-dynamic"` (`app/app/layout.tsx:7`) plus a 60-line hand-rolled Map/TTL/eviction cache (`app/lib/api.ts:11-59`). That's a direct Next-17 churn vector: the migration to `use cache` + `cacheLife`/`cacheTag` would rewrite exactly the module the rest of the app depends on, and the custom cache doesn't participate in framework invalidation (`revalidateTag`/`updateTag`) or survive multiple server instances. The spec explicitly allows runtime in-memory caching, so the behavior is compliant — but the *current-generation primitive* was skipped.

**Smaller items.** Raw `<img>` with `eslint-disable` comments (`app/components/PokemonCards.tsx:12-13`, `app/app/pokemon/[name]/page.tsx:67-68`) instead of `next/image` with `remotePatterns` — defensible given sprites come from an external origin (and the Oct 2026 Image Optimization advisory), but it forfeits format conversion; the query-string contract is built twice (`app/app/page.tsx:41` vs `app/components/Filters.tsx:8-13`), so renaming a param touches two files; `idFromUrl` hand-rolls regex parsing where `new URL()` is the platform answer (`app/lib/format.ts:55-58`).

**What's excellent.** Dependencies are exactly minimal: `next` pinned to the current stable, `react`/`react-dom` 19.3 (the version 16.4 ships), and `server-only` as a lean boundary guard — no axios, no lodash, no CSS framework. Platform reach is strong: `URLSearchParams` for query building (`app/app/page.tsx:42`, `app/components/Filters.tsx:9`), `findLast` (`app/lib/format.ts:26`), `at(-1)` (`app/app/pokemon/[name]/page.tsx:126`), native form controls, `loading="lazy" decoding="async"`, CSS custom properties and `aspect-ratio` (`app/app/globals.css:285`). All API access is funneled through one typed module (`app/lib/api.ts:92-160`) with derived datasets behind `app/lib/data.ts` — an upgrade would touch few files.
