## Review

This is a well-executed React Router v8 framework-mode app: current-stable dependencies (`react-router@^8.5.0`, correct for Oct 2026), manual route config with generated types, loaders that own URL-derived state, `throw data(..., { status: 404 })` for missing records, root `Layout`/`ErrorBoundary` exports, and a clean `@react-router/express` production server with immutable asset caching. The server/client boundary is genuinely clean — all API access lives in `lib/api.server.ts` (`.server` suffix keeps it out of the client bundle) and loaders return pre-shaped, serializable view models, so components render and nothing fetches in effects.

The one place it steps off the documented path is the home filter form (`app/app/routes/home.tsx:62-93, 118`): uncontrolled inputs read via DOM refs, a hand-rolled debounce, imperative `select.value` writes, and `useNavigate` where the skill and docs point at `<Form method="get">` / `useSearchParams`. It's thoughtful code — the mount effect that replays pre-hydration input is a real class of bug most apps miss, and the native `action="/"` with matching `name`s keeps a no-JS fallback — but it's ~50 lines of imperative machinery a reviewer has to reason about instead of a documented primitive, and it has a small window where typed query text can be lost if a pagination link is clicked before the debounce fires (link is built from `loaderData.filters`, `home.tsx:158, 164`).

Careful edge-case hunting found no serious bugs: 404s are thrown properly on every route (`move.tsx:26`, `type.tsx:22`, `not-found.tsx:5`), sort state can't leak across tables that remount by key (`pokemon.tsx:253`), missing values sort last in both directions (`MoveTable.tsx:50-54`), and `navigate({ search, hash })` correctly preserves pathname and `#moves` (`pokemon.tsx:170-171`). The residual risks are all minor: the module-level cache (`api.server.ts:10-21`) never evicts expired entries and is keyed by user-influenced URLs, so a crawler hitting arbitrary `/pokemon/<garbage>` grows it forever (a 404 `null` is cached per unique key); the non-null assertion at `MoveTable.tsx:48` is a latent TypeError if a sort key ever outlives its column; and `ErrorBoundary` only logs in dev (`root.tsx:53`), so production 500s leave no trace. Fetch fan-out on the Pokémon page (~40 version groups + one request per learned move, `pokemon.tsx:71-77, 120-124`) is bursty but bounded by the dataset and mitigated by the cache — acceptable for a local API, worth a TTL/LRU note.

Abstractions earn their keep: `format.ts` is small pure helpers, `Section`/`TypeBadge`/`PokemonCards`/`MoveTable` are focused and reused across four routes, and the `getIndex()` read model (`api.server.ts:74-114`) is the right way to avoid per-list re-fetching. Nit: `Move`/`Species`/`Pokemon` endpoint shapes are declared inline in both `pokemon.tsx:40-66` and `move.tsx:6-17` — they belong in `lib/types.ts` next to `Card`. `isbot` is an unused dependency (the framework's built-in server entry handles bot detection). A `typecheck` script and strict tsconfig are in place; the app ships no tests of its own, which is the main thing keeping this from "approve on sight".
