# Review: editability

## Scenarios worked through

**1. Remove the Abilities pages.** Delete `app/src/routes/abilities/` — it's fully self-contained (no helper in `server-api.ts` is ability-specific; the only inbound link is `app/src/routes/pokemon/[name]/index.tsx:229`). Then remove the `Abilities` section (`index.tsx:225-235`) and the loader's `abilities` field (`index.tsx:139-142`). Residue if you clean up properly: `Card.hidden` (`types.ts:20`), the `Hidden ability` note (`components/cards.tsx:22-23`), the `hidden` propagation (`server-api.ts:119`), and `.card-note` CSS (`global.css:204`) exist only for ability cards. No nav link to touch (nav only has Pokémon/Types, per spec). Five files, but ~12 deleted lines total and grep for `hidden`/`abilit` finds them all.

**2. Deoxys sprite fix.** This app already handles it correctly *and* centrally: `cardsFor` (`server-api.ts:112-124`) resolves every Pokémon reference to its species ID via `speciesNames()` and builds the sprite from that ID (`spriteUrl`, `server-api.ts:67-69`). One function covers the move, ability and type card lists; the home page builds cards from species IDs directly in `speciesIndex` (`server-api.ts:158-166`), so it's inherently right. A sprite-URL change is literally one function (`spriteUrl`). The only wart is that the *card construction* (id/name/label/sprite) is written twice — once in `cardsFor:120`, once in `speciesIndex:163` — so a non-URL card change would need two edits.

**3. Sort every card list by name.** Two sort sites, both in `server-api.ts`: `cardsFor` (`:124`, `a.id - b.id`) for move/ability/type lists, and `speciesIndex` (`:158`, sorts by species id) which feeds the home page. The home page's pagination slices after the sort (`routes/index.tsx:74`), so you can't sort inside `CardList` — you must touch the loader-side ordering. Two small edits in one file; grep `sort(` finds them.

**4. Items section shaped like Moves.** `Moves` is a single self-contained route (`routes/moves/[name]/index.tsx`, 100 lines) with no page-specific helpers leaked into `lib/`. Adding `/items` + `/items/:name` means two new route files; the genuinely shared machinery — `Section` (`components/section.tsx`), `CardList`/`PokemonCard`, `NotFound`, `api`/`slug`/`englishName`/`english`/`latestFlavorText` (`server-api.ts:39-69`), `orDash`/`pageTitle` — is all reusable as-is. You'd copy the loader/head/`<dl>` skeleton of the moves page (no "resource detail page" abstraction to extend), but no cross-cutting edits elsewhere.

**5. Data source / caching rules.** `API_BASE_URL` is read in exactly one function, `apiBase()` (`server-api.ts:14-16`), used by `api()` (`:27`) and `spriteUrl()` (`:68`) — nothing else in `src` mentions the URL. The in-memory cache (TTL, promise-dedup, error eviction) is entirely `server-api.ts:8-36`. Page HTTP cache and static-asset cache are separate, single sites (`routes/layout.tsx:4-6`, `entry.node-server.tsx:24-28`).

## Scores

- **removability: 4.** Route directories are self-contained and grep-clean, but ability support leaves a small scattered trail (loader field, section, `Card.hidden`, `cardsFor`'s hidden plumbing, CSS).
- **changeability: 4.** URL building (`homeHref`, `index.tsx:23`), sprite URLs (`spriteUrl`), reference→species mapping (`cardsFor`), and caching each have exactly one home. Deducted for the duplicated card construction/order and for pervasive `any`, which means the compiler can't catch data-shape regressions.
- **coupling: 5.** Textbook seams: `lib/types.ts` DTOs are the only contract components see; `server-api` is imported exclusively by route loaders (`grep server-api` → 6 route files only); components never import server code; filter state lives in the URL, not shared client state; server/client split is crisp. I'd point to this layering as an example for a small Qwik City app.
- **abstraction_design: 4.** Components are sized to real variation (optional `card.types`/`card.hidden`, `TypeBadge`'s `link` flag, `MovesTable`'s data-driven columns) with no over-generalization. Deducted for the `cardsFor`/`speciesIndex` duplication and the untyped PokeAPI shapes that make the data layer the weakest abstraction.

**Overall: 4.** This is code a team can own: one obvious place per concern, narrow interfaces, current framework idioms, and no cleverness. The two recurring deductions are `any`-typed API responses and a doubled card-building path — both cheap to fix now, both the kind of thing that gets expensive after a year of accretion.
