## Review

The app is a clean, textbook Qwik City v1 application whose package versions and generated boilerplate match the framework's **current stable line exactly**: `@builder.io/qwik`/`@builder.io/qwik-city` are pinned at `1.20.3`, which was released 2026-10-25 — five days before today — and is the newest stable (Qwik 2.0 is still in RC, so it is correctly not the baseline). I verified this against the Qwik releases page and the `next.qwik.dev/docs/upgrade/` guide.

**Latest APIs.** Every framework API in use is the current v1 generation: `routeLoader$` for all data loading (`app/src/routes/index.tsx:51`, `app/src/routes/moves/[name]/index.tsx:19`), `useSignal`/`useTask$` for client state, `head: DocumentHead` with `resolveValue`, `cacheControl` in a `RequestHandler`, and starter-identical `root.tsx`/`entry.*.tsx`/`tsconfig.json` (the tsconfig matches the 1.20.0 starter byte-for-byte in its compiler options). Notably, all event handlers use the `(event, element)` signature (`app/src/routes/index.tsx:96`, `app/src/routes/pokemon/[name]/index.tsx:251`), which is what Qwik v2 will *require* — the app is already v2-shaped there. No deprecated v1 APIs appear: no `useResource$`, no `useVisibleTask$`, no `qwik-labs`, no `server$`-era patterns. The 404 is handled with a catch-all route + `status(404)` (`app/src/routes/[...rest]/index.tsx:7`), the idiomatic v1 approach, and it already renders inside the layout the way v2's `404.tsx` will.

**Platform.** Native `fetch` (`app/src/lib/server-api.ts:27`), `URLSearchParams` for query building (`app/src/routes/index.tsx:24`), `new URL(...)` for query reads/updates (`app/src/routes/pokemon/[name]/index.tsx:252`), native form controls with real labels, and lazy images with intrinsic dimensions (`app/src/components/cards.tsx:12-13`). No polyfills, no hand-rolled fetch wrappers beyond a sensible 60 s promise-dedup cache. The one gap: server fetches have no `AbortSignal`/timeout, so a hung API request hangs SSR indefinitely.

**Dependencies.** Zero runtime dependencies; the six devDependencies are exactly the starter set at current versions. No CSS framework (per spec), nothing redundant.

**Churn resistance.** Data access is entirely behind `app/src/lib/server-api.ts`, view models are typed in `app/src/lib/types.ts`, and route loaders map API → typed view model — so a PokeAPI shape change touches one module. The deduction: `any` at the API boundary (`api<T = any>` at `server-api.ts:21`, `(v: any)` at `app/src/routes/pokemon/[name]/index.tsx:97`, `Promise<any[]>` at `server-api.ts:78`) means `types.ts` guards the component side only, not the wire format. A v2 migration would touch the six starter boilerplate files (package.json, root, entries, adapter configs) — but that's generator-owned boilerplate the migration CLI rewrites, and the business logic is plain TS modules that survive untouched.
