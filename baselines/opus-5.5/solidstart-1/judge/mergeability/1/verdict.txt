## Review notes

**Stack alignment (verified against current docs).** The app matches SolidStart v2 exactly: `vite.config.ts` composes `solidStart()` + `nitro()` from `nitro/vite` (app/vite.config.ts:6-10), Vite 8, Node `>=24` engines, built-in `~` alias, `vite build`/`node .output/server/index.mjs` scripts — all as prescribed by docs.solidjs.com/solid-start/v2. Data loading uses the recommended `query` + `"use server"` + `createAsync` + route `preload` trio (app/src/lib/queries.ts:3-13, app/src/routes/index.tsx:37-41), URL state via `useSearchParams`, `HttpStatusCode` for 404s, `mode: "async"` in `createHandler` (documented sync|async|stream option) with a comment explaining *why* (fragment links need complete HTML) — app/src/entry-server.tsx:3-4. The server/client boundary is clean: view models are only reachable through server functions using dynamic imports, so `model.ts` never ships to the browser.

**Real strengths.** `pokeapi.ts` is a small, well-commented server client: TTL cache with per-URL promise sharing, 404→`NotFoundError` semantics, a concurrency limiter, and cache invalidation on rejection (app/src/lib/server/pokeapi.ts:9-55). The spec's tricky rules (species-vs-pokémon card mapping, alternate-form exclusion, missing-values-sort-last, humanized vs English name rule) are all implemented deliberately in one place.

**What I'd push back on in review.**

1. **No error handling for non-404 failures** — every route renders `Show when={data()}` with a fallback only for `null`; a 500 or network failure from the API throws inside `createAsync`, there is no `ErrorBoundary`/`onError` anywhere, so `main` renders empty and the error is unhandled (app/src/routes/pokemon/[name].tsx:51-53, and same in moves/abilities/types/index).
2. **Expired cache entries are never evicted** — `cache.set` stores an `expires` stamp but nothing removes entries after expiry (only on rejection), so stale entries accumulate for the process lifetime (app/src/lib/server/pokeapi.ts:20, 33-35). Bounded by dataset size, but sloppy.
3. **NaN sort risk** — `groups.sort((a, b) => a.order - b.order)` will mis-sort if any version group has `order: null`, as some PokeAPI records do (app/src/lib/server/model.ts:208).
4. **`model.ts` is a 340-line god data module** — all six pages' view models plus shared indexes live in one file; cohesive and sectioned, but per-resource modules would age better.
5. **Repeated loading-vs-notfound idiom** — the `Show when={x()} fallback={<Show when={x() === null}>...}` double-Show trick (relies on `undefined` vs `null`) is copy-pasted across four routes and deserves a helper (app/src/routes/moves/[name].tsx:20-21 etc.).
6. **API payloads typed `any`** — `types.ts` carefully types view models, but the fetch layer is `api<T = any>` and model code casts through `any` throughout, so `strict: true` buys little at the API boundary.
7. **Minor duplication** — `param()` / `gameParam()` normalize search params independently in index.tsx and the Pokémon page; `MoveTable`'s header columns are declarative while the body cells are hand-written in a fixed order, so the two can drift.

Nothing here would block me from merging after one small round: #1 is the only change I'd insist on before approval; the rest are nits or nice-to-haves.
