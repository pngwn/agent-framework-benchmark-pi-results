## Review

The app is a SolidStart v2 Pokédex. I verified its API usage against the framework's current docs (docs.solidjs.com/solid-start/v2) and release state as of 2026-10-30:

- `@solidjs/start@2.1.0` is the **latest stable** (published 2026-10-22); `@solidjs/router@1.0.0` and `solid-js@1.9.18` are the latest stable router/Solid releases (Solid 2.0 is still at `2.0.0-rc.20`, so staying on the 1.9 line is the correct call, not a lag).
- The data-loading stack (`query` + `"use server"` + `createAsync` + route `preload`) is exactly what the v2 data-fetching doc prescribes; none of the v1-era primitives (`createServerData$`, vinxi, `nitropack`, `@solidjs/vite-plugin-nitro-2`) appear.
- `vite.config.ts` and `package.json` (vite 8, `engines.node >= 24`, `nitro` + `nitro()` plugin) match the v2 setup/migration docs character-for-character.
- `createHandler(..., { mode: "async" })` is the documented `StartServer` option and is required for `HttpStatusCode` to actually send 404s (per solid-start issue #1868) — the app even comments why.

The one genuinely forward-looking smell is pinning `nitro` to `^3.0.260903-beta`: Nitro v3 just hit RC (`3.0.261029-rc`, 2026-10-29) with a "Upgrading from Beta" breaking-change path, and a caret range on a prerelease version won't match `-rc` builds — a bump will have to be deliberate. Data access is otherwise isolated behind `lib/server/pokeapi.ts` + `lib/server/model.ts` with shared view-model types, so an API or framework move touches few files; the raw response layer is `any`-typed, though, so data-shape changes surface at runtime rather than compile time.
