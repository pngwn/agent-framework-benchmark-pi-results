## Review: forward-thinking

**Stack check (verified against current docs/releases, not memory):** SolidStart **v2 went stable Aug 2026** (github.com/solidjs/solid-start/discussions/2281); it's built on Vite 8's Environment API + Nitro v3's own `nitro/vite` plugin. The app matches the documented v2 setup exactly: `vite.config.ts` with `solidStart()` + `nitro()` (app/vite.config.ts:1-9), Node `engines: >=24` (app/package.json:20-22), and the data-loading guide's current primitives — `query` (renamed from `cache` in router 0.15), `createAsync`, route `preload`, `"use server"`. `@solidjs/start` 2.1.0 is the newest release (2026-10-22), `@solidjs/router` 1.0.0 is a pure version realignment of 0.16, and `@solidjs/meta` is still the documented head solution. No deprecated APIs (`cache`, `load`, `useRouteData`, `app.config.ts`, vinxi) appear anywhere.

The one place the app quietly opts out of the current model is linking: nearly every internal link is a raw `<a href>` (only the header nav uses `A`), which forfeits client-side transitions and means the hover/focus preload scheduling the router documents ("Anchors registered with Solid Router emit hover and focus events") never fires for the `preload` hooks written on every route.

**Other observations:** server data access is cleanly funneled through `lib/queries.ts` → `lib/server/model.ts` → `lib/server/pokeapi.ts`, with typed view models at the component boundary — but the PokeAPI payloads themselves stay `any` (model.ts:48, 178; pokeapi.ts:45), and `API_BASE_URL` is read straight from `process.env` rather than SolidStart 2.x's runtime-env module or Nitro runtimeConfig. Runtime deps number exactly six, all current, nothing redundant.
