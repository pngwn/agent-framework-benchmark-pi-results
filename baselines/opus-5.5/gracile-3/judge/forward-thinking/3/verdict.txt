## Review: Gracile-with-Lit Pokédex — forward-thinking

Framework check first: `@gracile/gracile` **0.11.0 is the current stable release** (published ~6 months before today; 0.11.1-next.* are the only newer tags). I verified the app's route API against the framework's own type surface (`@gracile/engine@0.12.0/dist/routes/route.d.ts` — `defineRoute({ handler, document, template, responseInit, handler: { GET } })` is exactly the current shape) and against the docs site's annotated `document.ts`/route examples and the official `minimal-server-express` starter. Nothing the app uses is deprecated.

### `latest_apis` — 5

The stack is pinned to the current generation and used the documented way:

- `app/package.json:8` — `@gracile/gracile` **0.11.0**, exact pin (wise for a framework that still self-describes as alpha; avoids surprise breakage).
- `app/src/routes/(home).ts:8-23` — `defineRoute` with `handler` returning props, `document`, `template` reading `props`: the current route contract, matching `route.d.ts` verbatim.
- `app/src/routes/api/species-index.ts:6-13` — server endpoint via `handler: { GET: ... }` returning `Response.json`, the documented "Server Endpoints" feature used instead of bolting an API onto express.
- `app/server.js:1-20` — structurally identical to the official `minimal-server-express` starter (`nodeAdapter`, `getClientBuildPath`, `printUrls`), with sensible hardening added (`disable('x-powered-by')`, immutable asset caching).
- `app/src/document.ts:1` — `html` from `@gracile/gracile/server-html` for the document, `lit` `html` for route templates: the documented split.
- `lit` 3.3.3 (registry latest as of 2026-05) and express ^5.1.0, `@types/express` ^5 — current.

No legacy-era patterns anywhere; the client side is deliberately vanilla (`lit` `render` + native DOM) rather than hydration, which is a legitimate "progressive interactivity" choice in current Gracile, not a legacy one.

### `platform` — 4

Reaches for the platform almost everywhere:

- `app/src/lib/api.ts:70-78` — global `fetch`, `response.body?.cancel()` on 404, `Response.json` status checks; no axios/node-fetch.
- `app/src/lib/browse.ts:22-44` — `URLSearchParams` both ways; `app/src/routes/pokemon/[name].client.ts:22` — `Intl.Collator` for locale-aware sorting.
- `app/src/routes/(home).ts:13` — native `<form method="get">` works without JS; the client script (`(home).client.ts:89-93`) merely enhances it and falls back with `location.assign` on error. Progressive enhancement done right.
- `app/src/templates/components.ts:38-40` — `loading="lazy"`, `decoding="async"`, intrinsic `width`/`height` to prevent CLS.
- Modern JS throughout: `.at(-1)` (`app/src/lib/data.ts:308`), `replaceAll` (`data.ts:140`), numeric separators (`api.ts:4`).

Deduction: no `AbortController`/`AbortSignal` anywhere (grep confirms zero matches). Rapid filter typing in `app/src/routes/(home).client.ts:34-36` is raced via a hand-rolled `latest` ticket counter, and `pokemon/[name].client.ts:39-52` does fetch+`DOMParser`+node-adoption with the same pattern instead of aborting stale in-flight fetches. Works today, but the platform primitive would cancel the requests, not just ignore the results.

### `dependencies` — 4

Lean and current, with one redundancy:

- `app/package.json:9` — `lit` 3.3.3 = registry latest. `express` 5.1 = latest. Dev deps: `vite` 8.3.5 (rolldown-based, current major), `typescript` 7.0.2 (native-port line, current), `@types/node` 24, `@types/express` 5.
- Redundant: `app/package.json:12-13` — `@lit-labs/ssr` and `@lit-labs/ssr-client` are declared as direct deps but **never imported by any app source** (grep `@lit-labs` in `app/src` → 0 matches), and both are already transitive deps of `@gracile/gracile` 0.11.0 / `@gracile/client` 0.5.7 per the registry manifests. The app uses no custom elements or hydration, so `ssr-client` in particular is dead weight. The official starter declares neither.

### `churn_resistance` — 4

Genuinely good architecture for a framework that's still pre-1.0:

- Data access is behind exactly two modules: `app/src/lib/api.ts` (fetch + cache, the only place that knows `API_BASE_URL`) and `app/src/lib/data.ts` (API records → typed view models). Routes only consume view models from `app/src/lib/types.ts`. An API change touches one file.
- Server and client render the **same templates** (`app/src/templates/components.ts:49` `browseResults` is used by both SSR `(home).ts:24` and the client script `(home).client.ts:15`) and the same filtering logic (`lib/browse.ts`), so SSR and client output can't drift — the classic MPA failure mode is designed out.
- The framework surface is confined to the 7 route files, `server.js`, and one line of `vite.config.ts:11` (`gracile({ output: 'server' })`). An upgrade touches few, thin call sites.

Two real couplings:

1. `app/src/lib/api.ts:33-35` + `app/vite.config.ts:5-8` — the `POKEDEX_BUILD_STEP` env-var flag works around Gracile's build-time handler invocation (rendering document shells). This behavior is not part of the documented `ModuleOptions` (`route.d.ts` shows `prerender`/`staticPaths` but no build-context flag), and the guard is repeated in all six handlers (`(home).ts:12`, `pokemon/[name].ts:111`, `moves/[name].ts:11`, `abilities/[name].ts:11`, `types/[name].ts:11`). If a future Gracile release exposes a first-class "is this a prerender pass" context flag — or stops calling handlers at build — six files need touching. At least it's centralized behind one function.
2. `app/src/document.ts:16-17` — stylesheet hrefs computed as `new URL('./styles/tokens.css', import.meta.url).pathname`, instead of the documented `/src/styles/global.scss`-style href that Vite rewrites during build. This depends on how the server bundle resolves `import.meta.url` and on the static middleware layout — exactly the kind of bundler-implementation coupling that breaks silently on a Vite major bump.

### Findings summary

The two medium-ish items are the build-step env hack and the CSS href trick; everything else is nitpicks on an otherwise current, well-modularized codebase. I'd approve this PR with comments on findings 1–3.
