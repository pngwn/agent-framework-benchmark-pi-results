## Review: Gracile + Lit Pokédex

I read the spec, the whole `app/` tree, and cross-checked the app's API usage against Gracile's current docs/engine source (v0.11.0 is current stable; `defineRoute` handler/document/template, `(name).ts` → parent-folder route, sibling `.client.ts` client bundles, `gracile.nodeAdapter`, `Response.json` endpoints — all confirmed idiomatic, and `@lit-labs/ssr`/`ssr-client` are required peer deps of the engine, so declaring them is correct).

The structure is genuinely good: a clean `lib/` layering (`api.ts` transport+cache, `data.ts` server-only loaders, `browse.ts`/`format.ts`/`types.ts` pure shared server/client modules, `templates/` shared Lit partials), with server-only code never leaking into client bundles. Client scripts handle races with tickets, fall back to full navigation on failure, and keep the URL as the source of truth — MPA-first, progressively enhanced, which is exactly Gracile's pitch. Lit's auto-escaping, slug-validated `getByName` (no traversal), semaphore-bounded fan-out, promise-cached 60s API cache with failures evicted, and per-route 404 status all hold up under scrutiny.

Two things I'd hold a review round for: the stylesheet is loaded via `new URL('./styles/tokens.css', import.meta.url).pathname` (`app/src/document.ts:17-18`) instead of the documented root-relative source path; it only works because Vite happens to resolve the emitted absolute filesystem path at build time and Gracile then strips the (dead) runtime link and re-injects the hashed one — invisible to the a11y-only tests, and a Gracile/Vite update could silently unstyle every page. Second, the `POKEDEX_BUILD_STEP` env-var gate (`app/src/lib/api.ts:21`, `app/vite.config.ts:7`) that stops Gracile's build-time document render from touching the API is a reasonable workaround (no framework feature exists), but it's a hidden global that every handler has to know about and deserves a comment in the routes that consume it.
