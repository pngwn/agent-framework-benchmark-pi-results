## Review: forward-thinking — Pokédex app (Next.js 16.4.3)

**Version currency.** The app pins `next@16.4.3`, which I verified is the latest stable release (released Oct 23, 2026, including the Oct 14 security fixes) and `react@19.3.1`, which matches what 16.4 ships (`app/package.json:6-8`). Nothing in the codebase is legacy-era: no Pages Router, no `getServerSideProps`, no class components, no `unstable_` APIs, no separate `viewport` in `metadata`.

**Current APIs used correctly** (each verified against the live Next.js docs):
- `await connection()` from `next/server` in `app/src/lib/api.ts:46` — the stabilized v15+ replacement for `unstable_noStore`, and still the documented way to opt out of prerendering.
- Async request APIs: `params`/`searchParams` as `Promise`s (`app/src/app/pokemon/[name]/page.tsx:35-36`) — the mandatory Next 15+/16 form.
- `generateMetadata` per page and the separate `viewport` export (`app/src/app/layout.tsx:13-17`) — current.
- Native `window.history.pushState`/`replaceState` shallow routing synced with `useSearchParams` (`app/src/app/HomeView.tsx:135-138`, `MovesSection.tsx:99-103`) — a documented pattern in the SPA guide ("pushState and replaceState calls integrate into the Next.js Router, allowing you to sync with usePathname and useSearchParams").

**The main forward-looking gap:** the Next.js 16.4 release post (Oct 6, 2026) says Cache Components is now "the best choice for every Next.js app", that all new `create-next-app` apps have it enabled, and that it "will become the default in Next.js 17". This greenfield app — built on exactly 16.4.3 — stays on the previous model: dynamic-everything via `connection()` + `cache: 'no-store'` plus a hand-rolled TTL/LRU in-memory cache (`app/src/lib/api.ts:15-33`) and `prefetch={false}` on every link (7 occurrences). That's defensible (it satisfies the spec's request-time-fetching rule and is fully supported in 17 — `connection()` keeps working), but the hand-rolled cache is precisely what `'use cache'`/`cacheLife` now covers, and the pervasive `prefetch={false}` is a workaround for the old model's expensive prefetches that partial prefetching solves.

**Churn risks:**
- The API boundary is untyped: `api<T = any>` (`app/src/lib/api.ts:44`) and `any`-typed records threaded through pages (`app/src/app/pokemon/[name]/page.tsx:84-100`, `abilities/[name]/page.tsx:36`) mean no compiler help when data shapes or refactor rules change. The data access itself is otherwise excellently isolated — all HTTP goes through `lib/api.ts`, all display helpers are pure (`lib/format.ts`), so a fetch-strategy change touches one file.
- Two client views depend on the loosely-specified corner of the router: `MovesSection.changeGame` writes with raw `replaceState` and expects `useSearchParams` to re-render. That sync has open bug reports (vercel/next.js#72322) and community reports that in 16.4 `replaceState` does not always update `useSearchParams` — exactly the kind of behavior most likely to shift again when the router is reworked for 17.
- `HomeView` re-implements link semantics by hand (modifier-key checks in `goToPage`, `app/src/app/HomeView.tsx:117-124`) rather than composing `next/link`, adding surface area that future router changes won't automatically cover.

**Platform usage is a strong point:** `URLSearchParams`/`URL` for all query handling, native `<select>`/`type="search"`/`<table>`/`<dl>` instead of JS widgets, CSS custom properties/grid/columns, `:focus-visible`, `loading="lazy"`, `fetchPriority="high"`, `padStart`, `.at(-1)`, ES2022 target, and no polyfills or hand-rolled utilities beyond a justified regex for API URL id extraction (`app/src/lib/format.ts:27`).

**Dependencies are exemplary:** three runtime deps, all first-party and current; no CSS framework (spec-compliant), no state/fetch library needed.
