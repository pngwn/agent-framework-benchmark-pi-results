I've reviewed the whole app (`app/src`), the spec, and checked the idioms against current Next.js (16.4.x: `params`/`searchParams` as Promises, separate `viewport` export, `connection()` from `next/server` to force dynamic rendering, `history.pushState` integration for shallow URL updates — all current and correct, so nothing to flag as outdated).

## Scenario walkthroughs

1. **Remove Abilities** — delete `app/src/app/abilities/`, then remove the Abilities section in `app/src/app/pokemon/[name]/page.tsx:160-174` (the only inbound links). Trivial leftovers: `.bullets` CSS (`globals.css:372`) becomes dead, and `layout.tsx:9`'s description mentions "abilities". No nav link exists. Difficulty 4.
2. **Sprite bug** — the URL is built in exactly one function, `spriteUrl()` at `app/src/components/PokemonCard.tsx:15`, and every list renders through `PokemonCard` (home at `HomeView.tsx:140`; moves/abilities/types via `PokemonCardList`). One fix covers all four lists. Caveat: if the fix needs actual Pokémon-record sprite data, `CardData` must gain a field and both producers (`cards.ts` and `page.tsx`) update. Difficulty 4.
3. **Sort by name** — sorting happens in two independent places: `cards.ts:22` (moves/abilities/types lists) and `page.tsx:65` (home), which builds its own parallel entry shape instead of reusing the card abstraction. Adding a user-facing sort control also means new client components for three server-rendered pages. Difficulty 3.
4. **Items section** — `lib/api`, `lib/format`, `Section`, `PokemonCardList` all stretch cleanly; but the detail-page boilerplate (fetch-by-slug + `notFound()` + `generateMetadata`) is copy-pasted in four pages, so a fifth copy is the path of least resistance rather than a shared helper. Difficulty 3.
5. **API base URL / caching** — genuinely centralized: `apiBaseUrl()` and the re-rooting of absolute API URLs (`api.ts:17-19, 41-42`), TTL/max-entries (`api.ts:10-11`), and `cache: 'no-store'` (`api.ts:31`) all live in `api.ts`; callers only call `apiBaseUrl()`. One leak: `spriteUrl` in `PokemonCard.tsx:15-17` separately hardcodes the media path scheme. Difficulty 4.

## Scoring rationale

- **removability: 4** — routes are self-contained directories; abilities costs one directory delete plus one section edit; only minor dead CSS/text left behind.
- **changeability: 4** — the concrete bug has a single, obvious fix point covering all lists; docking for the 4× duplicated slug-fetch/`notFound`/`generateMetadata` boilerplate and the 5× repeated `typeLabels.get(x) ?? humanize(x)` fallback (`types/[name]/page.tsx:39` is the only place that localized it).
- **coupling: 3** — props are narrow, server/client split is clean and explicit; but the positional `IndexEntry` tuple (`HomeView.tsx:19`, consumed with magic `e[2]`/`e[3]` at `HomeView.tsx:66-67`) tightly couples `page.tsx` and `HomeView`; `MovesSection` takes game state from two sources (`initialGame` prop *and* `useSearchParams`, `MovesSection.tsx:117-120`); and `lib/cards.ts:3` imports a type from `components/` (layering inversion).
- **abstraction_design: 3** — `Section`, `cardsFor(refs, note)` (callback instead of flag params, `cards.ts:11`), and `CardData` are well-shaped; but `CardData` didn't stretch to the home page's needs (types+generation), so home bypasses it with a bespoke tuple, and the detail-page pattern is pure copy-paste across four routes.
