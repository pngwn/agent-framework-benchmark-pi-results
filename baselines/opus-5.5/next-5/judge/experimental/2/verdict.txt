**Config scan** — `app/next.config.ts` sets only long-stable options: `poweredByHeader` (stable since 13.x), `compress: false` (stable), and `turbopack: { root: import.meta.dirname }` — the top-level `turbopack` key is stable since 15.3.0 (`app/next.config.ts:5`). No `experimental.*` block, no `cacheComponents`, no `unstable_`/`experimental_` names anywhere in `app/src` (grep confirmed zero matches).

**API surface** — imports are all stable: `Metadata`/`Viewport` exports, `next/link`, `notFound`, `useSearchParams`, `use client`, and Promise-based `params`/`searchParams` (stable since 15, default in 16). The single most "modern" API is `connection()` from `next/server`, used once inside the data layer (`app/src/lib/api.ts:1,44`). Per the official docs version history, `connection` was **stabilized in v15.0.0** (Oct 2024) — roughly two years before today, so it is neither experimental nor recently-stable, and the docs no longer flag it.

**Justification of the modern choices** — `connection()` is actually load-bearing here: the spec forbids fetching/embedding API data at build time, and without any request-time API like `cookies()`/`headers()`, pages would otherwise be prerendered at build; `connection()` forces request-time rendering. The docs even note it's the successor to `unstable_noStore`. Likewise, the hand-rolled 30s in-memory TTL cache plus `fetch(url, { cache: 'no-store' })` (`app/src/lib/api.ts:30-35`) sidesteps Next's `unstable_cache`/`use cache`/Cache Components family entirely — the lowest-risk option given the "data can change at any moment" requirement. Notably absent are Next 16's headline preview features (Cache Components/PPR, `proxy.ts`, Build Adapters) — the app didn't reach for any of them.

**Containment** — nothing to contain; the one newer-than-average API lives in a single shared module behind the `api()` wrapper, so swapping it would touch one file.
