## Review: `app/` Pokédex (SvelteKit), judged 2026-10-30

I read the whole app (19 source files) and verified the framework facts against current docs. Key context: **SvelteKit 3.0 shipped 2026-10-01** (current 3.1.1) and removed/renamed a lot — `svelte.config.js`, `$app/stores`, `$env/*`, `$lib`, `base/assets/resolveRoute`, `keepFocus/noScroll` → `reset`, `replaceState` → `replace`, `page.url` is now readonly, and config lives in the `sveltekit()` Vite plugin ([migration guide](https://svelte.dev/docs/kit/migrating-to-sveltekit-3), [release blog](https://svelte.dev/blog/sveltekit-3-is-here)). This app is not merely compatible with Kit 3 — it is written *in* Kit 3's idiom, three to four weeks after release:

- `app/vite.config.ts:6-13` — config in the `sveltekit()` plugin (`adapter`, `compilerOptions`), no `svelte.config.js`; exactly the Kit 3 layout.
- `app/vite.config.ts:9-11` — parametric `compilerOptions.runes: ({ filename }) => ...`, a feature added in Svelte 5.57 (March 2026, sveltejs/svelte#17951) for precisely this "runes for app code, leave node_modules alone" use case, with a comment noting it can drop in Svelte 6.
- `app/package.json:6-15,27-32` — deps sit on Kit 3's exact minimum matrix (svelte 5.57, TS 6, Vite 8, VPS 7, adapter-node 6); `#lib/*` is a real Node subpath-import, and imports use explicit `.ts` extensions, per the Kit 3 `$lib` → `#lib` migration.
- `app/src/routes/+error.svelte:2` / `pokemon/[name]/+page.svelte:16-19` — `page` from `$app/state` (not the removed `$app/stores`), and the doc-recommended `new URL(page.url.href)` copy for the now-readonly `page.url`, `goto(url, { replace: true, reset: false })` using the *new* option names.
- `app/tsconfig.json:2-3` — extends `$app/tsconfig` (not `.svelte-kit/tsconfig.json`) as Kit 3 requires.
- Components are uniformly Svelte 5: `$props`/`$state`/`$derived.by` (`MoveTable.svelte:57-70`), snippets (`+page.svelte:23-31`), `style:--badge-bg` custom-prop shorthand (`TypeBadge.svelte:9,11`). A repo-wide grep finds zero legacy constructs (`export let`, `$:`, `on:` handlers, `createEventDispatcher`, `$lib`, `$env/*`, `$app/stores`).

The main forward-looking reservations are the environment seam and the typing at the data boundary. `app/src/lib/server/api.ts:12` reads `process.env.API_BASE_URL` directly instead of Kit 3's `defineEnvVars` in `src/env.ts` + `$app/env/private` ([env docs](https://svelte.dev/docs/kit/environment-variables) — the `$env/*` modules are deprecated and will be removed in Kit 4). It works and is confined to one function, but it bypasses framework validation and hard-couples the app to the Node runtime (which is why `"types": ["node"]` appears in tsconfig). Likewise, data access is admirably centralized — every route load goes through `#lib/server/api.ts` and pages only see shaped, serializable objects — but the API shapes themselves are `any` (`get<T = any>` at `api.ts:29`, `englishEntry<any>` casts in the loads), so a PokeAPI shape change would surface as runtime bugs rather than type errors. Small stuff: a duplicated `MoveRow` shape between the page server and `MoveTable.svelte`, a fetch seam with no timeout/AbortSignal, a stray non-standard `<meta name="text-scale">`, and a debounce timer that isn't cleared on unmount.
