## Review: forward-thinking

**Framework currency.** This app is on SvelteKit **3.1.0** — the stable major released 2026-10-01 — and it uses its conventions correctly rather than the Kit 2 patterns most training data contains. I verified each claim against the official migration guide and blog (svelte.dev/docs/kit/migrating-to-sveltekit-3, svelte.dev/blog/sveltekit-3-is-here):

- Config lives in the `sveltekit()` Vite plugin with `adapter` and `compilerOptions` as top-level plugin options (`app/vite.config.ts:5-13`) — exactly the Kit 3 shape; there is no `svelte.config.js`. ✅
- `$lib` → Node subpath imports `"#lib/*"` declared in `package.json:11-13` and used with extensions (`+layout.svelte:2`). ✅
- `tsconfig.json:2` extends `$app/tsconfig` (not `.svelte-kit/tsconfig.json`) with `"types": ["$app/types", "node"]` — matches the Kit 3 tsconfig overhaul (kit PR #16458). ✅
- `$app/state#page` instead of the removed `$app/stores` (`+error.svelte:2`, `pokemon/[name]/+page.svelte:3`); `error(404, …)` without `throw` — the current idiom, `error()` is typed `never` (`moves/[name]/+page.server.ts:5`). ✅
- `goto(url, { replace: true, reset: false })` uses Kit 3's renamed options (`replaceState`→`replace`, `keepFocus/noScroll`→`reset`) (`pokemon/[name]/+page.svelte:19`, `+page.svelte:40`); `new URL(page.url.href)` copies the now-readonly `page.url` as the migration guide prescribes (`pokemon/[name]/+page.svelte:16`). ✅
- Svelte 5 runes throughout (`$props`, `$state`, `$derived`, `$derived.by`), snippets/`{@render}` instead of slots, `onclick`/`oninput`/`onsubmit` instead of `on:` (`MoveTable.svelte:47`, `+page.svelte:58`); runes forced project-wide via `compilerOptions.runes` with an accurate "remove in svelte 6" note (`vite.config.ts:7-9`). A grep found zero legacy remnants (`$lib`, `on:click`, `export let`, `$app/stores`, `throw error`).

**Platform.** Fetch with `res.body?.cancel()` on non-OK responses to avoid leaking undici bodies (`api.ts:45-55`), `URLSearchParams` for query building and `FormData` for reading controls (`+page.svelte:20`, `:30`), native `<form method="GET">` with a `<noscript>` submit fallback (`+page.svelte:58`, `pokemon/[name]/+page.svelte:118-126`), rem-based tokens, `:focus-visible`, `loading="lazy"`, keyed eaches, `localeCompare`/`replaceAll`/`padStart`. Notably `app.html:6` opts into `<meta name="text-scale" content="scale">` — a real, newly-shipped Chromium accessibility feature (MDN, Sept 2026; Blink Intent to Ship, Jan 2026) that is coherent here because `tokens.css:9` defines sizes in rem. That's platform-forward, not a mistake.

**Dependencies.** Zero runtime dependencies; the 8 devDeps are precisely the current toolchain (Kit 3 requires Svelte ≥5.57.1, Vite ≥8, vite-plugin-svelte 7, TS 6 — all satisfied at `package.json:16-24`). Nothing heavy, nothing redundant.

**Churn resistance.** All API access sits behind one module (`src/lib/server/api.ts`: base URL, URL resolution, TTL cache with promise de-duplication, localization helpers, indexes, card mapping) — an upgrade or API change would touch few files. The main weakness is that this boundary is largely `any`-typed (`get<T = any>` at `api.ts:29`, `TypeInfo.data: any` at `api.ts:118`, `(s: any)` casts and `as number` in `pokemon/[name]/+page.server.ts:87,158`), so upstream data-shape changes surface at runtime rather than compile time; view models are typed (`Card`, `MoveRow`, `EvolutionNode`) but the raw PokeAPI resources are not. Secondary nits: `process.env.API_BASE_URL` couples server code to the Node runtime (Kit 3 prefers `$app/env/private`), route path strings are hardcoded per-component, and the search debounce timer isn't cancelled on unmount.
