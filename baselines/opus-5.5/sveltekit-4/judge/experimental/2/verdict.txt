## Review: experimentalness

**Platform context (verified against current docs/notes):** SvelteKit 3.0.0 went stable on **2026-10-01** (blog: "SvelteKit 3 is here"; latest is 3.1.1, 2026-10-29). Svelte is at 5.57.x, Vite 8.3.x, TypeScript 6.0.x — all stable. Kit 3 moved configuration into `vite.config.ts`, replaced `$lib` with `#lib` subpath imports, renamed `goto` options (`replaceState`→`replace`, `keepFocus`/`noScroll`→`reset: false`), removed `$app/stores` in favour of `$app/state`, and requires TS 6 / Vite 8 / vite-plugin-svelte 7 / Svelte 5.57.1. Remote functions are **still experimental** per the Kit 3 announcement.

**What the app does:** It is a model Kit-3 citizen. No experimental, preview, RC or canary APIs anywhere — the measured `experimental` markers are empty, and a grep of `app/` for `experimental|unstable_|preview|beta` only matches transitive metadata in `package-lock.json`. The installed lockfile (`app/package-lock.json:394-407, 1129-1145, 1218-1246`) confirms stable versions only: kit 3.1.0, vite-plugin-svelte 7.3.1, adapter-node 6.0.0, svelte 5.57.2, vite 8.3.5, typescript 6.0.3.

**The only "newness" exposure:** the entire app rests on the SvelteKit 3 platform, whose stable release is four weeks old, and whose now-mandatory conventions (vite.config plugin options, `#lib`, renamed `goto` options, `$app/tsconfig`) are used in central places. Notably, these uses are *not* optional novelty — Kit 3 removed every older alternative (`svelte.config.js` unsupported, `$lib` alias no longer generated, old `goto` option names gone). The app also correctly avoided the one genuinely experimental flagship feature — remote functions — using mature `+page.server.ts` load functions instead (`app/src/routes/+page.server.ts:8`, `app/src/routes/pokemon/[name]/+page.server.ts:36`). The `runes: ({ filename }) => ...` compile option (`app/vite.config.ts:10`) is a documented, stable compiler option (`runes?: boolean | undefined | ((options: { filename: string }) => boolean | undefined)` per svelte.dev/docs/svelte/svelte-compiler) and mirrors the compiler docs' own advice to avoid forcing runes onto `node_modules`.

**Long-stable APIs used correctly:** `$app/state#page` (Kit 2.12.0, Dec 2024; PR sveltejs/kit#13140) at `app/src/routes/+error.svelte:2` and `app/src/routes/pokemon/[name]/+page.svelte:3`; `PageProps`/`LayoutProps` generated types (Kit 2.16.0, Jan 2025; PR sveltejs/kit#13308) at `app/src/routes/+page.svelte:5`, `app/src/routes/+layout.svelte:7`; Svelte 5 runes/snippets/`style:` with CSS custom properties throughout (`app/src/lib/components/MoveTable.svelte:55` `$derived.by`, `app/src/lib/components/TypeBadge.svelte:9`); `error()` and `afterNavigate` used in the post-Kit-2/3 call forms (`app/src/routes/pokemon/[name]/+page.server.ts:38`, `app/src/routes/+page.svelte:16`). Kit 3's readonly `page.url` is handled per the migration guide by copying before mutation (`app/src/routes/pokemon/[name]/+page.svelte:13`).

Risk assessment: minimal. Breaking changes are behind us (stable majors); the residual risk is only that patch/minor churn is active in the first month of these majors, and the `#lib` alias string is spread across nearly every module — though swapping it would be a single mechanical find/replace.
