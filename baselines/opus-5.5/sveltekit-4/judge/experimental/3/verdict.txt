I've reviewed the app, the spec, and the SvelteKit 3 documentation/release notes. Here's my assessment for the **experimentalness** dimension.

## Context

SvelteKit 3.0.0 shipped **Oct 1, 2026** (svelte.dev/blog/sveltekit-3-is-here) — 29 days before today. The app is written entirely in Kit 3 idioms and **contains zero experimental, preview, RC, or canary APIs**. Notably, the Kit 3 announcement explicitly says remote functions (the framework's flagship new direction) still require an `experimental` flag — the app does **not** use them, and solves its data needs with ordinary server `load` functions over HTTP (`app/src/lib/server/api.ts:1-80`).

What is "very new" here is *stable-only-recently*:

- **Kit 3 config-in-`vite.config.ts` + adapter passed to the `sveltekit()` plugin** (`app/vite.config.ts:5-13`) — this is the *mandatory* Kit 3 pattern; `svelte.config.js` is "no longer supported" per the official migration guide (svelte.dev/docs/kit/migrating-to-sveltekit-3).
- **`#lib` subpath imports** (e.g. `app/src/routes/+layout.svelte:2`, `app/src/routes/+page.server.ts:1`) — the Kit 3 replacement for `$lib`.
- **Function-form `compilerOptions.runes: ({filename}) => ...`** (`app/vite.config.ts:8-10`) — merged into Svelte on 2026-03-17 (sveltejs/svelte#17951) as the sanctioned replacement for the deprecated `dynamicCompileOptions`, with this exact node_modules-exclusion example in the PR itself.
- **`error()` called without `throw`** (`app/src/routes/pokemon/[name]/+page.server.ts:68-69`) — standard since Kit 2.16 and reinforced by Kit 3's "consistent error handling".
- **`$app/state`** (`app/src/routes/+error.svelte:2`) — stable since Kit 2.12 (Mar 2024) and now *required*, since `$app/stores` was removed in 3.0.

Dependency versions match Kit 3's documented minimums exactly (`app/package.json:14-21`: svelte ^5.57.1, TS ^6, Vite ^8.3, vite-plugin-svelte ^7.2, node >=22.17), confirming the app is aligned with the current stable release rather than next-channel tooling. A repo-wide grep found no `unstable_`/`experimental` markers in `app/src`.

## Scoring

- **reach: 3** — No experimental APIs at all, but the app is built centrally on a major release that is one month old and on a compiler option that is ~7 months old ("recently-stable APIs in central places").
- **containment: 5** — Nothing experimental to contain; the one non-default knob (runes forcing) sits in a single 17-line config file with a self-documenting removal note (`app/vite.config.ts:7-10`).
- **justification: 5** — Every new API is the documented, often mandatory, current-stable path (Kit 3 migration guide mandates vite.config.ts and `#lib`; `$app/state` is required since stores were removed; the runes function form replaces a deprecated plugin option), and the app resisted the genuinely-experimental remote functions.
- **overall: 4** — Exemplary conservatism: fully current-stable, no experimental reach; the only residual risk is the recency of Kit 3.0 itself, which caret ranges mitigate.
