I've reviewed the whole app and verified the APIs against current Nuxt 4.6 documentation and release notes. Here is my review.

## Review

**Stack currency.** This is a Nuxt 4-generation app written against the current stable line: `nuxt ^4.6.2` (4.6.3, released 2026-10-27, is the latest patch), `vue ^3.5.44`, `vue-router ^5.4.0` (v5 is what Nuxt ≥4.4 ships with — confirmed via the Nuxt 4.4 release notes and vue-router's v4→v5 migration guide), and `compatibilityDate: '2026-10-01'`. App-side code uses the current primitives: awaited `useFetch` behind one composable (`app/app/composables/usePageData.ts:5`), `useId()` for section headings (`app/app/components/PageSection.vue:3`), reactive `useHead` getters, `clearError({ redirect })` (`app/app/error.vue:9`), and `NuxtLink :external` for the out-of-router error page (`app/app/components/SiteHeader.vue:8`). The Nuxt 4 `app/` + `server/` directory layout is the current default structure, used correctly with auto-imported `server/utils`.

**The main forward-looking miss:** Nuxt 4.6 introduced the `nuxt/server` import surface precisely so server code survives the Nuxt 5 / Nitro v3 / h3 v2 upgrade. The blog says the auto-imported `defineEventHandler` family on Nuxt 4 "are still h3's own helpers" and to "import from `nuxt/server` explicitly… to use the new server runtime" (nuxt.com/blog/v4-6). All five server handlers (`app/server/api/pokemon/[name].get.ts:24`, `abilities/[name].get.ts:1`, `moves/[name].get.ts:1`, `types/[name].get.ts:10`, `types/index.get.ts:1`) still use the auto-imports, so the eventual Nuxt 5 migration touches every server file. Nothing is deprecated — the blog is explicit that "nothing in this release requires a migration" — but this is the exact churn the new API exists to prevent, and the app was written *on* 4.6.

**Boundary types.** All PokeAPI access is behind one module (`app/server/utils/pokeapi.ts`) and every page loads through `usePageData` — genuinely good isolation. But the payload types are hand-duplicated per page with no shared source of truth: `EvolutionNode` exists verbatim in both `app/server/api/pokemon/[name].get.ts:10` and `app/app/components/EvolutionList.vue:2`, and `PokemonData` (`app/app/pages/pokemon/[name].vue:9`) must be kept in sync by eye with an untyped (`any`-derived) server return. Nuxt 4 has a `shared/` directory and route-typed fetch for exactly this; the app opts out of `experimental.routeTypedFetch` too. Compounding this, there is no root `tsconfig.json` (the docs' required project-references file), so no type-check can catch drift — there is no type-check step at all (zero devDependencies).

**Platform & robustness.** The platform is used first in the right places: native `fetch` rather than an HTTP lib (`app/server/utils/pokeapi.ts:25`), `loading="lazy" decoding="async"` on sprites (`app/app/components/PokemonCard.vue:11`), logical properties and `aspect-ratio` (`app/app/assets/main.css:53`, `:369`), and a CSS custom property with a fallback for type colors (`app/app/components/TypeBadge.vue:3`). Two gaps: upstream fetches have no timeout/abort, so a slow PokeAPI response hangs an SSR render indefinitely (`AbortSignal.timeout()` or `$fetch`'s `timeout` would fix it), and query strings are rebuilt with `key.split('?')` string surgery instead of `URL`/`URLSearchParams`. The hand-rolled promise-cache (`app/server/utils/pokeapi.ts:5-6`) also re-implements Nitro's `defineCachedFunction`, which provides TTL, in-flight dedupe and pluggable storage for free.

**Dependencies.** Three runtime packages, no CSS/UI framework, no axios, no lodash — minimal and modern.
