## Review: `app/` (Nuxt Pokédex) — Editability

**Stack check:** `nuxt ^4.6.2` with the Nuxt-4 `app/`-directory layout, Nitro `server/` routes, auto-imported composables/components, `useId`, `useFetch`-based data loading — all current-stable idioms (Nuxt 4.6.3 released 2026-10-27; vue-router 5.4 is the current line). Nothing experimental. The architecture is a clean client/server split: Nitro handlers do all PokeAPI fan-out and shaping; pages consume versioned-ish DTOs via one thin composable, `usePageData` (`app/app/composables/usePageData.ts:5`).

**What holds up well**

- Removing Abilities touches exactly three places: delete `app/app/pages/abilities/`, delete `app/server/api/abilities/[name].get.ts`, and drop the `Abilities` section at `app/app/pages/pokemon/[name].vue:131-135`. No nav link, no cross-references, no dead helpers left behind.
- The sprite-bug fix has an obvious home: every card list's `sprite` field flows through `spriteUrl` (`app/server/utils/pokeapi.ts:15`), used by `cardsFor` (moves/abilities/types lists, `pokeapi.ts:125`) and by the home page payload (`app/server/api/pokedex.get.ts:47`). One fix in that one function covers every list; `PokemonCard` just renders the string (`app/app/components/PokemonCard.vue:9`).
- API base URL and the cache (TTL, eviction) live only in `app/server/utils/pokeapi.ts:6-33`. A data-source or caching-policy change is one file.
- `cardsFor(refs, extra?)` (`app/server/utils/pokeapi.ts:114-135`) is a genuinely stretchy abstraction: abilities feed Pokémon refs plus a `hidden` flag through the same path moves and types use, with the `extra` callback carrying only the variation.

**What I'd flag in review**

- `humanize` is implemented twice: `app/app/utils/format.ts:6` (client) and `app/server/utils/pokeapi.ts:43` (server). Nuxt 4 auto-imports a `shared/utils/` folder into both contexts, so this is avoidable drift risk — a display-rule change (e.g. `mr-mime` → `Mr. Mime`) lands twice.
- The excluded-types list is duplicated: `EXCLUDED_TYPES` in `app/server/utils/pokeapi.ts:60` vs. the inline array at `app/server/api/types/[name].get.ts:9`.
- The alternate-forms rule (`id > 10000`) appears in `cardsFor` (`pokeapi.ts:123`) and again in `app/server/api/pokedex.get.ts:20`.
- `learn: [string, string, number][]` (`app/server/api/pokemon/[name].get.ts:66`, consumed with positional destructuring at `app/app/pages/pokemon/[name].vue:59`) is an opaque positional contract between server and page; a named `{ versionGroup, method, level }` shape would be easier to extend (e.g. adding "at what level in which game").
- The home page payload (`pokedex.get.ts`) rebuilds card-shaped data (id/name/sprite/types) instead of reusing `cardsFor`, so card-shape changes touch two server builders.
- Page DTOs are re-declared as local interfaces in each page (`app/app/pages/moves/[name].vue:3-13` etc.) duplicating the server handler's output shape; harmless today but a silent-contract seam.
- Adding name-sorting to card lists is the weakest extension point: there is no shared "card list" past `CardGrid` (a bare `<ul><slot/>`, `app/app/components/CardGrid.vue:1`), so the sort would be written per-page (4 pages) or bolted into `cardsFor` server-side while the home list (`app/app/pages/index.vue:77`) sorts client-side by a different mechanism.
