## Review — editability of `app/`

**Architecture in brief.** The app is a strict two-layer design: `src/server/` (an `api-client.ts` with TTL caching + `loaders.ts` that builds view models) and `src/app/` (presentational components that receive typed VMs). Server and browser share data only through narrow VM interfaces (`app/src/app/shared/models.ts`) and a `PageData` service that hands server-rendered VMs to the browser via `TransferState` / the `/_data` endpoint (`app/src/app/data/page-data.ts`). Server code is imported only by the server config (`app/src/app/app.config.server.ts:3-4`) — that separation is genuinely clean and is the reason most scenarios below land well.

### Scenario findings

1. **Remove Abilities** — delete `app/src/app/pages/ability/`, then edit `app/src/app/app.routes.ts:39-42`, `app/src/server/loaders.ts:320-332` and `:410`, `app/src/app/shared/models.ts:27-32`, and the Abilities section in `app/src/app/pages/pokemon/pokemon-page.html:59-70`. Mechanical and named-after-the-feature, but spread over five places plus a directory. Difficulty 3.
2. **Sprite fix** — the sprite URL is derived in exactly one computed, `app/src/app/shared/pokemon-card.ts:44`, and *every* card list (home, move, ability, type) renders `<app-pokemon-card>`, so one fix covers all lists. Caveat: the URL scheme lives in the view layer, not in the VM, so if the fix needs per-species data you must also extend `Card` in `models.ts`, `toCards` in `loaders.ts:162-172`, and `home.ts`'s separate card props. Difficulty 4.
3. **Sort by name on all card lists** — one edit in `app/src/app/shared/card-list.ts:9-14` covers move/ability/type; home has its own grid (`home.html:36-41`) and its own sort in `home.ts:71-75`, so it needs a second edit. Difficulty 4.
4. **Add Items (Moves-shaped)** — mostly new files. Reusable: `CardList`, `PokemonCard`, `NotFound`, `humanize`/`orDash`, and every loader helper (`englishName`, `latestFlavorText`, `toCards`, `speciesNames`, `shortEffect` — `loaders.ts:86-160`). New: `loadItem` + a case in `loadPageData` (`loaders.ts:394-412`), `ItemVM` in `models.ts`, a route in `app.routes.ts`, a component. The title strategy picks up the new page for free as long as the VM has `title`. Difficulty 4.
5. **Change data source / caching** — API base URL and cache TTL live in `app/src/server/api-client.ts:8-13`; the browser-side TTL in `app/src/app/data/page-data.ts:13`; the `/_data` response cache header in `app/src/server.ts:28`. The default `http://localhost:9000` is duplicated in two files. Difficulty 3.

### Scoring rationale

- **removability 4**: features are colocated in page directories, per-page loader functions, and per-page VM interfaces; deletion is delete-a-directory plus deleting the correspondingly-named entries in three registries (routes, loader switch, models). Held below 5 by the switch/duplication registries.
- **changeability 4**: sprite URL, dex formatting, move-table sorting, title formatting each live in one component/function; every card list shares `PokemonCard`. Held below 5 by the two card-grid implementations (home vs `CardList`) and the sprite-scheme-in-the-view choice.
- **coupling 4**: components depend only on VM interfaces; server/client boundary is enforced by imports; shared state (`API_BASE_URL`) is explicit via `InjectionToken` + `TransferState`. Docked for the stringly-typed route→loader-path contract (`app.routes.ts:22-47` vs `loaders.ts:394-412`, including the `types/:name` → `/type/...` naming mismatch) and `PageTitleStrategy`'s dependence on the resolver key name `vm` (`page-title-strategy.ts:14-19`).
- **abstraction_design 4**: `Card`/`CardList`/`TypeBadge`/facts-dl and the loader helpers stretch to a new Items section with no copying and no flag creep (`link` on `TypeBadge` is the only flag and it's justified); home's divergence from `CardList` reflects real variation (pagination, types, priority) rather than bad abstraction.
