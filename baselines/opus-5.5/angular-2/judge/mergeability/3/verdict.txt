## Review

This is a genuinely well-built Angular 22 app. I verified the current-framework claims before crediting or dinging them:

- **Up-to-date primitives.** Zoneless by default (no `zone.js` in `app/package.json`), `@Service()` on `PageData` (`app/src/app/data/page-data.ts:44`) — the decorator the docs migrated to in v22.1 — `input.required` + resolved-data binding via `withComponentInputBinding` (`app/src/app/app.config.ts`, `app/src/app/app.routes.ts:11-13`), `linkedSignal` for sort/filter state resets (`app/src/app/pages/pokemon/move-table.ts:64`, `home.ts:29`), `@if/@for/@else` control flow everywhere, `RESPONSE_INIT` for the SSR 404 status (`app/src/app/pages/not-found/not-found.ts:11-13`), `RenderMode.Server` per-request SSR (`app/src/app/app.routes.server.ts:4`), `provideAppInitializer` + `mergeApplicationConfig` (`app/src/app/app.config.server.ts`), hydration with `withEventReplay` and TransferState reuse so the client never refetches what the server rendered (`page-data.ts:56-63`).
- **The custom scroll logic is legitimate.** I checked the RouterScroller source: `Scroll` events are emitted even with both `withInMemoryScrolling` options disabled, and the router docs themselves show an App-component subscriber + `ViewportScroller` as the sanctioned way to do custom restoration. `app/src/app/app.ts:21-41` implements exactly that, with a comment explaining why (keep position on filter/game change, top on page change). Right call.
- **The architecture is a deliberate BFF.** Instead of the browser talking to PokeAPI (or `httpResource` per component), the Express server builds compact view models per page (`app/src/server/loaders.ts`) and serves them to the browser via `/_data/...` (`app/src/server.ts:17-25`). This is justified: a Pokémon page needs ~100 large API documents but only a few KB of view model, and the home page would otherwise need 28 requests in the browser. It's documented in `README.md`. The cost is a stringly-typed internal protocol that duplicates route knowledge and uses a second path vocabulary (`/types/fire` in the browser vs `/type/fire` in `/_data`, `/` vs `/home`) — `app/src/app/app.routes.ts:10-12` vs `app/src/server/loaders.ts:390-407` — so every new page touches four places.
- **Real nits, not blockers.** No `"strict": true` in `app/tsconfig.json` (Angular scaffolds strict by default; all the `| null` types in `models.ts` are currently unenforced). No user-visible handling of a failed resolver: a client-side `/_data` 500 rejects the navigation and the user stays on the stale page (`page-data.ts:14-17`); the server 500s. The module-level client cache is TTL-only with no size cap (`page-data.ts:11-12`), unlike its server counterpart (`api-client.ts:40`). `@angular/forms` is a dependency nothing imports. `API_BASE_URL`/`publishApiBaseUrl` are oddly homed in `page-data.ts:45-53`.

Not-found handling, URL-synced filters, debounced search with proper cleanup, sprite `onerror` fallback, malformed-path defense in `loadPageData`, and bounded, self-evicting server caching are all done carefully. I'd approve after one small round.
