I've read the whole app (`app/` = 17 source files: 6 routes, 4 client-enhancement scripts, 5 lib modules, a shared document), the spec, and checked current Gracile docs/releases (`@gracile/gracile@0.11.0` is the current stable; the app's `defineRoute` handler/document/template shape, `(home).ts` route naming, `honoAdapter` server and `@gracile/gracile/server-html` usage all match the framework's current idioms — the app uses server-rendered `html` literals plus plain Custom Elements for progressive enhancement rather than hydrated Lit islands, which is a legitimate, documented Gracile mode).

## How the app is put together

- **Layers are clean and thin**: `lib/api.ts` (transport + cache) → `lib/data.ts` (domain shaping, e.g. `pokemonRefsToSpecies`) → `routes/*` (per-page loaders) → `lib/templates.ts` (`pokemonCard`, `cardList`, `section`, `notFound`) → `document.ts`. Client scripts (`.client.ts`) are pure enhancement over server HTML.
- **Cards have exactly one render point**: `lib/templates.ts:22-40` — every one of the four Pokémon-card lists (home, move "Learned by", ability, type) goes through it.
- **API base URL, TTL, cache size, concurrency and media URLs live in one file**: `lib/api.ts:3-8,71-73`.
- **The URL-building contract is shared, not duplicated**: `lib/home-url.ts` is imported by both the server route (`routes/(home).ts:7`) and the client script (`routes/(home).client.ts:1`).

## Scenario findings

1. **Remove Abilities**: delete `app/src/routes/abilities/[name].ts`; then `routes/pokemon/[name].ts` (template block 337-350, loader mapping 177-179, type field 37). No nav link exists to remove (`document.ts:22-27` only has Pokémon/Types), and grep confirms no other inbound references. Very clean — difficulty 4.
2. **Sprite fix**: rendering is single-point (`templates.ts:27`, `spriteUrl(card.id)`); card `id` provenance is centralized in `data.ts:32` (`pokemonRefsToSpecies`) for the three reference-based lists, with the home list's ids coming from `data.ts:18/111`. One render fix covers everything; an id-derivation fix is two functions in one file — difficulty 4.
3. **Sort cards by name**: a sort inside `cardList` (`templates.ts:39`) covers all four lists in one edit; the only wrinkle is that the home list is paginated before rendering (`(home).ts:60`), so cross-page ordering needs a second, findable edit — difficulty 4.
4. **Items section**: the entire lib layer (`api.ts`, `data.ts` `pokemonRefsToSpecies`, `format.ts`, `templates.ts`) and `document.ts` reuse directly; what gets copied is the ~60-line route scaffold (`moves/[name].ts:18-89` loader + the handler/404/title triad at 57-66). No resource-page factory exists — difficulty 3.
5. **API base URL / caching change**: one file, `lib/api.ts` — difficulty 5.

The main frictions: the "fetch → DOMParser → replaceWith" enhancement helper is hand-duplicated in both client scripts; the loader → 404 status → document-title fallback → template `notFound()` triad is copy-pasted verbatim in four routes; and the `isBuildRender` build-render guard is an incantation every new route must remember (forgetting it would fetch API data at build time, a spec violation).
