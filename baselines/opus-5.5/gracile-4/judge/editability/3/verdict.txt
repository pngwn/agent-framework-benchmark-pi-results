I've reviewed the app, the spec, and verified the app's Gracile usage against the framework's current docs and official starter (`defineRoute` handler/document/template, `@gracile/gracile/hono` + `getClientBuildPath`, `src/document.ts`, `(home).client.ts`, `404.ts` — all match current 0.11 conventions). Here's my assessment.

## Scenarios worked through

1. **Remove Abilities** — delete `app/src/routes/abilities/` and the Abilities section in `app/src/routes/pokemon/[name].ts:177` (data) and `:340-347` (template + type field at `:37`); `.bullets` CSS in `document.css:174` is shared, so leave or trim. Nav never links abilities. Two files.
2. **Sprite bug** — `app/src/lib/templates.ts:25` is the single funnel: home (`(home).ts` via `cardList`), moves, abilities and types all render through `cardList`/`pokemonCard` (`templates.ts:42`). One fix covers every list.
3. **Name sorting** — `pokemonRefsToSpecies` sorts by id (`data.ts:45`, covers moves/abilities/types lists) and the home index sorts by id (`data.ts:138`); either sort in those two places or once in `cardList`.
4. **Items section** — new `routes/items/[name].ts` reuses `api.ts`, `data.ts` helpers, `templates.ts` (`section`, `cardList`, `typeLink`), `document.ts`, `format.ts`; but the ~10 lines of handler/document/404 wiring are copy-pasted in every route (e.g. `moves/[name].ts:59-67`), and the `Move` API type is declared twice with divergent shapes (`pokemon/[name].ts:40` vs `moves/[name].ts:20`).
5. **API base URL / caching** — one file: `lib/api.ts:4` (base URL), `:6-8` (TTL/limits), `:66-70` (media/sprite URLs). Only `server.js:21` (a log line) knows the env var otherwise.

## Strengths

- Clean layering: `api.ts` (raw client) → `data.ts` (domain) → `templates.ts` (presentation) → routes as thin compositions; client scripts are opt-in enhancements coupled only via element ids and the shared `homeUrl`.
- The Deoxys-style species/Pokémon mapping is centralized in `pokemonRefsToSpecies` (generic over source type), so every card list inherits it.
- Framework-idiomatic: matches the official Hono server starter nearly verbatim (`server.js`), and the docs' "routes should be entry points, not hold logic" guidance is followed (data loading factored into `loadX` + `lib/data.ts`).

## Weaknesses

- Route wiring (`isBuildRender` guard, 404 status, `document({...context, title})` wrapper, `if (!data) return notFound()`) is repeated verbatim in 4 route files and would be copied a 5th time for Items.
- `Move` type duplicated across two files with different shapes — a move-schema change touches both.
- Two near-identical fetch/DOMParser/`replaceWith` client implementations (`(home).client.ts:100`, `pokemon/[name].client.ts:56`).
- `isBuildRender` keys off the internal `gracile-static` hostname; every new route handler must remember to call it or the build prerender hits the API at build time (a spec violation waiting to happen).
- All CSS in one 566-line `document.css` (the starter convention is route-scoped `(home).css` siblings), so feature removal can leave dead rules.
