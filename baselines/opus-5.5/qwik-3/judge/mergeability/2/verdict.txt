## Review

**Framework version check**: The app pins `@builder.io/qwik`/`@builder.io/qwik-city` to `^1.20.3` (`app/package.json:11-12`). As of today (2026-10-30) `1.20.3` is the latest **stable** release (Qwik 2.0 is still at `rc`). So the app targets the current stable framework and its docs.

**What's good**

- Data loading is exactly the recommended shape: every page uses `routeLoader$` (`app/src/routes/index.tsx:25`, `app/src/routes/pokemon/[name]/index.tsx:22`, `types`, `moves`, `abilities`), with no client-side fetching of API data, no hand-rolled routing. Server-only code (`process.env.API_BASE_URL`) stays inside loader bodies; components only `import type` from the server module (`app/src/components/pokemon-cards.tsx:3`), keeping the server/client boundary clean.
- 404 handling is idiomatic and complete: `status(404)` inside each loader (`app/src/routes/moves/[name]/index.tsx:8`) plus a `[...catchall]` route that sets the status (`app/src/routes/[...catchall]/index.tsx:6`), and `head` uses `resolveValue` to title even the not-found case (`app/src/routes/pokemon/[name]/index.tsx:224`).
- URL-as-state is done thoughtfully: filters serialize via `listUrl` (`app/src/routes/index.tsx:18-24`), page clamping happens server-side (`index.tsx:40-41`), typing uses `replaceState` while select changes push history (`index.tsx:84`), and the `method="get"` form doubles as a no-JS fallback.
- The shared pieces are small and earn their keep: `Section` (`app/src/components/section.tsx:11`), `MovesTable` with `useComputed$` sorting and missing-values-last logic (`app/src/components/moves-table.tsx:37-52`), `cardsForPokemon` reused by three routes (`app/src/lib/api.ts:103`).
- Comments explain *why* (cache TTL rationale at `app/src/lib/api.ts:3-4`, search-sync rationale at `app/src/routes/index.tsx:67`, `no-store` rationale at `app/src/routes/layout.tsx:5-7`).

**What I'd ask about**

- The API layer is untyped: `api<T = any>` (`app/src/lib/api.ts:14`) plus 13 `any`s in loaders (`app/src/routes/pokemon/[name]/index.tsx:38,103,120-126`). A typo in `flavor_text_entries` or `version_group_details` silently renders `—` and tests only catch the ones they check. This is my main ask.
- The Pokémon loader fans out ~1 fetch per learnable move per version group plus every version group and all types (`app/src/routes/pokemon/[name]/index.tsx:54-61, 90-95`), and a single non-404 failure bubbles up as an opaque 500 — there's no per-fetch resilience and no error surface other than the framework default.
- `go()` reads the selects out of the DOM via magic `name` strings (`app/src/routes/index.tsx:75-82`) instead of tracked signals — pragmatic for the no-JS form, but it couples behavior to markup.
- Cache eviction `cache.clear()`s the whole map when full (`app/src/lib/api.ts:30-32`) — a thundering-herd edge under a >5000-path crawl; an LRU would be kinder. Starter cruft also lingers (commented `ssr` block in `app/vite.config.ts:31-52`, unused `undici` devDependency at `app/package.json:35`).

I found no actual bug: JSX-escaped text everywhere, 404s cached as `null` only briefly, page params validated, no leaked listeners, sort/filter logic matches the spec's edge cases (missing values last in both directions, dedup of `method:level`, default game = highest `order`).
