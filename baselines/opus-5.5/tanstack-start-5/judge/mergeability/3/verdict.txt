I've reviewed the app against the current stable TanStack Start (1.169+) docs and APIs. Verification notes on the APIs being judged:

- `.validator()` on server functions is the current canonical API (`inputValidator` was deprecated and removed in mid-2026) — `app/src/lib/pokedex.functions.ts` uses it correctly.
- Start 1.169 stable requires Vite 8; `app/vite.config.ts` pins Vite ^8.3.5 with `tanstackStart()` before `viteReact()`, matching the docs exactly.
- `router.tsx` with the `getRouter()` factory + `Register` module augmentation, and `__root.tsx` with `HeadContent`/`Scripts` imported from `@tanstack/react-router`, mirror the official "build from scratch" guide almost line-for-line.
- The hand-rolled srvx production server (`dist/server/server.js` fetch handler + static client assets) matches the pattern TanStack's own examples use for `npm start` (`srvx --prod`).
- `hashScrollIntoView` and `resetScroll` are documented `NavigateOptions` — the moves-page game selector uses them correctly to avoid scroll-jumping on `#moves`.
- `RouteMatch.status` is a documented public field including `'notFound'`, but `m._notFound` (underscore-prefixed) at `__root.tsx:14` is a private field — the one genuine framework-facing wart.

The architecture is clean: thin route files, loaders calling server functions, `notFound()` thrown in loaders, view models typed in `lib/types.ts`, server-only data access confined to `lib/pokedex.server.ts` behind the server-function boundary in `lib/pokedex.functions.ts`. Correctness looked solid overall — dedupe-cached fetches with TTL and rejection cleanup, no SSR/CSR mismatch paths found, sensible aria/sort handling — with only minor edge cases (unknown `generation` value silently empties the list; server-side page clamp desyncs from the URL; cold-request fan-out of ~100 move fetches per Pokémon page). The main maintainability gap is pervasive `any` in the API-shaping layer despite `"strict": true`.
