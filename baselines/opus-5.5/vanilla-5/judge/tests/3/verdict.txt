## Review: test quality

**The app ships zero tests.** There is no test runner in `app/package.json` (`app/package.json:7-10` — only `dev`, `build`, `tsc --noEmit`, `start`), no test files anywhere under `app/` (grep for `test|spec|assert|expect` across `app/src` matches only comments and a route regex in `app/server.mjs:42`), and the measured facts confirm `tests: {files: 0, cases: 0}`. Everything the acceptance suite happens to cover is guarded only by `tests/`, which the team will not own.

The riskiest code is exactly the pure, easily-testable logic that has no coverage:

- **Data shaping** — `app/src/api.ts:145-165`: `getAll` fires one `?limit=100000` request and ignores `List.next`; a paginated response, a server-side cap on `limit`, or a refactor to chunked fetching would silently truncate every list and no one would know until a user noticed a missing Pokémon.
- **Sorting** — `app/src/table.ts:21-32`: the comparator has subtle rules (nulls always last, direction multiplier, index tie-break). Note that when *both* keys are null it returns `a.i - b.i` ignoring `dir`, so nulls reverse order inconsistently between ascending and descending sorts — precisely the kind of bug a single unit test would have caught.
- **Formatting rules straight from the spec** — `app/src/format.ts:6-38`: `humanize`, `dexNumber`, `idFromUrl`, `latestFlavorText` (last English entry, `\n`/`\f` collapse) are the spec's literal definitions and are trivially unit-testable. A regression in `findLast` vs `find` (api.ts `format.ts:22`) would flip flavor text to the oldest version with no signal.
- **Filtering/pagination/URL state** — `app/src/pages/home.ts:63-82`: needle match, type-slot matching, page clamp (`Math.min(filters.page, totalPages)` at line 74 — note the URL is not rewritten when clamped, so `/?page=999` displays page 22 while the URL lies), and `filtersQuery` canonicalization are all untested.
- **A real latent race the acceptance tests didn't catch** — `app/src/pages/home.ts:108-118`: the 150 ms search debounce timer is never cancelled on navigation. Type in search, click a card within 150 ms, and the timer fires `update()` → `updateUrl('/?q=…', replace)` (`app/src/url-state.ts:16-22`), replacing the Pokémon page's URL with the home query while the Pokémon view stays on screen. The `isShown` guard exists (`app/src/main.ts:79-82`) but `updateUrl` never checks it.
- **Error paths** — `app/src/main.ts:43-50` maps `NotFoundError`/`URIError` to not-found and everything else to the error page; `app/src/api.ts:131-139` caches rejected promises then evicts them. Both behaviours (eviction enables retry; a non-evicted failure would make a page permanently broken) are untested.

Given the code is plain TS functions with a thin DOM wrapper, vitest unit tests for `format.ts`, `table.ts`, and `api.ts` plus a handful of Playwright smoke tests mirroring the existing specs would be cheap and high-value; their absence is the single biggest gap in this PR.
