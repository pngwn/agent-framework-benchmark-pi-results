I've read the whole app (it's small: a client-side router over six hand-written page functions, a shared `h()` DOM helper, shared card/table/section components, a typed API layer with in-memory caching, and a tiny Node static server). Here's my review against the editability scenarios.

**Scenario walkthrough**

1. **Remove Abilities**: delete `app/src/pages/ability.ts`; drop the route in `app/src/main.ts:22`; delete the Abilities section in `app/src/pages/pokemon.ts:93-102,126`; drop the 404 resource route in `app/server.mjs:36`; optionally the now-unused `Ability` interface in `app/src/api.ts:50-56`. No nav link exists for it, no hidden references. Self-contained, obvious deletions.
2. **Sprite bug (Deoxys)**: sprites are built from the Pokémon ID, not the name — `app/src/api.ts:147` (`spriteUrl`) used only in `app/src/components.ts:50` (`pokemonCard`). Every card list (home, move, ability, type) renders through `pokemonCard`, and the species-name correction (deoxys-normal → deoxys) is already centralized in `speciesCards` (`app/src/components.ts:59-77`). One fix covers every list; in fact the bug class is largely pre-empted by the ID-based design.
3. **Sort by name on every card list**: two seams — `speciesCards`'s sort at `app/src/components.ts:76` covers move/ability/type pages, but the home list has its own path (`app/src/pages/home.ts:91-97` filtering the pre-sorted `speciesList` from `app/src/api.ts:139`). Two small, findable edits, but the split means "the order of Pokémon cards" is not one knob.
4. **Items section shaped like Moves**: the shared pieces (section, descriptionList, count, cardList, speciesCards, `getResource`, format helpers, generic `sortableTable`) are all reusable; what gets copied is the ~35-line page skeleton of `app/src/pages/move.ts` (fetch → h1 → facts dl → Effect → Learned-by), since there's no "resource detail page" abstraction. Plus `Item` type in `api.ts`, two route lines (`main.ts`), and one server route (`server.mjs`). Reasonable reuse, mild copy-paste.
5. **Change API base / caching rules**: base URL is centralized in `app/src/api.ts:9-13` on the client and `app/server.mjs:15` on the server (which injects it into the client, so the client default is only a dev fallback). Caching lives entirely in one `cache` Map + `get()` in `app/src/api.ts:106-124`. Two files, each one obvious spot.

**Notable strengths/weaknesses**: The declarative route table (`main.ts:19-26`) and the generic `speciesCards<T extends {pokemon: Named}>` with an `extra` callback are exactly the seams the scenarios reward. The main drift hazards are the server's duplicated copy of the route regexes and base-URL default, and the repeated `types.get(x) ?? humanize(x)` label-fallback pattern across three pages.
