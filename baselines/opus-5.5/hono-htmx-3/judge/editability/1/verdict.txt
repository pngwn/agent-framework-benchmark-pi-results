I've read the whole app (`app/src/api.ts`, `data.ts`, `index.tsx`, and all five view files), the spec, and the framework guidance. The app is a small, cleanly layered Hono + htmx app: `api.ts` (HTTP + cache) → `data.ts` (domain shaping) → per-route views with loaders co-located, sharing a small component set. Framework usage (Hono 4.13 `jsxRenderer`, `serveStatic`, htmx 2 attributes) is current and idiomatic. Now scoring editability.

## Scenario walkthrough

**1. Remove Abilities pages.** Three files: the route + import (`app/src/index.tsx:13`, `app/src/index.tsx:77-81`), `loadAbility`/`AbilityPage` (`app/src/views/details.tsx:53-78`), and — the trap — the Pokémon page's Abilities section, which hardcodes `/abilities/<name>` links (`app/src/views/pokemon.tsx:284-288`), so a removal that leaves no dead links must edit an ostensibly unrelated page. Nav needs no edit (abilities isn't in it, `layout.tsx:19-27`). Scattered but findable.

**2. Sprite bug fix.** Sprite URLs are built in exactly one function, `spriteUrl` (`app/src/data.ts:28`), consumed at exactly one render site, `CardList`'s `<img>` (`app/src/views/components.tsx:25`). Every card list in the app — home (`home.tsx:57`), move "Learned by", ability "Pokémon", type "Pokémon" — flows through `CardList`/`Card`, so one fix covers all four. Caveat: if the fix needed the Pokémon record's real `front_default` rather than an ID-derived URL, `Card` must gain a field and both producers (`cardsForPokemon` `data.ts:91`, `loadHome` `home.tsx:48-56`) must be updated — still few places, and the `Card` type is the obvious seam.

**3. Sorting by name on all card lists.** `CardList` (`components.tsx:23`) is the single render path for every list; a `sortBy` prop lands in one file. If sorting is done at the data level instead, there are only two producers (`data.ts:91`, `home.tsx:29`). Trivial.

**4. Items section shaped like Moves.** Touch `index.tsx` (routes) plus a new view module (or `details.tsx`). Reusable as-is: `api`/`apiList`/`idFromUrl` (`api.ts`), `englishName`/`humanize` (`data.ts`), `Section`/`Count`/`orDash` (`components.tsx`), the `loadX`/`Page` skeleton pattern. Not reusable: the detail-page body itself — `MovePage`'s dl/effect/learned-by structure is move-specific, so an `ItemsPage` is a parallel skeleton, and `details.tsx` already mixes three resources (moves/abilities/types) in one file. Moderate copy-paste.

**5. Change API base URL / caching rules.** Base URL is defined once (`api.ts:4`) and consumed via import (`api.ts:5`, `data.ts:28`); all caching state and rules (`FRESH_MS`, the `cache` map, stale-while-revalidate) live in `api.ts:6-45` alone. One file.

## Criteria scores

- **removability: 3.** Removal means scattered edits across route + view + a hard-linking page (`pokemon.tsx:288`), not entangled but not "delete a directory".
- **changeability: 4.** Sprite/URL logic, caching, type filtering all have single homes; only knock is that a data-dependent fix touches the `Card` producers.
- **coupling: 3.** Layering is clean and one-directional, state is explicit (e.g. `labels` map passed as a parameter, `pokemon.tsx:57-64`), and there's no client JS beyond inline htmx attributes. But route URL literals are duplicated across five files (`components.tsx:23`, `pokemon.tsx:178`, `details.tsx:86`, `details.tsx:146`, `home.tsx:19`), so renaming a route means grep-and-edit everywhere.
- **abstraction_design: 4.** `Card`/`CardList` models the real variation with optional `types`/`note` fields instead of flags (`data.ts:89`, `components.tsx:23-43`); `MoveTable` handles level-up vs. other methods by column filtering, and `sortRows` generalizes sorting (`pokemon.tsx:122-192`). Deductions: `details.tsx` is a three-resource grab-bag, and API records are typed `any` throughout (`details.tsx:53`, `pokemon.tsx:77,106-112`), so the contracts the abstractions sit on are implicit.
