## Review: test quality

**Verification of the measured facts:** `app/` contains no test files at all. `grep` for `describe|it(|expect|test` in `app/` returns only unrelated hits (`data.ts` type names, `latestFlavorText` etc.). `app/package.json` has no test script — only `build`, `start`, and `typecheck` (`tsc --noEmit`). The agent shipped zero tests of its own and relied entirely on the external acceptance suite in `tests/`.

That means the three risk-based criteria score at the floor, and the value of this review is in `untested`. The code has a lot of genuinely risky, pure-ish logic that is trivially testable with a fetch stub or pure-function unit tests, so the absence is a choice, not an obstacle.

What isn't guarded once the acceptance suite stops being the only check:

- **Filtering/pagination/URL state** (`app/src/views/home.tsx:22-60`): `parseHomeQuery` (lenient `parseInt` accepts `?page=2abc`), `homeUrl` canonicalization (default-param omission), the three-way filter in `loadHome`, and the `Math.min(query.page, totalPages)` clamp. A refactor of the data layer (e.g. switching `allSpecies()` to real pagination) could silently break page clamping or the count, and nothing in `app/` would fail.
- **Move-table sorting** (`app/src/views/pokemon.tsx:34-57`): nulls-last in *both* directions, the `sign * cmp || byName` tie-break, `aria-sort` emission, and the level-up default order. This is exactly the kind of comparator code where an "obvious simplification" flips nulls to the top on descending sort.
- **API client / cache** (`app/src/api.ts:28-45`): the stale-while-revalidate cache has real invariants — `entry.pending ??=` de-duplication, the fire-and-forget background refresh whose failure is swallowed (`.catch(() => {})` at `api.ts:40`), 404-as-null caching, and `apiUrl`'s fragile `url.indexOf('/api/v2/')` slicing (`api.ts:49`). None of it is covered; a caching refactor could serve stale-null or double-fetch per request without any failing check.
- **Alternate-form exclusion & dedup** (`app/src/data.ts:59-73` `cardsForPokemon`, and the `id < MAX_SPECIES_POKEMON_ID` guard used in `typesByPokemonId` at `data.ts:51`): the `< 10000` boundary, `idFromUrl` NaN handling (`api.ts:57`), and seen-set dedup are pure logic, easy to unit test, and easy to break.
- **Version-group selection in `loadMoves`** (`app/src/views/pokemon.tsx:68-116`): default = highest-`order` group, the `${move}|${method}|${level}` dedup key, method table ordering. The spec pins these precisely; nothing re-checks them.
- **Route-level contracts** (`app/src/index.tsx:14-15, 25-30, 41-61`): the htmx partial-vs-full-page decision, `Vary`/`HX-Push-Url` headers, and the three 404 paths plus `onError`. These are cheap Hono `app.request()` tests (`hono` supports that directly) and the app ships none.
- **`englishEffect`'s `$effect_chance` substitution** (`app/src/data.ts:24-26`): `String(chance ?? '')` produces a double space / broken sentence for moves whose template contains `$effect_chance` but whose `effect_chance` is null — a latent content bug no test would surface.

A partial mitigation: `app/` does wire TypeScript with `tsc --noEmit`, so pure type regressions are caught. But the heaviest data-shaping code bypasses it with `any` (`pokemon.tsx:73` `groups.filter(Boolean) as ...`, `details.tsx:36`, `data.ts:35-46`), so the type guard is weak exactly where the logic is riskiest.

Per the rubric, `signal_to_noise` for no tests is 3; everything else bottoms out.
