# Review: Hono + htmx Pokédex (`app/`)

## What's here

A 9-file SSR app: `api.ts` (fetch client with in-memory stale-while-revalidate cache), `data.ts` (domain helpers), five view files with colocated `load*` functions, an esbuild build script, and hand-written CSS over the supplied tokens. Deps are pinned to the current stable line — Hono 4.13.14 and @hono/node-server 2.1.5 (the actual latest releases as of this month), with `serveStatic` imported from the correct v2 subpath (`@hono/node-server/serve-static`).

## Assessment

**Idiom is genuinely strong.** The layout uses `jsxRenderer` with the module-augmented `ContextRenderer` exactly as hono's docs prescribe (`app/src/views/layout.tsx:3-7`, `:12`), routes use `c.render`/`c.html`, and `app.notFound`/`app.onError` follow the documented error-handling shape (`app/src/index.tsx:86`, `:94`). The htmx usage is better than most htmx code I see: partial detection via `HX-Request`/`HX-History-Restore-Request` so back-button restores get full documents (`app/src/index.tsx:17`), a correct `Vary: HX-Request, HX-History-Restore-Request` on the route that serves both forms (`:25`), `HX-Push-Url` with canonical URLs (`:28`, `:46`), debounced search via `hx-trigger="input changed delay:200ms, search"` (`home.tsx:93`), `hx-sync` replace to cancel in-flight filter requests, and a plain `method="get"` form action so the page degrades gracefully without JS (`home.tsx:76-79`). The concurrency dedup in the cache — in-flight promises shared via `entry.pending ??=` (`api.ts:24-33`) — is the right hand-rolled equivalent of a fetch-join layer and avoids the fan-out blowup `loadHome` would otherwise cause.

**Correctness is careful but not flawless.** Sort buttons in the move tables target themselves but have no `hx-sync`, so rapid clicks on two different column headers can race and the last-resolved response wins (`views/pokemon.tsx:159-161`); the game `<select>` does set `hx-sync="this:replace"` (`:319`), showing the author knew the concern. `app.onError` returns the full layout even for an htmx request, so an API failure mid-search swaps a whole page skeleton into `#results` (`index.tsx:94-103`). The cache is a module-level `Map` with no size bound (`api.ts:9`) — acceptable here per the spec and the fixed data set, but it's unbounded global state with no cap. Minor: `apiUrl` silently treats a URL lacking `/api/v2/` as a relative path (`api.ts:48-50`), and no `Cache-Control` is set anywhere.

**Structure is the codebase's best property.** api → data → views is a clean one-way layering; each page colocates its loader with its view (`views/details.tsx:9`, `:56`, `:102`), the shared surface is one small `components.tsx`, and the only global (the cache) is single-purpose and commented. The one thing I'd ask the author to change is the pervasive `any` at the API boundary (`api.ts:35`, `data.ts:49`, `pokemon.tsx:77`, `details.tsx:107`) — minimal interfaces for the handful of PokeAPI resources actually consumed would cost little and give the rest of the code real types. Redundant `hx-sync` attributes on the input/selects already covered by the form-level attribute (`home.tsx:94,99,110` vs `:82`) are nits.

I'd approve after a round of typing nits; nothing here needs rework.
